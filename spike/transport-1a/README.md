# 传输 1a：信令期限反例

这不是四端 SDK 原型，也不是完整信令实现。这里只用有限的虚拟时钟事件验证
[设计](../../docs/transport.md#非持久双向信令)的重试期限与缺口期限能否覆盖一个允许的故障时序。
观察结论见 [transport-notes](../../docs/transport-notes.md#6-信令重试与缺口期限的模型反例)，
待裁定事项见 [plan](../../docs/plan.md#传输模块与直连)。不改变产品或设计常量。

```sh
REMOTE_AGENT_HOME=/tmp/ra-transport-model CGO_ENABLED=0 \
  python3 spike/transport-1a/retry-gap.py
```

脚本不创建该状态目录，不读任何账户、配置或凭据，不打开网络连接，不调用 SDK。
只有 Python 标准库，不需要下载依赖。输出 JSON 包含每次发送、丢弃、缓存、ACK 和代次退休的时刻。
`sdk_observer_calls` 仅表示模型中本应调用 SDK 的位置，不能作 SDK 运行证据。
所有时间都是虚拟毫秒，帧是合成标记，不是 SDP、protobuf 或加密信封；不报告 wire 字节或真实恢复时延。

前提：双方 boot challenge、角色、成员 head、租约与信令认证已通过；发送方是确定的 Offerer。
Signal 与 Control 是可分别丢帧的假路径，未丢帧的传播延迟为零。
第一个 50 ms 汇集点已有完整的 16 个候选，发送方不等 SDP 的对端 ACK 就发送该批。
当前设计没有禁止这种流水发送；候选先到时只缓存，绝不越过 SDP 调用 SDK。
重复候选不延长首次缺口的 1 秒期限。原串、密文、frame ID 的真实构造不在此模型内；
只用固定合成字节及 SHA-256 检查同一逻辑帧的重试不变。

运行断言覆盖五种情况：

- 无丢包；一次 Offer 丢失；一次 ACK 丢失：两个逻辑帧均只处理一次。
- Offer 的初发与第一次重试丢失：50 ms 开始的缺口在 1050 ms 退休代次，1500 ms 的最后重试已过时。
  此情形保留发送端原重试，以观察旧代次拒绝；没有实现 Restart 通知。
- 每一代 Offer 都只丢前两份：给新代次零成本、立即重开的最有利条件，10 秒内仍无 SDP 可处理。
  这是压力反例，不是“总共只丢两帧”；也没有把 Restart/引导/ICE 的成本算作零成本产品保证。

接收端可以在缓存时就 ACK 候选，也可以在有序处理后 ACK；本模型选择后者。
改成前者会减少候选重试，但不会让缺失的 Offer 在 1050 ms 前到达。
若发送方等待每个前序序号被确认后才发下一个，反例的流水前提不成立；
这种发送窗口需要明确，并重新验证串行 RTT/重试成本，不能继续引用未经验证的 9.75 秒算术。

本模型只证明该允许时序下重试机会与缺口寿命不匹配，不证明所有实现都不可能连接、
不证明四端 SDK 不支持 WebRTC，也不证明 128 帧、3 MiB 或 9.75 秒已经被 SDK 实测突破。
