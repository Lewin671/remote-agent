# 文档规范

本文规定 `docs/` 下每份文档写什么、新内容写到哪、什么时候可以新建文档。改文档之前先读本文。

## 1. 文档类型

每份文档只属于一种类型，只回答一个问题：

| 类型 | 回答的问题 | 写 | 不写 |
|---|---|---|---|
| 边界 | 做什么、不做什么 | 目标、范围、信任边界、硬性规则 | 技术选型、实现方式 |
| 设计 | 怎么做、为什么这么做 | 架构、协议、**所有技术决策和理由** | 实测细节（链接到实测文档） |
| 实测 | 外部工具实际怎么表现 | 带版本号的观察结果、复现方法、踩过的坑 | 决策和对策（只写「据此的做法见 xxx」） |
| 计划 | 按什么顺序做、做到什么算完 | 阶段、任务、验收标准、**唯一一份待确认清单** | 决策理由、已解决问题的过程 |
| 界面稿 | 界面长什么样 | 布局、交互、文案 | 实测数据、取舍理由（写进对应的 md，界面稿只放链接） |

| 文件 | 类型 | 内容 |
|---|---|---|
| [scope.md](scope.md) | 边界 | 项目范围、组件职责、信任边界、MVP 做与不做 |
| [architecture.md](architecture.md) | 设计 | 各端部署、报文分层、通信方式、技术决策 |

| [claude-code-notes.md](claude-code-notes.md) | 实测 | Claude Code 的行为（MVP 之后接入，先存顺带测到的结果） |
| [plan.md](plan.md) | 计划 | 分阶段计划、各阶段任务和验收标准、待确认问题 |

仓库根目录的 README 只写给人看的一段简介和链接；AGENTS.md 只写开发流程和给 agent 的规则。两者都不重复本目录的内容。

## 3. 写之前：内容放哪

1. 先判断内容属于哪种类型，放进对应的文档
2. 在全仓库搜一下这件事是否已经写过。写过就改那一处，不在别处再写一遍
3. 其他地方需要提到时，只写一句话加链接，不复制内容

常见情况：

| 内容 | 放到 |
|---|---|
| 讨论出一个技术决策 | 设计文档的决策表，写明结论和理由 |
| 实测发现了某个行为 | 对应 CLI 的实测文档，注明版本；如果它改变了某个决策，同时更新设计文档 |
| 冒出一个还没定的问题 | plan.md 的待确认清单，不在其他文档里另开「待定」「待验证」小节 |
| 问题有了结论 | 结论写进它该在的文档，再从待确认清单里删掉 |
| 新需求 | 先对照 scope.md；落在「不做」里的，先改 scope.md |

## 4. 保持干净

- **只写现状，不写过程**：结论变了就直接改，不用删除线，不留「原来是……后来改成……」。历史用 git 查
- **一条信息只有一处原文**：两处写法不一致时，以原文为准，并把另一处改成链接
- **实测和决策分开**：实测文档记录事实，设计文档引用它得出做法。工具升级后只需重新验证实测文档，再看哪些决策受影响
- **和代码重复的内容不写**：代码写出来后，文档只保留代码里看不出的东西（为什么、约束、取舍），接口字段以 proto 为准

## 5. 新建文档

先考虑放进现有文档。满足以下任一条件时才新建：

- 新接入一个外部工具，需要记实测结果：按 `<工具名>-notes.md` 命名，如 `claude-code-notes.md`
- 某份文档里的一个主题已经长到别的内容难以阅读（大致超过 150 行），拆成独立的设计文档，原处留一句话加链接
- 出现了上面五种类型都装不下的内容：先和用户讨论，确定新类型后补进第 1 节

新建时：

- 开头第一段说明本文写什么、不写什么，并链接到相关文档
- 在第 2 节的表格里登记文件名、类型、内容；不登记的文档视为不存在
- 文件名用小写英文加连字符

## 6. 提交前自查

- [ ] 新内容放在了它类型对应的文档里
- [ ] 没有在两处写同一件事
- [ ] 解决的问题已从待确认清单删掉，结论已写进对应文档
- [ ] 新建或删除文档时，第 2 节的表格已同步
