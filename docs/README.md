# 文档规范

本文规定 `docs/` 下每份文档写什么、新内容写到哪、什么时候新建文档。改文档之前先读本文，提交前按第 7 节自查。

核心只有一条：**每项结论只有一个负责维护的位置**。其他地方需要提到时，写一句摘要加链接，不另起新结论。

## 1. 文档类型

| 类型 | 回答的问题 | 写 | 不写 |
|---|---|---|---|
| 边界 | 做什么、不做什么 | 目标、MVP 做与不做、组件职责、信任边界、隐私等硬性规则 | 技术选型、实现方式 |
| 设计 | 怎么做、为什么这么做 | 架构、协议、技术决策和理由、外部工具的使用方式 | 实测细节（链接到实测文档） |
| 实测 | 外部工具实际怎么表现 | 带版本号和证据等级的观察结果、复现方法、踩过的坑 | 我们据此怎么做（写进设计文档，链接回来） |
| 计划 | 现在做到哪、接下来做什么 | 当前状态、下一步及其验收标准、**全部未决事项**、已完成阶段各一行 | 决策理由、已解决问题的过程、已完成阶段的任务拆解、验收的详细记录 |
| 验收 | 我们的功能验证到什么程度 | 日期、版本和环境、走过的操作、没覆盖的范围 | 设计、待办；已撤掉的功能的记录 |
| 界面稿 | 界面长什么样 | 布局、交互、文案 | 实测数据、取舍理由、未决事项（写进对应的 md，界面稿只放链接） |

## 3. 写之前：内容放哪

1. 判断内容属于哪种类型，放进对应的文档
2. 在全仓库搜一下这件事是否已经写过。写过就改那一处，其他地方只留链接
3. 如果改的是一项结论，顺着链接把引用它的地方一起核对，别让摘要和原文说法不一

| 内容 | 放到 |
|---|---|
| 讨论出一个技术决策 | architecture.md 的对应小节，写明结论和理由 |
| 实测发现了某个行为 | 对应工具的实测文档，注明版本和证据等级；如果它影响某个决策，同时更新 architecture.md |
| 冒出一个还没定的问题，或一项待实测 | plan.md 的「待确认」；其他文档里需要提到时写「未定，见 plan.md」 |
| 问题有了结论 | 结论写进它该在的文档，再从「待确认」里删掉 |
| 做完一次验收 | 条件、结果和没覆盖的范围写进 acceptance-notes.md；plan.md 只改「当前状态」里的那一格 |
| 一项工作做完了 | 从 plan.md 的「下一步」删掉，更新「当前状态」；不在 plan.md 里留做法和过程 |
| 新需求或范围变化 | 先改 scope.md，再改设计和计划；界面稿不能先于 scope 扩大范围 |
| 界面要改 | 按第 5 节「界面稿的版本」出新一版 |

## 4. 写法

- **只写现状**：结论变了就直接改，不用删除线，不留「原来是……后来改成……」。改范围或信任模型时，把原因写进提交说明
- **实测要标证据**：每条注明验证时的版本；推断或没测过的，在句中标「推测」「未验证」。设计文档引用推测时要说明，不能当成保证
- **界面稿的数值是示例**：真正的取值以设计文档为准，未定的列在 plan.md
- **代码写出来以后**：接口字段以 proto 和代码为准，文档只保留代码里看不出的东西：为什么、约束、取舍、外部工具的行为

## 5. 界面稿的版本

界面稿放在 `docs/design/`，一个客户端一个文件，命名 `<客户端>-v<N>.html`，如 `client-v24.html`。**工作区里只有当前这一版**，旧版本在 git 历史里。

- **定稿后不改**：一版开始按它改代码，就算定稿。之后要改界面，用 `git mv` 把它改名为 `v<N+1>` 再改，这样上一版原样留在历史里。只允许对定稿做修相对链接这类不动内容的调整。还没定稿的一版可以直接改
- **每一版都完整**：没改的界面也要带上，读当前这一版就够
- **开头写相对上一版的改动**：只列改了什么；为什么改写进提交说明，取舍写进对应的 md
- **标题写版本号和日期**
- **亮色和暗色都要能看**：页面右上角放主题切换，默认跟随系统，和客户端一致
- **出新一版时**：同一个提交里把仓库中指向上一版的链接（`git grep 'client-v<N>\.html'`，只看 md）改到新版，同步第 2 节的表格
- **旧版本不是当前规则**：代码注释里的 `client-v7` 这类写法只说明那段代码当初照哪一版做的。要看旧版本：

  ```sh
  f=docs/design/client-v7.html
  git show "$(git rev-list -1 HEAD -- $f)^:$f" > /tmp/client-v7.html
  ```

## 6. 新建文档

优先放进现有文档。以下情况才新建：

- 新接入一个外部工具需要记实测结果：命名为 `<工具名>-notes.md`
- 某个设计主题复杂到在原文档里难以维护：拆成独立的设计文档，原处留一句话加链接
- 内容不属于第 1 节任何一种类型：先和用户讨论，定下新类型后补进第 1 节

新建时：

- 开头一段说明本文写什么、不写什么，链接到相关文档
- 在第 2 节的表格里加一行
- 文件名用小写英文加连字符

## 7. 提交前自查

- [ ] 新内容放在了对应类型的文档里，没有在别处再写一遍
- [ ] 改了结论的，引用它的地方已经核对
- [ ] 解决的问题已从「待确认」删掉，结论已写进对应文档
- [ ] plan.md 里没有新增过程记录：状态写在「当前状态」，证据写在 acceptance-notes.md
- [ ] 新建或删除文档时，第 2 节的表格已同步
- [ ] 改了界面稿的，按 [design-system.md](design-system.md) 第 8 节的审查清单看过
- [ ] rebase 后看一眼别人刚推的文档改动，确认和自己的结论不冲突
