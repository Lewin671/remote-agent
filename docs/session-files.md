# 会话里的文件

本文写任意文件如何从客户端到原生 CLI、保留多久以及网页怎样显示，以及反方向 Agent 怎样把电脑上的文件交给客户端（[最后一节](#agent-给客户端发文件)）；图片自身的编码、占位和确认见 [session-images.md](session-images.md)，外部工具证据见 [Claude Code](claude-code-notes.md#文件路径引用)、[Codex](codex-notes.md#文件路径引用)，验收见 [acceptance-notes.md](acceptance-notes.md#文件附件phase-a2026-10-28)。协议字段以 proto 为准；三端整合状态与剩余联合验收见 [plan.md](plan.md)。

## 传输与信任边界

文件沿用图片命名的机器级 Begin / Put / Status / Complete / Abort 指令，端到端加密，经中继转发到电脑；中继不保存文件正文，不解析名字、哈希和路径。设备身份由命令签名证明，传输和完成 ID 都只允许原设备续传或发送。文件上传独立受 `file_upload` capability 控制；未声明能力时客户端不提供文件选择，不提升协议版本。网页、Android 和 iOS 均已接入；原生客户端自己的来源授权和缓存约束见 [Android](android-client.md#文件附件)、[iOS](ios-client.md#文件附件)。

所有客户端在每次发送 file_ids 前必须核对目标机器当前的 file_upload 能力；不是 true 时拒绝整条操作并提示更新电脑上的 remote-agent，不能删除附件字段后只发文字。这覆盖 Send、新建会话、失败消息重发、结果未知请求的原样重试和放回输入框；放回时先检查，再改草稿或移除失败记录。未知结果保持原始请求 ID、截止时间与附件 ID，能力恢复前不重发，也不能把本地能力拒绝当作原请求未执行的证明。封装／签名等异步处理后及每次网络重试前仍须复查当前能力。Android / iOS 的独立上传与发送实现同样遵循此规则。

已接受的边界：机器信息尚未刷新、仍缓存支持文件的旧 capability 时，客户端无法知道电脑已经换回旧 daemon；它仍可能忽略未知的 file_ids。不提升协议版本时需先刷新机器信息才能阻止这类已知降级发送。

单文件 100 MiB，每条消息最多 6 个文件，另可带 6 张图片。原始文件名最多 255 UTF-8 字节；非空文件名选择文件传输，格式必须为 UNSPECIFIED。允许空文件。每块最多 768 KiB，重复块与断点续传沿用图片规则。客户端调用 Complete 丢回复后，若 Status 仍是 RECEIVING 且 persisted_bytes 等于 total_bytes，说明校验可能仍在锁外进行；应使用相同 transfer_id 重试幂等 Complete 或继续查询，不能把缺少 file_id 当成上传失败而重传全部字节。Android / iOS 各自的上传实现也遵循这条规则；完成时只流式核对总长度、SHA-256（通过打开的描述符在全局上传锁外读取，重新加锁后先核对归属、Deleting 和持久化传输代次，再核对状态和文件身份；描述符保持打开直到完成处理结束），不解码、不压缩、不删元数据，字节原样保存。网页明确提示「文件原样发送，包含其中的元数据」。

## 落盘与原生输入

完成文件位于 `uploads/pending/<file id>/<safe name>`；消息被受理时整体检查图片与文件，移动到 `uploads/<session id>/files/<file id>/<safe name>`。新会话先确认所有文件实际存在再启动 CLI。目录 0700、文件 0600；所有路径由 daemon 生成。原始名字取 basename，NFC 规范化，非 Unicode 字母/数字/组合标记（Mark）及 `._-+=,` 的字符换成 `_`，连续 `_` 合并，去掉前导 `.`/`-`；以 UTF-8 边界截到 100 字节并保留扩展名，空名字用 `file`。上传根目录含任意空白时，图片和文件能力都关闭，避免 Claude 的 `@` 在空白处结束。

图片仍先逐张粘贴为占位，文件不走图片占位。最后一次 bracketed paste 的正文是用户文字加两个换行，再按客户端顺序每文件一行：Claude Code 使用 `File: @"<绝对路径>" (file)`，Codex 使用 `File: <绝对路径>`。固定前缀使单张 PNG 文件不会被当成图片路径粘贴；Claude 的双引号保证 Unicode、无扩展名及 `+`/`-` 结尾的名字完整解析，末尾标记结束 @ 文件补全，确保一次 Enter 提交，实测见工具记录。没有用户文字时只写文件行；同条消息还有图片时，先加入两个换行，使文件行与 CLI 的图片占位分开，避免首行识别失效。按现有提交锁、租约、阶段落盘和 Enter 规则发送；确认比较的是组合后的整段正文和本次图片证据。原始用户文字、文件列表和组合正文保存在 queue.json，steer、queue、CLI 暂存和重启恢复不重新解释路径或换顺序。标题只取用户文字，纯文件或图片消息不生成标题。

CLI 自己决定怎样读取文件；路径引用不保证特定格式一定内嵌进模型上下文。Claude 的小文本自动附件、大文件太大及 ZIP 工具读取的区别见工具实测。daemon 不读取 Agent 在回复中提及的任意文件；用户文件的事件信息只对会话上传目录里的精确路径行做 stat，不把文件内容发送回客户端。

## 从相册选视频

「＋」里的相册入口同时列出图片和视频，名字是「照片和视频」。选中的视频不走图片的编码和占位，按文件原样上传和引用，受同一套文件规则约束：单个 100 MiB、每条消息最多 6 个文件、需要电脑声明 `file_upload`。电脑不能收文件时相册只列图片。草稿里视频和图片排在同一排缩略图里，视频的缩略图角上写时长；超过大小上限的视频在选中时就提示，不开始上传。发出后在消息里按文件条目显示。三端都还没有实现，见 [plan.md](plan.md)。

## 保留、配额与恢复

图片和文件共享电脑原有上传配额，默认 1 GiB；未完成的剩余字节预留也计入。空间不够时返回 ResourceExhausted，入口和错误文案统一称为附件存储。未完成传输一小时无新字节过期，未使用的完成文件 24 小时过期；状态查询和重复块不延期。

领取调用返回不持久化的本次新领取凭据；失败受理只能凭该凭据退回本次新领取的附件，重用同一会话已领取的文件不会被退回或过期删除。批量领取中途失败也撤回已写入的所有新引用。Session 的领取归属不代表消息已受理。受理证据绑定附件 ID 和会话，不依赖有界的请求去重记录；文件一旦被消息受理就属于会话，Agent 可在后续任意一轮再次读取。它不进入图片 LRU，即使消息取消、执行结束、没有队列引用，也保留到整个会话上传目录被现有退出清理删除。ImageStorageUsage 的上传占用包含文件；使用中的文件始终计入 protected，不计入 reclaimable；清理按钮不能删除它。逆向移动失败时保留 Session 归属和待回退标记；启动恢复与 GC 根据标记补完返回 pending，不能把仍在会话目录的字节标成未归属。GC 删除完成时保留的 .part 前也须重新同步完成记录，同步失败则保留原始副本。完成及移动前同步新目录的全部祖先，移动后检查目录同步结果，完成记录提交前保留原始 .part。启动时补完中断的移动，再恢复持久队列；失败新会话的文件退回 pending，清除空的文件 ID 子目录和会话目录。CLI 暂存（Held）的图片在运行时和重启时都不持有队列引用，文件保留对应引用。未使用文件和中断完成留下的孤儿目录按期限清理。

### 上传记录与字节的状态转换

图片与文件共用以下顺序。`moveUpload` 是双向移动的唯一入口，`recoverUpload` 是启动与 GC 共用的传输恢复入口；返回方向由持久化的 `Returning` 决定，删除由 `Deleting` 决定。启动时先补完这些传输意图，再恢复会话并检查 tmux 存活；磁盘上的 Exited 尚不能单独授权删除，仍存活的 tmux 会话先持久化清除 Exited，再加载历史并重新附着；历史不可读也不能保留错误的退出标记。修正写盘失败则启动失败，不启动存储 GC。退出／孤儿清理及图片原件 LRU 只在全部会话恢复后启动，使用已经恢复的状态和 turn pins。文件完成保留原字节，图片完成写入清除元数据后的字节，两者共用 `commitUpload`。记录用原子替换并同步所在目录；新目录连同祖先同步至状态目录。

| 转换 / 入口 | 持久顺序 | 中断或 I/O 失败后的恢复 |
|---|---|---|
| 无记录 → receiving / Begin | 生成新的随机传输代次，建立并同步 partial、pending 目录及祖先 → 创建、同步空 `.part` → 保存含代次的记录 | 记录未提交时重试 Begin；无记录的 `.part` 由 GC 清理。已提交的幂等 Begin 返回同一状态和代次；Abort 后即使复用同一 transfer_id 也产生新代次 |
| receiving → receiving / Put | 写入块 → 文件 fsync → 保存 persisted 偏移 | 记录不领先于已同步字节；状态查询后的重传验证已确认的重叠部分，覆盖尚未确认的尾部 |
| receiving → complete / Complete | 校验、建立目标目录并同步 → 写清理后的图片或硬链接原文件 → 同步目标目录及祖先 → 保存完成记录 → unlink `.part` → 同步 partial | 完成记录之前保留原始副本，重试 Complete；无记录的目标按孤儿清理。记录可见但同步失败时保留目标与原始副本；Complete 重试、启动和 GC 先重同步目标与记录再清理 `.part` |
| 文件锁外哈希 → 锁内完成重检 / Complete | 保持哈希描述符打开，重读记录 → 验证设备归属 → 拒绝 Deleting → 核对传输代次 → 检查完成状态或原文件身份 → 继续完成 | Abort 的 unlink 或目录同步失败也已提交删除意图；不能返回旧的完成 ID 或提交新完成记录，由启动 / GC 继续删除。代次不一致返回 Aborted，不能把旧哈希用于新一轮传输，即使文件名、长度、哈希参数与 inode 都相同，或新一轮已经完成。图片完成全程持上传锁，没有这一解锁窗口 |
| pending → claimed（已领取、尚未受理；图片与文件相同）/ take、启动 reconcile | 保存 Session 前向意图 → 建立并同步目标目录 → rename → 同步目标及源目录 → 保存本次引用；此时尚无受理证明 | 意图已提交时先补完移动；随后按可读的持久队列和历史核对受理。没有受理证据的领取走统一 Returning 路径退回 pending，图片不能当成已取消消息直接删除 |
| claimed → accepted / Send、新建会话首条消息 | queue.json 原子保存输入及附件受理见证 → 同步成功后保存上传记录的 Accepted 标记 → 只有标记同步成功才可在下一次队列保存中移除临时见证；最后发布 QUEUED 事件 | queue rename 后目录 fsync 失败时不提前标记 Accepted；重启以实际存留的队列为准。标记写入失败或记录暂不可读时，见证继续随队列保存，即使消息取消／结束且 QUEUED 事件缺失也不会丢失受理证明 |
| claimed 且队列未受理 / 启动引用恢复 | 逐条重读上传记录，按附件 ID 查当前 Queue / Held、临时受理见证、历史 QUEUED / HELD / 用户消息、Accepted / 图片 Exposed / Embedded 证明 | 全部证据缺失才持久化 Returning 并返回 pending，成功后清除该会话的 Accepted。队列或历史不可读时保留归属待修复，不能把未知当作未受理；已受理文件即使最后引用消失仍保留，图片沿用取消与 LRU 清理规则 |
| session → pending / untake、批量领取撤回、失败创建、未启动会话 release | 保存 Session + Returning（本次拒绝的引用已撤回）→ 同一个移动入口 rename → 同步目标及源目录 → 清除 Session、Returning、Refs 并保存 | mkdir、rename 或任一同步失败都保留方向与旧 owner；启动、GC 和再次领取先完成返回，不能向已消失的会话重新领取。清除 owner 的写入失败同样可以重试 |
| 已在 Returning / startup、GC、再次领取、session exit | 重同步返回意图 → 检查字节在两侧的实际位置 → 补移动与两侧同步 → 清除 owner | rename 后崩溃不重复反向移动。源目录已不存在时同步最近的现存祖先；两侧字节都已消失则解除临时归属，使记录可以过期 |
| 已受理消息引用变化 / queue、Held、结束、取消、重启 | 队列变化持久化 → 保存引用；图片另保存 Exposed / Embedded 证据 | 启动按持久队列与受理证明恢复引用；加锁后重新加载记录并核对会话与附件身份，不能用先前快照覆盖新的 Returning / Deleting 或重建已删除记录。Returning / Deleting 不参与引用重建。Held 图片不持有队列引用，文件持有；文件最后一条引用消失仍保留到会话退出 |
| receiving / pending → 删除 / Abort、过期 GC | 保存 Deleting → 删除目标字节 → 同步字节所在目录 → 删除 `.part` 并同步 partial → 删除记录并同步 partial | 删除意图保留到字节删除已同步；启动和 GC 幂等重试。待删除 ID 不再可完成、领取或通过状态查询作为有效上传 |
| session 图片 → 删除 / 未暴露图片取消、已内嵌图片 LRU | 与上一行共用 `deleteUpload` | 删除失败不丢记录，启动、GC 或存储清理重试；Returning 不进入 LRU |
| session → 删除 / 会话退出、Exited GC、无元数据孤儿清理 | 启动完成 tmux 存活恢复后才能按 Exited 清理；对每条记录先完成 Returning，其他走 `deleteUpload` → 无失败才删剩余会话目录并同步 | 仍返回中的字节不能随退出目录删除；Exited 元数据及每条删除意图支持重试 |
| 未启动会话 → 删除会话元数据 / unstarted、创建失败 | 全部附件返回成功 → 删除会话元数据与空上传目录 | 返回意图本身写不进去时保留 Starting 元数据，下一次启动继续撤回；不能把失败创建恢复成已受理会话 |

移动在意图提交前失败不会更改字节位置；意图提交后任一步失败都按持久方向恢复。rename 后、两侧 fsync 前仍以旧 owner 为准；只有两侧同步成功才能清除归属。清理空 ID 子目录不参与所有权提交，残留空目录可由 GC 清理。无记录的临时写入与孤儿字节由原有过期扫描清理。

## 历史事件与网页

daemon 在每个解析出的用户消息里识别精确的 `File: @"<path>" (file)`、`File: <path>`，以及本机输入的 `@<path>` 或 `<path>` 行：路径必须位于本会话的 `uploads/<session id>/files/<file id>/<safe name>`。识别不依赖传输记录或内存请求，所以本机输入、历史重放和重启后仍有效；文件已删除时大小为 0。UserMessage 保留 CLI 原文，另带 SentFile；共享排队事件也带文件引用，正文仍是原始用户文字。旧客户端继续看到原始路径。

各客户端都须从带有正文、image_ids 或 files 的 HELD_BY_CLI 输入快照恢复已受理消息的元数据，不能要求先见过 QUEUED 事件。即使只有文件、没有文字，也显示相同文件条目；同时保留来源与发送模式。已有 QUEUED 原文和来源时继续使用，不能被快照里的截断文字覆盖；实时模式可以更新。只有阶段／状态的后续事件不清除附件信息。此规则同样适用于 Android / iOS。

网页只隐藏事件中已识别的完整路径行及其前一行空分隔，不隐藏包含路径的普通句子。草稿、排队、发送中、失败后恢复与已发送消息都用同一个文件条目：文件图标、名字中间省略、大小，上传中显示进度，失败可重试，编辑时可移除。

电脑声明文件能力时，两个输入框的＋打开「图片 / 文件」小菜单；否则沿用直接选图。拖放文件夹会提示先压缩成 ZIP，不把文件夹的零字节条目上传；不可读取的源文件显示失败并要求重新选择。普通零字节文件仍可发送。拖放、粘贴的非图片归文件，图片归图片；从「文件」选中的图片也原样发送。两类数量分别计算。大文件逐个读取、用浏览器原生 SHA-256 计算并上传，完成后释放字节缓冲，保留源 File 对象用于换机器、到期和恢复时重传。不新增哈希依赖。网页仅在当前账户内存保留文件，刷新后要重新选择；过期上传不能发送，恢复到输入框必须重新上传本机副本，没有副本就提示重选。未知结果请求保留首次文件 ID，不因草稿重传而修改。

所有客户端在移除、换机器（包括 A → B → A）、重试、到期重传或恢复草稿时，必须先同步使旧完成状态、远端 image/file ID、目标机器与到期时间失效，并使旧异步结果无效，再调用 abort 或等待读取、哈希、全局上传槽位、网络操作。恢复时保留的旧 ID 只是历史引用，不能先变成可发送状态；没有本机副本时立即失败。网页对图片和文件共用 generation 与失效入口。已发送或结果未知请求保留它首次提交的不可变附件快照，清空输入框不 abort 已交给该请求的传输。

| 草稿入口 | 同步动作 |
|---|---|
| 移除 | 先移出草稿并使 generation、ID 失效，再 abort |
| 换机器、重试、过期、图片原图切换 | 先进入 preparing、清除 ID / machine / expiry 并递增 generation，再 abort 和排队 |
| 恢复本机副本 | 加入时立即失效历史 ID，再排队重传 |
| 恢复远端引用且无副本 | 立即清除历史 ID 并显示失败，阻止发送 |
| 发送后 clear | 先移出草稿并清除 generation，丢弃迟到结果；已交给请求的附件不取消 |

新会话首条消息的本机 File 在创建成功后随草稿清空，当前没有保存到该首条消息的待确认记录；与首条图片相同，这是已知缺口，并非可恢复保证。放回输入框时如果只剩服务器/daemon 的文件引用而没有本机副本，文件条目明确标为失败、提示重新选择，并阻止发送；本轮不改创建响应或重设计首条消息缓存，后续取舍见 [plan.md](plan.md) 的待确认。

## Agent 给客户端发文件

做不做、信任边界和中继能看到什么见 [scope §4「Agent 发来的文件」](scope.md#agent-发来的文件)；字段以 proto 为准。电脑端（协议、daemon）已实现，客户端还没有，进度见 [plan.md](plan.md)。

### 发起

托管会话的 `remote_agent` MCP 提供 `send_file(path)`，三种 CLI 共用同一个 MCP 进程（接入见 [architecture §18](architecture.md#托管会话的工具入口)）。MCP 只把路径交给 daemon 本机专用的 `LocalService.SendFile`：请求带 MCP scope 头，必须和请求里的会话一致；来源是远程客户端的调用一律拒绝，加密指令里也没有对应的 Command。不改提示词，能力只靠工具描述。工具不声明 `readOnlyHint`，免得 CLI 因此在询问模式下跳过确认；daemon 不另加确认（理由见 scope）。

成功时工具返回 `status: "offered"`、`file_id`、名字、大小、SHA-256 和一句说明：文件已放进对话，用户在客户端里下载，成功不代表用户已经下载。失败以工具错误返回原因：路径不在范围内（提示先复制进项目目录）、在拒绝名单里、是目录（提示先打 zip）、不是普通文件、超过 100 MiB、本轮已满 6 个、附件存储已满、复制时文件在变。每次调用一个文件。

### 校验

相对路径按会话工作目录解析。先把路径里的软链接全部解析成真实路径，再判断：

- 在本会话上传目录 `uploads/<session id>/` 里（`shared/` 除外）的，直接允许：用户发来的文件常常要原样转回去，它们在状态目录里
- 否则必须在项目目录（会话工作目录）或系统临时目录（daemon 的 `os.TempDir()` 和 `/tmp`）里，并且不在拒绝名单里：remote-agent 状态目录，以及家目录下的 `.ssh`、`.gnupg`、`.aws`、`.azure`、`.kube`、`.docker`、`.netrc`、`.git-credentials`、`.config/` 下的 `gcloud`、`gh`、`remote-agent`、`google-chrome`、`chromium`，`.mozilla`，`Library/` 下的 `Keychains`、`Cookies`、`Safari`，以及 Chrome、Firefox 的配置目录。名单写在代码里，没有配置项；它防误发，不是安全保证
- 只接受普通文件，空文件也行；目录、FIFO、设备和 socket 拒绝
- 打开时不跟随最后一级链接，也不阻塞（检查后被换成 FIFO 也不会卡住）；打开后再核对仍是普通文件、和检查时是同一个 inode，并把原路径重新解析一遍、必须得到同一个真实路径，挡住检查和打开之间的替换
- 单个最多 100 MiB，和上传方向一致；每轮最多 6 个。轮次取 daemon 读完 transcript 后的当前轮，计数来自会话已提交副本里记下的轮次，重启后不清零

### 副本与生命周期

daemon 当场复制一份，之后原文件被改或被删都不影响。副本放在 `uploads/<session id>/shared/<file id>/`（数据和一份记录，目录 0700、文件 0600），和这个会话的上传在同一棵目录里，所以沿用上传的配额和清理：

- **配额**：计入附件存储配额。在上传锁内先检查空间（不够时按[保留、配额与恢复](#保留配额与恢复)回收可回收的图片原件），再把暂存文件预设成目标长度占住空间；复制和哈希在锁外进行，不挡上传。空间不够返回 ResourceExhausted。存储占用把副本算进所属会话的 protected，清理按钮删不掉它
- **提交**：复制、fsync 和写记录都在暂存目录 `shared/<file id>.tmp/` 里完成；再加锁复查本轮计数，rename 成 `shared/<file id>/` 并同步目录链。rename 是唯一的提交点，同步失败就撤回；只有提交过的副本会被提供
- **崩溃恢复**：中断留下的暂存目录从不提供，GC 在它超过一小时后删除（复制只要几秒，不会删到进行中的）
- **清理**：随会话上传目录一起删：会话退出时的清理，以及 GC 发现退出元数据时的补删。没有单独的保存期限，会话结束后就不能再下载；用户应在会话还在时下载

### 在对话里出现

文件引用挂在这次 MCP 调用的工具调用事件上（`ToolCall.shared_files`），不新增事件类型：旧的 Android 和 iOS 会把不认识的事件类型当成坏密文，加字段则三端都忽略，所以不提升协议版本。daemon 在解析出的工具调用里认出 `remote_agent.send_file`（Claude Code、Codex 的写法）和 `remote_agent/send_file`（Antigravity 的写法，按现有解析推测，未实测，见 [plan.md](plan.md) 的「待确认」），从 CLI 记录的工具输出里找出 32 位十六进制的 `file_id`，确认是本会话已提交的副本才挂上（Claude Code 2.1.322 已实测，见[实测](claude-code-notes.md#send_file-mcp-工具实测)）；名字、大小、哈希和真实路径都取自副本记录，不取输出里的文字。识别和用户消息的文件识别一样无状态，历史重放和重启后结果相同。

已接受的缺口：一轮在工具返回之前被中断，或者 CLI 没把结果写进记录时，副本已经在电脑上，对话里却没有条目，用户无从下载，它随会话一起清理。

客户端本来就不收工具输出，旧客户端只看到一行 `remote_agent.send_file` 工具调用和请求里的路径，下载不了。

### 下载

客户端只在机器声明了 `shared_files` 时提供下载。按 `shared_file_chunk_bytes`（768 KiB）的整数倍偏移，逐块经 `Forward` 发会话级指令 `GetSharedFileChunk`；电脑不在线就取不到，中继不排队也不保存文件。每个结果的数据都恰好是一整块，文件结束后补零，客户端按 `size_bytes` 截掉补的零、核对 SHA-256，不一致整份作废。空文件也取一块。共用测试向量在 [`testdata/shared-files/`](../testdata/shared-files/README.md)。

它是只读指令：不写已接受指令的记录，结果不落盘，同一请求可以重发，断了从下一个偏移接着取。只有账户里的 Client 能取：Command 用途的信封要求签名者是 Client 成员（`deviceauth` 的 `Header.Scope`），只读指令跳过记录这一步在这项检查之后，Machine 既封不出这样的指令，伪造的也通不过；daemon 处理时再要求来源是签了名的客户端设备或本机。这些都有测试。

取块结果封装时不压缩，长度字段用定长编码，所以每块密文一样长：中继只能从取了几块、什么时候取推算出以块为单位的大概大小，而且只在用户下载时。挂了 `shared_files` 的工具调用事件会比平时长一些，和事件密文长度本来就公开属于同一级。

### 给客户端实现者

- 条目放在 Agent 一侧那次工具调用下，显示名字和大小，点开能看到电脑上的完整路径，让用户下载前看得出是什么文件。电脑不在线时写「电脑不在线」，下载置灰；会话已结束、副本已删时取块返回 NotFound
- 保存用的名字在本机再清理一遍：去掉路径分隔符、控制字符和双向控制符
- 网页不在新标签打开下载的 blob，也不用文件原本的 MIME 类型（同源的 HTML 会在网页的源里执行），一律按 `application/octet-stream` 触发下载
- 下载时显示进度、允许取消；`GetSharedFileChunk` 是会话指令，header 要带会话 ID
