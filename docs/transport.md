# 传输模块与直连

本文负责客户端与 daemon 间的分层、路径选择、恢复、安全绑定与路径状态展示；不定义账户、历史同步或原生 CLI 行为。范围见 [scope.md](scope.md)，既有信封与指令见 [architecture §10](architecture.md#10-报文同步和指令)，证据见 [transport-notes.md](transport-notes.md)，分期、验收和全部未决事项见 [plan.md](plan.md#传输模块与直连)。第 0a 的结果契约与第 0b 的 Link/Router/RelayPath 分层已实现；第 0c 的中继活性与换网恢复已实现。协议 16 的 1c 在本地实现 daemon 与网页的只读/文件 DirectPath；Android 的 1d 本地实现同样的只读/文件 DirectPath（模拟器验收；真机与审批 p99 另记），iOS 当前只实现认证编解码与 Unsupported，保留 relay。副作用指令热备、原生移动端 DirectPath 和终端旧流续接仍属后续阶段，已发布产物尚未包含本地 1c。文中的初始预算是实现及验收的起点，不是已测性能。

## 1. 分层与职责

首个请求不等待 ICE；直连就绪即优先使用，明显更差或故障时退回中继，规则见第 3 节。增加或移除 Path 不改变业务身份和授权。单路故障与本机换网的停顿目标分别见第 4 节，不承诺两路同时失效时即时回显。

| 通信 | 负责者 | 内容 |
|---|---|---|
| 与 server 通信 | 账户、同步和推送组件 | 账户鉴权、成员状态与租约、事件先落库再推送、多设备同步、图片显示副本和推送；继续独立调度 |
| 与对端设备通信 | Link / Router / Path | 指令与结果、终端、上传分块、只读查询、`GetSharedFileChunk` 下载 |
| 协商 | 独立信令组件 | 经 server **新增一种不落库的定向转发**，双向送达设备对设备加密的信令；不复用业务 Command 或历史广播 |

```text
会话 / 指令 / 终端 / 文件 / 电脑状态
共享封装、安全入口、逻辑流重组、幂等、执行准入与结果协调
                         │ 已封装帧
Link：call / open stream / transfer / status / capabilities
                         │
Router：可达性、优先级、路径代次、探测、升级与退路
                         │
Path：RelayPath / DirectPath / 后续路径（仅收发不透明帧）
信令组件：独立的非持久定向转发与设备身份绑定
```

四端同构：Go `internal/transport`、网页 `web/src/transport`、Android `core/transport`、iOS `RACore/Transport`。共享取消、迟到、重复、乱序、背压和网络变化的一致性场景。后续原生直连由 iOS App 注入 WebRTC SDK 适配器、Android 网络与 JNI 回调进入 core；1c 两端不引入 WebRTC SDK，也不显示直连设置。

Link 提供调用、有序可靠流、分块传输、可订阅的对端可达性和已认证能力。server 的 machine `online` 只代表中继观察，不能阻止仍可直连的操作；协议版本、文件能力改由 Link 上 daemon 签名的能力握手提供，绑定设备、进程实例、成员 head 和有效期限，最长 60 秒，变化立即更新，到期先刷新。server 转发的 machine meta 仅作发现与缓存，不作授权；在只接 RelayPath 时仍读取既有已认证 meta，保持原行为。可达不等于有权执行，能力也不替代逐次安全校验。界面不能自行按 socket 状态重发。

### 当前实现与目标边界

协议 15 已包含第 0a 期的显式完成证据、进程级执行/安全状态、独立同步、v4 接受记录与五类签名结果。第 0b 在此基础上接入四端 Link/Router/RelayPath；客户端 call/delivery 证据、可达性与能力投影、逻辑流由 Link 持有，relay 登录、epoch、NotForwarded 与物理流由 RelayPath 适配；daemon 的共享 endpoint、执行与发布仍属进程。第 0b 不改 wire、存储格式、文案或纯 relay 的业务策略。验收边界和后续阶段见 [plan](plan.md#直连实施与验收)。1c 在同一 endpoint 上接入设备对认证信令和 daemon/网页 DirectPath：只读请求、上传块与共享文件下载可换路；有副作用的其他指令与终端仍经 relay，未启用双发或旧终端续接。

现有终端物理腿结束后，Link 的纯 relay 策略仍结束该逻辑流；主 WS 与独立终端的所有权分离，不等于终端腿已能续接。下文的终端 ACK、旧流输入水位查询与 AttachPath 仍是目标设计，协议 15 尚未提供。0c 的无重复执行、无丢失输入适用于带 request ID 的 Send/Command；主流试探与重连不能取消健康独立终端、清掉已有画面或重打无法确认的按键。真实终端腿丢失沿用新流+快照；旧流续接、有界输入缓存与未知输入逐项确认在第 1/3 期实现。

### 正确性前提与所有权

**以下是第 0a 已建立、第 0b 必须保持的前提，后续跨连接重试和 direct 继续遵守。** 取消结果与同 ID 协调的既有验收范围见 [验收记录](acceptance-notes.md#传输-0a-最终结果-wire2026-11-13未发布本地分支)，不能将单路结果扩大为尚未实现的跨路径保证。

- 一个 daemon 进程只有一个 dispatcher，拥有安全 endpoint、接受日志、成员同步、执行上下文、同 ID 协调器、逻辑终端注册表及资源池。`session()` 只拥有该路 WS 登录凭据、socket 和转发等待者；独立成员同步循环持有自己的登录凭据与 HTTP client，凭据续期不依赖主 WS（见第 5 节）；执行、`workers` 和 `terminals` 不随主 WS 排空或销毁。进程退出才停止 dispatcher，不能同时打开互不协调的 endpoint。
- 所有路径共用入口，先作大小/范围检查、验签解密，认证后查询同 ID 记录，新执行再检查当前成员/租约并准入。把当前 `handleCall` 的 Machine、Command Purpose、请求 ID 长度检查和 `readTerminal` 的 Machine/Session/Request/Purpose 绑定全部搬入该入口；请求 ID 保持现有 16–128 字节及合法字符约束。直连每帧 Sender 还必须等于信令绑定的对端设备，不能只证明它是某个账户成员。终端重组与 Accept 的顺序见第 3 节。
- 一次副作用操作只执行一次。开始执行前持久记受理，执行中重复只加入有界结果等待表：每 key 最多 32 个、全局 256 个，每个等待不超过原操作期限与 30 秒中的较短者；等待表满立即回复 `unknown/busy`，等待超时回复 `unknown`，均只允许原 ID 查询；只有确有本进程运行者才入表，重启残留及已结束未定案立即回复 unknown。等待者、成员同步和信令都不占执行槽。区分未知 epoch 与执行在途，后者不能触发成员拉取。
- 关闭连接或取消等待者不表示 CLI 撤销。执行上下文属于 dispatcher，遵守原操作截止时间；后端因取消、超时、关闭返回时，除非有可信的完成证据，必须保留不确定状态，不能将 `canceled` / `deadline_exceeded` 缓存为确定失败。撤销阻止新准入并关闭流，不倒推已经准入的副作用未执行。

### 结果类别与证据矩阵（第 0a 期最终契约）

Link 使用五类结果，`executed` 包含确定的业务失败，不等于业务成功：

| 类别 | 证据与调用方行为 |
|---|---|
| 未发送 `not_sent` | 本地所有尝试均未发出，或符合下表的 server 入队前诊断。daemon 必须保证原授权以后不能新执行，才能允许换 ID；路径诊断只证明该次尝试 |
| 确定拒绝 `rejected` | daemon 对请求绑定的单调终局原因签名：信封无效、结构/范围非法、协议不符、成员已移除。相同授权载荷的迟到副本仍拒绝；改正载荷必须用新 ID |
| 已执行 `executed` | daemon 明确确认操作完成或业务已定案，含成功、确定业务失败；精简记录可只返回类别与结果正文不可恢复标志 |
| 未定 `unknown` | 可能受理且无可信终局结果；只查询/重试原 ID，不自动换 ID 做副作用 |
| 冲突 `conflict` | 同 ID 不同载荷，或后端确定的版本/对象冲突。必须带冲突种类；前者不能证明原载荷的结果，后者保留现有重载/编辑冲突流程 |

容量、租约、时钟、未知 epoch、存储故障不是单调拒绝，不能签发 rejected；没有持久终态拒绝时也不能签发 not_sent，恢复后只可重试原 ID。daemon 的 not_sent 必须在回复前已持久保存绑定载荷 hash 的终态拒绝，保证迟到或重放副本不再执行，或有截止时间已过且未执行的证明。本版没有终态拒绝持久化形式，四类未受理拒绝统一为 unknown，客户端不把 daemon 的单独 not_sent 声明作为释放 ID 的证据。过期且缺记录仍不能证明过去没执行，保持 unknown。成员移除按本次授权所绑定的成员身份/密钥判定，重新加入不是恢复旧授权。无效签名只能拒绝该字节串，不能拿其声称的 ID 覆盖另一份已认证请求；未能认证逻辑身份的拒绝对业务结果仍是 unknown。先查经认证的同 ID 记录：已受理不能被后来的范围/版本拒绝改写成未执行，同 ID 不同载荷返回 conflict。

`CommandResult` 的签名密文内增加显式 `outcome`、`reason`、请求 key hash、载荷 hash 和 `result_available`；外壳也能表达无法解码为 Command 的认证入口结论。daemon 在每个后端调用点依据完成证据分类，不从 Connect 字符串反推副作用。后端没有完成证据即 unknown；取消/超时可以是 unknown，也可以在已有可信完成证据时是 executed。定时任务 revision 冲突、文件传输 generation/对象冲突标 `conflict/business`，保留业务码及重载流程；同 ID 载荷冲突标 `conflict/identity`，不允许把原操作当未执行。业务冲突已定案的本次调用可缓存，identity conflict 不覆盖原记录。查完已有身份和运行者后，过期且缺记录先返回 unknown，不能由当前结构或协议检查改称 rejected（包括手动升级丢弃的旧记录）。结构/范围/协议等单调拒绝检查在新请求持久受理前完成；已经进入后端的回调不能再用 rejected 表示业务失败。

`ForwardReply` 转发该密文证明，外层只携带路由需要的类别/原因码；server 不读取结果或错误明文。客户端核验签名、请求/载荷绑定和内外一致性，最终以密文中的类别为准。server 自发失败的 `not_forwarded` 同时绑定 attempt ID 与 relay 实例 epoch。relay 在同一临界区封存拒绝或入队决定；已拒绝的相同请求体副本只能重取同一拒绝，已入队、仍在处理或请求体不同的副本均为 unknown。入队后断线、写失败或超时不能补称未转发。错误码仅供诊断及业务呈现，不作结果类别判断。第 0a 即定下最终结果格式，第 1 期复用，不重新定义。

relay 启动时随机生成 epoch，每个 HTTP 响应（含登录及 `/healthz`）返回该值；客户端把本次看到的 epoch 固定在 Forward 请求体里，底层重发只能重放原字节，收到新值只影响下一次显式 attempt。旧实例、缺失 epoch、表满、请求体尚不可读或其他无法封存的拒绝均无 `not_forwarded`，保持 unknown；仅完全由请求体决定的无效格式可不记录直接拒绝。内存表以 epoch 内 attempt ID 为键，不随鉴权头改变；全局最多 65,536 条、每账户 8,192 条，不提前驱逐。relay 对新 attempt 的查询窗口延伸到原 deadline + 结果保留期；保留期与 daemon 精简终态表共用 `deviceauth.ResultRetention`（10 分钟）。窗口内可转发同一原信封查询，daemon 仍先查保留记录、再检查新执行期限，绝不延长原授权。拒绝与入队记录保留到原 deadline + 结果保留期 +1 分钟；同 attempt 的封存结论覆盖整个查询窗口，过查询窗口一律 unknown。清理同时要求单调经过时间和墙钟截止都已过；维护墙钟高水位，回拨不能使清理后的旧请求重新获准。

正常时钟下按最远 deadline 为准，relay attempt 最长驻留 21 分钟；65,536 / 1,260 ≈ 52.0 attempt/秒（全局）、8,192 / 1,260 ≈ 6.50 attempt/秒（单账户）是最坏期限分布下的持续准入容量。每次显式重试占一条，透明副本复用同一条；回拨等时钟变化可延迟清理；达到容量仍背压为 unknown，不缩短封存期。

四端以每次调用、每次网络交接各自拥有的句柄维护共享证据：登录、预检、取消没有登记便无权结算；每个投递最多结算一次；分类时读取当前证据，并计入尚在预检的并发副本。恢复构造器必须明确传入 prior，不能默认当作首次发送。Android 在 RPC 边界强制禁用连接重试并使用 one-shot body；Go 与 iOS 保持当前传输行为并以真实连接断开回归覆盖，浏览器不承诺一次 fetch 只有一次物理投递。正确性依赖 relay 封存和冻结在请求体内的 epoch，不依赖客户端能看见每次底层重发。

epoch 的发现与缓存以实际 API 来源为准。网页的同源代理模式统一使用 `apiBase`，Vite dev/preview 同时代理 `/healthz`、RPC 和 WebSocket；不能因冷启动发现 epoch 而绕过代理直连账户中的后端地址。

web 与 Go 的按授权 ID 派发历史索引只在没有活跃 call、且原 deadline + 结果保留期已过后清理；同时核对经过时间，墙钟跳变不能提前清掉证据。新调用、关闭调用和停止客户端会检查清理，空闲时每 30 秒检查一次。清理器只持有不含密钥/载荷的索引，不持有整个 Remote/Client。索引删除不清空尚被调用方持有的 RequestSlot 证据；Go 对已过窗口的重新打开授权维持保守 prior，不能因回拨或索引已清理而变成首次发送。Android/iOS 的派发证据由各个 PreparedCommand 持有，没有随只读轮询增长的同类全局索引；pending 对象的证据不因过期而清空。

保留期仍以 `deviceauth.ResultRetention` 为单一维护来源。`scripts/gen-result-retention` 从该策略生成网页、Android 与 iOS 常量，Go full 核对三端产物与 daemon 的值一致。正常时钟、默认一分钟 deadline、每五秒一次轮询时，索引只覆盖约十一分钟的请求，加至多一个清理周期；活跃或尚未到窗口的授权不以容量/LRU 规则提前驱逐。

下表是四端共用测试向量的规范。H 表示**此前其他尝试**可能进入准入；当前尝试也可能已进入时归入 H=是。H=否包含发起过 HTTP 但收到与该次 attempt 绑定的转发前拒绝。所有状态码枚举须逐个生成向量，不能只测一条代表值。

| 来源 | 状态/证据 | H=否 | H=是 |
|---|---|---|---|
| 本地 | 校验失败、取消、过期、无网、槽/队列不足，能证明本次尚未准入/发出 | not_sent | unknown |
| 本地 | 已发出后的取消、超时、断线、解密/签名/请求绑定失败 | unknown | unknown |
| server 自发 | Unavailable（电脑离线、队列满）、ResourceExhausted（配额/限流），有 `not_forwarded` | not_sent，保留电脑离线等具体原因 | unknown；该次未发送不能覆盖先前尝试 |
| server 自发 | Unauthenticated、PermissionDenied、InvalidArgument、FailedPrecondition，有 `not_forwarded` | not_sent，保留登录/更新等具体原因 | unknown |
| server 自发 | canceled、deadline_exceeded、unknown、aborted、internal、unavailable 或其他码，无 `not_forwarded` | unknown | unknown |
| daemon 签名且绑定有效 | outcome=rejected，单调原因；任何诊断码 | rejected | rejected，仅限相同载荷且不存在已受理证据，否则协议矛盾按 unknown 报诊断 |
| daemon 签名且绑定有效 | outcome=executed；成功或任意错误码（包括 unknown/canceled/deadline_exceeded） | executed | executed |
| daemon 签名且绑定有效 | outcome=unknown；任何码，包括 unknown、aborted、internal、unavailable | unknown，只重试原 ID | unknown，只重试原 ID |
| daemon 签名且绑定有效 | outcome=conflict/business；aborted 等业务码 | conflict，原有编辑/文件冲突流程 | conflict，原有编辑/文件冲突流程 |
| daemon 签名且绑定有效 | outcome=conflict/identity；任何码 | conflict，原载荷单独查询 | conflict，原载荷单独查询 |
| daemon 签名且绑定有效 | 队列/槽、授权、租约、时钟等瞬时拒绝，未持久终结原授权；包括仅声称 outcome=not_sent | unknown，保留原 ID 退避重试 | unknown，原 ID 查询 |
| 伪称 daemon 或无有效绑定 | 缺类别、未知类别、内外不一致、伪签名或拒绝了未经认证的 ID | unknown | unknown |

Router 合并全部路径/尝试：有仍可能返回可信结果的路径就继续等，所有路径失败或到期才向等待者呈现 unknown；主动停止等待不是终局。not_sent 不能仅由 daemon 本次尚未准入推出；逻辑授权还必须不能被迟到副本再次执行。rejected 只限相同不可变载荷的终局拒绝。server 的未转发标志仅是诚实 relay 对本次调度的说明，不是密码学上的 daemon 执行证明，不能推翻 daemon 或其他路径证据。重试保留原 ID/载荷/期限，不把任何服务器状态用作自动换 ID 的授权。第 0a 已按此矩阵验证现有单路结果；多路径合并仍属后续阶段。

### 接受记录、保留与时序

受理记录增加经解包后的原始业务载荷与不可变 scope/原截止时间的域隔离 SHA-256，排除加密随机数和密钥 epoch；相同授权重试必须保留首次序列化的原始字节，不能把 protobuf 解码成对象再编码（map 的顺序可能改变）；换密钥只重新加密这些字节，不改变 hash。客户端保存待发送请求时，一并密封保存原字节、scope、ID 和原 deadline，并在可能发出前完成保存；损坏或旧格式的待发送记录不靠重新序列化恢复。同 key 先认证再比较 hash，不同则 conflict，不能返回另一载荷的缓存正文。`accepted` 表增加 `payload_hash`、`retain_until`、显式状态/类别，逐条校验和覆盖新字段，并保留接受记录时间水位；不再用 Done/Failed 两位推导结论。本期不做全表 manifest；逐条校验和与时间水位不能检测整行删除或整库回滚，额外完整性证明列在 [plan](plan.md#传输模块与直连) 的待办。

**采用独立精简条目预算**，保证截止时间后固定 **10 分钟**可查询终局类别，全文结果仅尽力保留：

- 全文缓存仍为 8,192 条 / 16 MiB，计入 key、正文和开销。平均每条仅 2,048 字节；单个近 768 KiB 结果加开销只能存约 21 条，不能靠此预算保证全量宽限期。正文被驱逐时标 `result_available=false`，不能编造业务返回值。
- 独立持久精简表为 **65,536 条 / 16 MiB**，每条按 **256 字节**计费，包含域隔离 key hash 32、载荷 hash 32、deadline/retain_until 共 16、状态/类别/原因及完成标志 16、校验和 32，另预留索引/条目逻辑开销 128。合计 256；不存长 key 或正文。SQLite 页/WAL 的物理空间另行监控，16 MiB 是逻辑准入预算，不能宣称数据库文件恰为 16 MiB。
- 准入原子预留精简条目和运行记录；全文预算不足可不留正文，精简预算不足不执行，只回原 ID 可重试的 unknown/背压，不能提前驱逐未到 retain_until 的条目。请求最远截止为现在 +10 分钟，故最长驻留 20 分钟；65,536 / 1,200 ≈ **54.6 次/秒**是最坏截止分布下的持续受理容量，突发受条数限制，满即背压。不是无界吞吐承诺。
- `retain_until = 原 deadline + 600 秒`，到点前精简条目与防重复身份不能删除。到点后无论过去是否完成，缺记录的过期 ID 对外**永久 unknown，永不重新执行**；记录仍在时可返回已有证据。不能延长旧授权 deadline 来“恢复”过期操作。超过恢复目标的断网立即显式显示结果待核对；恢复后自动查原 ID，宽限内可恢复类别，正文丢失要显示结果详情不可恢复；宽限后缺记录标结果无法确定，供用户查会话事件并自行决定新操作，不能自动重做。

| 时序/状态 | 唯一处理 |
|---|---|
| 同 ID 在途；等待表未满/满 | 有运行者则有界等待；表满立即 unknown/busy，不占执行槽，不取消原执行 |
| 已完成，截止后、retain_until 前查询 | 认证后先查记录，再判新执行期限；返回原类别及仍可得的正文 |
| 过期且缺记录 / 无效信封 | 必须拆分内部错误：前者 unknown 且不执行，后者仅按可认证的单调拒绝规则处理；不能都映射 ErrInvalid/rejected |
| 运行中越过保留期、持久条目被剪枝 | 独立进程运行表仍阻止第二次执行；结束后不重建过期条目，对外 unknown，释放运行登记和槽 |
| 回调结束但无可信定案，或连精简类别也无法记录 | 第三状态 `ended_unknown`，当前及后续等待者立即 unknown，不再入等待表；能持久化则记精简状态，失败时磁盘原 in-progress 仍阻止重执行 |
| 重启后残留 in-progress / ended_unknown | 无本进程运行者，立即 unknown，不进等待表、不重新执行 |
| 回调取消/超时/关闭 | 回调接口须返回 `final(outcome, result)` 或 `undetermined(reason)`，error 另作诊断；marshal 成功不代表定案。无证据返回 undetermined，不能落假终局 |
| Open 与原子 start 之间到达副本 | 共享执行闸门重新查 key/hash 并完成持久准入；只一个回调启动，执行期间不持全局锁 |

受理后的状态代数为 `running → final(executed/business conflict) 或 ended_unknown`，运行者只在内存登记；身份 conflict 不改变此状态。全文超限不必降为 unknown，只要精简终局类别可保存。终局证据只在原子保存成功后回复为可恢复结果；正文写失败但精简终局提交成功可回复该类别及详情不可恢复。精简提交也失败、或保留期已过，即使本次回调算出了结果仍统一回复 unknown，避免首份与后续查询结论分叉。

此存储变化把 daemon 安全状态代数从 **3 升到 4**（`storageVersion` 和 `security-v4.db`，相关初始化/配对路径一起改）。产品不自动迁移、不并行打开旧 endpoint、不猜旧记录 hash。升级先停止旧 daemon 并核对在途操作，通过仓库内一次性手动工具备份、校验并保留原配对身份、成员链、密钥和租约；旧接受记录没有载荷 hash，不迁移，旧授权结果查询保持 unknown。工具在使用截止时间前逐条验证原 v3 接受记录的形状和 checksum；任一记录不符即拒绝，dry-run 也给出明确错误，不跳过损坏行。全部记录通过后要求旧截止时间全部已过，并保留持久时间下界，避免旧请求在时钟回拨后重新准入。具体操作与回退限制见[开发说明](development.md#安全状态-v3-到-v4-的一次性手动升级)。四端协议统一为 15，必须一起更新。自动更新策略的 state-generation 为 4；旧 daemon 的自动更新器遇到状态代数变化会停下，手动迁移工具成功后才写入新标记，不能仅用协议升级替代这一屏障。升级要求须写入发布说明。

终局类别与正文可用性分别传达：正文不可恢复时保留已确定类别，客户端刷新最新状态；身份冲突不返回原记录正文、不覆盖原记录，也不能当作原提交未执行而换 ID 自动重发。

### 重构必须移除的连接依赖

第 0b 已按下表经 Link/dispatcher 适配，只有 RelayPath，保持现有业务行为。除显式 online 条件外，按钮的 unlinked 宽限、后台下载、live polling、以及连接检查中“server ping 失败是否跳过对端”也取 Link 状态；历史、账户、推送和 server GetImage 仍保留各自的 server 条件。后续路径继续遵守这些边界：

| 位置 | 改造边界 |
|---|---|
| 网页 `remote.ts` 的 schedules / snapshot / 操作入口 | `this.conn === online` 与 machine `online` 改问 Link 可达性、能力和授权；历史同步仍单独看 server |
| Android `Remote.forwardOnWorker` 及上层按钮 | machine `online` 拒发改问 Link；`retryOfUnknown` 例外不能代替统一证据模型 |
| iOS `RemoteLive`、`ProjectRows` 等 UI/core 闸门 | 主连接与 machine `online` 条件改问 Link；逐个核对，而非只换 `forward` |
| 网页 `reconnectNow` / `drop`、Android socket cleanup、iOS `RemoteTerminal.finish` | socket 只结束 Path；逻辑终端由 Link 持有。仅 RelayPath 时仍可按既有策略结束流，但不由物理连接直接调用产品 onClose |
| 三端 machine meta 消费者 | online、protocolVersion、fileUpload 等能力经 Link 提供，不直接借 server 状态授权 |
| daemon `session()` / securitySyncLoop / execute / workers / terminals | 第 0a 期建立的进程级所有权在第 0b 期接入 Link，网络同步、执行和终端不能随连接被统一取消 |

## 2. 路径与资源隔离

RelayPath 适配既有 HTTPS `Forward`、主 WS 和独立终端 WS。第 0b 期完成所有权重构，第 0c 期在协议 15 上实现中继活性与原 ID 调用恢复。账户、历史、通知和图片显示副本不改语义；新增信令定向转发见第 5 节。

DirectPath 四端统一用 WebRTC DataChannel，daemon 用 Pion，自建 STUN，不部署 TURN 或依赖第三方 STUN/TURN。一条路径在加密传输连上、且对端确认之后就交付使用，不另外要求 STUN 返回的映射地址：有公网地址、不在 NAT 后面的设备本来就拿不到这种候选，STUN 不可达时所有设备也都拿不到，再要求它只会让已经通了的路径白白留在中继。daemon 的本机地址候选固定用一个 UDP 端口（默认 41478，环境变量 `REMOTE_AGENT_DIRECT_PORT` 可改，`0` 改回随机端口），每个本机地址一个套接字，网络变化后按新地址重绑；公网映射候选仍用随机端口。这样电脑前面的防火墙可以只放行这一个端口的入站 UDP：浏览器把本机地址藏在 mDNS 名字后面，自建 STUN 目前只有 IPv4，电脑拿不到浏览器的 IPv6，不会先朝它发包；默认的有状态 IPv6 防火墙因此丢掉浏览器发来的检查，只剩单向（2026-11-16 实测两台联通 IPv6 之间因此连不上，手机浏览器因公开本机 IPv6 能连上）。放行这个端口后浏览器的检查直接到达电脑。UDP 被挡、NAT 不可穿透、STUN 不可用就走 HTTPS/WSS；浏览器保留默认 mDNS/候选隐私，不为取地址申请音视频权限。

选择 WebRTC 因为浏览器可用且四端有共同实现路径。[实测](transport-notes.md#2-吞吐与排队)中 QUIC 的吞吐与资源更好，但原型假定 UDP 可达，未验证手机集成或打洞。本期不引入 QUIC；上层不能看到 PeerConnection/SDP。

bulk 用**独立 PeerConnection**隔离拥塞；可靠有序 DataChannel 承载业务，独立的不重传小通道只作探测。指令/审批优先于终端，终端优先于 bulk，各自有界队列并给探测留发送预算。初始传输片为 16 KiB，遵守 `maxMessageSize` 并预留 framing 空间，不能直接发 768 KiB 应用块。先封装再分片，有界重组后进入共享安全入口，未认证数据不推进水位；每片入缓存前核对该消息实际保留字节加本片长度不超过声明总长，并核对实际 peer 缓存预算，不能只按未认证的声明长度计费；上传按已持久 offset 推进，不照搬原型八块并发窗口。

第 1 期的 daemon 分类调度在**纯中继下就启用**，不等待 DirectPath 或独立 bulk 路径：执行槽按 daemon 全路径合计 8 个划分，交互/Interrupt/审批 2 个，普通指令与非 bulk 只读 4 个，bulk 2 个。**三池互不借用**，普通/bulk 不能占交互预留；交互按会话轮转、每会话最多 1 槽，machine 级交互以发送 peer 作为公平性 key，不能用多个 request ID 绕过。

读循环只做有界外层解析与分类入队，不同步等待解密 worker、执行槽、成员网络拉取、fsync 或后端；命令种类在密文内，由共享安全入口解密后分类，不信任 server 标签。认证工作用独立有界队列（64 帧/4 MiB，单 peer 至多 8 帧/1 MiB）与 2 个 worker，按密文帧计费；worker 验签解密后分类，未知 epoch 交独立同步等待队列（每 peer 1 个、全局 8 个、5 秒期限），不占认证 worker。整帧仍受 1 MiB 上限。

认证后的执行队列按**解密、解压后实际保留在内存的业务对象大小**计费，包含 protobuf 正文，不能把正文藏在另一张未计费表中。全局预算为：

| 队列 | 命令 | 条数 / 字节 |
|---|---|---|
| 交互控制 | Interrupt、ResolveApproval、AnswerQuestion、AnswerPlan、CancelInput、ResumeInput、GetLiveSnapshot | 32 条 / 4 MiB |
| 交互输入 | Send | 16 条 / 4 MiB |
| 普通 | 普通指令与非 bulk 只读 | 64 条 / 4 MiB |
| bulk | 上传与 GetSharedFileChunk | 16 条 / 4 MiB |

两个交互子队列共用 2 个交互槽；槽空出时**控制子队列严格优先**，Send 不得排在已排队的控制操作之前，也不得占用控制子队列的字节。交互池中 ResolveApproval 与 GetLiveSnapshot 共用预留容量，其余控制命令和 Send 同时最多占 1 槽。每 peer 同时最多 1 个 GetLiveSnapshot 占槽；槽空出时先调度 ResolveApproval。审批与快照均可使用空闲交互槽，并仍受每会话最多 1 槽限制。每个（子）队列内按 peer 公平调度，每 peer 的条数和字节都限制为该队列全局预算的 1/4。唯一例外：该 peer 在此（子）队列中当前没有排队项时，一条请求可以超过 peer 字节份额，但必须放得进该队列剩余的全局字节预算，并完整计费；不能用多个 request ID 叠加例外。上传块仍为 768 KiB，MaxChunkBytes、wire 字段和已密封请求不变；大 Send 仍进入交互输入队列。

每个执行（子）队列的全局字节预算不得小于合法解码正文上限 4 MiB，配合空 peer 单条例外，使合法的大控制请求、输入和上传块都能进入空队列；计费口径变化时也必须保持这一容量下限。

控制子队列内部依次优先 ResolveApproval、AnswerQuestion/AnswerPlan/Interrupt、CancelInput/ResumeInput、GetLiveSnapshot；同优先级继续按 peer / 会话公平轮转。GetLiveSnapshot 的所有用途统一归类，不靠 wire 区分，不受其余控制/输入并发最多 1 的限制，只受每 peer 快照并发 1、每会话 1 槽和总交互 2 槽限制；仍是只读、不写接受日志，plan 的核屏步骤也受 5 秒交互期限约束。客户端发送控制命令前必须完成的读取与该控制命令同池，不能在忙时跳过重新核验或预填 observedEventSeq。

审批指标覆盖三端实际发起的 GetLiveSnapshot → ResolveApproval 完整流程：客户端按产品行为在审批前自己读取最新状态（Android 实际是两次读取加一次审批，三个串行命令），不预填 observedEventSeq，不能只测直接发送 ResolveApproval，也不为压低数字省去读取。数字只在写明条件时才有意义，验收记录必须说明用的是哪个口径，并报告实际获槽 / 完成比例：

- **调度口径 p99 ≤100 ms**：纯中继、本机 server 与 daemon（往返可忽略）、普通池与 bulk 池同时占满，也覆盖长 Send（含超期未退出）与快照洪泛。它验的是队列与执行槽，不含设备 CPU 受限的影响；三端的现值见 [1b 验收](acceptance-notes.md#1b-分类调度与完整审批验收2026-11-15)。
- **端到端口径（直连 bulk 饱和）**：真实客户端、真实 relay 往返，直连 bulk 在同一台设备上加解密、与审批争用 CPU，所以上限随设备和构建而定，不套 100 ms，每端各写条件和上限。**Android p99 ≤350 ms**：iMac 上 4 核 x86_64 模拟器（API 35），非调试且已编译的构建，本机隔离 server 与 daemon，机器静默，harness 的 relay 往返中位数 17 ms（纯 HTTP 3 ms，约 5% 有 45–60 ms 的尾巴），每次 100 个样本；现值 p99 空闲 200–247 ms、饱和 223–299 ms，中位数约 55 ms 与 98 ms，其中等回复只占约 15–20 ms，其余是客户端（[测量记录](acceptance-notes.md#transport-1d-approval-2026-11-16)）。网页和 iOS 还没有同条件的端到端数字，不借用 Android 的；换设备或构建要重测，p99 ≤100 ms 不适用于这一口径。

执行消费者先查同 ID 协调状态，重复进等待表；新请求**先取槽，再在执行闸门内复查并持久受理**。队列满或排队期限内仍无槽，未持久化终态拒绝时回复 unknown/busy，Router 按证据矩阵合并并退避原 ID；不留虚假的 in-progress。认证队列堵塞只拒当前帧，不阻塞读取审批、心跳或结果。

交互最长占槽 **5 秒**，普通 **60 秒**，bulk **10 秒**，且不超过原 deadline；Send 的 5 秒只覆盖持久入队步骤，不等模型完成。输入/文件长任务必须拆成有界后端调用。实现须让具体后端 I/O 遵守期限并确认回调退出，不能仅取消 ctx 就假释放仍运行的槽；违反期限的回调标 unknown、隔离该资源并停止向它准入，仍计原槽，禁止新 goroutine 绕过 8 槽。放弃执行与发布最终结果在同一把锁下作一次性决定；发布方先取得受理状态锁，再竞争该决定，已放弃的执行不得持久化 final 或通过 Lookup 返回成功。contextio 等后台 I/O 在外层返回后仍未退出时也继续计原槽；不可取消的锁和文件调用按实际资源隔离。此情形验收失败，不能声称仍满足调度上界。其他会话的队列到期照常返回，不能无限等待。审批从已认证入队到获槽或明确背压的 **p99 ≤100 ms**，同时报告实际获槽/完成比例，不能以全拒绝冒充及时审批；健康有界后端下无洪泛的不同会话审批须成功完成。

两路重复只占原执行的一个槽；等待、ACK、信令、成员同步不占槽，另有 CPU/队列限额。磁盘 bulk 不在共享调度锁内等 fsync；uploads 全局锁公平性必须验证。

`GetSharedFileChunk` 明确为只读类：验签、当前成员/租约和共享对象授权仍执行，**结果不进接受日志、不落盘**，允许重新求值，进入 bulk 池；上传 Put 依靠 durable offset 幂等。下载对象、固定副本与生命周期由 [session-files.md](session-files.md) 负责；该接口及三端下载已实现，第 0b 经 Link 复用现有只读实现；分类执行池属于本步纯中继调度，跨路径续传随后接入，不另定一套路径/版本规则。server `GetImage` 显示副本仍走原服务。

初始资源预算：daemon 最多 8 个客户端 peer，每 peer 最多交互/bulk 两个 PC，客户端最多连接 4 台 daemon；同代次替换短暂并存也计入上限，超限保留 relay。每客户端最多 8 条逻辑终端、每 daemon 合计 16 条。每 peer 发送与重组各最多 2 MiB / 128 帧，daemon 全局各 16 MiB；单密文重组上限 1 MiB、期限 5 秒。候选、信令、重连另见第 4/5 节。daemon 自己实施数量、帧率和字节限额，不依赖 server 的每设备 16 条 WS 或账户 streams 额度替直连把关；这些本地上限不声称实现账户全局计费限额。多客户端与多 daemon 验收必须同时施压。

## 3. 选路、指令与终端

### 升级与热备

**直连优先，中继兜底**（2026-11-17 起的策略，取代此前「直连须先证明更快才升级」的规则；实施进度见 [plan.md](plan.md#传输模块与直连)）。

1. 认证 relay 可用即交付，首个请求不等 ICE；直连在后台建立，失败按第 4 节退避，网络代次变化重新建立。
2. **就绪即优先**：某用途的 DirectPath 就绪（加密传输连上、对端确认、能力快照有效）就成为该用途的首选路径，不先测速、不要求比中继快。两条路差不多快时也走直连：少绕一跳，减轻中继的流量，中继故障时已建立的直连还能继续用。
3. **副作用指令两路同发**：直连就绪时，交互指令（发送、审批、提问与计划的回答、中断、取消/恢复输入）**只封一次，两路发送完全相同的密文字节**，取先到的可信结果；daemon 按 request ID 合并，只执行一次（第 0a 期的结果契约）。重封只用于依法允许的密钥更新，业务身份不变；不按 Path 分配序号。这样指令有直连的延迟，又不会因为直连无声断开而落到「结果未知」。文件正文不双发；终端的双发规则见下文「终端连续性」。
4. **明显更差才退回**：硬故障或软期限立即退回中继，不等 ICE `failed`。按实际请求的完成时间判断（不另做热身测速）：最近 30 秒内直连至少 8 个、中继至少 4 个样本（中继样本来自热路径每八次保留一次的对照），且 `median(direct) > 1.5 × median(relay) + 20 ms`，该用途退回中继；文件按同一文件不同块分段比较，吞吐低于中继 70% 时退回。退回后等待 60 秒再让直连重新优先，连续退回时等待翻倍、最长 10 分钟，网络代次变化或直连重建后清零；重新优先不需要证明更快，只需路径就绪。
5. **只在前台保持直连**：手机 App 和网页标签页在前台时建立并保持直连；进入后台、锁屏或标签页隐藏时关闭直连，全部走中继；回到前台重新建立。省电，也避免后台 NAT 映射过期造成的无声断路。
6. **显示**：界面不并排比较两条路，只在「连接」组状态行右侧和会话顶栏轻气泡里显示**当前正在走的那条路**的响应时间，取最近 60 秒实际请求样本的中位数（至少 3 个才显示）；没有新样本时保留上次测得的数字，只用于显示，退回或硬故障时清掉。标题只写实际在用的路径，不再有「正在测速」；「正在用中继」的第二行只在按第 4 条退回后写「直连较慢，暂时改用中继」，或在并发直连槽已满时写槽满的说明。文件在实际传输时按第 4 条比较。
7. 不改 wire，不改协议号。观测每路最多保留 512 条、60 秒。

理由。旧规则要直连先证明更快才升级，真实使用中只读请求稀疏、样本攒不够，两条路差不多快时也一直留在中继，界面常停在「正在测速」。两台设备能直接连通时，直连通常不比绕一趟中继慢；真正的风险是路径无声断开和个别网络下更慢，前者由指令两路同发和软期限兜住，后者由第 4 条按实际样本退回，0.7/1.2 换成「就绪即优先 + 1.5 倍退回 + 退回后指数等待」，避免振荡。选路决策是纯逻辑，迁移第 6 步时进共享 Go 核心，三端只保留 WebRTC 执行器（[architecture · 客户端共享核心](architecture.md#客户端共享核心)）。

能力通过已认证的 Control 1 与 [Control 14 CapabilitySnapshot](transport-wire-draft.md#冻结后的第一个扩展capabilitysnapshotcontrol-14) 提供；快照失效时上传立即回 relay，下载不依赖上传快照。迟到的较旧 Control 序号不能覆盖较新的能力。硬故障立即回 relay，按第 4 节的全抖动退避（均匀分布在 1 / 2 / 4 … 秒的上限之下，最高 30 秒）开启新的有界协商轮并重新测量；旧 SDK 和未退出的写入继续占资源预算。一轮失败、或已建立的路径断开，各算一次失败，同一轮的多条路径只算一次；路径稳定保持 30 秒以上，序列从头开始；主连接恢复、网络代次变化、本机重新打开直连、收到 daemon 新进程实例（新 boot nonce）的 Probe，都立即清除等待中的延迟，不能让旧失败拖慢新的开始。界面只在确有一次重试已排定时才写「稍后会自动再试」。上传换路先经 relay 查询持久 offset，再在有效期限内重试原授权；不延长过期授权，后续取块/续传调用使用新 ID 和已验证 offset。

网页按本设备、账户与电脑保存「直连：自动／关闭」，默认自动。电脑状态页的交互栏仍显示中继，文件栏显示实际文件路径；健康的只读 PC 不能使已经关闭的 bulk PC 显示为直连。iOS 的协议层认证未知类型后回 Unsupported，不分配 SDK 对象；Android 按上述规则建连，关闭开关或 DirectPolicy 关闭时同样不分配。

### 指令与结果

同一副作用操作只准备和授权一次；双发、换路沿用原 request ID、授权载荷和截止时间。入口按 ID 合并执行及等待者，第 1 节的五类结果适用于每路及合并结果。只读可重复求值，不能充作副作用幂等证据。持久记录只有开始时继续 unknown；不因连接换代重建业务 ID，不把取消 HTTP 当取消 CLI。

接收端可在验签前合并相同密文哈希的在途校验，并丢弃已经验证过的字节级副本（每 peer 最多 4,096 个 SHA-256，保留 10 秒）；未验证帧不能进入“已验证”缓存。哈希命中不推进业务/ACK 水位；缓存被驱逐后仍须完整验签并由逻辑去重保护。不同密文即使声称同 ID 也必须验签，冲突载荷返回 `conflict/identity`，不覆盖原受理结果。这是省重复验签开销，不是身份验证的替代。

### 终端连续性

一个逻辑流只拥有一个 tmux control 连接。两方向各有路径无关的序号分配器、连续应用 ACK、失败水位和有界 replay；第一个业务序号为 1，0 表示尚未应用。范围/签名/当前成员/租约验证后，**先按流、方向、序号重组，再对下一个连续可执行帧调用 Accept**。不能把第 7 帧先交 Accept 执行再等第 6 帧。已应用水位、冲突摘要、失败水位独立于接受日志保留到流结束，不能随 60 秒信封过期而丢失。

输入、输出方向各自的缺口缓冲最多 128 帧 / 1 MiB，按实际保留的完整编码字节在插入前核对；重复不重复计费，消费释放相应字节。两方向独立计时，每个缺口到期点为 min(首次被后续帧证实 +10 秒, 等待帧的原 deadline)，到期未补齐即进入网络恢复，重发或另一方向推进不刷新；补齐后清除该缺口期限。已连续收到但尚未渲染的输出不是网络序号缺口；输出 ACK 仍只在渲染后推进。只有下一个连续序号可应用。输入、输出方向的重复都比较原授权身份 hash；已渲染输出的摘要独立于可驱逐的 replay 正文保留，摘要缺失不能仅凭旧序号确认，不能把输出冲突传播成 Input fail-stop。流内旧序号只确认、冲突拒绝，四端现有 `seq <= last` 即关流必须改造：Go `internal/relay/terminal.go:readTerminal`、网页 `remote.ts:openTerminal`、Android `Remote.kt:openTerminal`、iOS `RACore/RemoteTerminal.swift:openTerminal`。验证过期帧不能绕过截止时间；缺口等到帧过期就进入网络恢复，不能永远等或跳号。发送时的 60 秒截止时间也包含本地排队和补发，不延长已授权帧。

输入帧是**顺序处理单元，不是可回滚事务**：Input 每 256 字节一条 tmux send-keys，可能只注入前半帧。仅该帧全部 tmux 命令明确完成才给成功 ACK，写 socket 不算完成。**fail-stop 只由 daemon 侧 tmux Input 注入失败、超时或结果未知触发**；记录失败序号/已知或可能前缀并立即认证通知，其后依赖输入全部停止，另一条路也不能补打失败帧。Resize、History 等非输入失败不触发 fail-stop：记录该帧失败类别并推进连续“已处理”水位，后续帧继续；查询时必须能分清成功应用与已处理失败。

ACK 携带最高连续已处理序号及输入成功水位/失败状态：不能把越过失败帧的处理水位解释为所有输入成功。Input 失败也推进已处理水位、固定失败水位，后续输入只记为 blocked、不注入；认证失败/缺口不推进任何水位。输出 ACK 在渲染消费完成推进；输入成功水位在 tmux 全帧完成推进。每 20 ms 或累计 16 帧发 ACK，失败立即发送，不逐传输片确认冒充应用成功。

每方向输出 replay 最多 2 MiB / 512 帧 / 30 秒，越界只表示不能补全输出，**不等于 Input fail-stop**。输入每流缓存 64 KiB / **30 秒（direct 10 秒恢复目标的 3 倍）**；重发仍遵守原 60 秒信封 deadline。活流输入的成功/失败水位、每个未确认帧的摘要及结果保留至流结束；旧流重建后再保留 30 秒查询期，每 daemon 最多 16 个活流 +16 个退休查询条目，各最多 128 条/64 KiB 明细，超额暂停新输入/建流，不能静默丢仍待查询的水位。输出与输入预算独立，大输出不能驱逐输入依据。

新增路径交换认证的流 ID、双方进程实例、路径代次、双向水位与失败信息；barrier 最多等 5 秒，超时只放弃新腿。中继腿恢复用 `AttachPath` 绑定原 stream ID、sender、session、新腿 ID/代次和水位，server 按新腿 ID 配对；daemon 查注册表挂载，**不调用 OpenTerminal、不新开 tmux**。旧回调不能关闭新 Path。

路径全断、缺口过期或输出 replay 越界是**网络恢复**：daemon 实例未变时，先用独立认证 `InputStatus` 查询旧逻辑流的输入水位/失败明细。成功的输入不重发，明确尚未应用且原授权有效的输入在旧流按原序补发；daemon 明确拒绝的过期未应用帧可结束旧流，不把后续输入无声跳接到新流。若仅输出无法补齐，核清输入并以 barrier 停止旧流准入、取得最终水位后，才用全新 stream ID + OpenTerminal +快照重建；明确未应用且仍有效的待发输入可在新流重新授权续接，绝不重放已应用/部分失败输入。水位查询与关闭 barrier 必须串在旧流执行序上，不能以仍可能前进的快照作为重发依据。

daemon 实例变化/重启、旧水位已不可得时不作 Input fail-stop 归因，但暂停自动输入，必须用户确认后新流+快照；已有 daemon 注入 fail-stop 同样需确认重建。**确认**表示用户已核对 CLI 画面及按序列出的成功、部分失败、未知和尚未发送内容，并决定放弃旧队列后继续新输入；不是证明旧输入未执行，也不是授权一键重打未知内容。未知/部分失败内容保持可核对，不标送达、不默认选中重放；用户若决定重发须作为独立新输入。仅尚未发送的内容可恢复为可编辑草稿。快照只恢复画面，不能证明按键次数。

终端输入、resize、ACK/barrier/失败控制帧总是热备。输出密文帧 ≤4 KiB 且每流热备副本不超过 32 KiB/s（突发 64 KiB）时封一次两路发；超阈值输出按序只走当前优选路径，保留另一腿以便补发。大输出也不进入文件 bulk PC，仍受终端队列及 replay 预算约束，不能抢审批槽；其切路恢复受探测及 replay 时间限制，不承诺一个包间隔。业务按相同逻辑水位确认两路，不生成 ACK 回环。

物理路径丢失不直接调用产品 onClose，不清屏、不失焦、不重新抢尺寸。真正重建保留旧画面直到新快照可用，并单独处理未知输入。进程崩溃不能承诺任意 CLI 的 exactly-once。

### 分块续传

bulk 软期限从 `max(500 ms, 4×近期 RTT + 调度余量)` 起，交互/切换窗口探测可每 50 ms，空闲降频，后台停止。超预算启动备用续传，不判电脑离线；250 ms 仅为受控低延时配置，[有限窗口原型](transport-notes.md#3-网络切换与热备)不能证明真实网络零误切。

上传换路先查 Status，只认 durable `persisted_bytes`，按同一 transfer ID、offset、字节及哈希重发。**原块请求尚有效时沿用原 request ID/截止时间；块已过期时允许新 request ID 和新期限重发相同 offset**，安全来自上传的归属、重叠字节比较和持久 offset 幂等，而非重复执行 CLI。这个例外不适用于会话创建、消息、审批等副作用指令。下载在固定共享副本内按已经校验并持久保存的连续 offset 恢复，允许只读块用新 ID 重新求值；副本删除/过期按文件设计失败，不悄悄切换文件。进度不归零，未确认尾部不算完成。

## 4. 网络切换与第 0 期中继修复

### 可测的恢复承诺

以下都是**待产品验收的目标**，前提为客户端在前台可调度、daemon 进程可调度、授权有效；不将系统无网或挂起时间算入可用网络上的恢复预算：

| 情形 | 目标与测量起点 |
|---|---|
| 单路故障，备用路仍通 | 热备范围内的交互流量，故障后最大应用间隔相对健康对照增加不超过一个正常包间隔（20 ms 发包场景为增加 ≤20 ms）；记录两路 RTT，该目标仍须在非对称 RTT 下验收：备用路的传播时延可能使其不达标，需如实报告并由计划中的目标校准决定后续处理 |
| 本机 Wi-Fi↔蜂窝等，两条路同时失效 | 从新网络可用的通知/首次可验证探测起，relay 达认证 Ready 且一次真实 Link 调用可用目标 ≤3 秒，direct 恢复身份绑定与业务可用目标 ≤10 秒；不把只收到 Ready 当作业务恢复 |
| 无系统 hint 的静默黑洞 | 前台活性阈值下限 15 秒，随观测心跳间隔与停顿自适应放宽至最高 60 秒（手机与 daemon 共用，静默黑洞发现耗时 ≥15 秒；有系统网络变化通知仍立即重连），再按 relay / direct ≤10 秒恢复，分别记录发现与恢复；不能用 hint 场景掩盖静默故障 |

双路断开目标以[旧中继 RST 约 1.18 秒到 Ready](transport-notes.md#1-既有中继与网络失效)为有限依据，为重拨与认证留到 3 秒，另给信令/ICE 到 10 秒；该单次本地测量不是移动网络证明。超 RTT 条件、大输出、重放越界分别报告偏离，不能改写成已经达到目标。

0c 预算内的在途 Send/Command 保留原业务字节、scope、ID 与原 deadline；需要换密钥时仅重新加密这些字节。认证 Ready 唤醒旧 HTTP 等待者，用新的 attempt/epoch 查询或重送；客户端先于 daemon 恢复时，未确定结果的调用最多等待 3 秒的短暂 Unavailable，不把该等待当作未执行证明。新调用的绑定 not_sent 仍立即返回。三端复用现有连接状态，主流试探不清掉健康独立终端画面。

以下终端恢复承诺属于第 1/3 期：输入每流有界缓存 64 KiB / 30 秒，不显示虚假已送达，超限停止接收并明确要求处理，不能静默丢输入。恢复先按第 3 节查询旧流输入水位，网络型不确定自动续接，水位不可得才要求确认；副作用结果按原 ID 核对。超恢复目标需给可证实状态，不能永远隐藏失败。

### 第 0c 期活性与重连

已在第 0a 正确性与第 0b 重构之后实现，协议、存储和产品文案不变。账户同步组件接收统一网络代次和活性信号，但其同步结果不等同对端可达性。网络变化只退休旧代次的登录/成员 HTTP 轮次，原同步 owner 继续，新轮次不等旧网络的长超时；旧响应不能安装或清掉新轮次状态。

接入客户端引擎时先交付已经观察到的网络签名。尚未收到系统观察时不伪造签名，首次真实观察只记录基线（即使已经 Ready），后续签名差异才推进网络代次。这样账户加载前收到的基线不会丢失，首次 Ready 前的真实换网也能退休旧登录。

恢复用登录、安全 pull 与成员目录都有 owner 自己的整轮期限（恢复路径为 3 秒），单个 waiter 的超时不决定共享工作寿命；超时或拒绝必须清槽或更新被拒凭据，后继可以开始新轮次。首次 start 可加入已有工作，真正的 stop→start（包括尚未收到首个 Ready 的情况）必须先退休停下期间的旧网络轮次。

唤醒 Touch 失败不缓存成永久拒绝：下一次操作可重做 Touch，或由同代、同 revision 的完整安全同步解除 barrier；旧同步成功不能解除较新的 barrier。业务 request ID、原始字节及授权 deadline 不因此改变。

候选建连代次只控制候选；已激活腿的排队帧和 Ready 后续工作直到该腿真正退休才失效。独立历史读取属于 buffer 与客户端生命周期，列表/偏好失败退避属于读取 owner，不以另一条主流的 online 转变作为唯一重试机会。Forward 重试保留 S6 原始字节、scope、request ID 与 deadline；验证过的安全 head 改变时重新加密，不能把旧密文跨换钥继续发出。只保存了信封的恢复入口先核验本设备签名并解包原字节，不能重新编码命令或重新观察用户操作。

原生 Forward 的换路不消耗普通重试次数，但整个操作受原 deadline + 结果保留期的固定截止限制；Ready、凭据更新与再次等待都不延长它。截止时仅退出该调用的等待并保留 unknown，未发送的过期调用保留原 expired/not_sent 规则；共享授权由其 owner 结算，单个 waiter 到期不能清理它。

健康终端保留其独立腿。已打开的终端腿在主流恢复之后才报错，也会按自身关闭事件重开新流、取得快照；前后台/离开页面仍可显式退休它，初次开流失败不形成立即重试循环。保留旧画面，不重打未知按键。

| 端 | 改造 |
|---|---|
| 网页 | online/offline、可见性、freeze/resume 及支持时的 `navigator.connection.change`；原始收帧更新心跳，不等历史解密；移除 60 秒静默等待，换网唤醒原 ID 的 Forward，不让旧 HTTP 独自等约 45 秒 |
| Android | 比较默认 Network handle、地址、LinkProperties 与能力；合并通知，真实路径变化才推进代次；缩短前台 ping 预算，原 ID 调用可协调恢复 |
| iOS | NWPathMonitor 核对路径信息，同接口 Wi-Fi/DHCP 靠活性兜底；不能只比较接口名，缩短现有 20–40 秒检测 |
| daemon | macOS/Linux 接口/路由/地址通知加有界探测，替代仅 25 秒 ping + 20 秒等待；新 relay 建连不等待旧 workers/terminals 排空，旧 Path 只停止接收并退役等待者，进程级执行仍共享同一配额 |

初始前台心跳为 1 秒，手机与 daemon 共用 `shared/linkcore` 的同一活性规则：收到 2 个心跳前保持 60 秒默认阈值，之后静默判可疑阈值为 `min(max(15s, 3×cadence) + 3×stall, 60s)`。其中 `cadence` 为心跳间隔 EWMA（`(7×cadence + dt)/8`），防止 TCP 重传后突发排空把间隔压低；`stall` 对超过 `cadence` 的帧静默快升（每次上升差值一半）、在平稳非突发心跳上慢降（按 `7/8` 衰减），因此经历长时间停顿后阈值回落到 15 秒下限较慢，换取弱网持续抖动期间不反复误判。静默黑洞发现耗时在手机与 daemon 上均为 ≥15 秒；有系统网络变化通知或真实读错/关闭仍立即重连。daemon 仅因 `suspect` 发起候选建连时，若旧腿在候选发出 `StreamHello`（中继据此取消旧腿）之前重新收帧，立即中止候选并继续使用旧腿，不毁掉仍在工作的连接与在途调用；单次探测失败不发布电脑离线。每目标重连令牌桶容量 2、每秒补 1 个，进程全局容量 4、每秒补 2 个；重复通知合并，首次有效换网可立即用令牌，耗尽只保留最新代次。失败按 1/2/4…最高 30 秒全抖动退避，系统通知不能清零桶或反复重置退避。daemon 拨号预算按触发原因区分：仅 `network` 换网在已有缓存 token 时收窄为 3 秒以快速放弃失效旧路由，`lost`、`wake`、`suspect` 与首次登录保留 15 秒完整预算，避免高 RTT/丢包线路上反复打断尚在进行中的 TCP/TLS/WS 握手。新网络的快速恢复目标以桶有可用额度为条件；风暴测试同时报告限流后的恢复延迟，不能声称任意通知洪泛都 ≤3 秒。恢复测量（`internal/relay/recovery_measure_test.go`）对 `blackhole` 场景的单样本等待上限为 25 秒，与 ≥15 秒静默发现下限对应。

允许一个旧路径与一个试探新路径短暂并存，认证响应后才切换，旧回调不覆盖新状态；daemon 候选发 `StreamHello` 由中继顶替主连接后旧路可立即退役，独立执行不受影响。共享 8 槽仍可能被长操作占用，要靠隔离和准入保证交互，不能通过无限新建 worker 绕过上限。弱网、调度暂停和 bulk 下若仍触发误判，代价限定为有限探测/重拨，**不能取消已执行操作、重复执行、结束逻辑流或连累另一条健康路**；长时休眠/调度暂停检测独立保留 3 秒跳变阈值，不随网络静默阈值拉长。验收统计每小时误试探次数、流量及恢复分位，初始目标健康 3% 独立丢包下误发布离线为 0、额外试探 ≤6 次/小时；未满足先调预算，不放宽安全语义。

后台不以伪音频/VoIP 或无限 ping 保活，暂停活性累计。回前台/休眠唤醒先 Touch、刷新成员/租约，核对单调时钟与路径代次，再恢复 relay、结果/offset 及逻辑流；不能直接用睡眠前的 socket。daemon 重启丢弃 PC、内存 replay 和旧进程实例，副作用只查持久结果，终端必须新流+快照，未知输入不重打；唤醒越过租约先停收发；第 1/3 期接入终端恢复后，仅 replay 越界仍先查询旧输入水位，不把网络恢复变成注入 fail-stop。客户端同样遵循平台进程回收边界。

## 5. 协议与安全绑定

保留现有业务信封加密、签名、AAD 和防重放；DTLS 不替代设备授权。绑定还能防错误设备连接、IP 暴露和 DoS，但不能消除 relay 已知的交互元数据，热备仍有中继小流量。第 3 期启用终端直连后，输出优先走直连数据通道（中继 `/v1/term` WebSocket 仅承载低速镜像帧与恢复腿，恢复腿 `TermHello.StreamId` 与普通流保持相同 32 位小写十六进制格式，但直连就绪时不会先在中继上出现 `openTerminal` 命令），因此**第 3 期流量形态对中继可见（例如长连但下行稀疏）属于已接受的侧信道**，中继仍无法读取明文、密钥或区分恢复腿与普通流的流 ID 格式。

### 第 1 期验证后冻结的 wire 契约

第 0a 的结果格式是最终格式并单独协调协议升级；**第 1 期 1a 已完成 Go Pion、浏览器（含 WebKit）、Android 和 iOS 独立 SDK 验证，下列 wire 字段及既有语义于 2026-11-15 冻结为协议 16**，不重定义结果。终端重组、ACK、InputStatus、replay、barrier/AttachPath 先用两条可注入故障的假路径跑完整状态机和四端向量，第 3 期才接真实热备；第 2/3 期仅启用已定义能力。字段编号和编码由实现时 proto/安全编码及共用向量负责，本表规定不能拖到后期的语义。已有[已冻结字段与安全编码](transport-wire-draft.md)，已有四种语言信令轨迹、实际 SDK 互连及终端假路径模型的[实验记录](transport-notes.md#9-四端信令真实封装与跨-sdk-互连)；已冻结（协议 16，整合时若被占用则顺延），不代表产品安全、并发或真机性能验收。冻结后同协议只能新增可以返回 Unsupported 的类型，不修改已有语义。

| 格式 | 第 1 期必须覆盖的语义 |
|---|---|
| 外层定向帧 | ToDevice、FromDevice（server 从登录设备写入）、Signal/Control 类别、发送者本地 frame ID、有界密文字节及 PeerFrameResult；无历史序号、无落库 ACK，离线立即失败 |
| 身份与代次 | 固定域/账户、双方设备和角色、machine、协议、成员 epoch+head、双方进程随机实例、随机 connection ID、PC 用途、generation、双方 boot challenge、信令方向与单调序号、短期限 |
| 分片 | 消息 ID、片号/总片数、完整密文长度与 hash、路径代次；重组后才验业务信封，片级收到不算业务 ACK |
| 逻辑流 | stream ID、方向、路径无关逻辑 seq、原期限；流 ID 永不复用；路径 generation 不重置逻辑 seq |

业务信封的 Header.Seq 是逻辑序号，不绑定某一条路径代次；分片外层的路径代次只用于该路重组和旧回调隔离，不能授权、推进逻辑水位或改变两路相同的业务密文。控制体将需要认证的路径代次显式签入；TransportControl 不走业务接受日志，所有 Control 都签入双方当前进程实例，ACK 等再依赖逻辑水位防重放，策略更新另依赖原子持久化 revision 幂等。daemon 重启时旧实例的任何 Control 均拒绝，即使内存水位已丢；引导 Probe/Challenge 是唯一可在实例未知时使用的类型，不能执行控制动作。

未启用能力收到相应控制体时返回认证的 unsupported，不执行；不能以忽略未知控制体代替解析。四处协议号（Go `internal/protocol`、网页 `web/src/protocol.ts`、Android `core/Version.kt`、iOS `RACore/Version.swift`）同值；具体号随实现基线确定，本次文档不改。控制/信令使用固定 type ID + 有界 payload 的可扩展编码，未知 type ID 可被认证后明确回复 unsupported；在此编码中，新增 TransportControl 变体或信令类型，且旧端按固定编码返回已认证 `unsupported`、发起方保留 relay 而不改变既有操作语义，属于同一协议内扩展，不升协议；这不是旧协议降级。改变已有字段/类别/授权含义、未知类型处理或使旧端误解的行为，仍按 [architecture §4](architecture.md#4-协议设计要点) 升级，不写旧协议降级。可关闭直连只是**同一协议内运行时开关**，不能回退上一期二进制；升级/重建要求必须写发布说明。

### 非持久双向信令

选**新增定向 server 帧**，不采用 Forward 长轮询应答：双方主 WS 均可发送 `DirectedPeerFrame`，server 校验登录设备、同账户目标及 Client↔Machine 角色，向指定设备的主 WS 投递 `PeerFrameDelivery`；daemon 可主动发送 answer、追加候选和 ICE restart，不需等客户端轮询。外层 sender 不取客户端自报值，接收端解密后还核对签名身份和内层目标；server 只见路由标识、长度和时序。同一种定向帧另设 Control 类承载加密 TransportControl，让能力握手、AttachPath、远程策略及确认也有双向 relay 载体；已有终端腿及 direct channel 可直接承载控制密文。Signal/Control 分类不暴露业务内容，不能据外层类别免去内层 Purpose 校验。离线不排队、不补投、不广播、不写数据库或持久日志；对端断线就失败，重连重新协商。

定向投递增加 `PeerFrameResult(frame_id, delivered|offline|limited, retry_after)`，返回发送者当前主 WS，绑定其本地随机 frame ID；delivered 只表示已写入目标 WS，不表示对端已认证/处理。队列驻留超时返回 limited，目标先断开返回 offline；成功回执丢失可重投同 ID。同一（发送者、目标、类别）队列 FIFO，Signal 与 Control 之间不保序，内层序号/状态机负责顺序；接收方重复确认而不重复调用 SDK。server 为回执另留每 peer 512 帧/256 KiB（计入 Control 全局预算），丢回执走相同重试，不从 delivered 推断业务执行。

Signal 与 Control **各自使用独立于现有 `peer.out` 的有界队列及字节记账**，共用 socket writer 但主推送优先、各队列公平轮转。超额仅丢当前定向帧并回 limited，绝不因信令洪泛调用现有 sendFrame 的慢接收方断连分支；socket 本身故障仍正常断连。Signal 单帧 ≤64 KiB，每设备 **256 帧/s、突发 256，4 MiB/s、突发 4 MiB**；账户 **1,024 帧/s、突发 1,024，16 MiB/s、突发 16 MiB**。每目标 Signal 队列 256 帧/4 MiB、驻留 ≤1 秒。Control 每设备 512 帧/s（突发 1,024）、512 KiB/s，账户 2,048 帧/s、4 MiB/s，单帧 ≤16 KiB、每目标 512 帧/1 MiB、驻留 ≤1 秒。server 全局定向待发送 **32 MiB，其中 Signal 至多 24 MiB、Control 保留 8 MiB**，不挤占主推送预算。daemon 自身同等或更严限额，不能依赖中继守规矩；各入口认证 CPU 另限额。

发送端按相同 token bucket 跨 PC 公平节流，优先握手/Confirm，再候选。候选每 50 ms 汇集，前 2 批（批次 0、1，覆盖首批 host 与随后 STUN 返回的 srflx）在 50 ms 到期或攒满 16 个时即发以保持 Trickle，第 3、4 批（批次 2、3）攒满 16 个或收集结束时发出（每代至少可发 34 个），超过剩余批次容量但仍在 64 个上限内的候选计入诊断丢弃计数、不静默丢弃也不超批，`EndCandidates` 上报实际发出的候选数与批次数；每帧至多 16 个、每个编码 ≤1 KiB；每 PC 每代次最多 64 个，最多 4 批，超量结束本次协商保留 relay，不用每个候选单独抢帧。每方向最多允许 **32 个未确认序号**在途，窗口满时等待认证 ACK，不再发新序号；重传不新占窗口。每个需确认的信令以认证的对端序号 ACK 为成功依据（ACK 走独立 Control 预算，不再反向请求 ACK）；PeerFrameResult 只能加速诊断。未确认在 **500 ms、再 1 秒**重发相同序号/密文/本地 frame ID，至多重试 2 次（总 3 次）；limited 尊重 retry_after 且仍计重试/总期限，offline 暂停到对端发现更新。从本次网络可用/重启恢复起总期限 **10 秒**（含 relay 重建），超时只退 relay，后续按第 4 节退避重开 connection/generation，不无限重发或无限生成新代次。

预算按 daemon 重启后 **8 客户端 ×2 PC=16 PC**并发重建核算，不假定“约 6 个候选”：每发送方向每 PC 最多 1 SDP +4 候选批 +End +Confirm=7 帧；112 帧加设备对引导/确认预算 16 帧，共 **128 帧、≤3 MiB**。三份含重试至多 **384 帧、9 MiB**；至多 384 个序号 ACK（每个 ≤1 KiB，共 ≤384 KiB）另计 Control，落在其 1,024 帧突发/512 KiB/s 内；突发后帧调度 ≤(384−256)/256=0.5 秒，字节调度 ≤(9−4)/4=1.25 秒，取较大 1.25 秒，加重试定时 1.5 秒、relay 重建/认证 3 秒、实例发现/引导 1 秒、ICE/DTLS 3 秒，得到 **9.75 秒**的条件性预算。10 秒内成功的丢失前提按**整轮引导（Probe 到双方 Confirm 的关键信令及其确认）合计最多丢两帧**计，不是每条消息都允许丢两份还承诺成功；分布在两条不同消息时通常各增加 500 ms，同一消息连丢两份最多增加 1.5 秒。每条消息最多三份只规定有界尝试，超出整轮丢失前提不作 10 秒成功保证；既有串行下界模型保留为[超出前提的退路测试](transport-notes.md#8-完整引导链的串行重试下界)。接收每个缺口的 **2.5 秒**分别从该缺口首次被更高序号证实缺失时起，与重试并行计时，不是成功路径必须额外等待的步骤；缺失帧及时补齐就立即继续，不再加 2.5 秒。仅就缺口修复而言，要求最后重试在缺口到期前到达（1.5 秒重试加最多 1 秒传播/调度余量），32 个在途序号窗口不把正常每 PC 7 帧串行化。若 limited、调度或丢失使缺口真正到期，新 generation 的协商成本不能继续套用本次 9.75 秒成功预算，且不得延长原 10 秒总期限；须单列实测结果。客户端发向一个 daemon 的汇总预算也须满足账户限制；八客户端总初发不超过同一组 128 帧，不能把每客户端预算乘八漏算。该算术以授权仍有效、无额外成员追赶、公平调度、WS 在 3 秒内恢复且 RTT/SDK 在分项预算内且整轮合计最多丢两帧为前提；超出前提、洪泛限流或 SDK 较慢时，本轮仍在 10 秒截止，关闭本轮 PC/待发送队列/计时器并保留必要防重放 tombstone，保持 relay 业务可用，按既有全抖动退避和网络代次规则再试；这些场景如实记为本轮未建成，不能把容量算术当成功率实测。第 1 期 1a 已以四端实验完成字段冻结；产品实现仍须复验实际帧数与耗时，超 3 MiB/128 帧必须先改预算并复验。

### 设备对加密、指纹与防重放

含 IP 和 ICE 凭据的 SDP/候选用**双方成员状态中已认证 X25519 密钥**导出设备对密钥，经 HKDF 的固定信令域、账户、排序设备 ID、双方进程实例和 connection ID 隔离，使用 AEAD 并由发送设备签名；不用账户内共享的内容密钥。Probe/Challenge 也设备对加密并签名，可用不含 SDP 的引导域交换 boot nonce；正式代次密钥只在双方 nonce 都已认证后导出。不能从 server 普通 meta 接收密钥。实现须提供四端加密/签名/编码一致向量，不自创另一套成员身份系统。

每次进程启动随机生成 boot nonce，先 Probe/Challenge。冷启动只有成员公钥、没有对端进程信息时，Probe 显式标记 recipient_unknown 并留空接收方实例/nonce；这种表示仅允许 Probe。Challenge 回显所响应 Probe 的整包 hash，携带自身实例/nonce，发起方匹配仍有效的本地 Probe 后才安装对端信息；之后消息必须带已知值。Offer 必须绑定接收方当前 nonce。已认证、角色/connection/用途/代次及 SDP 均有效并绑定当前 nonce 的首份 Offer，本身就是对 Challenge 的隐式引导确认；即使 Signal 先于 Control ACK 到达，也直接准入正式代次，不再拒收等待显式 ACK。显式 Challenge ACK 则核对首次冻结 Challenge 的原 Context（方向、实例、nonce、connection、seq、generation/use）与整包 hash；bootstrap 的 generation/use 均为 0，不能与接收 PC 的用途 1/2 比较。Offer 的隐式引导确认不伪造带原 hash 的序号 ACK；Probe 的普通投递 ACK 也不替代收到 Challenge 的证明。老 Offer 在接收方重启、内存缓存丢失后仍不能重新建连。daemon 主 WS 重连后发送签名的实例公告，客户端见新实例立即废弃旧 PC；主 WS 尚不可用而 direct 活着时，Link 的实例探测间隔不超过 1 秒（不复用后台停止的性能探测）。收到旧 nonce/实例的 Offer 不创建 PC；由已签名实例公告/发现触发新 connection 的 Probe，再回复与该 Probe 关联的 Challenge，保留 stale_instance 诊断，限每 peer 每秒 1 次。不能生成没有 Probe hash 的主动 Challenge。该发现预算计入上述 10 秒。Probe 重放最多触发受限新 challenge，不能创建 PC 或送 SDP。缓存 key 覆盖双方设备、实例、connection、generation、方向和序号，保存到信令截止时间 **加当前 `deviceauth.MaxClockSkew`**（当前代码为 5 分钟，不是 10 分钟）；信令期限最多 30 秒。每 peer 最多 2,048 条、全局 16,384 条，满时拒绝新协商，不能提前驱逐仍有效的防重放项。关闭连接仍保留 tombstone 到窗口结束。**产品硬性要求：Close 或 generation 退休后，仍有效的原授权/身份/期限下，按原 hash 绑定的重复 ACK 必须保持幂等可发送；不能以 Closed 或当前 generation 阻断已接受旧包的回执，不能因此重新开放 SDK 准入。冲突 hash、未见旧包和失效授权拒绝，ACK 不形成回环。** 持久成员时间 floor 防时钟回退，回退异常暂停协商。

每方向每 generation 序号从 1 单调增加，Offer/Answer/Candidate/Confirm 都计数；完全相同重发仅返回已有确认，不重调 SDK，同序号不同 hash 拒绝。乱序最多缓冲 **32 条 / 2.5 秒**。**每个缺口**分别从首次证明它缺失的更高序号帧到达时起算；同一序号或后续序号的重发不刷新计时，新的后续帧也不延长已有缺口。一个缺口补齐后，下一缺口继续使用自己的首次发现时间，既不继承前一缺口的期限，也不从补齐时重新起算。实现可保留至多 32 条乱序帧各自的首次到达时间，以仍位于当前缺口之后的最早证据确定期限，不能按不可信的序号差分配缺口条目。缺口期限同时取等待消息原 deadline 与整轮截止时间的最小值；出缓冲及 SDK 动作实际交付前重验原包 deadline、当前身份和代次。分页 InputStatus/Barrier 必须在同一查询点冻结双向水位与明细，并将完整双向快照绑定到 token；后续各页不得重读 live 输出水位，见[冻结契约](transport-wire-draft.md#格式边界)。所有已知类型先完整解析及校验正文（含 Restart 目标用途/代次与 Close schema），再修改缓存、代次或产生动作；proto3 默认值省略与显式默认值同义，原签名字节不重编码。延迟回复、结果、分页和 ACK 在最终发送时重查当前租约、成员身份/密钥及逻辑授权代次；授权失效抑制发送，保留已完成证据。只有缺口到期才退休 generation 并尝试重开，仍受原 10 秒总期限约束，不能让候选越过未验证的 SDP。ICE restart 增 generation、换 ICE 凭据，connection 与对端身份不变；进程实例变化必须新 connection。glare 采用固定规则：按 device ID 字节序较小的一方作 Offerer，另一方只发 Restart 请求；冲突 offer 拒绝并保持确定角色，不同时安装两份 SDP。

双方必须先同步到**同一已验证成员 epoch+head**才协商。收到未知的较新 epoch 可有界拉取并验证链后重启协商；旧 epoch 不借历史成员身份继续连接，也不按发送方旧 head 放行。同步不成功就保留 relay；任何 Install 改 head 后重新校验会话，并重建受影响的信令代次/指纹绑定，不允许旧 head 无限续命。

下列 SDP 安全约束须先在第 1 期用四端真实 SDK 原串验证可实现，再冻结具体语法与共享正负向量；未通过不得宣称该端可直连。SDP 以严格 UTF-8、CRLF 行结束解析，拒绝 NUL、重复/歧义属性和未知媒体；只允许一个 `m=application` SCTP section、无音视频、无 `ice-lite`，恰好一个有效的 sha-256 指纹值，session 继承与每个 m-section 的声明必须一致，其他算法、冲突或同 scope 重复指纹均拒绝。只采用 trickle：Offer、Answer、ICE restart SDP 内出现任何 `a=candidate` 行均拒绝，包括 session 级、媒体级、一个或多个候选；不能绕过 Candidate 消息的计数与 ufrag/代次门。发送方只在收集候选之前取得原串。不通过字符串裁剪“修好”SDP；验证的 hash 覆盖**完整原串**，交 SDK 的必须就是已验证的原串，不能重序列化。验证 candidate 绑定当前 ICE ufrag/代次，每 PC 每代次最多 64 个候选，按第 5 节批量节流；禁止凭候选扫描额外端口。

每 PC 只允许预定义的业务 channel 和探测 channel（固定 negotiated ID 0/1），无额外 DCEP 通道、媒体或未声明通道；探测不承载业务。先验签、设备/角色、目标、head、租约、nonce、序号、期限，再交 SDK。DTLS 必须核验认证指纹；双方 Confirm 签名绑定两份 SDP hash、指纹、nonce、connection、generation 和用途后才开放业务。重放、拼接、伪指纹、ICE 凭据替换均拒绝，不关闭 SDK 指纹校验。

### 撤销、寿命与关闭直连

成员同步是独立进程级循环（客户端在前台可调度时运行，daemon 只要求进程可调度，不称“前台”），由安全组件用本机账户设备签名登录，独立持有 token 与 HTTP client。token 过期/Unauthenticated 时丢弃旧 token，重新 challenge/login 并原子替换，合并并发续期；凭据未恢复不能声称同步成功，PermissionDenied/成员失效立即暂停新准入及相应流。主 WS 断开但 direct 活着时仍通过独立 HTTP client 同步，不等待 WS session 重建或取消。

**成员同步与 ensurePublished 拆成独立循环和队列**，不共用可跨网络 I/O 持有的锁或 RPC 槽；发布步骤慢、失败或 60 秒超时不能推迟安全定时器。每次 Install、InstallLease、Touch 后（即便报错）触发所有 direct 会话重新校验双方成员/角色/密钥/head 与有效租约；本地安装与收发闸门原子生效，关闭资源异步完成。仅收输出也检查，每帧（含输出/控制）核对 Sender，失效立即停新帧、停止输出并关闭 PC。

安全同步按**固定起点每 15 秒**尝试，整轮含登录/全部分页/租约安装限 **5 秒**，不在上轮完成后再睡 15 秒。已验证分页可原子 Install 并立即撤销对应 peer；单次 `GetSecurityStates` 遇到可重试的瞬时传输错误时，在本轮 5 秒预算内清理空闲连接并用新连接重试一次；5 秒到仍未追完或重试后仍失败则保留已安装部分、记录未完成，**暂停 direct 收发和新准入**，并在 1–2 秒后按短退避再试（不再空等完整周期），下一轮从当前已验证 head 继续，不将部分追赶标作成功/续寿命。普通换网通知只退休旧 HTTP 轮次并立即触发同步，不清空既有新鲜度窗口，仍受 20 秒 `until` 窗口与同步失败暂停规则约束；系统休眠唤醒与鉴权失效立即清空新鲜度并暂停 direct。此时不承诺撤销全量已同步，只承诺不再用未完成同步维持 direct；relay 控制也继续执行自身成员/租约检查。

PC 寿命不超过租约 NotAfter，定时器粒度最多 1 秒，不因无流量延长；续租重新校验才延长，设备密钥变化重建。诚实可用 server 新状态可读起，整轮能在期限内完成时，**15+5+1=21 秒内关闭失效 peer；本机已 Install 起 ≤1 秒；NotAfter 起 ≤1 秒停止收发**。同步超时（含多页）也在该轮到期后 ≤1 秒暂停 direct，不能持续输出等下次成功；server 不可达/扣留撤销时不声称新状态已读到或全局 ≤21 秒，只受失同步暂停与现有租约边界保护（租约最长 72 小时），不能把旧 head 当新鲜证据。发布慢不得改变这两个数。挂起不收发，唤醒先 Touch/同步和校验；时钟异常按安全 floor 暂停，不额外加时钟偏差延长 NotAfter。信任边界见 [scope §4](scope.md#4-信任边界)。

daemon 提供持久的 `direct_enabled` 本机设置和 Client 经已认证 `DirectPolicy` 的远程关闭能力；管理端可改机器策略，普通客户端只能关闭自己的 peer。关闭动作可经 relay 送达，不要求 direct 健康；策略带单调 revision，回执签名，daemon ≤1 秒关该范围所有 PC、停 STUN/ICE，重启仍关闭。重新开启机器策略仅本机或管理端可做；任一端关闭即不建立 direct。两路都不可达时远程设置不能声称已生效，待认证回执；不新增 server 解密控制面。各端本机 off/auto 默认开，保存粒度见计划。

## 6. STUN 与诊断

自建 STUN 仅发现映射，独立 IPv4/IPv6 UDP 入口，HTTPS 代理不能自动承载；不做 TURN、端口预测或扫描。小响应、源地址内存短期限流与全局预算防反射放大，关闭持久 IP access log。生产容量等未决见计划。

日志不记 IP、端口候选串、SDP、ICE 凭据、指纹全文、原始 ICE 错误对象、内容或密钥，关闭或接管 Pion/libwebrtc 默认调试输出。仅本机有界滚动聚合候选类型/地址族、字节数、RTT p50/p95、吞吐、队列峰值、建连/恢复耗时、退路原因、unknown、replay/快照和 ICE CPU；不上传。信任域暴露见 scope。

## 7. 界面规则

界面只订阅 Link 状态，采用「**会话顶栏轻气泡 + 设置收敛状态 + 人话排障单**」方案：主路径不并列展示双路测速对比，也不向用户展示 ICE / DTLS / SCTP / 候选对计数等工程术语；热备 relay 副本不把主路径写成中继。可达性与 socket 分开，soft timeout 不发布电脑离线；server 历史同步不可用按 [architecture · 断线](architecture.md#断线时显示什么) 单独提示。

- **会话顶栏直连标记与轻气泡（手机与宽屏，含 iPad / Android 平板）**：当电脑在线、会话未结束且交互/读取路径（`加载` 或 `文件`，第 3 期含 `终端`）至少一条正在走直连时，会话顶栏状态文字末尾追加 ` · `、12px 直连图标（网页与 Android 用 Lucide `zap`，iOS 用 SF Symbols `bolt.horizontal`）与「直连」二字（均为 `ink2`，图标与文字同时出现，不单靠图形表达状态）；走中继、会话已结束或电脑离线时不加任何标记。点会话副标题直连区（宽屏点工具栏状态区的 `⚡ 直连`，触区均补足 ≥44×44）在下方锚定弹出无遮罩轻气泡（点外部、按 `Esc` 或系统返回键收起）：第一行显示绿点与「直连 <电脑名> · 14 ms」（样本未满 3 个时不写毫秒数）；第二行 13 号 `ink2` 说明「加载记录与收发文件直接连电脑；发消息和审批始终经中继。」（第 3 期启用终端直连后一并写入终端）；底栏左侧写简要状态（「连接稳定」，仅单一通道走直连时写「仅加载走直连」或「仅文件走直连」）、右侧放蓝字「连接设置 ›」跳进该电脑设置页的「连接」组。**气泡打开期间若路径回落到中继，不强行关掉用户正在读的气泡**，就地用 200 ms 交叉淡入切换为浅灰实心点「经中继连接 <电脑名> · 168 ms」、说明换为「当前所有操作都经中继连接电脑，不影响正常使用。」、底栏左侧换为「已切回中继」；重新切回直连同样就地淡入恢复。仅显示可证实的结果，不仅凭超时断言对称 NAT。
- **设置 › 电脑的「运行与存储 › 直连」行与统一弹层（每台电脑独立，收敛为 5 种状态）**：直连设置的唯一完整入口收敛在「运行与存储」组内的「直连」摘要行（行尾写 `● 正在使用 · 14 ms ›` / `中继 · 184 ms ›` / `已关闭 ›`，未连通时副行写人话原因），点开直达统一「直连」半屏弹层（宽屏与平板为居中对话框），每台电脑各自维护独立状态、RTT 样本窗口与最近 3 轮内存诊断缓冲。弹层上半部放「允许直连」开关与当前生效路径状态及单一响应时间，未连通时下半部**一步直达**三行人话自检（行首点与分隔线统一对齐 `34px`）+「重新尝试直连」+「复制诊断给支持」，**不再套双层弹层，也不画双路测速对比行**（「文件传输 / 响应时间 直连 X · 中继 Y」）。共收敛为 5 种状态：① 正在用直连（绿点「正在用直连」+ 右侧当前直连 RTT；仅一种用途走直连时第二行注明「用于加载」或「用于文件」）；② 正在建立 / 测速热身（墨色转圈「正在建立直连…」或至多 5 秒「直连已连上，正在测速」）；③ 自动留在中继 · 中继已够快或并发让位（浅灰点「正在用中继」+ 右侧当前中继 RTT + 第二行正向说明「当前网络下中继同样顺畅，已自动选用」「当前网络下中继响应更快，已自动选用」，或多电脑超出本机同时直连上限 4 台时的「同时直连的电脑已达上限，进入这台电脑的会话时自动切换」；均属正常自动调度，不显示排障自检）；④ 直连未连通 · 自动走中继（浅灰点「正在用中继」+ 右侧当前中继 RTT + 第二行人话原因，并在弹层下半部直接露出三行人话自检）；⑤ 已关闭 / 不支持 / 电脑离线（本机关闭或电脑离线时收起实时状态行，离线不显示过期 RTT；浏览器无 WebRTC 写「这个浏览器不支持直连」，原生客户端版本尚未实现直连如第 1 期 1e 前的 iOS 写「当前应用版本暂不支持直连」，daemon 本机关闭写「电脑上已关闭直连」，`DirectPolicy` 策略关闭写「电脑策略已关闭直连」并按管理端/普通客户端权限提供重开或只读说明，开关均 40% 置灰）。连接检测里每台在线电脑名下仍只放一行同一套状态词的摘要（「正在用直连」「正在用中继 · 两边的网络隔开了，不能直接连通」），不放速度，客户端整体不支持直连时只在连接检测页脚末尾说明一次；电脑状态页不放传输路径。画法与完整状态矩阵见 [design-system · 「直连」与排障](design-system.md#6-组件)，界面稿见 [client-v65 · 直连](design/client-v65.html#direct)。
- **人话排障自检与支持诊断复制**：在统一「直连」弹层的下半部（仅状态 4 时展示）自上而下放置一句人话结论与一句不影响正常使用的说明、三行自检摘要卡（「电脑在线并响应」「局域网或公网直通」「后台自动重试」，每行状态由行首绿点或浅灰实心点表达，行尾状态词一律用 `ink2` 不染绿，文字与分隔线统一对齐 `34px`）、主按钮「重新尝试直连」和蓝字「复制诊断给支持」加底部隐私说明，**不在界面上展示候选地址分类、ICE 状态、加密握手、数据通道或收发包计数**。完整诊断数据只保留在客户端内存中用于生成「复制诊断给支持」的纯文本（只读本机 SDK 已有信息，不改 wire、不加网络流量）：每台电脑在内存里保留最近三轮，每轮完整输出 `加载` 与 `文件` 两条通道的本机与电脑候选地址个数（按类型、地址族和范围分，mDNS 隐藏的只计数）、STUN 错误码、ICE / DTLS / SCTP / 数据通道的状态和相对本轮开始的时刻、`getStats` 里候选对的结果（成功、失败、进行中，发出的探测和收到的回应、往返时间）、被拒绝的信令及原因，以及这一轮为什么结束。**内存和复制出的纯文本都不存、不含具体 IP 地址、端口、SDP、ICE 凭据、指纹、SDK 原始错误文字或对话内容**：地址只取一次分类（IPv6 全球 / 本地唯一 / 链路本地，IPv4 私网 / 公网 / 运营商共享）即丢弃。额外的开销只有有界 `getStats`（每个连接最多 6 次：状态变化、一轮截止前约 1.5 秒、关闭前，打开弹层或点复制时按需再读，同一时间只发一个，不改变任何传输行为）。点「重新尝试直连」立即发起一轮（进行中按钮 40% 置灰并显示转圈「正在尝试…」，经过同一套发现预算，不重置失败退避计数，结束后至少冷却 2 秒；若重试成功连上则显示「直连已连上」600 ms 后自动更新为已连直连状态或收起）；点「复制诊断给支持」成功时就地显示 1.5 秒 `ink2`「已复制」，失败时显示 2.5 秒 `red`「没能复制，请检查剪贴板权限」。画法见 [design-system · 「直连」与排障](design-system.md#6-组件)，界面稿与完整 3 轮双通道剪贴板纯文本示例见 [client-v65 · 为什么没连上](design/client-v65.html#direct-diag)。
- 切换仅用 200 ms 淡入（退出 160 ms 淡出）更新图标与文字，不 toast、震动或横幅；可见页面每 5 秒更新 RTT，隐藏停止显示用探测，Router 活性探测另计。超过恢复预算、输入超限或 fail-stop 必须明确呈现，不能以隐藏错误维持表面连续。
- 本机「直连」开关默认开，关闭后不发 STUN/ICE，只影响本机；说明文字以 design-system 的「直连」条目为准。机器策略关闭时说明限制来源（区分电脑本机 `direct_enabled` 关闭与远程 `DirectPolicy` 关闭），不让普通客户端本机开关覆盖 daemon 策略；仅管理端可在已认证链路上重新开启 `DirectPolicy`。

以上文字与时延为设计示例；完整界面稿（含手机与宽屏的会话顶栏轻气泡、收敛后的 5 种直连状态、统一排障弹层及剪贴板纯文本示意）见 [client-v65 · 直连](design/client-v65.html#direct)，三端产品实现进度见 [plan.md](plan.md#直连实施与验收)。
