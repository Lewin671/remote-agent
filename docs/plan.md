## 下一步

按顺序做；第一项是当前的主要工作。

1. **任意客户端管理的联合验收**。按 [architecture §9](architecture.md#9-账户设备和密钥) 和 [AGENTS.md](../AGENTS.md)，在独立 `RA_DEV_DIR` 从无账户环境开始，用网页新建账户、加入真实电脑并经 server → daemon → tmux 操作真实 CLI。验收三端六条有向交接、设备移除/档案重接/删除、创建及恢复断点、72 小时租约与 48 小时否决；网页手机宽/宽屏及亮暗主题、iOS/iPad 与通知/锁屏分别核实，未验证部分保留限制。通过后再统一发布任意客户端管理功能，协议仍为 10。
2. **真机验收**。在自己的 Android 手机和 iPhone（PWA）上走一遍，清单在「待确认 › 真机」。验收标准：清单里每一项有结论，问题修掉或记进本文
3. **Codex 0.159.2 的命令结果**。按新格式解析退出码或失败，再把 0.159.2 列为已验证版本。验收标准：失败的命令在客户端显示 ✕ 和退出码，`remote-agent doctor` 通过
4. **定时任务的客户端**。客户端通过 `MachineCapabilities.scheduled_tasks` 判断支持情况，复用 Schedule 机器指令查询和管理任务；接入 `MachineMeta.schedule_revision` 变更拉取与离线快照，再实现独立「定时」入口、新建/编辑和运行历史，以及对话中的静默轮折叠。设计见 [architecture §18](architecture.md#18-定时任务)
5. **历史分段读取**。现在事件层从序号 1 读全量，长会话第一次打开慢（瓶颈是下载量，见 [architecture §10](architecture.md#10-报文同步和指令) 的「后台和内存」）；网页再次打开已经靠本地密文缓存只取增量。剩下的是第一次打开：先取最新一段显示，更早的在后台补，需要让状态推导不依赖从序号 1 开始的完整历史。三端共同规则和共享向量已建立，见 [共同规则](architecture.md#客户端状态推导的共同规则)；快照及历史分段读取尚未实现，网页、Android 和 iOS 都要接入
6. **v8 以后的界面改动补验收**。两端逐屏对照 client-v38（网页的 v8 改动也没有逐屏对照过），并连真实 CLI 走一遍设置类页面
7. **清理被登录 shell 取代的机制**。客户端开的会话现在由登录 shell 现算环境（[architecture §6](architecture.md#6-接入-codex)），`agent.env`、`daemon.sh install` 写进服务的 `PATH`、以及用户自己的 `~/.local/shims` 包装脚本都只是为了在没有这步之前把环境补上。先在真实使用里观察一段时间：从手机新开的会话能直接用到新装的命令和升级过的 CLI，不需要重装服务或改 `agent.env`；确认后删掉 daemon 读 `agent.env`/`codex.env` 和 install 写 `PATH` 的逻辑，并同步 README 和 architecture §6

- API 26 到 28 上保存图片要请求存储权限，还没做
- 大图过期、校验失败这两种状态没有在真实数据上看过

**网页的小缺口**：终端自动按宽度缩放字号，没有 Android 那样的 A− / A+。

## 待确认

所有还没定的问题和待实测的行为都列在这里，有了结论就写进对应的文档，再从这里删掉。

**真机**

- Android：终端里系统字体的中文、回退的符号和 emoji 显示；字号调节、键盘弹出和旋转；中文输入法在终端里输入、在输入框里多行输入；终端方向键；设了锁屏时通知里的「允许」「拒绝」要先解锁；FCM 在国内网络和省电策略下的到达；连续使用一天没有 ANR 和崩溃（模拟器上只验证了英文输入和没有锁屏的情况，见 [android-notes.md](android-notes.md)）
- 两端：断线提示（v30）在真机上的表现：飞行模式、信号满格但不通、切换 Wi-Fi 和蜂窝时会不会误报「连不上服务器」、服务器停掉后 10 秒的提示和详情
- 网页：终端视图的按键栏、键盘弹出、系统选图和分享面板、推送（iPhone 要先添加到主屏幕）、扫码配对，都只在本机 Chrome 上验证过

**范围和产品**

- 协议 10 的交接管理权走签名交接，管理端丢失的恢复在诚实中继等待 48 小时；后续需要补真实手机验收
- 协议 10 的租约参数（72 小时、剩余 24 小时续期、最多 12 小时一次）是初始值，按实际使用中的电量、流量和“多久开一次 App”再定
- 状态更新现在靠 60 秒轮询和遇到未知状态时立即拉；要不要在 server 收到新状态时给在线设备发一条只含 epoch/哈希的提示，未定
- 客户端暂时没有结构化的会话存储故障或「已持久受理但记录失败」状态；同步 RPC 能返回明确错误文字，但三端仍按通用错误呈现，新建会话也不能同时返回会话结果和记录警告。本地 send 对此仍以非零退出报告记录错误。是否增加独立的协议字段及客户端呈现，未定。现有 `StatusDetail` 只承载 CLI 状态说明，不能拼入诊断（[architecture · 事件提交](architecture.md#10-报文同步和指令)）
- 损坏的会话事件记录目前会阻塞后续读取，daemon 重启也可能跳过该会话。需要设计保留原日志的损坏记录隔离、可确认序号的占位、状态不确定性和恢复流程，再统一处理日志索引、批次与 checkpoint；本轮暂不修复。
- Android 通知的系统布局可能截断未被 daemon 截短的审批正文，现有 `truncated` 不能证明已显示全文。要不要把所有「允许」改为「查看全文」，或改用能确认全文已显示的自有审批界面，未定（[android-client · 按钮](android-client.md#推送和通知里审批)）
- 新会话首条图片的本地副本目前随创建成功释放，网页和 iOS 也一样；创建响应没有首条消息的队列请求 ID。要不要在协议里返回该 ID 后接入待确认记录，或先保留为可恢复的草稿、只在用户移除时释放，未定（[session-images.md](session-images.md)）
- 网页上一个新会话的请求还没回来时，给下一条草稿加的图片会在那个会话启动成功时一起清掉（图片托盘按项目共用）；Android 和 iOS 只取走请求带的那几张。要不要让网页也这样，未定
- Codex 让一条命令先返回、转到后台继续跑时，聊天里是一次「已完成」的工具调用加一次名为 `exec` 的调用，读起来像两件事。要不要把这两条并成一条，未定（在 Codex 0.162.0 上看到）
- 额度页的「重新读取」和「API 计费」状态在界面稿和 [architecture · 账户额度](architecture.md#账户额度) 里有，网页和 Android 都还没有实现；做不做、何时做未定
- Android 的会话和项目页在平板与横屏上仍是手机布局，要不要做网页那样的侧栏加主区域未定
- 客户端切换 fast 模式是否要做（优先级低）
- 运行中的会话要不要也能分叉（比如主任务跑着，另开一支问别的）。现在只允许空闲和已结束的会话（[architecture §13](architecture.md#13-daemon-设置与远程新建会话)）；要做得先实测两个 CLI 怎么处理停在一轮中间的记录，再定复制来的历史在哪里收尾
- 连接检测里「较慢」的界线（服务器 500 ms、电脑 1500 ms）是初始取值，用一段时间后按实际延时再定
- 会话图片的保存期限（30 天）和配额（1 GiB）、预览长边 320px、显示版 2048px、加密后整个信封不超过 1 MiB 都是初始取值（[session-images.md](session-images.md)），要用实际截图和一段时间的用量看清晰度、流量和空间再定
- server 的过期图片仍保留状态行，SQLite 空间用于后续复用；是否需要定期压缩数据库及历史元数据期限未定
- 图片过期后要不要支持从电脑重新取（daemon 从 rollout 或 transcript 里重新编码上传）；需要机器在线，也要一个新的指令
