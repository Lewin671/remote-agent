## 1. 各端与部署

```
 手机 / 平板 / 浏览器              VPS（海外）                         每台电脑
 ────────────────────             ───────────                         ────────
 PWA / Android App                 Caddy（HTTPS）                      remote-agent（Go）
   │  网页来自 Cloudflare Pages      └─ remote-agent-server（Go）        ├─ daemon
   │  App 侧载安装                      SQLite                          ├─ 本地 CLI 命令
   │                                                                    └─ hook 入口
   └──────── HTTPS / WSS ────────▶ api.<域名> ◀──────── HTTPS / WSS ─────┘
                                                                     tmux ─ codex
```

| 端 | 形态 | 部署 |
|---|---|---|
| `remote-agent` | Go 单二进制：daemon、本地 CLI（`remote-agent codex` 等）和 hook 入口都在里面 | 每台电脑一个 |
| `remote-agent-server` | Go 单二进制，SQLite 存储，不直接对外暴露端口 | VPS 上，前面由 Caddy 负责 HTTPS 和反向代理，域名为 `api.<域名>`（当前部署在 `ra.remote-agent.top`，见下文） |
| `web` | PWA，React + Vite + TypeScript | Cloudflare Pages，挂在子域名 `app.<域名>` 上，用 CNAME 指过去，域名不用迁到 Cloudflare |
| `android` | 原生 App，Kotlin + Jetpack Compose，见 [android-client.md](android-client.md) | 自己签名的 APK，侧载安装 |
| `ios` | 原生 App，Swift + SwiftUI，见 [ios-client.md](ios-client.md) | 装到真机的渠道未定（[plan.md](plan.md)），目前只在模拟器上运行 |

当前的 VPS 上有一个多个服务共用的 Caddy（docker compose 项目 `/opt/caddy`，占用 80/443），server 因此也用容器部署：接入 Caddy 所在的 docker 网络 `proxy`，不映射主机端口，Caddyfile 里只加一个站点块反代过去。镜像基于 `scratch`，以 nobody 运行，内存上限 128 MiB。`scratch` 里没有 CA 根证书，而 Web Push 和 FCM 都要访问 HTTPS，所以 server 二进制带上了 Go 的 `x509roots/fallback`（Mozilla 的根证书），系统里没有根证书时使用它。部署文件和脚本在 `deploy/`。

网页部署在 Cloudflare Pages 的项目 `remote-agent` 上（`remote-agent.pages.dev`），自定义域名 `remote-agent.top` 由阿里云 DNS 用 CNAME 指过去。用的是经典的 Pages 而不是 Workers 静态资源：Workers 绑定自定义域名要求域名托管在 Cloudflare，Pages 则支持外部 DNS 用 CNAME 接入。新版 wrangler 默认把 `pages project create` 转成 Workers，所以创建项目时要加 `--force`，之后的部署不用。构建时会生成 `_headers`，让 Pages 在响应头里带上和页面里一致的 CSP，外加 `frame-ancestors 'none'` 等只能靠响应头生效的限制。server 的 `ALLOWED_ORIGINS` 要包含网页的地址。

网页代码**不由 VPS 提供**：如果 VPS 被攻破后能替换网页的 JS，端到端加密就会被绕过。放在另一个平台上，攻击者必须同时攻破两处才行。Cloudflare 账号因此也成了关键资产，必须开启两步验证。

代码放在同一个仓库：一个 Go module，外加 `web/`、`android/` 和 `ios/` 三个目录。

### 产品版本与发布

各端使用根目录 `version.properties` 中的同一个产品版本，Android 的 `androidVersionCode` 每次发布递增。正式 tag 为 `vMAJOR.MINOR.PATCH`，与文件严格一致；daemon/server 的 `--version`、网页和 App 设置页显示产品版本和源提交。协议版本独立，不随产品版本自动增长；产品版本不同不是拒绝连接的理由，协议版本不同才是（见第 4 节的「版本」）。

Go 构建要求至少 1.26.9，发布流水线用 `govulncheck` 检查代码可达的已知漏洞。

发布按开发任务完成触发，不按时间触发：agent 完成一项功能或相关修复并验收后，按 [AGENTS.md](../AGENTS.md) 自动更新版本、推送 tag，无需逐次确认。新功能升 minor，修复升 patch，1.0 以前的不兼容改动升 minor，1.0 起升 major。纯文档、界面稿和测试改动不发版。GitHub 的 `Release` 流水线从 tag 运行 Go、网页、Android 检查，全部通过才发布：正式签名 APK，daemon（macOS 和 Linux 的 arm64、amd64）和 server（Linux 的 arm64、amd64）的压缩包，网页包，以及覆盖全部文件的 `SHA256SUMS`。源提交写在私有 Release 的说明中，各端仍统一版本。我们自己的部署仍从源码安装（daemon/server）和 Cloudflare Pages（网页），这些压缩包是给别人部署用的，见下文「公开发布」。已发布 tag 和附件不覆盖；暂时失败允许重跑，代码修复使用新版本。

正式 APK 缺少固定签名或 Firebase 客户端配置就停止发布，不退回 debug 签名。GitHub Secrets 的 `ANDROID_SIGNING` 保存签名 keystore 与签名参数，`ANDROID_GOOGLE_SERVICES` 保存客户端配置；FCM 服务账户和账户加密密钥不进入构建流水线。签名密钥必须另有本地备份。手动 `Build development APK` 生成独立 `.dev` 应用，与正式版数据分开，使用固定签名以便后续覆盖升级，推送关闭，产物保留 3 天。

**公开发布**：源码仓库和它的 Release 是私有的，App 拿不到，别人也拿不到。所以最新一版发布成功后，流水线把这一版的全部文件和一份清单 `latest.properties`（版本、versionCode、协议版本、APK 文件名、SHA-256、大小、发布说明）发布成公开仓库 `Lewin671/remote-agent-releases` 的一个 Release。它有两个用途：App 读最新 Release 的清单、按版本号下载 APK（[android-client · 更新](android-client.md#更新)）；别人照那个仓库的说明部署自己的中继、网页和 daemon。源码不公开；那个仓库的主分支只有说明文档、安装脚本和自部署模板（源文件都在 `deploy/releases-repo/`，该目录在 `main` 上一变，`Public pages` 工作流就用 `scripts/sync-public-pages.sh` 把它同步过去，不等发版），发布的文件不进 git。

给别人用的产物不带我们自己的部署：`scripts/build-dist.sh` 构建网页时不设默认中继（我们自己的网页由 `pnpm run deploy` 另行构建，带默认中继）；server 的压缩包里是 `deploy/releases-repo/self-host/` 的模板（自带 Caddy），不是 `deploy/` 里接入我们那台共用 Caddy 的那份；Go 构建关掉了自动嵌入的仓库信息，压缩包的文件头不记打包者。`scripts/public_scan.py` 把关，查到就失败、不发布，有三层：按名单查域名、主机名、邮箱、设备号、私钥和填了值的 setup token，压缩包和 APK 逐个成员查；按文件名拒绝部署的配置和状态（`.env`、数据库、密钥、日志、sourcemap）和链接，不看内容；打包时（`--release`）要求这一版的文件和每个压缩包的成员正好是预期的那些，多一个少一个都不行。它在打包（`package-release.sh`）、公开上传（`publish-public.sh`）和同步页面（`sync-public-pages.sh`）时各运行一遍。名单挡不住没见过的标识，所以新增公开内容时仍要人看一遍。

别人的部署有两处和我们的不一样，公开文档里写明：正式 APK 绑定我们的 Firebase 项目，别人的 server 发不了 FCM，App 在他们那里没有推送（网页的 Web Push 不受影响）；网页由他们自己托管。

私有仓库的 `Release` 工作流直接调用 GitHub API 在公开仓库建 Release：GitHub Secrets 的 `RELEASES_TOKEN` 是仅选 `remote-agent-releases`、只有 Contents 读写权限的细粒度令牌（另附 GitHub 必需的 Metadata 只读），不设到期日；只在公开发布这一步使用。页面同步仍用 `RELEASES_DEPLOY_KEY`。`publish-public.sh` 先扫描产物和 tag 的公开说明，核对完整文件集合、`SHA256SUMS` 和 APK 清单；先建草稿，上传完再下载所有附件逐个核对，全部一致才公开。草稿可重试；已公开版本只核对，不改附件或说明，内容不同就失败。只发布私有仓库标为最新的版本，旧 tag 重试不会替换较新版本。公开文件不经过 git 分支，也不等另一条工作流。

公开发布失败时，手动运行 `Release`，填入 tag 并选 `publish_only=true`：只有该 tag 的私有 Release 已公开时才允许继续，取回原附件、检查校验值并重建清单，不重跑构建。产物和 tag 校验使用 tagged checkout，公开发布工具和隐私扫描使用本次工作流所在的提交，因此修复工具后可重试旧版本；网页包的成员名单取自该 tag 的 `web/public`。需要修复产品代码时仍发新版本；不填 tag、不选 `publish_only` 则跑全端检查和打包演练，不公开任何版本。清单和公开 Release 的说明只用 tag 中面向用户的变化和升级要求，不带私有提交日志或部署信息。

Release 不自动部署 VPS/Cloudflare、不升级本机 daemon，各端分别部署；App 的更新也要在手机上点一下，再由系统确认安装。当前部署脚本仍从本地工作目录构建，并嵌入版本和源提交；它不是从 Release 晋级产物的入口。各端不保证跨版本互通：协议版本变了就要一起升级，数据格式变了要手动迁移或重建，这些升级要求写在发布说明中。

## 2. 报文分层

所有跨网络的消息都分两层，类似信封和信纸：

- **外层（信封）**：发给谁、哪个会话、序号、鉴权。server 靠它来转发和存储，**server 能读**。
- **内层（内容）**：消息、工具调用、审批、终端数据、指令。先用 Protobuf 编码，再加密，**只有客户端和 daemon 能读**。

以手机发一条消息、Codex 回复为例：

```
 手机（PWA）                    server（VPS）                 电脑（daemon）                  Codex（tmux 里）
 ───────────                    ─────────────                 ──────────────                  ────────────────

 ① 用户输入
   "帮我修一下这个 bug"
        │
   [生成内层] 写成内层消息
   [加密]     内层 → 密文
   [生成外层] 装进信封：
     发给 机器A / 会话123
        │
        └──── 外层 ─────────▶ [读外层] 看收件人
                               存密文，转发给机器A
                               （内层打不开）
                                     │
                                     └──── 外层 ─────────▶ [读外层] 找到会话123
                                                           [解密]  密文 → 内层
                                                           [读内层] 拿到文字
                                                                 │
                                                                 └─ tmux 粘贴 + 回车 ─▶ ② Codex 开始干活
                                                                                             │
                                                                                        写 rollout 文件
                                                                                             │
                                                           [读 rollout] ◀────────────────────┘
                                                           [生成内层] "已修改 main.go …"
                                                           [加密]     内层 → 密文
                                                           [生成外层] 装进信封：
                                                             来自 机器A / 会话123，序号 42
                                                                 │
                               [读外层] 存下序号42 ◀──── 外层 ────┘
                               推给所有在线客户端
                                     │
 [读外层] 会话123 有新消息 ◀─ 外层 ──┘
 [解密]  密文 → 内层
 [读内层] ③ 显示 Codex 的回复
```

| 角色 | 外层（信封） | 内层（内容） |
|---|---|---|
| 手机 / 其他客户端 | 生成、读取 | 生成、读取 |
| server | 读取，按它转发、存储 | **碰不到**，只存和转发密文 |
| daemon | 生成、读取 | 生成、读取 |
| Codex | 不涉及 | 不涉及：只知道 tmux 输入进来的文字，以及自己写出的 rollout |

本地 CLI、hook 和 daemon 之间的通信不经过 server，只有一层，不需要加密。

发给 server 自己处理的请求（登录、拉列表和历史）只用到外层字段，返回的会话内容仍是密文。密钥怎么来、设备怎么配对、报文的具体格式见第 9、10 节。

## 3. 通信方式

**所有通信都通过 IDL 定义，不手写请求。** IDL 用 Protobuf，工具链用 `buf`；Go 端用 protoc-gen-go 和 connect-go，TS 端用 protobuf-es 和 connect-es。

```
 客户端                              server                             daemon
 ──────                              ──────                             ──────
 ① 普通请求（登录、查列表、拉历史）
    ──── HTTPS（ConnectRPC）────▶  处理并返回

 ② 发给 daemon 的指令（发消息、审批、新建会话…）
    ──── HTTPS，Forward ────────▶  不拆开，原样转发 ── 主 WebSocket ──▶  解密并执行
    ◀────────────── 结果原路返回 ─────────────────────────────────────

 ③ 实时推送（新事件、审批提醒、机器上下线）
    ◀──── 主 WebSocket（一直连着）──  主动推送  ◀──── 主 WebSocket ──── 上报

 ④ 终端画面（只在打开终端视图时）
    ◀──── 终端 WebSocket ────────▶  只转发，不存储 ◀── 终端 WebSocket ─▶  tmux
```

| 链路 | 承载方式 | 理由 |
|---|---|---|
| 一问一答（调 server） | ConnectRPC over HTTPS | 超时、错误码、重试都是现成的；接口由 proto 生成；可以用 curl 调试 |
| 客户端发给 daemon 的指令 | 统一走一个 `Forward` 接口：外层只写目标机器、请求 ID 和密文；具体指令在加密的内层里用 `oneof` 区分 | server 只按机器转发，连"是发消息还是审批"都分辨不出来 |
| 实时推送 | 主 WebSocket，打开 App 就连上，一直保持 | server 需要主动往下推；浏览器里的 ConnectRPC 不支持双向流 |
| 终端 | 单独一条 WebSocket，打开终端视图时建立，离开就断开 | 终端输出量大，和审批提醒挤在一条连接里会把提醒堵住；网络慢时可以单独断开重连，然后重新抓屏幕快照 |
| 本地 CLI、hook ↔ daemon | ConnectRPC over unix socket | 和上面用同一套工具；只有本机进程能连上 |

daemon 和 server 之间同样分主 WebSocket 和终端 WebSocket 两条连接。

主流连接有就绪期限；建立 WebSocket 不代表已经收到 `Ready`。浏览器不能观察控制帧 Ping/Pong，所以 server 还发送不含会话内容的应用心跳，网页按原始帧到达更新时间，不等待历史补齐处理完成；长时间收不到任何帧时主动失效旧连接并重试，不依赖关闭握手完成。网络恢复或默认网络切换会替换已有连接，旧连接的回调不能接管新连接。登录和历史 RPC 有期限，避免挂起请求挡住后续重试与补齐。

协议 4 的网页依赖 server 的应用心跳，升级时先更新 server，再更新 daemon（重启）和客户端。本机命令与 daemon、客户端与 daemon 仍按协议版本互相核对；server 不核对这个密文内的版本号。历史信封的格式不变，不需要清理数据或重新配对。

### 为什么当前不做 P2P

**决策：客户端与 daemon 继续通过 HTTPS / WSS 连接 server，由 server 转发密文；当前不实现 P2P 直连，也不加入“直连优先、失败走中继”的双路径。**这里的 P2P 指客户端与 daemon 之间的数据直连。

2026-10 的调研实际观察到两类 IPv4 UDP 路径：一类是端点无关映射、地址和端口依赖过滤；另一类在同一本地 socket 访问同一服务器的不同端口时，公网映射端口发生变化，符合地址和端口依赖映射（通常称对称 NAT）。后者的过滤类型没有确定。结论只适用于采样路径，不能据此判断所有移动网络、CGNAT 或 TCP 行为。

不采用 P2P 的理由：

- **常用网络不能保证普通打洞成功。** 对称 NAT 中，访问发现服务器与访问对端可能得到不同的公网端口，发现到的地址不能直接保证对端可达。直连结果还取决于另一端的映射、过滤和防火墙，不能因为某一侧支持打洞就承诺连通。
- **要保证可用，仍需保留中继。** P2P 是可以尝试的优化，不是这里可靠连接的前提。直连优先会增加候选地址交换、打洞、超时回退、链路切换和网络变化后的重新探测；网页、Android、iOS 和 daemon 都要实现并验证，指令与事件还要保持原有顺序和恢复语义。
- **IPv6 暂不能替代中继。** 获取 IPv6 地址不等于允许入站连接，双方还需具备可达的 IPv6 路径。本次没有验证 IPv6 端到端直连，不能把它作为通用连接条件。
- **P2P 不能直接消除现有 server 的职责。** 账户与设备鉴权、密文历史同步、设备路由和推送仍由 server 承担。当前已有端到端加密，内容保密不依赖于是否直连；中继仍能看到必要的路由元数据，信任边界见 [scope.md](scope.md#4-信任边界)。
- **目前优先保证连接可靠、断线恢复和各端行为一致。** 本次只验证了 NAT 行为，没有验证 P2P 的端到端延迟或带宽收益，不足以支持增加一套传输路径。

对端有可达公网端口、合适的映射与过滤组合，或者双方 IPv6 可达时，仍有直连机会。只有后续中继延迟或带宽成为已测量的瓶颈，并且代表性的移动网络、家庭网络和网络切换测试证明直连有稳定收益时，再评估 P2P；评估仍须包含中继兜底及各端一致性成本。

参考：[RFC 4787：UDP NAT 映射与过滤分类](https://www.rfc-editor.org/rfc/rfc4787.html)、[RFC 5128：NAT 下的 P2P 与打洞限制](https://www.rfc-editor.org/rfc/rfc5128/)、[Tailscale：直连与中继](https://tailscale.com/docs/reference/connection-types)。

## 4. 协议设计要点

以下原则已经定下，具体做法见第 10 节：

- **指令并发**：daemon 对转发指令设固定并发上限，重连共用同一个限额；重复请求等待可随连接取消，避免不可信 server 用大量密文或重放占满本机内存。
- **幂等**：`Forward` 里的指令都带稳定的请求 ID，daemon 记住已经处理过的请求，重试时直接返回原来的结果，不重复注入
- **防重放**：加密时把版本、发送方、目标机器、会话 ID、请求 ID 或序号、截止时间一起纳入认证数据；过期或重复的审批一律拒绝
- **历史和实时衔接**：server 先写库再推送；客户端按序号去重、补缺口
- **终端积压**：终端帧设大小上限，缓冲队列有长度上限；客户端太慢时断开终端流，重新抓快照
- **离线**：daemon 离线时，server 立即返回"不可用"，不替它排队
- **版本**：不做跨版本兼容，版本不一致就拒绝并提示更新，不逐项降级（规则见 [AGENTS.md](../AGENTS.md)）。全项目只有一个协议版本号（`internal/protocol`，网页、Android 和 iOS 各有一份同值常量），旧版本会误解的改动才提升它。daemon 把它写进机器元数据，客户端发现不一致就不向这台机器发指令，并说明该更新哪一端；客户端把它写进每条指令，daemon 发现不一致就拒绝执行。本机命令和 daemon 之间通过本地 socket 的请求头和响应头互相核对，覆盖更新后没重启的 daemon 和旧会话里还在运行的 MCP 进程。server 只转发密文，不参与核对；它不认识的接口按普通错误返回。信封格式另有自己的版本号（`Header.version`），已存的历史靠它继续可读，所以协议版本提升不影响读取旧会话

## 5. 技术决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 语言 | daemon 和 server 都用 Go，全部重写，不复用 Happy 和 botmux 的代码 | 单二进制、内存占用低、方便分发；需要的功能远少于 Happy |
| 参考实现 | Happy（协议、加密、客户端交互）和 botmux（tmux、Codex 的各种坑）**只作参考** | 两者都是 MIT 协议，但它们是 TS 写的，而且范围远大于本项目 |
| 客户端 | 自己写 PWA（React + Vite + TypeScript），部署在 Cloudflare Pages；Android 和 iOS 另做原生 App（[android-client.md](android-client.md)、[ios-client.md](ios-client.md)） | PWA 一套代码覆盖所有设备，不上架应用商店，网页不和 server 放在一起；Android 是主力手机，终端和通知要做到原生体验 |
| 通信 | Protobuf 定义所有接口；一问一答走 ConnectRPC，实时推送和终端各用一条 WebSocket | 见第 3 节 |
| HTTPS | server 只监听本机端口，由 Caddy 负责证书和反向代理 | |
| server 存储 | SQLite | 单用户，部署简单 |
| tmux 接入 | 使用独立的 socket（`tmux -L remote-agent`）；P0 直接执行 tmux 命令（建会话、抓屏、存活检查），终端视图（P2）再接 control mode（`tmux -C`） | 不影响平时用的 tmux；P0 不需要 pane 的字节流，会话存活由 tmux 和 PTY 代理判断 |
| 输入 | tmux pane 里跑一层 PTY 代理（`remote-agent pty-host`），Codex 以原生 TUI 跑在它下面；本地按键和远程注入都经过它，见第 6 节 | 注入时要先确认输入框为空再写入；只靠 tmux 命令，检查和写入之间本地敲的键会混进远程消息 |
| tmux 依赖 | 必需；安装脚本和 `remote-agent` 启动时检查是否存在、版本是否满足 | |
| 输出来源 | Codex rollout jsonl，不从屏幕解析消息 | 屏幕内容不可靠 |
| 审批超时 | 拒绝；默认 10 分钟，`remote-agent daemon --approval-timeout` 可调 | 安全优先；手机上从收到提醒到处理需要时间 |
| 本地状态 | 每个会话一个目录：`session.json`、append-only 的 `events.jsonl` 和待发消息 `queue.json`；事件记录里带着读到的 rollout 位置，同时充当读取进度。一次追加的几条事件（一行 rollout 解析出的，或分支复制来的历史）是一批：位置记在最后一条上，其余各条带 `more` 标记；崩溃后文件末尾只剩半批时，打开日志会把这半批整批截掉。事件只在有人读的时候留在内存里，两分钟没读就释放，下次读时再从文件加载；追加和等待新事件只需要条数，不用加载 | 重启后从记录的位置接着读，事件序号连续、不重复，写了一半的那一行重读时每条事件只出现一次；已受理的消息不丢；单用户、单机，不需要数据库 |
| `/` 开头的输入 | 客户端不直接注入：常用命令做成按钮和面板，其余先提醒再发送 | 带参数的斜杠命令会被当成普通消息发给模型；打开菜单的命令在手机上看不到（[codex-notes §6](codex-notes.md#6-踩过的坑)） |
| 上下文提示 | 占用超过 80% 时提示，并提供「压缩」按钮（注入 `/compact`） | 数据来自 rollout 的 `token_count` |

## 6. 接入 Codex

下面每条做法都基于 [codex-notes.md](codex-notes.md) 里的实测，括号里的「notes §n」指它的第 n 节。升级 Codex 后要跟着复核。

- **启动**：tmux pane 里运行 `remote-agent pty-host -- codex …`。
  - **环境变量**：环境变量取自发起的 `remote-agent codex` 进程，再叠加 `~/.remote-agent/agent.env`（放代理等变量，所有 CLI 共用一份；daemon 由 launchd 启动时读不到 shell 里的配置。没有这个文件时读以前的 `codex.env`），并设置 `RA_SESSION=<会话 ID>`、`RA_EXE=<remote-agent 的路径>`。
  - **不上命令行**：这些变量不经过 tmux 的命令行（命令行对本机所有用户可见，而环境变量里常有 API key），而是存进会话目录下只有自己可读的 `env.json`，供恢复会话时沿用；每次启动另写一份副本交给 PTY 代理，读取后删除。
  - **hook**：用 `-c` 注入 `PermissionRequest`、`SessionStart` 两个 hook，只对这个会话生效。hook 的定义（命令和 `timeout`）必须固定：Codex 每个 hook 位置只记一份信任，定义一变就要重新信任，而且会顶掉之前的信任。所以命令写成 `"$RA_EXE" hook codex`，不含二进制的路径，换了路径或同时跑测试用的另一份二进制也不用重新信任（notes §3、§5）
- **locale**：daemon 没有 UTF-8 的 locale 时（launchd、systemd 启动就是这样）自己补上 `LC_CTYPE`，tmux 和 Codex 都继承它。否则 tmux 会把输出里的 tab 和非 ASCII 字符换成 `_`：会话列表读不出来，所有会话都会被当成已经消失，屏幕里的 `›` 也认不出来。标成已结束、但 tmux 会话其实还在的会话，daemon 启动时会重新接上
- **恢复会话**：`codex resume <Codex 会话 ID>`，沿用原来的环境变量和参数，去掉位置参数（如第一句话），再用最近一轮的模型、effort 和审批模式覆盖；审批模式只在最近一轮的沙箱、审批策略和审批方与某个标准模式完全一致时才覆盖，免得把只读沙箱之类的更严设置放宽。Codex 不接受重复的 `-m`，命令行的审批选项又比 `-c` 优先，所以被覆盖的选项先从原参数里去掉
- **启动弹窗**：用 `-c` 关掉检查更新、限额换模型提示等能关的弹窗；关不掉的 `Trust this folder?`、`Hooks need review` 每个目录或每套 hook 只问一次，客户端提示去终端处理。能不弹就不弹；信任目录是安全决定，留给用户在终端里做（notes §5）
- **启动时不注入**：Codex 在新目录启动时会先闪一下输入框再弹出信任对话框（notes §10），所以会话处于「启动中」时不注入，等状态检测连续两次看到同样的画面、进入空闲再说
- **防弹窗挡输入**：每次注入前先抓屏，确认没有弹窗挡着。判断画面时只看屏幕底部；以列表里选中的行判断有没有弹窗，标题只用来给弹窗命名，对话里出现同样的字不算（notes §5、§6、§10）
- **等画面**：轮询屏幕，等到预期画面出现再操作，并设超时；不用固定的 sleep（notes §6）
- **输入**：远程消息按到达顺序排队，一次注入一条；队列在受理前写入 `queue.json`，重启后接着发。请求 ID 会记住最近 1000 个，重试不会重复发送。写入前记下 `history.jsonl` 的位置和当前事件序号。事件记录和 `queue.json` 是先后两次写入：消息离开队列时先把结果记成事件，再从 `queue.json` 里去掉，结果记不下来就留在队列里稍后再试。daemon 重启时拿事件记录核对队列：结果已经记下的消息直接去掉，不再结算一次；最后一轮被中断而等待的消息还没存成暂停的，先补上暂停再恢复发送。已经写入、但 CLI 还没记下用户消息的那些（Codex 运行中发的消息要到下一次工具调用后才记；Claude Code 暂存着的）也从事件记录和暂存列表里重新认出来，之后出现的用户消息照样带上请求 ID 和来源；带图的消息除外，事件里没有它的文件和占位编号。`queue.json` 在但读不出来时，里面可能有已受理的消息和防重发的请求 ID，这个会话不再受理新消息、也不改写这个文件（其余照常：能看、能审批），等文件修好或删掉、重启 daemon 后恢复。
  - **写入**：注入时 daemon 先让 PTY 代理暂存本地按键，等 80ms 让已经敲下的键显示出来，再抓屏：输入框就绪且没有未发送的草稿，才一次写入 bracketed paste 包起来的正文和回车，然后放开暂存。暂存期间本地敲的键不丢，放开后按顺序进入新的输入框；PTY 是按顺序的字节流，它们一定排在这条消息的回车之后。
  - **有草稿或弹窗时**：本地有草稿或有弹窗时，消息继续排队，绝不覆盖或拼接草稿。
  - **确认提交**：写入后以 `~/.codex/history.jsonl` 新增一行（已知 Codex 会话 ID 时只认这个会话的行）或 rollout 里出现这条用户消息，确认提交成功（notes §1、§10）。每条消息的状态以事件记录：排队、已提交、无法确认。
  - **确认不了不重发**：10 秒内确认不了的记为「无法确认」，**不重发**，因为按键已经送到，重发可能提交两次；写入时恰好 daemon 停了的，重启后同样只等确认、不重发。
  - **迟到的记录仍然算数**：Codex 在一轮开始后才记录用户消息，可能晚于这 10 秒（notes §10）。「无法确认」之后 rollout 里出现了这条消息，daemon 补记「已提交」，和这条用户消息一次写入事件记录、排在它前面，顺序与按时确认的一样（客户端靠这个顺序判断消息是谁发的）。客户端以每条消息最后一个状态为准，被推翻的「无法确认」不再提示；这种补记的「已提交」确认的一定是紧跟其后的那条用户消息，客户端不拿它去认领前面的消息。daemon 只在内存里记着哪些消息无法确认：重启后才到的记录不再改口。
  - **互斥**：注入、回答提问和中断共用一把锁，同一时刻只有一个操作使用 PTY 代理；代理也只允许持有暂存的连接写入和放开。正文里的控制字符会被去掉，避免提前结束粘贴
- **运行中的消息分两种**：
  - steer 是插入这一轮，daemon 照上一条的规则在输入框就绪时写入：Codex 运行中按回车就是插入当前这一轮；Claude Code 运行中回车会先进它自己的队列，等当前工具调用结束再并入这一轮（claude-code-notes §10）。
  - queue 是等这一轮结束再发，由 daemon 留在自己的队列里，看到这一轮结束（Codex 的 `task_complete`，Claude Code 的 `turn_duration`）后才按上一条的规则写入，不借用 Codex 的 Tab：两个 CLI 行为一致，daemon 重启后还在，也能照常取消。空闲时两者没有区别。
  - **还没送到 Agent 的消息都能撤回**，不分 steer 和 queue：还在 daemon 队列里的直接移除（`CancelInput`）；Codex 的 steer 一写进终端就插进这一轮，算已送达，不能撤回；Claude Code 的 steer 写进后先留在 Claude Code 自己的队列里，直到当前工具结束才并入，这期间 daemon 按 ↑ 把它拉回输入框、清空，以 transcript 出现不是 `absorbed_mid_turn` 的 `queue-operation remove` 为撤回成功；先被并入了就报「已送达，不能取消」。↑ 会把 Claude Code 队列里的消息全部拉回，所以同时排着的其他消息在清空输入框之前先存回 daemon 的队列并暂停，确认输入框清空后才放开，照常重新写入；daemon 中途停了或输入框清不掉时它们保持暂停，等用户发送或取消，不会丢，也不会写进还留着原文的输入框。
  - **默认**：客户端默认发 steer，和两个 CLI 自己按回车一致；发送请求里带一个字段区分两种，没填时按 steer。
  - **一轮被中断后**，还没写入的消息（queue 的，以及 steer 但还没写入的）都暂停，不自动发出，等用户逐条选择发送或取消：中断往往说明方向变了，排好的后续消息可能已经不适用。暂停状态和原因同步给所有客户端
- **判断输入框**：抓屏时保留颜色属性（`capture-pane -e`），按**样式属性**判断，不按转义序列的字面写法：逐个解析行首的 SGR 序列得到加粗、变淡、反色，再看第一个可见字符。Codex 升级常换写法（0.159.0 把 `\e[1m` 换成了 `\e[0;1m`），样式本身不变。输入框的提示符是加粗的 `›`，占位提示是淡色字（前面可能先有背景色设置，判断时跳过开头的样式和空格，看第一个可见字符是不是淡色），列表里选中的行是加粗反色的 `›`。只有看到占位提示才认定输入框是空的：多行草稿的第一行可能是空的，其余行和底部状态栏分不开（notes §10）
- **找到 rollout**：`SessionStart` hook（发出第一条消息时触发）把 `RA_SESSION` 和 `transcript_path` 一起报给 daemon（notes §3）。CLI 是先启动、会话后登记的，启动得快的 CLI（Claude Code 在已信任的目录里）可能在登记完成前就发来这个 hook；daemon 让它等到登记完成再处理，不回「没有这个会话」，否则之后再没有 hook 的会话（如 bypass）就一直绑不上 transcript
- **轮次和空闲**：一轮以 `task_started` 开始，以 `task_complete` 或 `turn_aborted`（被中断）结束；屏幕底部的输入提示符作为辅助（notes §1、§8）
- **模型提问**：问题从 rollout 的 `function_call` 读出，它在等待回答时就已经写入，不需要 hook。回答时暂存本地按键、抓屏确认选择框还在，再注入选项编号；以 rollout 的 `function_call_output` 为准，先在终端里答了的就收回卡片。异步提问（`request_user_input_async`）不单独处理，一轮结束后当普通消息回复（notes §9）
- **中断**：只在一轮运行时发 Esc，绝不发 Ctrl-C。空闲时发 Ctrl-C 会清空输入框，再按一次会退出 Codex（notes §8）
- **切换模型和 effort**：空闲时操作 `/model` 菜单：按显示名在屏幕上找模型的编号并按下，在档位列表里用方向键移到目标档位后按 `s`，只改当前会话（回车会改全局默认值）。Max、Ultra 在 `More reasoning…` 子菜单里。以底部状态栏出现新的模型和档位为成功，认不出菜单就按 Esc 退出并报错。rollout 要到下一轮才记录新模型（notes §2），所以 daemon 先记一条 `SettingsChanged`，会话信息立即按它更新，下一轮的 `turn_context` 再校对。可选的模型和档位读自 `~/.codex/models_cache.json`；打开模型选择页时重新读取，避免客户端一直使用旧列表。配置中的默认模型也列为一个可明确选择的选项：缓存有它时保留其完整档位，即使它标为隐藏；缓存暂时没有它时仍列出模型，但不猜测支持的档位
- **切换审批模式**：询问、自动、完全放行分别是 `/permissions` 菜单的 1、2、3，按数字直接选中；完全放行还要在 `Enable full access?` 里按 1 确认，以屏幕出现 `Permission selection requested` 为成功。计划模式用 Shift+Tab 切换，以状态栏右侧的 `Plan mode` 判断当前状态。运行中也能切，下一轮起生效（notes §4）。同样先记 `SettingsChanged`
- **压缩上下文**：空闲时输入 `/compact`。压缩在 rollout 里是一条 `ContextCompaction`，无论是客户端发起的还是终端里敲的，都解析成「上下文已压缩」事件
- **计划**：Plan 模式下模型给出计划后，rollout 里的 `Plan` 条目解析成 `PlanProposed` 事件，屏幕上的 `Implement this plan?` 让会话处于「计划待批准」，客户端显示计划卡片，回答时注入 1、2 或 3（notes §4）
- **工具开始**：rollout 在调用工具时先写一条 `custom_tool_call`（或 `function_call`），结束时写同一个 `call_id` 的 `*_call_output`，中间可能有描述它做了什么的 `item_completed`（如 `CommandExecution`）。开始解析成带 `call_id` 的 `ToolStarted`；期间完成的第一个条目用这个 `call_id` 报成 `ToolCall`，同一次调用的后续条目用 `<call_id>#2` 这样的 ID；没有任何条目的调用（很多 `exec` 就是这样）在输出到来时补一条 `ToolCall`，保证每个开始都有结束。`wait` 是在等之前让出的 exec 单元（输出以 `Script running with cell ID N` 开头），不算新的调用，它的输出结束的是那个 exec。让出这条输出不产生事件，所以 daemon 重启后解析器除了重放事件日志，还要把 rollout 从头到已读位置再过一遍，只取回「哪个单元属于哪次调用、哪个 `wait` 在等它、现在跑的是哪次调用」；只有重放后还有没结束的 `exec` 时才读
- **菜单操作的共同做法**：和注入一样拿控制锁、暂存本地按键，并在操作期间续期暂存；每一步都先确认画面再按键，等不到预期画面就按 Esc 退出。操作期间暂停状态检测，免得把自己打开的菜单当成弹窗
- **命令参数**：Go 代码调用 tmux 和 codex 时一律传参数数组，不拼 shell 字符串

## 7. 审批

`remote-agent hook codex` 作为 Codex 的 `PermissionRequest` hook，通过 unix socket 把请求交给 daemon。daemon 先读完 rollout，按最近一次 `turn_context` 的 `approvals_reviewer` 判断会话的审批方式：

| 会话的审批方式 | hook 的行为 | 用户看到什么 |
|---|---|---|
| 开着 `auto_review`（Codex 的 `Approve for me`） | 不输出、正常退出，交给 `auto_review` | 手机上不弹审批卡；模型在操作前拿不准时会在对话里问你（已实测），直接回复即可；`auto_review` 直接拒绝后模型会不会来问，未验证 |
| 没开 `auto_review` | 把请求转到客户端，等待回复；超时拒绝 | 审批卡片：允许、不允许（见下文「客户端只允许单次审批」） |

依据：Codex 先调用 hook，hook 不表态时才交给 `auto_review`；hook 只能返回 allow 或 deny 加 message，做不到原生审批框里的「以后不再询问」（notes §3、§4）。

- **hook 的超时**：hook 定义里的 `timeout` 设为 3600 秒，审批超时必须比它短。hook 自己超时的话，Codex 会改为在终端里弹原生审批框（notes §3），就做不到「超时拒绝」了
- **daemon 连不上**：hook 什么都不输出，交给 Codex 在终端里弹原生审批框，仍然由人决定。审批等待中 daemon 重启时，hook 会重试 30 秒，连上新的 daemon 后重新发起审批；旧的那条记为「已取消」

**Claude Code** 的审批走同一个入口 `remote-agent hook claude`，但规则不同，不照搬上面的 `auto_review` 分支：

| | 做法 | 依据 |
|---|---|---|
| 转不转给客户端 | 所有模式下都转：`PermissionRequest` 只在 Claude Code 要弹权限框时才触发，bypass 和 auto 放行的请求根本不会来 | [claude-code-notes §6](claude-code-notes.md#6-审批permissionrequest) |
| 终端里 | 原生权限框和 hook 同时出现，电脑和手机谁先答算谁的 | 同上 |
| 本地先答 | 屏幕上见过的权限框消失、这个工具已经有了结果或这一轮结束时，把卡片记为「已在终端处理」（`APPROVAL_DECISION_TERMINAL`）并让 hook 退出。本地选了「允许」时 Claude Code 不会结束 hook，只能靠 daemon 自己发现 | 同上 |
| 超时 | 照样返回拒绝；原生框随之消失 | 同上 |
| AskUserQuestion、ExitPlanMode | 它们也会触发 `PermissionRequest`，hook 直接不表态，不出审批卡；它们由第 16 节的提问和计划处理 | notes §6、§7、§8 |

### 客户端的审批模式

客户端的模式切换只做 Codex 和 Claude Code 都有的 4 种，这样接入 Claude Code 时不用改界面：

| 客户端 | Codex | Claude Code |
|---|---|---|
| 询问 | `Ask for approval`（`/permissions`） | manual |
| 自动 | `Approve for me`（`auto_review`） | auto |
| 计划 | Plan mode（Shift+Tab，和权限相互独立） | plan |
| 完全放行 | `Full Access` | bypass（启动时没允许的会话置灰） |
| 不提供 | — | accept edits |

各项的实测情况见 [codex-notes §4](codex-notes.md#4-审批模式) 和 [claude-code-notes.md](claude-code-notes.md)。

- **客户端只允许单次审批**：「允许」通过 hook 返回 allow；「不允许」可附说明，通过 hook 返回 deny，不中断整轮。「以后不再问」由用户在原生终端里选择，daemon 不自动按原生审批框的第二项。现有 hook 和屏幕信息不能把这个选项可靠绑定到特定工具请求，同前缀命令、同名文件和留在历史里的文本都可能误匹配。daemon 不声明远程永久审批能力；客户端发来永久审批请求时明确拒绝，保留原审批等待用户处理。
- **「询问」的语义不抹平**：Codex 在工作区内改文件、跑命令本来就不问，只有联网和越界才问；Claude Code manual 每一步都问。客户端按 CLI 实际发来的请求显示
- **Codex 的计划模式**：计划模式和权限是两个开关。选「计划」只打开计划模式、权限不变；选其他三种会先关掉计划模式再切权限
- **以 CLI 为准**：客户端只发「切换」指令，显示的是从 rollout、transcript 或屏幕读回来的结果；在电脑终端里切的，聊天里记一条。终端切到了这 4 种以外的模式（如 accept edits），照实显示
- **会话中途切到完全放行要二次确认，新建会话不确认**：新会话的审批模式来自项目设置（第 13 节），在项目设置里选完全放行本身就是明确的选择，按它新建时不再弹确认，项目页的设置摘要用红字标出，会话里写在导航栏的状态行。
  - **项目设置没指定时**：项目设置没指定时用 daemon 设置里的默认模式，再没有就沿用 CLI 自己的配置。
  - **读出 CLI 的默认模式**：沿用 CLI 配置时，客户端事先不知道它是什么，所以 daemon 把每个 CLI 实际生效的默认模式读出来放进机器元数据（`AgentInfo.default_mode`，只读配置、不改任何文件）：Claude Code 按它的优先级读托管设置、项目的 `.claude/settings.local.json` 和 `settings.json`、用户的 `~/.claude/settings.json` 里的 `permissions.defaultMode`，都没有就是 manual；Codex 读 `config.toml` 顶层和所选 profile 的 `approval_policy`、`sandbox_mode`、`approvals_reviewer`，没写的按 Codex 的默认值。`config.toml` 用 TOML 解析器（BurntSushi/toml）读，不按行猜：`'never'` 这样的字面量字符串、`profiles.x.sandbox_mode = …` 这样的点号键、内联表都是合法写法，Codex 照它们启动，漏读一种就会把完全放行的配置报成询问。读不出来（文件读不了、不是合法 TOML、这几个键的值不是字符串）就标为未知。
  - **客户端怎么显示**：客户端用它在摘要里如实显示：完全放行照样用红字，未知写「CLI 配置（未读到）」，两种都不拦截新建。
  - **为什么不拦截**：这些默认值都是用户自己写的配置，和在项目设置里选完全放行一样算明确选择，所以 daemon 也不据此拒绝新建

## 8. 项目标识

项目按会话工作目录的**绝对路径**判定：路径相同就是同一个项目，不同电脑上路径相同的目录也算同一个项目；项目名是路径的最后一段。分组在客户端完成（`web/src/model.ts`），路径在加密的会话元数据里，server 看不到。同名但路径不同的是两个项目，列表里用路径区分。

会话标题由 daemon 从第一条用户消息生成，写进加密的会话元数据：去掉开头的图片占位（`[Image #N]`），取第一行的首句（到第一个中文标点，或后面跟空格的英文标点为止，前 4 个字符内的断句不算），最多 40 列宽（汉字算 2 列），超出加省略号。理由：整句当标题既不概括内容又必然被截断，而首句不需要调用模型，内容也不出本机。只有图片没有文字的消息不产生标题，由下一条消息命名；还没有标题时客户端显示「项目名 · 开始时间」。

用户可以给会话重命名。自己起的标题存在 daemon 的会话记录（`session.json`）里，优先于自动标题，之后的消息不再改它；留空保存就清掉它、恢复自动标题。标题一行，最多 60 个字，由 daemon 去掉首尾空白并把换行等空白折成空格后校验。理由：标题本来就由 daemon 写进加密的会话元数据，改名走同一条路，所有客户端和通知自然一致，server 仍然只看到密文；代价是电脑离线时改不了。已结束的会话也能改。只改 remote-agent 显示的标题，不动 CLI 自己的会话名（Claude Code 的 `/rename`、Codex 的自动标题），免得为一个显示用的名字去驱动终端菜单。

### 会话列表排序

网页、宽屏侧栏和 Android 使用相同规则：「需要处理」先按审批、问题、计划、终端弹窗排列，同类型按当前待处理请求的开始时间从早到晚；多项审批或问题取仍待处理项中最早的时间，解决后转到下一项。「进行中」包括启动、运行、空闲和离线会话，按会话创建时间从新到旧，离线不改变位置。「已结束」按实际退出时间从新到旧。时间相同使用会话 ID 的字典序；项目排序时间相同时使用项目路径的字典序。分区变化会移入对应列表，当前选中会话继续遵守侧栏保留规则。

等待和退出时间由 daemon 从本地事件日志重建；计划等待从稳定终端画面首次显示批准提示时记录，弹窗从进入对应阻塞状态时记录。时间跟随加密会话摘要传输，server 无需解密或参与排序。后台输出和重连的上传时间只用于最近活动显示，不决定会话或项目列表的位置，也不决定新会话从哪个会话继承配置：继承取列表顺序里最靠前的会话，即未结束的优先（创建时间最新的），否则最近结束的。理由：会话列表按这个顺序分页取回，按它继承，已取到的部分就足以确定继承自谁；按上传时间的话，一个被改名或重传过的旧会话可能排在没取到的页上。会话没有等待或退出时间时用创建时间；摘要未解密时用零和 ID，摘要首次到齐后再按创建时间归位。

### 主页的范围

主页和宽屏侧栏是一条会话时间线：需要处理、进行中，然后是已结束的会话，按今天、昨天、近 7 天和月份分组。它的范围是某个项目或全部项目，由标题切换。理由：按项目分组的主页在只有一个项目时几乎是空的，要找的会话都藏在项目页里；把项目变成范围后，一个项目的人看不到项目这一层，多个项目的人仍然可以按项目看。

- **默认与记忆**：未移除的项目只有一个时范围是它，否则是全部项目。用户选过的范围记在这台设备上（网页 `localStorage`，Android 和 iOS 本机设置），不进账户偏好，因为不同设备常常看不同的项目；记住的项目已移除或不存在时按默认。Android 和 iOS 的本机设置是磁盘上的明文，所以记的不是项目路径，而是用账户密钥对路径算出的标记（第 9 节的 `home-scope`），对照项目列表才认得出是哪个项目；网页记的是路径。宽屏上打开某个项目会把范围换成它
- **范围内有什么**：全部项目列出未移除项目的全部会话；已移除项目的会话只在需要处理和进行中里出现，和上文「从项目列表移除」一致。某个项目的范围里，进行中和已结束只列它自己的会话；需要处理不受范围限制，始终列出账户里全部待处理的会话，免得别的项目的审批被范围挡住，不在范围内的那几行写出项目名
- **行内写什么**：第二行是状态词和预览；项目只在全部项目里写（以及上面说的范围外的待处理项），CLI 只在范围内的会话用过不止一种时写，机器只在账户里不止一台电脑时写。理由：只有一个项目、一种 CLI、一台电脑时，这三项每行都一样，是噪音
- **筛选**：范围内会话超过 8 个时提供按标题筛选，不分大小写的子串匹配，在客户端对已解密的会话摘要做，标题不离开客户端；不搜对话内容（[scope.md](scope.md)）
- **已结束的分页**：先显示 30 个，滚到底再加 30 个；显示到已取到的末尾时再向 server 取下一页，见下文「会话列表分页」
- **宽屏没有项目页**：选中项目后侧栏列出它的会话，主区域是它的新建输入框。手机保留项目页作为新建页，范围是某个项目时新建按钮直接进它

### 会话列表分页

客户端不一次取回全部会话。`ListRemoteSessions` 的第一页是全部未结束的会话，加最近结束的 50 个；之后每页是游标之后的 50 个已结束会话，从最近结束的到最早的，结束时间相同按会话 ID。理由：会话只增不减，全量取回的下载和解密都随总数增长；而界面真正需要完整的只有未结束的会话（需要处理、进行中），已结束的只在往下翻时才用到。

- **server 知道什么**：会话状态在加密的元数据里，server 分不出哪些已结束，所以 daemon 在 `PutSession` 里另外用明文告诉 server 结束时间（`ended_ms`，未结束是 0），server 只用它分页和排序。这比原来多暴露了「这个会话已结束、何时结束」；结束的时刻 server 本来就能从这次上传的时间大致看出（[scope.md](scope.md) 第 4 节）。客户端显示和排序仍用加密元数据里的时间，`ended_ms` 只当游标用。取 daemon 上报的值而不是 server 的更新时间，是因为重传元数据不该改变会话在列表里的位置
- **结束时间取值**：元数据里的结束时间；没有记录的取创建时间，和客户端排序的规则一致（上文「会话列表排序」）；都没有时取 1，保证已结束的会话不为 0。会话被恢复后回到 0
- **和 server 不一致时**：daemon 连上后在 `ListSessionHeads` 里看到 server 存的 `ended_ms` 和本地不同，就重传这个会话的元数据。server 的会话表新增这一列后，已有的行由此补齐，不写迁移代码
- **项目从哪来**：项目原来由客户端从全部会话里归出来，分页后只有旧会话的项目会消失。所以每台机器在加密的 `MachineMeta` 里带一份项目摘要：路径、已结束会话数、最近创建和最近结束的时间。它只在会话开始或结束时变化，不随会话运行重传。客户端的项目列表是各机器的项目摘要加上已取到的会话；是否有未结束的会话仍看会话本身。用「新项目…」选好目录时，客户端把所选机器写进这个项目的项目设置（第 13 节）；一个项目只在项目设置里出现、还没有会话时也列出来，按添加时间排在所有会话已结束的那一组，这样它在刷新后和账户的其他客户端上都在。项目设置里的机器已不是账户里的机器时不列。选的目录已经是项目时不写，项目设置保持原样。范围里「共 N 个」的 N 来自摘要里的已结束会话数
- **往下翻**：显示到已取到的已结束会话末尾、server 还有下一页时，取下一页。范围是某个项目时，一页里可能没有它的会话，就接着取，直到够显示一屏或取完
- **筛选**：按标题筛选要对全部标题做，所以开始筛选时把剩下的页都取回来，取完之前末尾写「正在加载更早的会话…」。筛选是偶尔的操作，为它在 server 上建索引就得让 server 看到标题
- **按 ID 取**：打开的会话不在已取到的范围里时（通知、链接、分叉来源），用 `session_ids` 单独取它；取不到才显示「找不到这个会话」
- **重新连接后**：第一页重新取回。本地已有而这一页里没有的会话：所属机器已不在的删掉；已结束、且按游标排在这一页之后的保留（它属于后面的页）；其余的删掉（已不存在，或在别处被取到时再出现）
- **本地缓存**：网页缓存第一页的密文和机器列表，下次打开先显示。事件缓存不再按会话列表清理，只按容量淘汰最久没打开的，因为客户端不再知道完整的会话集合

### 项目列表偏好

项目仍按绝对路径分组。常用、隐藏和项目设置（第 13 节）都属于账户，在客户端之间同步；用独立用途密钥加密后交给 server 存储和转发，server 只能看到不含路径的对象 ID、修订号与密文。客户端解密后按项目路径匹配，不向 server 上传明文项目名或路径。常用按设为常用的顺序稳定排列，其他项目先按是否有未结束会话分组：有未结束会话的项目在前，所有会话已结束的项目在后；各组按项目内最近创建会话的时间从新到旧排列，相同时间按项目路径字典序。运行、空闲、等待处理和离线都算未结束，状态之间切换、输出和重连不改变项目顺序。新建会话可以前移项目，最后一个未结束会话退出时项目移到已结束组。旧会话缺少创建时间时用零，摘要首次解密后按创建时间归位。

偏好写入带预期修订号：冲突时取回最新密文、解密，再重做当前项目这一项改动，保留其他项目的并发改动。界面先显示保存中，server 确认后更新列表；断线时显示缓存，修改的入口按禁用显示。新设备读取账户偏好；退出或清除本机数据只删除本地缓存，不删除账户的常用项目。

「移除项目」只是隐藏入口，不结束会话、不删除历史、不屏蔽提醒；隐藏项目不出现在项目列表或新建选择器，进行中的会话与待处理项仍照常展示。移除前确认一次，确认后没有撤销，也没有已移除项目的列表：界面上移除就是移除，少一套「恢复」的概念和页面。要再用，把同一个目录加成新项目，客户端发现它在隐藏列表里就取消隐藏，原来的会话、历史和项目设置都还在；从通知或会话进到隐藏项目的页面时可以查看，页面上有「重新添加」，加回来之前不能新建。新增会话不会把隐藏项目自动放回列表。偏好对象的格式没有变，仍是常用、隐藏和项目设置三个列表。

项目在范围菜单、新建时的选项目和项目管理三处是同一个列表：同样的分组和排序、同样的两行（名字；路径加进行中的数量，没有进行中而它的电脑都不在线时写「电脑不在线」）、同样的「新项目…」，只有行尾不同。两端各由一个共用的组件画，免得三处各自演变。

主页和范围菜单见 [client-v38 · 主页](design/client-v41.html#home)，项目管理的布局与具体交互见 [client-v38 · 项目管理](design/client-v41.html#projects)。目标机器离线时由用户选这次用的机器，不改项目设置，也不在输入中途自动更换机器或 CLI。在新建输入框旁切换 CLI 保留草稿，改用项目设置里这个 CLI 的那一套。

## 9. 账户、设备和密钥

一个账户对应一个随机的 32 字节**根密钥**。第一台电脑用 `remote-agent account init` 生成它；server 上只有一个账户，第一次登记设备时必须带上 server 配置里的一次性 setup token，账户建好后 token 就不再起作用。

所有密钥都从根密钥派生，一个用途一把（HKDF-SHA256，info 为 `remote-agent/v1/<用途>`）：

| 用途 | 派生出的密钥 | 用来 |
|---|---|---|
| `account-sign` | Ed25519 账户密钥 | 签设备登记；server 只存它的公钥 |
| `wrap` | AES-256 | 加密会话密钥 |
| `machine-meta` | AES-256 | 加密机器元数据（机器名、系统） |
| `command` | AES-256 | 加密客户端发给 daemon 的指令和返回结果 |
| `notify` | AES-256 | 加密推送里的通知内容，只给 Android App 在后台解密用（[android-client.md](android-client.md)） |
| `account-prefs` | AES-256 | 加密账户级的偏好对象（项目的常用、隐藏和项目设置，第 8、13 节） |
| `device-meta` | AES-256 | 加密客户端设备的元数据（名称、平台），见下文「设备目录」 |
| `home-scope` | HMAC-SHA256 | Android 和 iOS 给主页范围里记住的项目算标记，只在本机用（第 8 节「主页的范围」） |

每个会话另有一把随机的**会话密钥**，加密这个会话的事件和元数据。它存在 daemon 的会话目录里（`relay.key`），用 `wrap` 加密后上传到 server，客户端从 server 取回再解开。

**设备**：每台电脑、每个浏览器和每个 App 都有自己的 Ed25519 设备密钥，设备 ID 是公钥 SHA-256 的前 16 字节。登记时用账户密钥签名，server 用账户公钥验证；登录时设备签 server 给的一次性 challenge，换取 30 天有效的 token。设备登记由账户密钥签名，而不是由一台已登记的设备签名：单用户场景下根密钥本身就是信任根，这样新设备加入时不需要旧设备在线。

**指令签名**：`command` 密钥是账户里所有设备共用的，只能证明「账户里有设备发了这条指令」，而 server 不可信，它说的发送方也不能当真。所以客户端用自己的设备密钥给每条指令的信封签名（`Envelope.signature`），签的是上下文 `remote-agent/v1/envelope-signature\0` 加上 header、nonce、密文的原始字节，每段前面带 4 字节大端的长度。server 转发时核对 header 的发送方就是登录的设备，并附上这台设备登记时的原文和账户签名；daemon 先用账户公钥验证登记，再用登记里的设备公钥验证信封签名，两者都对才把来源记为这台设备（`ORIGIN_KIND_CLIENT`）。没有签名或签名验证失败的指令拒绝执行。字节格式的测试向量在 `internal/e2e/testdata/v2-vectors.json`。

**把根密钥交给新设备：配对**。已有设备（网页的「设置 › 添加设备」或 `remote-agent account pair`）显示二维码和 8 位配对码，新设备扫码、输码（网页），或用 `remote-agent account join --code` 加入。实现在 `internal/e2e/pair.go`、`internal/relay/pair.go` 和 `web/src/pairing.ts`，要点：

- **8 位码只用来找到配对**，不参与加密，也不算授权：server 能看到它，熵也只有 26 位多
- **先承诺、后揭示**：已有设备建配对时只交出自己一次性 X25519 公钥的 SHA-256；新设备发出公钥之后，已有设备才揭示公钥，新设备核对它和承诺一致。已有设备的公钥在看到新设备的公钥之前就定了，替换密钥的 server 没法挑选让两边图案碰巧一致的密钥
- **四个 emoji**：双方用 X25519 共享值和整个会话记录（配对 ID、两把公钥、新设备类型）经 HKDF 派生 32 位，映射到 256 个 emoji 里的 4 个。用户核对一致后在已有设备上允许，已有设备才用同一共享值派生的密钥封好根密钥和 server 地址交出去。被替换过密钥的两端算出的图案不同
- **二维码**带上承诺，扫码的新设备直接比对，不只依赖人工核对
- **限制**：配对 5 分钟过期，同一时间只有一个候选设备，每个码最多 3 次加入；错误的码在全局按每分钟限流。限流预算耗尽后不再查询任何配对码；已有设备取消时清掉待领取密文。配对状态只放在 server 内存里。密文只给持候选令牌的新设备，响应丢了可以重取；新设备加入完成后确认收到，server 随即清掉密文，把配对标为「已交付」再保留一分钟。发起方看到「已交付」才报成功，超时或配对中途消失则提示结果不确定；结果不确定时发起方仍留着这次配对，离开页面或换新码时照常取消，清掉待领取密文
- 新设备拿到根密钥后，照常用账户密钥签名登记自己

新设备等待核对时可取消或因图案不一致返回填码页：停止本次轮询和后续自动加入，丢弃本次临时配对密钥，保留服务器地址、清空旧码；不把本地退出说成 server 已撤销。旧候选仍可能占着配对码，提示已有设备拒绝旧请求并生成新码。取消与允许同时发生时，注册前需重新检查取消状态；如果登记已经开始或完成，不能报「已取消」，应确认登记结果，再提示已经加入或结果尚未确认。界面见 [client-v38 · 设置与配对](design/client-v41.html#settings)。

各端的服务器地址只接受 HTTPS，本机 loopback 地址允许 HTTP 用于开发，Android 调试还支持模拟器的 `10.0.2.2`；正式 Android 的网络配置禁止 HTTP。服务器地址不能带用户凭据，Go 也拒绝片段和查询。Go、网页和 Android 的 API 请求拒绝重定向，避免登录签名、setup token 或 bearer 被转交给另一个地址。Go 和 Android 的 WebSocket 握手也拒绝重定向；浏览器 WebSocket 没有关闭重定向的 API，仍依赖所配置 HTTPS 服务及浏览器的混合内容策略。

账户密钥串 `ra1.<根密钥>.<server 地址>`（`remote-agent account secret`）仍可作为备用方式粘贴，它不放进 URL，以免留在浏览历史里。

**浏览器怎么存**：设备私钥存成不可导出的 `CryptoKey`（IndexedDB）；根密钥除了不可导出的 HKDF 密钥，还存一份原始字节，因为配对时要把它交给新设备（WebCrypto 的不可导出密钥取不回原始字节）。代价是页面一旦被注入脚本，根密钥能被带走；不过那种情况下脚本本来就能通过页面解密全部内容，差别在于带走后长期有效。配对上线前加入的浏览器没有原始字节，不能发起配对，要重新加入一次。不同的网页来源（如 localhost 和 `app.<域名>`）各有各的存储，换了地址要重新加入。App 怎么存见 [android-client.md](android-client.md)。

### 多客户端的界面状态

每个会话属于固定机器和 CLI。已接受的消息、队列、模型、模式、上下文与处理结果是共享状态，以 daemon 发出的事件与元数据为准；项目列表偏好跨端同步；客户端草稿、当前视图、滚动位置和通知偏好各自独立。多端输入仍按到达顺序注入，不增加会话独占。某个客户端断线只说明它的数据可能过期，不意味着电脑或其他客户端离线。

### 断线时显示什么

从客户端到电脑要经过三段：本机网络、服务器、电脑。客户端只报离自己最近的那一段故障，并且只在连接提示条一处说；更远的一段此刻无从得知，不沿用断线前的说法。界面见 [client-v38 · 断线](design/client-v41.html#link)。

| 判断 | 结论 | 没结束的会话 |
|---|---|---|
| 连着服务器 | 无提示；电脑在不在线以服务器说的为准 | 照常 |
| 系统说本机没有网络；Android 上解析不出服务器地址也算 | 本机网络不通 | 未连接 |
| 有网，开始连接或断开不到 10 秒 | 正在连接，不下结论 | 保持原样；这次启动后还没从服务器取到过列表时算未连接 |
| 有网，10 秒后仍没连上 | 连不上服务器，原因在详情里 | 未连接 |

- **为什么不沿用旧状态**：缓存里的电脑一律当作不在线读出来，断线前的「运行中」也可能早就结束。照旧显示会把本机没网说成电脑离线。已结束是不会变的事实，照常显示；等待审批的卡片和计数也保留，它们不会因为断线消失
- **10 秒**：切换 Wi-Fi 和蜂窝、服务器重启通常在几秒内恢复，这段时间只转圈。网络回来时重新计时
- **本机有没有网**：Android 用系统的默认网络回调，没有默认网络就是没网，失去时立即断开当前连接，不等心跳超时。不用系统的「已验证」标记：它依赖系统自己的探测地址，探测不通不代表到不了自部署的服务器。信号满格但实际不通时系统仍报告有网，这时解析服务器地址会失败，所以把解析失败也算作本机网络不通。浏览器只有 `navigator.onLine`，分不出「有网但不通」和「服务器停了」，统一说连不上服务器，并在详情里写明两种可能
- **电脑为什么不在线**：服务器只知道 daemon 的连接断了，分不出睡眠、断网还是程序退出，状态卡把三种可能都写出来。要区分需要 daemon 退出时告知服务器，属于协议改动，没有做
- **连接检测**：连着但慢、或时断时续时，上面这些提示什么都不说，所以另有一个手动的检测（设置里，以及宽屏侧栏底部的连接状态），按段测一次往返：到服务器是三次对 `/healthz` 的请求，取居中的一次，免得第一次建连或一个慢包算进去；到电脑是一条只读设置的加密指令（`getSettings`），走和真实操作相同的路：客户端 → 服务器 → daemon → 服务器 → 客户端。两者都是 server 和 daemon 本来就应答的请求，不用改协议。服务器没回应时不再测电脑。服务器 500 ms、电脑 1500 ms 以上标「较慢」，是初始取值。只在打开和点「再测一次」时测，不在后台常测：常测要耗电和流量，而延时只在觉得慢的时候才有人看
- **读取失败**：没连着服务器时读取历史失败不单独提示，连上后自动补齐；连着时才在原处给出红条和重试，原因写成中文，底层错误只出现在详情里

设备目录和来源展示：server 只提供设备 ID、设备类型与加密元数据；人类可读的客户端名称不以明文登记。客户端名称放在独立用途密钥加密的元数据中；消息与队列的发送设备 ID，以及处理来源写在加密事件内，由 daemon 按已认证的指令来源记录，不能信任客户端自报的来源。来源没记录或无法可靠匹配时写「另一客户端」或「本地终端」，不猜具体设备，也不凭卡片消失推断允许或拒绝。server 另外记下每个客户端主连接最近一次连上或断开的时间，和电脑的最近在线时间一样是明文；设备目录用它写「上次使用」，让人认出早就不用的客户端并移除。上次使用不代表正在观看或有独占权。

其他端处理了审批或提问时同步收回卡片，普通消息草稿保留；正在输入但未提交的拒绝理由暂存在本客户端，可复制，不能自动当作下一条审批的理由。终端尺寸属于共享 tmux 窗口，任何端主动适配后，所有端按收到的新尺寸更新；不能仅根据自己之前点过适配来显示「已适配」。取消适配与断开时遵循第 11 节的 latest 规则，不承诺恢复旧设备记录的尺寸。

## 10. 报文、同步和指令

字段以 `proto/remoteagent/v1/{envelope,relay,remote}.proto` 为准，这里只写约束和理由。

**信封**：内层先编码成 Protobuf，再用 AES-256-GCM 加密。`Header` 写明用途、机器、会话、序号或请求 ID、截止时间和发送方，序列化以后**原样**作为附加数据参与认证，接收方解开后按原始字节解码，从不重新编码。接收方逐项核对 header 和信封所在的位置（哪台机器、哪个会话、第几号、哪个请求），所以 server 没法把一个信封挪到别处。nonce 是 12 字节随机数。server 也会读 header（它是明文），只用来尽早拒绝放错位置的请求，安全性不依赖这一步。

**压缩**：密文压不动，所以压缩在加密之前做：内层超过 256 字节、且压缩后更小时，用 DEFLATE（RFC 1951，不带 zlib 或 gzip 的头）压缩后再加密，`Header.compression` 写明，它和 header 其余部分一起参与认证。会话密钥、图片和配对载荷不压缩：前两者压不动，配对发生在两端核对协议版本之前。接收方解密后按 header 解压，不认识的压缩方式一律拒绝，解压结果超过 64 MiB 也拒绝，免得一个小信封撑爆内存。选 DEFLATE 是因为它到处都有：Go 用 `compress/flate`，Android 用 `java.util.zip`；网页打包了 fflate（MIT，纯 JS），不用浏览器的 `CompressionStream`，因为 `deflate-raw` 这个格式在各浏览器里出现得比网页其余依赖的能力晚，而解不开压缩的客户端就读不了 daemon 发来的任何东西。事件、元数据、指令和终端输出都走这条路，server 上存的事件密文也跟着变小。代价是密文长度会反映内容的可压缩程度；server 看不到明文，也没法往同一个信封里掺入自己选的内容反复试探，所以不构成 CRIME 那样的攻击。HTTP 层的 gzip 对信封没有用，不另外开。

**事件上传**：daemon 连上后先查 server 已有到哪个序号（`ListSessionHeads`），再按序号从后面接着传；server 只接受紧接着的序号，已有的跳过，有空缺的拒绝。server 已有的会话先传事件、再传元数据：事件是客户端在等的东西，先传元数据会让每批事件多等一次往返。daemon 记住每个会话上次传过的元数据，重连后只传有变化的；已结束会话的记录还写进会话目录（`relay.sent`，用会话密钥算的摘要，不含内容），重启后 server 仍持有同一修订号就不再重传，其余已结束的会话一次只同步一个，给进行中的会话留出请求名额。重试时同一序号的事件会用新 nonce 重新加密：本地日志里每个序号对应的内容不会变，所以解出来的明文相同，server 保留第一份。每个会话一把密钥，随机 nonce 的数量远低于 GCM 的使用上限。

**客户端同步**：先连上 WebSocket，再拉会话列表的第一页（[第 8 节](#会话列表分页)）和缺的事件，这样两者之间不会漏掉。server 先写库再推送；客户端按序号去重，推送来的事件如果前面有空缺，就先放着，再用 `GetEvents` 补齐。会话和机器的元数据带递增的修订号（header 的 `seq`），客户端只接受更新的版本，server 也只保留最新的。

**指令**：客户端的指令统一走 `Forward`，header 里带 128 位随机的请求 ID 和 60 秒后的截止时间。daemon 的处理规则：

- 截止时间已过的拒绝；比现在晚 10 分钟以上的也拒绝，并提示检查时钟
- 执行前先把请求 ID 记为「开始」并落盘，执行后记下结果，也落盘（`commands.json`）；文件无法读取或格式损坏时禁用远程指令，保留原文件，修复并重启后恢复，不把损坏记录当作空记录
- 同一个请求 ID 再来，直接返回记下的结果；如果只记了「开始」没有结果，说明上次执行到一半 daemon 停了，返回「结果未知」，**绝不重新执行**
- 记录保留到截止时间过后，因为过了截止时间的指令本来就会被拒绝

server 把指令原样转给那台机器的 WebSocket，最多等 30 秒。机器不在线时立即返回「不可用」，**不排队**；已经转发出去但没等到结果时，返回「可能执行了、也可能没有」，客户端用同一个请求 ID 重试即可。

**WebSocket**：路径 `/v1/stream`，承载二进制 Protobuf 帧。浏览器的 WebSocket 不能自定义请求头，所以第一帧发 token，认证通过前 server 不发任何数据；浏览器连接还要检查 `Origin`；原生 App 不发 `Origin`，server 用的 coder/websocket 对没有 `Origin` 的请求直接放行，App 同样靠第一帧的 token 认证。server 每 20 秒 ping 一次；某个连接积压超过 256 帧或 16 MiB 就断开它，它重连后从历史补；只数帧不够，一帧事件可以接近 1 MiB。Android 的主连接和终端连接也每 20 秒 ping 一次，换网络后悄悄断掉的连接靠它发现；浏览器发不了 ping，网页改为给建连设 15 秒上限，并在浏览器报告网络恢复时跳过退避立即重连。两端都留着上次登录的 token，回到前台直接用它开连接；只有 server 以 1008 拒绝第一帧时才丢掉 token 重新登录，网络丢掉的握手不算。每台机器同时只保留一条连接，新连接顶掉旧的。主连接和终端连接在 token 到期或设备被移除时都取消，认证登记和移除共用锁，避免连接在移除期间重新进入。

**后台和内存**：App 进入后台、网页页面隐藏时，都关闭主连接和终端连接并暂停界面计时，回到前台或恢复可见后重新同步。两端只为当前消费者保留完整解密历史：网页页面与待处理卡片显式持有，Android 按事件流订阅保护，图片确认只在确实仍等待处理时持有。无人使用的历史按最近使用回收，默认最多 8 个会话、估算内容量 16 MiB，并在闲置一分钟后释放；估算不等于进程堆内存上限，活动会话仍保留完整历史以推导状态。回收不删除历史、Android 磁盘密文缓存或待发图片。网页同样把读到的事件密文存在浏览器的 IndexedDB 里（`web/src/eventcache.ts`）：再次打开会话时先从本地读，按原样解密和核对位置，只向 server 取之后的事件。理由：历史是整段下载的，而到 VPS 的链路慢（实测约 270 KB/s，最长的会话要下 30 秒以上），瓶颈在传输而不在解密或渲染。缓存里只有密文，密钥本来就在同一个浏览器里，没有新增暴露；server 已经没有的会话在列表刷新时清掉，总量超过 256 MiB 时按最近打开时间回收，退出账户时整库删除。本地副本比 server 的历史长或解不开时丢弃重取。Android 和 iOS 的磁盘密文缓存里某个会话有一条解不开时，同样整段丢弃这个会话的事件、从 server 重取。同一个库里还存着上次列出的机器、会话和账户的项目偏好（同样是密文）、各台机器上次报告的模型列表和 daemon 设置（解密后的，只有模型名和默认值），以及登录 token：打开网页时在第一次绘制前读出来，直接显示上次的列表、范围和新会话设置，机器和 server 回话后再更新，偏好在读到 server 的副本前不能修改；并直接用 token 连接，省掉登录的两次往返；token 被 server 拒绝时流会被关掉，下一次重试再登录。token 泄露的后果小于同样存在浏览器里的根密钥（第 9 节）。网页长会话只挂载视口附近的行，展开状态由会话视图保存；回看位置需要重载时，等完整历史或明确失败后恢复，避免把旧位置套在分页前缀上。网页和 Android 主连接串行处理并限制在途帧与字节，字节预算直到处理完成才释放；Android 在复制前拒绝超大的推送帧，积压超限时丢弃排队帧并重连补齐。网页终端预算直到 xterm 消费完成才释放，超预算断开后重新同步，不跳过字节。

**大小限制**：单个信封不超过 1 MiB，一次上传不超过 500 个事件，推送帧超过 1 MiB 就拆开发。历史按条数和序列化字节数共同分页，客户端按返回游标连续读取。WebSocket 认证 hello 使用独立的小帧上限；等待认证和活跃连接同时受固定限额约束，过载明确拒绝。HTTP RPC 在解码请求正文之前限制并发和读取时长；声明正文不超过 64 KiB 的请求另有一组更多的名额，因为它们大多在等待（转发给电脑的指令、慢链路上的一页历史）而不是在解码，不该被几个大请求挡在外面；声明了压缩的正文不论多小都按大请求算，因为解压后可以接近正文上限；认证请求使用更小的正文上限。推送去重状态和异步发送同样有容量限制，过载返回可重试错误，不消耗被拒通知的去重键。

**网页**：事件内容一律当文本渲染，不插入 HTML；Markdown 里只有 http(s) 的链接可以点，其他目标（大多是本机文件路径，也可能是 `javascript:`）显示成等宽文字；构建产物带 CSP，只允许运行自己的脚本。service worker 除了显示推送，还保存应用外壳（页面、脚本、样式、字体和图标）：打开网页时先用保存的页面回答，同时在后台取新的留给下一次，所以启动不等 Cloudflare 的连接（实测冷连接的握手要 0.6 到 2.7 秒），发布后的新版本在第二次打开时生效。新页面只和它点名的脚本、样式一起保存，免得两次发布之间留下一个取不到脚本的页面；按需加载的部分在页面稳定后提前取好，取不到（服务器已经换了更新的版本）就丢掉保存的页面，真正用到时再整页重载到当前版本。API 在另一个域名，不经过 service worker。脚本分成几块：第三方库单独一块，发布新版时文件名不变，浏览器继续用缓存；终端（xterm）、配对用的曲线和二维码、图片编解码在用到时才取。网页和 server 要放在同一个注册域名下（`app.<域名>` 和 `ra.<域名>`）：拦截扩展常按「第三方请求」过滤，实测 AdGuard 会拦掉跨站发往 `*.*.top` 的 WebSocket（[browser-notes §1](browser-notes.md#1-adguard-拦截发往-top-的跨站-websocket)）。本地开发遇到这种拦截时，可以用 `RA_PROXY` 让 vite 把请求转发到 server，同时用 `VITE_SAME_ORIGIN_API=1` 构建。

## 11. 终端视图

客户端打开终端时，发一条加密指令 `OpenTerminal`，带上随机的流 ID。客户端和 daemon 各自用这个流 ID 连 server 的 `/v1/term`，server 把两条连接配对后原样转发，**不存储、不解析**：配对要求一端是客户端设备，另一端正是客户端指定的机器；先到的一方最多等 20 秒。

- **画面来源**：daemon 为每条流起一个 tmux control mode 客户端（`tmux -C attach`），它不参与窗口尺寸的计算。先开始接收 `%output` 里这个 pane 的输出，再用 `capture-pane -e` 和光标位置拼出快照，快照之后把收到的输出全部转发。抓屏前后到达的输出可能已经在快照里，会再画一遍；Codex 用绝对坐标绘制，重画不改变结果，而丢掉它们会让画面缺块。窗口尺寸变化时（`%layout-change`，比如电脑上调了终端大小），重新发快照
- **回看历史**：新建 tmux pane 的保留上限为 100000 行，已有 pane 不追溯扩大。实时画面不留本地回滚：在终端上往上滑（触摸、滚轮、触控板）进入回看，同一块区域换成只读的历史阅读区，没有单独的「历史」入口。首次请求在本机用 `capture-pane -e` 生成固定快照，再按游标倒序取每页最多 200 行、256 KiB 的整行，行内带 SGR 颜色序列；客户端只解析颜色和字形属性，按实时画面的字号和列宽显示，其他控制序列丢弃，不当作终端指令回放。滑近顶端自动加载更早内容并保留阅读位置；回看时新输出不移动画面，只提示有新输出，点提示、滑到底或按任意按键回到实时，按键照常发出。回看不改变远端程序。快照不随输出或窗口尺寸变化而改变，避免分页重叠或漏行；关闭连接后游标失效，再次回看重新抓取。为什么不把旧内容拼进实时终端的回滚：实时流从快照开始，拿不到可靠的对齐点，拼接会重行或漏行
  - 每条流只保留一份历史快照，存在权限为 0600、创建后立即 unlink 的本机临时文件中，不落到中继，也不会在 daemon 崩溃后留文件。单次捕获限 64 MiB、5 秒，超出报错，不悄悄删掉较早记录。单行超出一页预算也明确报错。
  - 历史请求和响应经过现有终端信封加密。独立工作协程抓取快照，输出和输入继续处理；只排队一条请求，洪泛时关闭该客户端的流。三端把历史响应计入积压上限；请求超时可重试，迟到或上一次回看的响应不进入新页面。
  - Codex 用 `--no-alt-screen` 启动，把输出留在 tmux 历史里。已丢弃或 CLI 未写入终端历史的内容不能恢复；完整对话仍看聊天页。
- **加密**：每一帧用会话密钥封成信封，类型分输出和输入，`request_id` 是流 ID，`seq` 是各自的帧序号，接收方要求序号严格递增，乱序或重放就断开
- **输入**：客户端敲的键经 `tmux send-keys -H` 进入 pane，走的是和本地键盘相同的路，所以注入消息时对本地按键的暂存同样挡住它们
- **尺寸**：客户端每次连上终端，收到第一份快照后自动适配一次：`resize-window` 到客户端能放下的大小。用户点「还原」或关闭终端时把 `window-size` 设回 `latest`；在这个终端点过「还原」后重连不再自动适配，要手动点「适配」。没适配时客户端按列数缩小字号，最小缩到 6（Android 为 dp、iOS 为 pt、网页为 CSS px，与「字号」可选的最小值相同）；到 6 还放不下整行就保持 6，实时画面和回看都可以左右滑动查看，回看打开时停在实时画面当前的横向位置。手势按起手方向区分：横向是平移，向下拖是进入回看。Android 和 iOS 的「字号」可选 6 到 22。别处改了尺寸不自动抢回，免得两个客户端来回改。网页上已适配的终端在面板宽度变化（调整浏览器窗口、在「终端」和「并排」之间切换）后重新适配，高度变化不触发，所以手机键盘弹出不改远端尺寸。Android 已适配时主动调整字号也重新适配
- **积压**：输出通道满了就结束这条流，客户端重连后拿到新的快照；server 写一侧超过 10 秒写不出去，两边一起断开

## 12. 推送通知

server 首次启动时生成 VAPID 密钥对，存在数据库里。客户端订阅时说明要哪几类通知：「等我处理时」（审批、提问、计划、终端弹窗）和「一轮结束时」。

- **谁决定推送**：server 看不懂事件，由 daemon 在事件上传成功之后调用 `Notify`，只说明会话 ID 和类别。只对两分钟内发生的事件通知，重连后补传旧事件不会推送。server 因推送容量已满而拒绝的通知，以及连接中断、没等到 server 答复的通知，daemon 记着，在这两分钟内每轮同步再发一次，重连后也一样；server 明确拒绝的不再发
- **内容**：只有通用文案（「有会话在等你处理」），外加用于跳转的会话 ID，符合 scope 第 4 节「推送不含具体内容」。同一会话同一类别 15 秒内只推一次
- **客户端**：service worker 收到推送时，如果应用正开着并在前台，就不再弹通知；点通知打开对应会话。iPhone 上要先把网页添加到主屏幕才能订阅推送。推送服务返回 404 或 410 时，server 删掉这个订阅
  - 网页每次连接成功后按本机保存的推送偏好重新登记订阅，包括设备被移除后重新配对的情况；只在浏览器已有通知许可时恢复，不再次请求许可。
- **推送后端**：`SetPushTarget` 按类型登记推送目标，Web Push 和 FCM 并存，旧的 `SetPushSubscription` 留给网页。server 用 FCM HTTP v1 发送，服务账号文件由 `-fcm-service-account`（`RA_FCM_SERVICE_ACCOUNT`）指定，`deploy/deploy.sh` 发现本机有 `~/.config/remote-agent/fcm-service-account.json` 时把它复制到 server 的数据目录并设好；没配置就不发 FCM，`SetPushTarget` 返回未启用；FCM 说 token 失效时删除。没有可用的 GMS 时静默降级为 App 内查看，不做 UnifiedPush
- **Web Push 出站限制**：订阅端点必须使用公网 HTTPS 的 443 端口；每次连接解析 DNS，拒绝非公网地址并直接连接核验过的 IP，防止 DNS rebinding。请求不用环境代理，也不跟随重定向；失败日志不写可能含订阅凭据的 URL。
- **Android**：推送走 FCM，内容是 daemon 加密的密文，通知里可以直接审批，见 [android-client.md](android-client.md)
- **iOS**：原生 App 还没有推送，只能打开 App 查看；要用 APNs，做不做未定，见 [ios-client.md](ios-client.md#还不能做的)

## 13. daemon 设置与远程新建会话

daemon 的设置存在 `~/.remote-agent/settings.json`，客户端可以读取和修改：审批超时（30 秒到 hook 超时之前）、新项目默认的模型、effort 和审批模式（项目设置的初值，也是项目设置不适用时的回退）。未设置的项沿用启动参数或 Codex 自己的配置。

- **远程新建会话**：客户端指定机器、目录、第一句话，以及可选的模型、effort、审批模式；daemon 把它们换成 codex 的 `-m` 和 `-c` 参数，第一句话像普通消息一样排队，等 Codex 的输入框出现再发。会话的环境变量用 daemon 自己的，不用客户端的。目录由客户端通过 `ListDirectories` 逐级浏览选择，隐藏目录不列出
- **新会话的配置属于项目，用哪个 CLI 每次新建时选**：每个项目有一份项目设置，写明新会话用的机器，以及每个 CLI 各一套的模型、effort 和审批模式（Claude Code 还有上下文窗口），改动只影响之后新建的会话。理由：配置是项目的属性，放在输入框的「＋」里会和「这条消息带图片」混成一层；从最近一个会话隐式继承又让人看不出、也预测不到下一次会用什么。CLI 是例外：同一个目录里不同的任务常常适合不同的 CLI，放进项目设置的话每换一次都要进出设置，还顺带改掉了项目的默认值；所以新建输入框旁常驻一个 CLI 切换，项目只记住上次用的那个作为下次的默认。切换一直看得见，下一次会用什么仍然可以预测；每个 CLI 各存一套，来回切换不丢另一套的模型和审批。项目设置存在账户偏好里（第 8 节），用 `account-prefs` 加密，按项目路径匹配，所以换设备也一样，server 看不到内容
  - **目录不是设置**：项目就是按目录路径认的（第 8 节），换目录等于换项目，所以项目设置里只显示路径、不能改；要在别的目录开会话，从主页标题的范围菜单换项目或选「新项目…」
  - **初值**：新项目从所选机器的默认设置（daemon 设置，见下文）开始；还没保存过设置的已有项目，用列表顺序里最靠前的会话（未结束的优先，否则最近结束的，见[第 8 节](#会话列表排序)）的配置作初值，计划模式换成机器默认。第一次从项目里新建会话时把所用配置存为项目设置，之后只有用户改才会变；某个 CLI 在这个项目里还没用过时，它那一套从机器默认开始；记住的 CLI 随每次新建更新
  - **审批模式**：可选询问、自动和完全放行；计划只是一段临时状态，不作项目默认。选了完全放行，新建时不二次确认，见第 7 节
  - **不适用时**：所选机器离线，项目页提示并让用户选这次用的机器，不改项目设置；所选模型或 effort 在这台机器或这个 CLI 上没有，就用机器的默认值并提示；记住的 CLI 在这次的机器上没装，就用装了的那个并提示，不改记住的值
  - **界面**：项目页标题下一行写所选 CLI 和它那一套设置的摘要，点开或从 ⋯ 进入项目设置；新建输入框旁是 CLI 切换，这台机器只装了一个 CLI 时不出现；新建区和会话输入框共用单行起步的布局，两处的「＋」都只用来添加图片，本会话的模式、模型和上下文在会话导航栏的 ⋯ 菜单里。这样新建只需要写第一句话，要改设置有固定的地方
- **分叉会话**：从一个会话当前的对话另开一个会话，原会话不动（`ForkSession`，本地命令 `remote-agent fork <id>`）。用的是 CLI 自己的分叉（`codex fork <id>`、`claude --resume <id> --fork-session`），所以新会话的上下文由 CLI 负责，remote-agent 不拼接或重放对话
  - **新会话是什么**：同一台电脑、同一个目录、同一个 CLI，有自己的 remote-agent 会话 ID、tmux 会话和密钥；环境变量、参数和「最近一轮的模型、强度、审批模式」都按恢复会话的规则取自原会话（第 6、16 节）。标题沿用原会话自己起的标题或自动标题，之后各改各的。不需要第一句话，CLI 就绪后直接空闲
  - **什么时候能分叉**：原会话空闲或已结束，并且发过消息。运行中、启动中，或有审批、提问、计划、终端弹窗等着时拒绝：一轮中间的记录还没写完，分叉出来的历史会停在半截，两个 CLI 对半轮的处理也没有实测。运行中分叉要不要做未定，见 [plan.md](plan.md)
  - **历史靠复制事件**：daemon 把原会话的事件复制给新会话，再记一条 `SessionForked`（原会话 ID 和当时的标题），之后才是新会话自己的事件。不从 CLI 的记录重读，因为两个 CLI 的分叉记录都不能直接当历史用：Codex 的新 rollout 只引用父 rollout，不含之前的内容；Claude Code 要到分叉后发第一条消息才写新 transcript（[codex-notes §11](codex-notes.md#11-分叉)、[claude-code-notes §11](claude-code-notes.md#11-压缩恢复和分叉)）。复制让两个 CLI 走同一条路，分叉后立刻能看到历史，消息的来源设备也保留
  - **复制什么**：对话本身（消息、推理、工具调用、轮次、用量、设置变化、已处理的审批和提问）。原会话自己的进程和队列状态（`SessionState`、`InputState`）不复制，没人处理过的审批和提问也不复制，在新会话里它们已经没法回答；原会话退出时停在一轮中间的，复制到这里补一条「已中断」的轮次结束。复制和读取位置在同一把锁下取，原会话此后写进记录的内容归新会话去读
  - **Claude Code 的重复记录**：新 transcript 开头是原会话记录的副本，沿用原来的 `uuid`。分叉时 daemon 把原 transcript 已读部分的 `uuid` 存进新会话目录（`fork-copied`），读新 transcript 时跳过这些行，免得历史出现两遍；没有 `uuid` 的记录都是新会话自己的
  - **图片**：复制的事件保留内嵌预览，大图标为「只有预览」：显示版用原会话的密钥加密、存在原会话名下，传完后本地已经删掉，新会话拿不到；要看大图回原会话。不重新上传，也不让客户端跨会话取图
  - **结果不确定时**：分叉的回复没收到时，客户端留着这次请求，再点重发的是同一个请求（[第 10 节](#10-报文同步和指令)的「指令」），daemon 从日志里答出已经建好的会话，不会分叉出第二个；菜单关了再开也一样。请求过期后不再重发，菜单里那一项变成「放弃上次的分叉」，放弃之后再点才是新的一次
  - **推送**：复制的事件不触发推送（`Session.forked_seq` 以前的都跳过），否则刚结束的一轮会在分叉时再提醒一次
- **机器级指令**：新建会话、列模型、浏览目录、读写设置不属于某个会话，信封头里不带会话 ID；daemon 拒绝带了会话 ID 的机器级指令
- **移除设备**：客户端可以在 server 上删除一台设备：删掉它的登记、登录凭证和推送订阅，并断开全部主连接和终端连接；如果是机器，连同它的会话和事件密文一起删除，并断开它的连接。server 持久记录被移除的设备公钥标识，拒绝重放旧的签名注册请求恢复该设备。旧数据库升级时还会固定新注册的签名时间下限，拒绝用签名时间早于该下限的注册原文恢复已经丢失的设备记录；已登记设备的正常登录和原样重试不受影响。升级时已开始但未完成的配对需要重新发起，新设备的时钟必须晚于升级时间。这不是根密钥吊销：手里还有根密钥的设备仍可生成新的设备密钥重新登记。机器详情页底部提供「移除这台机器…」，先确认删除记录和断开连接的影响再执行；客户端详情保留独立的客户端移除入口。被移除的客户端靠登录被拒得知：server 不向没登录的人透露某个设备是否存在或被移除过，所以登录失败只有一种回答（`PermissionDenied`）；客户端的登录同时只发一个，被拒后换新的 challenge 再试一次（server 重启会丢掉内存里的 challenge），仍被拒就认定 server 不认识自己，停止重连，整屏提示「已被移出账户」，由用户选择删除本机密钥后重新加入，或再试一次。客户端不自动删除本机密钥：server 数据被重置时同样会走到这里，根密钥留着才能重新登记

### 工具执行反馈

过程不是用户关心的重点，客户端只用一行表示一次工具调用：运行中写命令和计时，失败写退出码，连续完成的折成「运行了 N 条命令」。不做工具详情页，不显示工具输出，也不提供跳转终端的入口：失败原因由 Agent 在回复里说明，想看过程的用户自己切到终端标签。这样客户端不需要解析和传输输出，也不会把不可靠的中间状态当成进度展示。daemon 上传事件时因此去掉工具输出，输入和标题相同时（shell 命令通常如此）也只留标题（`internal/relay/slim.go`）；本机的事件日志保持完整。实测这两项占已存事件字节的约 45%。

客户端收到 ToolStarted 后立即显示这一行，未完成的不能收进完成分组；等待审批和工具运行中分开显示。计时从 daemon 的事件时间算，各端同一起点，未知起点不猜；客户端断线时停住并写「等待同步」。Claude Code 按调用 ID 配对开始与结果；Codex 也按 `call_id` 配对，但这不代表能单独停止某个工具。转到后台的调用写「后台运行」，之后不追踪它是否结束；daemon 仍在 `ToolCall.background` 里标明来源（模型要求的、超时移到后台的、终端里按 Ctrl+B 的、一轮结束时仍在运行的），客户端不用从结果文字猜。中断只中断本轮，不保证终止后台命令（[codex-notes.md §8](codex-notes.md#8-中断和运行中的输入)）。

## 14. 适配 Codex 升级

remote-agent 依赖 Codex 的屏幕和 rollout，Codex 升级可能改变它们。做法是让变化尽量不破坏功能，破坏了要能看出来、能查出哪一项：

- **容忍写法变化**：画面按样式属性和文字判断（第 6 节）；菜单按标题和选项文字定位；rollout 里认不出的条目保留为通用工具调用，不报错
- **看得出来**：排队的消息发不出去时，daemon 在会话信息里给出原因（终端有草稿、有弹窗、认不出输入框）；认不出输入框超过 20 秒会记一条带 Codex 版本的警告，网页上提示可能是 Codex 升级改了界面
- **查得出来**：`remote-agent doctor` 用独立的 daemon、状态目录和 tmux，在 `~/.remote-agent/doctor-work` 里以 GPT-6-Luna 低档位真的跑一个会话，逐项检查：认出输入框、区分本地草稿、注入并读回回复、切模型、切审批模式和计划模式、中断、终端快照。失败时附上画面分析的结果（不含内容）
- **记录版本**：daemon 读 `codex --version` 放进机器元数据，可执行文件变了（CLI 升级）就重新读，不用重启 daemon；代码测试过的版本（`codex.TestedVersions`）和本机 doctor 通过的版本算「已验证」，否则启动日志和网页的机器详情里提示运行 doctor

## 16. 接入 Claude Code

Claude Code 和 Codex 走同一条路：原生 TUI 跑在 tmux 的 PTY 代理下，输出读 transcript，审批和轮次边界靠 hook，屏幕只用来判断状态。客户端能做的操作两者一致（第 7 节的 4 种审批模式就是按两者共有的定的）。具体做法依据 [claude-code-notes.md](claude-code-notes.md) 的实测，随实测补全。

- **会话属于哪个 CLI**：会话信息、新建会话、列模型都带 `Agent`；以前的会话没有这个字段，按 Codex 处理。机器元数据列出本机装了哪些 CLI 和版本，客户端只提供装了的
- **daemon 的分层**：会话生命周期、事件序号、持久化队列、控制锁、审批的竞争处理、同步和终端流是共用的；每个 CLI 各自实现三组接口（`internal/agent`）：启动和恢复（参数、版本、模型列表）、事件来源（绑定 transcript、增量解析、确认消息已提交）、终端控制（认输入框、注入、中断、回答提问、计划、切换设置）。屏幕、菜单、参数和 JSON 格式的知识只留在各自的包里（`internal/codex`、`internal/claude`）
- **环境变量**：和 Codex 共用 `~/.remote-agent/agent.env`（第 6 节），代理这类配置属于电脑，不属于某个 CLI
- **新建会话的默认值**：daemon 设置里 Codex 和 Claude Code 各有一套默认模型、推理强度和审批模式，作为新项目的初值；项目设置（第 13 节）里每个 CLI 的那一套各从对应的默认值开始
- **工具开始**：Claude Code 会并行调用工具，`ToolStarted` 带上调用 ID 配对，不按先后顺序

下面是 Claude Code 这一侧的具体做法，括号里的「notes §n」指 [claude-code-notes.md](claude-code-notes.md) 的第 n 节。

- **启动**：`remote-agent pty-host -- claude --settings <会话目录>/claude-settings.json --session-id <uuid> …`。settings 文件只放 remote-agent 的 hook（`SessionStart`、`PermissionRequest`，以及只匹配 AskUserQuestion 和 ExitPlanMode 的 `PreToolUse`），命令同样写成 `"$RA_EXE" hook claude`；它和用户自己的 hook 一起运行，不改 `~/.claude/settings.json`，也不需要信任（notes §1、§3）。会话 ID 由 daemon 生成，记作会话的 CLI 会话 ID
- **模型、推理强度、审批模式**：新建时换成 `--model`、`--effort`、`--permission-mode`；没指定就不传，沿用 Claude Code 自己的配置。「完全放行」对应 `bypassPermissions`：只有启动时就允许了 bypass 的会话能切过去（notes §5），daemon 按启动参数和 `~/.claude/settings.json` 的 `defaultMode` 判断，不可用时会话信息里标出来，客户端置灰。remote-agent 不替用户加 `--allow-dangerously-skip-permissions`
- **恢复会话**：transcript 已经存在时用 `--resume <id>`，否则（从没发过消息）仍用 `--session-id <id>`；沿用原来的参数（取多个值的选项保留全部的值，少一个就可能放宽限制），再用最近一轮的模型、推理强度和审批模式覆盖，同名选项先从原参数里去掉。Plan 模式下 Claude Code 临时换用的模型不算会话的模型，免得恢复后一直用它。bypass 是否可用按启动时记下的结果，不重新读可能已经改过的全局设置。恢复时 transcript 里的 `permission-mode` 记录是上次的模式（notes §2），所以当前模式以屏幕上的模式行为准。`--bare`、`--safe-mode` 会关掉 settings 里的 hook，不接受
- **启动弹窗**：信任目录的光标默认在 `No, exit`，回车就退出（notes §1），和 Codex 一样留给用户在终端里处理，客户端提示去终端
- **找到 transcript**：`SessionStart` hook 在信任目录后、第一条消息前就触发，带 `transcript_path`
- **解析 transcript**：带 `origin.kind: human` 的用户记录是新一轮的开始和用户消息，`task-notification` 的只开始一轮（后台工作结束后 Claude Code 自己回应）；`turn_duration` 是正常结束，`[Request interrupted by user…]` 是被中断，两者可能先后都有，只记第一个；`isMeta`、斜杠命令、压缩摘要都不算用户消息；运行中并入这一轮的消息（`queued_command` 附件）记为用户消息但不开新的一轮。`tool_use` 记为 `ToolStarted`（带调用 ID），`tool_result` 按调用 ID 配成 `ToolCall`；`thinking` 记为推理（终端里默认折叠，按 ctrl+o 能看到同样的内容）。`compact_boundary` 记为「上下文已压缩」。模型和推理强度取自 `assistant` 记录，以及 `/model` 的输出记录（notes §9）：在电脑终端里切的模型要到下一次回复才出现在 `assistant` 记录里，Plan 模式下的回复又不算数，只看回复会把已经换掉的模型当成当前的，进而判错 auto 是否可用。输出里的显示名换成别名（`Sonnet 5.5` 记作 `sonnet`），和经 remote-agent 切换时记的一样；不属于这几个别名的保留原名。上下文占用由 `usage` 算出，窗口大小按模型推断（notes §2）
- **输入**：和 Codex 相同的排队、暂存本地按键、bracketed paste。输入框的判断按 Claude Code 的画法：两条横线之间只有一行，`❯` 后面没有普通样式的字（光标是反色的一格，占位提示是淡色）才算空（notes §4）。运行中也可以注入，Claude Code 会把它排进当前这一轮；以 transcript 里出现这条用户消息或 `queue-operation` 的 `enqueue` 记录为已提交
- **计划框和菜单的折行**：窄屏时标题和选项会折行，识别时把相邻两行连起来看，选项的续行并入选项。`/model` 菜单末行的提示和切换成功的那句话同样会折行（notes §9），都去掉折行再比，否则模型已经切了却报失败
- **本地先答审批**：除了看到的权限框消失、这一轮结束，这个请求的工具调用完成也算，覆盖状态检测还没看到框就已经在终端答了的情况。调用和请求按完整输入的摘要对应（审批事件和工具调用都带这个摘要，客户端直接比较，不自己算）；几个请求输入完全相同时，一次完成收回其中最早的一个。审批请求一律出卡片，daemon 不预判「调用已经执行过」：
  - **限制**：在终端里答得太快、调用在审批请求登记到 daemon 之前就执行完了，这张卡片不会因为这次完成而收回，要等这一轮结束才收回；在这期间点它不起作用，因为 Claude Code 已经不等这个 hook 的答复了。曾经尝试用「最近完成的调用」提前跳过这类请求，连续几轮都引出了会静默跳过真实审批的竞争，所以放弃：宁可多一张过时的卡片，也不能漏掉一次审批
- **中断**：只在运行中发 Esc
- **模型提问**：让原生选择框照常出现。问题由 `PreToolUse` hook 报给 daemon（hook 立即返回、不表态），因为 transcript 可能要等回答之后才写入这次调用（notes §2）；transcript 里随后出现的同一调用不再重复。回答时暂存本地按键、确认屏幕上是这个问题（窄屏折行的问题去掉折行再比，认不出或认出多个就报错，不猜），再按选项编号，出现提交页就按 1。屏幕上已经是提交页（在终端里答完、还没提交）时不按任何键，报「问题不在屏幕上」：提交页也列着问题原文，但那里的 1 是提交终端里选的答案，2 是取消整次提问。多选时数字键是切换勾选，所以先读当前的勾选状态，只按和答案不一致的，再按 →。以 transcript 的 `tool_result` 为准，本地先答了就收回卡片。**不用阻塞 `PreToolUse` hook 回答**：那样虽然能直接把答案交给模型，但 hook 等待期间电脑终端里看不到问题，违背「电脑和手机操作同一个会话」（notes §7 两条路的实测对比）
- **计划**：`ExitPlanMode` 同样由 `PreToolUse` hook 报来，记为 `PlanProposed`，屏幕上的计划框让会话处于「计划待批准」。批准（`IMPLEMENT`）按「Yes, manually approve edits」那一项，执行后回到 manual；继续规划（`KEEP_PLANNING`）按 Esc，留在 Plan 模式；Claude Code 没有「清空上下文再执行」，这一项返回不支持。hook 批准计划不起作用（notes §8）
- **当前审批模式**：以屏幕上的模式行为准。在电脑终端里用 Shift+Tab 切的，daemon 从屏幕看到后记一条 `TurnContext`（`permission_mode`），不用等下一条消息；会话信息的 `mode` 按第 7 节的对应关系给出，accept edits 这类没有对应的给 UNSPECIFIED，原名在 `permission_mode` 里
- **切换审批模式**：空闲时切到 Plan 用 `/plan`，直接到达。其余用 Shift+Tab 在模式行上一格一格地走到目标模式，每按一次都读模式行确认；转一圈都没遇到目标就报错并回到原来的模式。按放行的范围，模式从严到宽是 plan、manual、accept edits、auto、bypass。运行中也能切（notes §5），但途中（以及目标不可用时回来的路上）只要有一个模式比目标宽，就不切，免得那一瞬间放行了工具调用。是否运行中在拿到终端控制之后才判断（切模型、压缩同样如此）：之前拿着控制的注入可能刚开始了一轮，所以要重新读 transcript，并把「已写入还没确认的消息」和屏幕上的忙碌迹象（输入框上方的转圈行、变暗的提示符，notes §4）也算作运行中。
  - **空闲时途经更宽的模式**（主要是从 Plan 模式切出：Shift+Tab 只能单向走，也没有离开 Plan 模式的命令，notes §5）：
    - **做法**：屏幕上有后台工作（模式行的 `· 1 shell`、输入框上方的 `Waiting for N background agent`、模式行下的后台子代理列表，notes §10）时不切，告诉用户原因；否则先算出整条路径，把要按的 Shift+Tab 一次写完，中间不读屏幕，最后核对模式行。
    - **哪些模式可用**：算路径要知道 bypass 和 auto 可不可用：bypass 按会话启动时记下的能力（`full_access_unavailable`）；auto 按模型（Haiku 4.5 及更早的没有；其余 Claude 模型有：sonnet、Haiku 5.5 实测，opus、fable 推测；只知道别名 `haiku` 时算未知，因为它指 4.5 还是 5.5 随 Claude Code 版本变，notes §5），或这个会话用同一模型时屏幕上出现过 auto；未知的按可能可用处理，运行中不走会经过它的路；状态栏的 `auto mode unavailable for this model` 不作依据，它在换到有 auto 的模型之后还会留一阵（notes §5）。已知不可用的目标直接报错，不按键。
    - **唯一的例外**是 auto 可不可用算不出来（还不知道会话的模型、屏幕也没提示）：这时按「不可用」计数，只会少按、不会多按；如果因此停在 auto 上（比目标宽），立即把差的键补上，这是第二次写入。目标实际不可用时回到原来的模式
  - **为什么这样取舍**：一律拒绝的话，bypass 或 auto 可用的会话（本机默认就是）就没法从远程离开 Plan 模式。空闲时这一轮没有工具调用；可能在这一瞬间调用工具的只有后台工作，看得到就拒绝
  - **残余风险**：连按期间 Claude Code 依次经过的宽松模式仍会存在几十毫秒（按键和界面刷新的时间，未精确测量）；屏幕上看不出来的后台工作（比如列表被挤出屏幕、Claude Code 改了提示的写法）挡不住；后台工作在检查之后、连按之前的一瞬间启动也挡不住
- **切换模型和推理强度**：空闲时 `/model`，用方向键移到模型那一行、←/→ 调推理强度，按 `s` 只改当前会话。菜单有两种列法（notes §9）：每个别名一行时就是那一行；按版本列、后面还跟着旧版本时，别名指的是同名里版本号最高的那一行，版本号分不出高低（相同，或名字后面不只是版本号）就报错不选，不能把最后一个同名的旧版本当成这个别名。弹出 `Switch model?` 时按它的「Yes, switch to」那一项，只在菜单已经消失、确认框和这一项都在时才按，免得把数字按进菜单改掉默认模型。以对话里出现 `Set model to … for this session only` 为成功。数字键和回车会改全局默认值，不用（notes §9）。
  - **可选的模型**：可选的模型是 Claude Code 的别名（opus、fable、sonnet、haiku），列表写在代码里；会话信息里的模型是完整的模型 ID。
  - **上下文窗口**是项目设置里独立的一项（`ProjectSettings.standard_context`，新建时随 `CreateSessionRequest.standard_context` 交给 daemon），只对 Claude Code 有意义，默认 1M：这是 Claude Code 自己的默认值，所以没设置过的项目行为不变，用默认模型时也能选。
  - **选标准时**：选标准时 daemon 在会话环境里加 `CLAUDE_CODE_DISABLE_1M_CONTEXT=1`，固定为 200k（notes §2）；环境随会话保存，恢复时不变，会话信息里的窗口也按 200k 报告。
  - **选 1M 时**：选 1M 且模型是有 1M 窗口的别名时，daemon 把它写成 `opus[1m]` 交给 `--model`，窗口本来就是 1M，这样做只是让终端标题写出 `(1M context)`；没指定模型时不改参数。
  - **为什么不编码进模型名**：不把窗口编码进模型名：那样默认模型下没法选，也会让已有项目的含义悄悄改变。窗口在启动时就定了，会话里切换模型不涉及它。
  - **模型列表**：模型列表带每个模型最大的上下文窗口（`ModelInfo.context_window`），客户端据此判断模型有没有 1M 可选（Haiku 没有）；Codex 不填，因为 `models_cache.json` 里的窗口和会话实际报告的不一致（codex-notes §1），它的实际窗口在会话的上下文占用里看
- **压缩**：空闲时 `/compact`，以屏幕出现 `Compacting conversation` 或 transcript 出现 `compact_boundary` 为开始
- **额度**：从状态栏命令的输入采集，见下节

### 账户额度

设备页提供额度详情，按这台机器上安装的 CLI 分组，显示 CLI 登录账户的用量；它与会话上下文占用、累计 token、remote-agent 的图片存储配额分别展示。不同 CLI 不相加，不按模型或会话切分账户额度；不同机器也不凭套餐名推断为同一个账户。界面见 [client-v38 · 账户额度](design/client-v41.html#quota)。

Codex 继续用 rollout 的额度字段（[codex-notes §1](codex-notes.md#1-数据从哪读)）。Claude Code 的 transcript 没有账户额度，额度只在状态栏命令的输入里（[claude-code-notes §2](claude-code-notes.md#2-transcript)）。

- **采集**：daemon 在会话的 `--settings` 里把状态栏设成 `"$RA_EXE" statusline claude`（不改用户的设置文件）：它把输入转给 daemon（500 毫秒超时，失败也不影响状态栏），再用同样的输入运行用户原来的状态栏命令（启动会话时按 Claude Code 的优先级读出、存在会话目录里），输出和退出码原样交回，`padding`、`refreshInterval` 也照搬，所以终端里看到的状态栏不变。
- **读不到时**：托管设置里定了状态栏时它会盖过 daemon 的，额度就读不到，报「不支持」。
- **区分账户**：账户用 `~/.claude.json` 里 `oauthAccount` 的账户和组织 ID 算一个短指纹来区分（ID 本身不离开电脑），套餐取 `organizationType`，有 `oauthAccount` 才标为订阅登录；读不出账户时不合并，按来源会话分开。
- **保存**：额度按账户存在 `~/.remote-agent/quota.json`，重启后只沿用当前登录账户的记录，看到新账户的数字就清掉旧账户的。数字不变时一分钟内不刷新记录时间，免得机器元数据频繁变化。
- **上报**：结果放在 `MachineMeta.quotas`，每个 CLI 一项或几项，状态分等待（还没收到额度）、正常、失败和不支持。
- **边界**：采集只读取 CLI 已有数据，不主动给模型发消息，不把登录凭据交给 server，不调用未公开的账户接口。额度元数据端到端加密同步，server 只收密文，日志不记录额度或账户内容。

客户端按来源提供的窗口显示已用百分比、重置时间和最近收到时间。重置时间写两部分：还有多久（一天以上写到小时，一天以内写到分，按客户端时钟算）和重置的时刻（当天写「今天 14:10」，其他日子写出日期和星期，如「10月8日 周四 14:10」）。只写星期分不清是哪一天，只写时刻又要自己算还剩多久。时刻统一转换为北京时间（`Asia/Shanghai`，UTC+8），日期和星期也按北京时间判断，最近收到时间也一样，页面底部说明一次「时间按北京时间显示」。Claude Code 的 5 小时、7 天分别可缺失；只有真实收到其他限额窗口时才显示该窗口，不承诺按模型额度或额外用量。套餐名未知就省略，读到的内部代号换成名称显示（`prolite` 写 Pro Lite，`claude_max` 写 Max）；API 计费须由可靠的登录方式信息确认，不能从 `rate_limits` 缺失推断。API 用量和账单到服务商控制台查看，不把会话估算费用当成账户余额。

- 有效数据：80% 起橙色提示，100% 标「已用尽」；不自动切换 CLI 或模型，不拦截发送。缺重置时间只省略时间，缺用量则标「未获取」，不补成 0%。
- 尚未收到任何额度：显示「暂未获取额度」。明确不支持读取时显示「暂不支持读取额度」。单个窗口缺失不清空其他有效窗口；账户没有的窗口（CLI 根本没上报）不显示，不占一行「未获取」。「最近收到」的时间每个 CLI 只写一次。
- 机器离线、重置时间已过或来源确认数据陈旧：旧数值标「上次记录」，显示时间与原因，条形变灰。重置时间过了只标「等待更新」，不自行归零；客户端时间用于展示，不作为 CLI 已恢复可用的证明。
- 读取失败：说明失败并保留带时间的上次记录；「重新读取」只重读本机已采集数据，不能保证向服务商刷新，机器离线时置灰。额度页不提供跳转终端的入口，不支持读取时只提示可在本机 CLI 里查看 `/usage`。
- 确认换登录账户后清掉旧账户快照；无法可靠识别账户变更时不复用持久化缓存，显示未获取。多会话的账户额度不累加，只有能确认同一账户的数据才能合并，取最新的：Codex 按 rollout 里的上报时间；Claude Code 的状态栏输入不带时间，空闲会话会一直重复它上一次回复时的数字，所以逐个窗口比较，重置时间晚的算新，重置时间相同时取已用比例高的（一个窗口内用量只增不减），落后的上报不覆盖记录、也不刷新「最近收到」；状态栏输入也不带账户，所以换登录账户后，某个会话原样重复它在旧账户下报过的数字时不算新账户的（那是它上一次回复时旧账户的额度），等它的数字变了才计入；未知账户归属时保留来源会话区分。

## 18. 定时任务

定时任务属于 Remote Agent，由所属电脑的 daemon 保存和执行，不依赖 Codex 或 Claude Code 的内部调度。任务内容、目标目录和执行消息不以明文交给 server；远程管理复用加密的机器指令。任务模型由 `internal/schedule` 维护，本地 CLI、MCP 和协议接口共用；客户端界面尚未实现，见 [plan.md](plan.md)。

### 托管会话的工具入口

每次新建和恢复托管会话时，增加名为 `remote_agent` 的本地 stdio MCP，命令为本机二进制的 `mcp` 子命令，并绑定 Remote Agent 会话 ID。Codex 使用单次 `-c` 配置覆盖，Claude Code 使用会话目录中的私有 MCP 配置；Claude 的显式 `--mcp-config` 来源合并到该文件，用户其他 MCP 保留。不修改全局配置、项目配置、AGENTS.md 或 CLAUDE.md，不注入会话指令、system prompt 或 skill；能力由 MCP 工具描述和参数 schema 提供。

Claude Code 托管进程设置 `CLAUDE_CODE_DISABLE_CRON=1`，关闭其会话内 cron 和 `/loop`；新建和恢复都应用，不改变普通启动的 CLI、桌面端或云端任务。Codex 未配置未经验证的内置调度禁用开关。外部 CLI 的版本支持和实测边界分别见 [codex-notes.md](codex-notes.md) 与 [claude-code-notes.md](claude-code-notes.md)。MCP 与 CLI 都连接私有本地 daemon socket；会话 ID 是上下文标识，不是独立授权凭据，同一操作系统用户属于本机信任域。

模型通过 MCP 获得的是受限委托：只管理本会话创建的任务，只恢复本会话；新会话限同项目、同 CLI 和相同的完整标准审批配置。Plan、未知或自定义权限不能通过该入口创建执行任务，不能把只读沙箱按界面的「询问」标签扩大为可写沙箱。创建、修改、手动执行和延迟派发都校验限制；来源权限改变后旧任务暂停，由用户 CLI 或远程客户端确认后接管：新会话的任务按目标里写的权限比对；恢复本会话的任务按创建时记在任务上的权限（`scoped_mode`）比对，没有这项记录的同样暂停。用户 CLI 和加密远程客户端仍拥有机器级任务管理能力。这约束模型的 MCP 工具，不提供同一操作系统用户之间的进程隔离。

MCP 每次操作先确认 daemon 支持受限委托；不支持时拒绝工具调用。新 daemon 也拒绝旧 MCP 的无委托标记会话请求，明确的用户 CLI 调用使用独立入口标记。升级需要更新二进制并重启 daemon、重新连接会话内的 MCP 进程；升级前模型创建的未完成任务暂停，由用户 CLI 或远程客户端确认后接管。

### 触发与执行

支持一次性带时区的绝对时间、固定经过时长的周期，以及当前轮结束后的延迟。固定间隔不承诺每日当地时间或夏令时语义。`after_turn` 在登记时绑定具体轮次；已经空闲或退出时从登记时计时，审批和提问不会结束这一轮。绑定轮次被中断或未经正常结束就退出时暂停，用户明确恢复后才重新安排。重复的延迟任务从每次执行结束后再计时，同一任务不重叠、不累计排队遗漏周期；可限制执行次数。

执行目标可恢复原会话，或在指定项目新开对话。恢复保持原 Remote Agent ID、CLI 对话 ID、环境及原有恢复规则；新开对话从来源会话取项目、CLI 和可继承的配置，换 CLI 时不继承另一 CLI 的模型与 effort。新会话不能直接以 Plan 模式启动；来源模式未知或非标准时，用户需明确指定启动模式。创建时已有明确配置的字段固定在任务中，留空且无法继承的字段使用执行时 daemon/CLI 默认值。

执行消息进入现有 queue 模式，等待当前轮结束，不覆盖本地草稿、绕过弹窗或改变审批权限。任务暂停和取消只停止未来调度，不中断或撤回已经交给会话队列的消息；使用现有取消输入、中断和恢复输入操作处理当前执行。轮次正常结束只表示该次执行结束，不代表消息中的业务目标成功。

### 持久化与恢复

任务及最近 100 次执行记录保存在本机私有 `schedules.json`，原子替换并落盘。创建支持稳定请求键，修改支持修订检查；受损或未知版本的文件会使 daemon 启动失败，不静默丢弃任务。

dispatching 状态在新建/恢复会话和注入消息之前保存。daemon 在该边界退出时恢复为“无法确认”，不自动重试；已持久化的 queued/running 执行则通过原会话的队列、请求 ID 和事件游标继续跟踪，不重复发送。消息提交无法确认、执行失败或中断时停止自动续跑。其中「无法确认」的那次执行，事后被 CLI 的记录确认了（第 6 节「迟到的记录仍然算数」），就接着跟到这一轮结束、照常续跑，不重发；等不到记录就一直停在不确定。这期间暂停任务不影响接回，任务保持暂停；恢复、立即运行、改定义或取消则表示放下那次执行，之后不再接回（操作前会先看一眼记录是否已到）。daemon 只在内存里记着哪次执行在等，重启后不再接回。

电脑和 daemon 需要运行，客户端无需在线；relay 断线不阻止本地调度，原有审批和消息同步机制仍有效。休眠或停机后默认只补最近一次、期限为 24 小时，可调整期限；超过期限记录跳过，周期任务转到下一次。绝对时间支持十年内的时间，间隔以秒计。当前加密接口提供查询和管理，客户端离线任务缓存、变更订阅与界面后续实现。
