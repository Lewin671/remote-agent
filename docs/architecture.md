## 1. 各端与部署

```
 手机 / 平板 / 浏览器              VPS（海外）                         每台电脑
 ────────────────────             ───────────                         ────────
 PWA / Android App                 Caddy（HTTPS）                      remote-agent（Go）
   │  网页来自 Cloudflare Pages      └─ remote-agent-server（Go）        ├─ daemon
   │  App 侧载安装                      SQLite                          ├─ 本地 CLI 命令
   │                                                                    └─ hook 入口
   └──────── HTTPS / WSS ────────▶ api.<域名> ◀──────── HTTPS / WSS ─────┘
                                                                     tmux ─ codex
```

| 端 | 形态 | 部署 |
|---|---|---|
| `remote-agent` | Go 单二进制：daemon、本地 CLI（`remote-agent codex` 等）和 hook 入口都在里面 | 每台电脑一个 |
| `remote-agent-server` | Go 单二进制，SQLite 存储，不直接对外暴露端口 | VPS 上，前面由 Caddy 负责 HTTPS 和反向代理，域名为 `api.<域名>`（当前部署在 `ra.remote-agent.top`，见下文） |
| `web` | PWA，React + Vite + TypeScript | Cloudflare Pages，和 server 在同一个注册域名下（当前在 `remote-agent.top`，见下文） |
| `android` | 原生 App，Kotlin + Jetpack Compose，见 [android-client.md](android-client.md) | 自己签名的 APK，侧载安装 |
| `ios` | 原生 App，Swift + SwiftUI，见 [ios-client.md](ios-client.md) | 装到真机的渠道未定（[plan.md](plan.md)），目前只在模拟器上运行 |

当前的 VPS 上有一个多个服务共用的 Caddy（docker compose 项目 `/opt/caddy`，占用 80/443），server 因此也用容器部署：接入 Caddy 所在的 docker 网络 `proxy`，不映射主机端口，Caddyfile 里只加一个站点块反代过去。它是公共中继：服务器上的 `.env`（不在仓库里）设 `RA_SIGNUP=open`，`RA_TRUSTED_PROXIES` 设成 `proxy` 网络的地址段，让 server 按 Caddy 报告的真实地址限流。镜像基于 `scratch`，以 nobody 运行，根文件系统只读（SQLite 的临时文件写在 64 MiB 的 tmpfs `/tmp`），内存上限 256 MiB，健康检查由二进制自己的 `healthcheck` 子命令请求 `/healthz`。`scratch` 里没有 CA 根证书，而 Web Push 和 FCM 都要访问 HTTPS，所以 server 二进制带上了 Go 的 `x509roots/fallback`（Mozilla 的根证书），系统里没有根证书时使用它。部署文件和脚本在 `deploy/`。

网页部署在 Cloudflare Pages 的项目 `remote-agent` 上（`remote-agent.pages.dev`），绑定根域名 `remote-agent.top`。Pages 绑定根域名要求域名的 DNS 托管在 Cloudflare，所以 `remote-agent.top` 的 NS 指向 Cloudflare：根域名由 Pages 自动解析，`ra` 是指向 VPS 的 A 记录，只做 DNS、不经 Cloudflare 代理（Caddy 自己签证书，WebSocket 直连）。绑子域名时 Pages 也接受外部 DNS 用 CNAME 接入，那样域名不用迁。新版 wrangler 默认把 `pages project create` 转成 Workers，所以创建项目时要加 `--force`，之后的部署不用。构建时会生成 `_headers`，让 Pages 在响应头里带上和页面里一致的 CSP，外加 `frame-ancestors 'none'` 等只能靠响应头生效的限制。server 的 `ALLOWED_ORIGINS` 要包含网页的地址。

网页代码**不由 VPS 提供**：如果 VPS 被攻破后能替换网页的 JS，端到端加密就会被绕过。放在另一个平台上，攻击者必须同时攻破两处才行。Cloudflare 账号因此也成了关键资产，必须开启两步验证。

代码放在同一个仓库：一个 Go module，外加 `web/`、`android/` 和 `ios/` 三个目录。

### 产品版本与发布

各端使用根目录 `version.properties` 中的同一个产品版本，Android 的 `androidVersionCode` 每次发布递增。正式 tag 为 `vMAJOR.MINOR.PATCH`，与文件严格一致；daemon/server 的 `--version`、网页和 App 设置页显示产品版本和源提交。协议版本独立，不随产品版本自动增长；产品版本不同不是拒绝连接的理由，协议版本不同才是（见第 4 节的「版本」）。

Go 构建要求至少 1.26.10，发布流水线用 `govulncheck` 检查代码可达的已知漏洞。

发布按开发任务完成触发，不按时间触发：agent 完成一项功能或相关修复并验收后，按 [AGENTS.md](../AGENTS.md) 自动更新版本、推送 tag，无需逐次确认。新功能升 minor，修复升 patch，1.0 以前的不兼容改动升 minor，1.0 起升 major。纯文档、界面稿和测试改动不发版。GitHub 的 `Release` 流水线从 tag 运行 Go、网页、Android 检查，全部通过才发布：正式签名 APK，daemon（macOS 和 Linux 的 arm64、amd64）和 server（Linux 的 arm64、amd64）的压缩包，网页包，以及覆盖全部文件的 `SHA256SUMS`。源提交写在私有 Release 的说明中，各端仍统一版本。我们自己的部署由 `scripts/ship.sh` 从 tag 的源码构建上线（server、Cloudflare Pages 上的网页和本机 daemon），这些压缩包是给别人部署用的，见下文「公开发布」。已发布 tag 和附件不覆盖；暂时失败允许重跑，代码修复使用新版本。

正式 APK 缺少固定签名或 Firebase 客户端配置就停止发布，不退回 debug 签名。GitHub Secrets 的 `ANDROID_SIGNING` 保存签名 keystore 与签名参数，`ANDROID_GOOGLE_SERVICES` 保存客户端配置；FCM 服务账户和账户加密密钥不进入构建流水线。签名密钥必须另有本地备份。手动 `Build development APK` 生成独立 `.dev` 应用，与正式版数据分开，使用固定签名以便后续覆盖升级，推送关闭，产物保留 3 天。

**公开发布**：源码仓库 `Lewin671/remote-agent` 是公开的（2026-10-17 起；之前源码私有，产物另发到 `Lewin671/remote-agent-releases`，那个仓库已归档，只留着让旧安装升级过来）。每一版的全部文件和一份清单 `latest.properties`（版本、versionCode、协议版本、APK 文件名、SHA-256、大小、发布说明）就发布成本仓库的 Release，标为最新的那个有两个用途：App 和 daemon 读它的清单、按版本号下载（[android-client · 更新](android-client.md#更新)、[daemon 更新](#daemon-更新)）；别人照根目录的 README 和 [self-hosting.md](self-hosting.md) 部署自己的中继、网页和 daemon。安装脚本 `install.sh` 和自部署说明直接从 `main` 读取，改了不用发版。

给别人用的产物不带我们自己的部署：`scripts/build-dist.sh` 构建网页时不设默认中继（我们自己的网页由 `pnpm run deploy` 另行构建，带默认中继）；server 的压缩包里是 `deploy/self-host/` 的模板（自带 Caddy），不是 `deploy/` 里接入我们那台共用 Caddy 的那份；Go 构建关掉了自动嵌入的仓库信息，压缩包的文件头不记打包者。`scripts/public_scan.py` 把关，查到就失败、不发布，有三层：按名单查域名、主机名、邮箱、设备号、私钥和填了值的 setup token（指向我们自己的条目放在 Secret `RA_PUBLIC_DENY` 和本机 `~/.config/remote-agent/public-deny`，不在公开的源码里；读不到就不发布，命中时只报序号），压缩包和 APK 逐个成员查；按文件名拒绝部署的配置和状态（`.env`、数据库、密钥、日志、sourcemap）和链接，不看内容；打包时（`--release`）要求这一版的文件和每个压缩包的成员正好是预期的那些，多一个少一个都不行。它在打包（`package-release.sh`）和发布（`publish-public.sh`）时各运行一遍。名单挡不住没见过的标识，所以新增公开内容时仍要人看一遍。

别人的部署有两处和我们的不一样，公开文档里写明：正式 APK 绑定我们的 Firebase 项目，别人的 server 发不了 FCM，App 在他们那里没有推送（网页的 Web Push 不受影响）；网页由他们自己托管。

`Release` 工作流用自己的 `GITHUB_TOKEN` 发布，不需要别的令牌。`publish-public.sh` 先扫描产物和 tag 的公开说明，核对完整文件集合、`SHA256SUMS` 和 APK 清单；先建草稿，上传完再下载所有附件逐个核对，全部一致才公开。草稿可重试；已公开版本只核对，不改附件或说明，内容不同就失败。旧 tag 重试不会把较新版本挤下「最新」。

发布失败时，手动运行 `Release` 并填入 tag 重跑。产物和 tag 校验使用 tagged checkout，发布工具和隐私扫描使用本次工作流所在的提交，因此修复工具后可重试旧版本；网页包的成员名单取自该 tag 的 `web/public`。需要修复产品代码时仍发新版本；不填 tag 则跑全端检查和打包演练，不公开任何版本。Release 的说明只用 tag 中面向用户的变化和升级要求，不带提交日志或部署信息。

Release 不自动部署 VPS/Cloudflare：我们自己的部署在 Release 工作流成功后由本机的 `scripts/ship.sh` 一次上线，从 tag 的干净 checkout 构建并嵌入版本和源提交，按 server（代码有变才部署）、网页、本机 daemon 的顺序逐个部署并核对线上版本，不从 Release 晋级产物，也不需要在 GitHub 存服务器或 Cloudflare 的凭据。别人的 daemon 可由本机用户显式开启兼容版本自动更新；App 的更新也要在手机上点一下，再由系统确认安装。各端不保证跨版本互通：协议版本变了就要一起升级，数据格式变了要手动迁移或重建，这些升级要求写在发布说明中。

### daemon 更新

`remote-agent update check` 检查最新正式版；`update`（可加 `--version X.Y.Z`）安装比磁盘当前版本新的兼容版；`update status` 显示运行版本、空闲状态、自动更新设置和最近结果。首次使用需通过公开 Release 安装器升级到带更新命令的版本。源码构建带 `source` 渠道，只有 `build-dist.sh` 产出的 `release` 渠道允许自更新，避免覆盖开发者安装。

自动更新默认关闭，每台机器单独用 `update auto enable --time 04:00` 开启、`update auto disable` 关闭。macOS 使用独立 LaunchAgent（本地日历时间，登录时也检查，睡眠错过的日历触发在唤醒后合并执行）；Linux 使用独立 systemd user oneshot 和带 `Persistent=true` 的 timer，随机延后最多 10 分钟。Linux 的用户服务需保持用户 manager 运行，和 daemon 自身的服务前提相同。定时器触发独立保留的 `remote-agent.updater` 副本（每次更新前刷新为当前已验证的安装），它在无残留事务时读取磁盘当前版本，避免副本版本落后阻止后续更新；新主程序无法执行时仍可恢复事务。定时器仅触发这个本地 CLI 更新进程，不改 daemon 的 unit 或安装时的 PATH，也不在 daemon 进程里更新自己。

更新清单复用每个 tag 的 `latest.properties`，附件名由版本和平台推导；每平台大小与 SHA-256 来自已校验的 `SHA256SUMS`，公开发布时再次核对附件和清单。清单与下载通过 HTTPS，附件重定向不得降到 HTTP。信任根是官方 GitHub 发布账户与 TLS；SHA-256 校验传输和文件一致性，不是独立的发布签名。只取正式版，不降级；先确定最新版本，再从固定 tag 获取清单和附件。最新版本不兼容时记录阻止原因，不自动寻找更旧版本。

协议版本和 daemon 全部持久数据的存储代数必须与当前安装相同，并且该版明确允许自动安装；缺字段、未知格式、需人工迁移的版本均拒绝，手动 `update` 也不绕过。破坏性升级仍按发布说明使用安装器、协调客户端与会话内 MCP 重连。中继只转发密文，不核对这个协议号，临时断网不作为回滚条件。

存储代数及该版自动安装许可由 `internal/updater/policy.json` 同时提供给编译产物和发布流程。任何 daemon/本机 CLI 写入的持久格式（账户、设置、定时任务、会话及输入队列、图片等）不再能被上一版安全读取时，必须递增代数并将自动安装许可关闭，在发布说明写明人工处理。入口在读写前核对状态目录的 `state-generation`；第 1 代允许为已有安装补上标记，之后拒绝不同代数或未标记的旧数据，不迁移、不改写未知数据。标记只能防止明确的代数不匹配，不能替代开发者对存储格式变化的审查。

第一版只更新标准后台服务正在管理的安装；未安装服务、已停服务、服务路径不同、运行 PID 与服务 PID 不同均拒绝。daemon 在恢复会话成功后，才在 owner-only Unix socket 提供独立于协议 interceptor 的健康接口及空闲判断。它观察运行中回合、菜单操作、审批、问题、计划、输入队列和 held、未确认输入、未匹配输入、启动中的会话、待完成图片上传和定时任务；连续观察空闲至少 30 秒才允许尝试，下载完立即再次核对。忙时推迟到下次触发，不中断任务；这仍是重启前的观测，不能保证本地原生 CLI 在最后检查之后不会开始工作。tmux/PTY host 不被 updater 停止，远程连接短暂重连。

更新进程按安装路径持有排他锁，校验下载及压缩包固定成员，验证候选程序报告的版本、渠道、协议和代数后，将旧二进制备份、事务日志和目录同步落盘，再原子替换并重启服务。新版本和服务 PID 必须一致且稳定至少 5 秒；失败恢复旧二进制并重启。目录里保留 `remote-agent.previous` 一份上一版供人工恢复；依赖声明更新到状态目录的 `THIRD_PARTY_NOTICES.txt`。不改会话数据、账户或 tmux server。

中断后的下一次 `update` 先处理残留事务，再访问发布源：确认新版本健康则提交，否则回滚。自动恢复累计三次仍失败就停止并要求人工重试；已回滚的同一目标版不再自动安装，用户可运行一次手动 `update` 重试。自动更新未开启时，可手动用 `remote-agent.updater update --helper-for /绝对路径/remote-agent` 触发同样的恢复入口；该参数只允许从目标旁的更新器副本调用。最近结果和失败原因保存在状态目录，`update status` 可查；LaunchAgent 输出在 `update.log`，Linux 输出在 user journal。自动更新开关不会由安装器或 Release 默认打开。


## 2. 报文分层

所有跨网络的消息都分两层，类似信封和信纸：

- **外层（信封）**：发给谁、哪个会话、序号、鉴权。server 靠它来转发和存储，**server 能读**。
- **内层（内容）**：消息、工具调用、审批、终端数据、指令。先用 Protobuf 编码，再加密，**只有客户端和 daemon 能读**。

以手机发一条消息、Codex 回复为例：

```
 手机（PWA）                    server（VPS）                 电脑（daemon）                  Codex（tmux 里）
 ───────────                    ─────────────                 ──────────────                  ────────────────

 ① 用户输入
   "帮我修一下这个 bug"
        │
   [生成内层] 写成内层消息
   [加密]     内层 → 密文
   [生成外层] 装进信封：
     发给 机器A / 会话123
        │
        └──── 外层 ─────────▶ [读外层] 看收件人
                               存密文，转发给机器A
                               （内层打不开）
                                     │
                                     └──── 外层 ─────────▶ [读外层] 找到会话123
                                                           [解密]  密文 → 内层
                                                           [读内层] 拿到文字
                                                                 │
                                                                 └─ tmux 粘贴 + 回车 ─▶ ② Codex 开始干活
                                                                                             │
                                                                                        写 rollout 文件
                                                                                             │
                                                           [读 rollout] ◀────────────────────┘
                                                           [生成内层] "已修改 main.go …"
                                                           [加密]     内层 → 密文
                                                           [生成外层] 装进信封：
                                                             来自 机器A / 会话123，序号 42
                                                                 │
                               [读外层] 存下序号42 ◀──── 外层 ────┘
                               推给所有在线客户端
                                     │
 [读外层] 会话123 有新消息 ◀─ 外层 ──┘
 [解密]  密文 → 内层
 [读内层] ③ 显示 Codex 的回复
```

| 角色 | 外层（信封） | 内层（内容） |
|---|---|---|
| 手机 / 其他客户端 | 生成、读取 | 生成、读取 |
| server | 读取，按它转发、存储 | **碰不到**，只存和转发密文 |
| daemon | 生成、读取 | 生成、读取 |
| Codex | 不涉及 | 不涉及：只知道 tmux 输入进来的文字，以及自己写出的 rollout |

本地 CLI、hook 和 daemon 之间的通信不经过 server，只有一层，不需要加密。

发给 server 自己处理的请求（登录、拉列表和历史）只用到外层字段，返回的会话内容仍是密文。密钥怎么来、设备怎么配对、报文的具体格式见第 9、10 节。

## 3. 通信方式

**所有通信都通过 IDL 定义，不手写请求。** IDL 用 Protobuf，工具链用 `buf`；Go 端用 protoc-gen-go 和 connect-go，TS 端用 protobuf-es 和 connect-es。

```
 客户端                              server                             daemon
 ──────                              ──────                             ──────
 ① 普通请求（登录、查列表、拉历史）
    ──── HTTPS（ConnectRPC）────▶  处理并返回

 ② 发给 daemon 的指令（发消息、审批、新建会话…）
    ──── HTTPS，Forward ────────▶  不拆开，原样转发 ── 主 WebSocket ──▶  解密并执行
    ◀────────────── 结果原路返回 ─────────────────────────────────────

 ③ 实时推送（新事件、审批提醒、机器上下线）
    ◀──── 主 WebSocket（一直连着）──  主动推送  ◀──── 主 WebSocket ──── 上报

 ④ 终端画面（只在打开终端视图时）
    ◀──── 终端 WebSocket ────────▶  只转发，不存储 ◀── 终端 WebSocket ─▶  tmux
```

| 链路 | 承载方式 | 理由 |
|---|---|---|
| 一问一答（调 server） | ConnectRPC over HTTPS | 超时、错误码、重试都是现成的；接口由 proto 生成；可以用 curl 调试 |
| 客户端发给 daemon 的指令 | 统一走一个 `Forward` 接口：外层只写目标机器、请求 ID 和密文；具体指令在加密的内层里用 `oneof` 区分 | server 只按机器转发，连"是发消息还是审批"都分辨不出来 |
| 实时推送 | 主 WebSocket，打开 App 就连上，一直保持 | server 需要主动往下推；浏览器里的 ConnectRPC 不支持双向流 |
| 终端 | 单独一条 WebSocket，打开终端视图时建立，离开就断开 | 终端输出量大，和审批提醒挤在一条连接里会把提醒堵住；网络慢时可以单独断开重连，然后重新抓屏幕快照 |
| 本地 CLI、hook ↔ daemon | ConnectRPC over unix socket | 和上面用同一套工具；只有本机进程能连上 |

daemon 和 server 之间同样分主 WebSocket 和终端 WebSocket 两条连接。

主流连接有就绪期限；建立 WebSocket 不代表已经收到 `Ready`。浏览器不能观察控制帧 Ping/Pong，所以 server 还发送不含会话内容的应用心跳，网页按原始帧到达更新时间，不等待历史补齐处理完成；长时间收不到任何帧时主动失效旧连接并重试，不依赖关闭握手完成。网络恢复或默认网络切换会替换已有连接，旧连接的回调不能接管新连接。登录和历史 RPC 有期限，避免挂起请求挡住后续重试与补齐。网页建连前的本机读取、登录和安全同步分别计时；登录与同步允许一个完整 RPC 加本地校验的等待时间，每次认证响应和安全状态分页请求的开始、完成都会更新进度，不把正常的多次往返误算成一次握手超时。网页连接状态和断线提示独立通知界面，不等待列表批量解密结束。

协议 4 的网页依赖 server 的应用心跳，升级时先更新 server，再更新 daemon（重启）和客户端。本机命令与 daemon、客户端与 daemon 仍按协议版本互相核对；server 不核对这个密文内的版本号。历史信封的格式不变，不需要清理数据或重新配对。

### 为什么当前不做 P2P

**决策：客户端与 daemon 继续通过 HTTPS / WSS 连接 server，由 server 转发密文；当前不实现 P2P 直连，也不加入“直连优先、失败走中继”的双路径。**这里的 P2P 指客户端与 daemon 之间的数据直连。

2026-10 的调研实际观察到两类 IPv4 UDP 路径：一类是端点无关映射、地址和端口依赖过滤；另一类在同一本地 socket 访问同一服务器的不同端口时，公网映射端口发生变化，符合地址和端口依赖映射（通常称对称 NAT）。后者的过滤类型没有确定。结论只适用于采样路径，不能据此判断所有移动网络、CGNAT 或 TCP 行为。

不采用 P2P 的理由：

- **常用网络不能保证普通打洞成功。** 对称 NAT 中，访问发现服务器与访问对端可能得到不同的公网端口，发现到的地址不能直接保证对端可达。直连结果还取决于另一端的映射、过滤和防火墙，不能因为某一侧支持打洞就承诺连通。
- **要保证可用，仍需保留中继。** P2P 是可以尝试的优化，不是这里可靠连接的前提。直连优先会增加候选地址交换、打洞、超时回退、链路切换和网络变化后的重新探测；网页、Android、iOS 和 daemon 都要实现并验证，指令与事件还要保持原有顺序和恢复语义。
- **IPv6 暂不能替代中继。** 获取 IPv6 地址不等于允许入站连接，双方还需具备可达的 IPv6 路径。本次没有验证 IPv6 端到端直连，不能把它作为通用连接条件。
- **P2P 不能直接消除现有 server 的职责。** 账户与设备鉴权、密文历史同步、设备路由和推送仍由 server 承担。当前已有端到端加密，内容保密不依赖于是否直连；中继仍能看到必要的路由元数据，信任边界见 [scope.md](scope.md#4-信任边界)。
- **目前优先保证连接可靠、断线恢复和各端行为一致。** 本次只验证了 NAT 行为，没有验证 P2P 的端到端延迟或带宽收益，不足以支持增加一套传输路径。

对端有可达公网端口、合适的映射与过滤组合，或者双方 IPv6 可达时，仍有直连机会。只有后续中继延迟或带宽成为已测量的瓶颈，并且代表性的移动网络、家庭网络和网络切换测试证明直连有稳定收益时，再评估 P2P；评估仍须包含中继兜底及各端一致性成本。

参考：[RFC 4787：UDP NAT 映射与过滤分类](https://www.rfc-editor.org/rfc/rfc4787.html)、[RFC 5128：NAT 下的 P2P 与打洞限制](https://www.rfc-editor.org/rfc/rfc5128/)、[Tailscale：直连与中继](https://tailscale.com/docs/reference/connection-types)。

## 4. 协议设计要点

以下原则已经定下，具体做法见第 10 节：

- **指令并发**：daemon 对转发指令设固定并发上限，重连共用同一个限额；重复请求等待可随连接取消，避免不可信 server 用大量密文或重放占满本机内存。
- **幂等**：`Forward` 里的指令都带稳定的请求 ID，daemon 记住已经处理过的请求，重试时直接返回原来的结果，不重复注入
- **防重放**：加密时把版本、发送方、目标机器、会话 ID、请求 ID 或序号、截止时间一起纳入认证数据；过期或重复的审批一律拒绝
- **历史和实时衔接**：server 先写库再推送；客户端按序号去重、补缺口
- **终端积压**：终端帧设大小上限，缓冲队列有长度上限；客户端太慢时断开终端流，重新抓快照
- **离线**：daemon 离线时，server 立即返回"不可用"，不替它排队
- **版本**：不做跨版本兼容，版本不一致就拒绝并提示更新，不逐项降级（规则见 [AGENTS.md](../AGENTS.md)）。全项目只有一个协议版本号（`internal/protocol`，网页、Android 和 iOS 各有一份同值常量），旧版本会误解的改动才提升它。daemon 把它写进机器元数据，客户端发现不一致就不向这台机器发指令，并说明该更新哪一端；客户端把它写进每条指令，daemon 发现不一致就拒绝执行。本机命令和 daemon 之间通过本地 socket 的请求头和响应头互相核对，覆盖更新后没重启的 daemon 和旧会话里还在运行的 MCP 进程。server 在登记、登录和配对时核对协议号；转发密文指令时不参与内层核对，它不认识的接口按普通错误返回。信封格式另有自己的版本号（`Header.version`），已存的历史靠它继续可读，所以协议版本提升不影响读取旧会话。当前协议为 11：在手机管理端、签名成员状态链、租约和执行隔离上增加定时轮次、独立结果通知和任务会话列表语义。11 与 10 的搭配及升级要求见[第 18 节](#协议版本与升级)。daemon、本机命令（包括会话内 MCP）、中继和全部客户端需协调更新，不能保留旧执行程序继续发布新内容；恶意中继不会替用户阻止旧程序。中继数据库布局为 6，daemon 状态代数为 3，自动安装关闭。协议 9 或更早版本升级必须先按[手动升级指南](self-hosting.zh-CN.md#升级到手机管理端协议-10)让手机成为管理端并重新配对保留设备。

## 5. 技术决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 语言 | daemon 和 server 都用 Go，全部重写，不复用 Happy 和 botmux 的代码 | 单二进制、内存占用低、方便分发；需要的功能远少于 Happy |
| 参考实现 | Happy（协议、加密、客户端交互）和 botmux（tmux、Codex 的各种坑）**只作参考** | 两者都是 MIT 协议，但它们是 TS 写的，而且范围远大于本项目 |
| 客户端 | 自己写 PWA（React + Vite + TypeScript），部署在 Cloudflare Pages；Android 和 iOS 另做原生 App（[android-client.md](android-client.md)、[ios-client.md](ios-client.md)） | PWA 一套代码覆盖所有设备，不上架应用商店，网页不和 server 放在一起；Android 是主力手机，终端和通知要做到原生体验 |
| 通信 | Protobuf 定义所有接口；一问一答走 ConnectRPC，实时推送和终端各用一条 WebSocket | 见第 3 节 |
| HTTPS | server 只监听本机端口，由 Caddy 负责证书和反向代理 | |
| server 存储 | SQLite | 单用户，部署简单 |
| tmux 接入 | 使用独立的 socket（`tmux -L remote-agent`）；P0 直接执行 tmux 命令（建会话、抓屏、存活检查），终端视图（P2）再接 control mode（`tmux -C`） | 不影响平时用的 tmux；P0 不需要 pane 的字节流，会话存活由 tmux 和 PTY 代理判断 |
| 输入 | tmux pane 里跑一层 PTY 代理（`remote-agent pty-host`），Codex 以原生 TUI 跑在它下面；本地按键和远程注入都经过它，见第 6 节 | 注入时要先确认输入框为空再写入；只靠 tmux 命令，检查和写入之间本地敲的键会混进远程消息 |
| tmux 依赖 | 必需；安装脚本和 `remote-agent` 启动时检查是否存在、版本是否满足 | |
| 输出来源 | Codex rollout jsonl，不从屏幕解析消息 | 屏幕内容不可靠 |
| 审批超时 | 拒绝；默认 10 分钟，`remote-agent daemon --approval-timeout` 可调 | 安全优先；手机上从收到提醒到处理需要时间 |
| 本地状态 | 每个会话一个目录：`session.json`、append-only 的 `events.jsonl` 和待发消息 `queue.json`；事件记录里带着读到的 rollout 位置，同时充当读取进度。一次追加的几条事件（一行 rollout 解析出的，或分支复制来的历史）是一批：位置记在最后一条上，其余各条带 `more` 标记；崩溃后文件末尾只剩半批时，打开日志会把这半批整批截掉。事件只在有人读的时候留在内存里，两分钟没读就释放，下次读时再从文件加载；追加和等待新事件只需要条数，不用加载 | 重启后从记录的位置接着读，事件序号连续、不重复，写了一半的那一行重读时每条事件只出现一次；已受理的消息不丢；单用户、单机，不需要数据库 |
| `/` 开头的输入 | 客户端不直接注入：常用命令做成按钮和面板，其余先提醒再发送 | 带参数的斜杠命令会被当成普通消息发给模型；打开菜单的命令在手机上看不到（[codex-notes §6](codex-notes.md#6-踩过的坑)） |
| 上下文提示 | 占用超过 80% 时提示，并提供「压缩」按钮（注入 `/compact`） | 数据来自 rollout 的 `token_count` |

## 6. 接入 Codex

下面每条做法都基于 [codex-notes.md](codex-notes.md) 里的实测，括号里的「notes §n」指它的第 n 节。升级 Codex 后要跟着复核。

- **启动**：tmux pane 里运行 `remote-agent pty-host -- …`。会话分两种来源，按新建请求里有没有带环境变量区分（客户端经过 relay 来的命令不带，relay 会把客户端的去掉）：
  - **从终端开的会话**：`pty-host -- <CLI 路径> …`，直接执行 CLI；环境变量取自发起的 `remote-agent codex` 进程，也就是那个终端，里面临时 `export` 的变量照旧有效。执行哪个 CLI 也和在那个终端里敲命令一样：用户配置了路径（同下）就用它，否则 daemon 按命令名在会话环境的 PATH（终端的 PATH，`agent.env` 设了 PATH 时以它为准）里找，和 shell 查 PATH 的规则一致：按顺序，跳过空项和相对路径，取第一个可执行的普通文件。所以终端 PATH 里排在前面的包装脚本（比如加代理的 shim）照样生效，不会被 daemon 启动时 PATH 里的那个绕过。PATH 里找不到（包括没有 PATH）时不启动，也不退回 daemon 自己的那个，而是在建 tmux 会话前报错，说明命令、找的是终端的 PATH 还是会话保存的 PATH，以及可以用 `REMOTE_AGENT_CODEX`/`REMOTE_AGENT_CLAUDE` 给 daemon 指定路径；恢复、分叉和从这类会话派生的定时任务都按 `env.json` 里保存的 PATH 重新找，找不到同样不启动。找到的路径和登录 shell 的报告一样记成这个 CLI 的位置（见下面「CLI 怎么找」）。`doctor` 的会话不带调用方的环境，仍用 daemon 自己的 CLI。
  - **客户端开的会话**：`pty-host --clean-env -- <登录 shell> -l -i -c <脚本> …`。账号的登录 shell（macOS 从目录服务、Linux 从 `/etc/passwd` 取；取不到时退回 `$SHELL`，再退回 `/bin/sh`）以交互式登录 shell 加载用户的 shell 配置后 `exec` CLI，和电脑上新开一个终端标签页一样；CLI 按用户配置的路径（`REMOTE_AGENT_CODEX`/`REMOTE_AGENT_CLAUDE`，或 `--codex`/`--claude`）或按命令名在新 shell 的 PATH 里解析。环境每次现算，所以改了 shell 配置、升级 nvm、装新命令、CLI 换了位置，都在下一个会话生效，不用重新 `install` 或重启 daemon。
    - **起点环境**：shell 拿到的是新终端的环境，不是 daemon 的：身份和系统变量（HOME、USER、LOGNAME、SHELL、TMPDIR、locale、`SSH_AUTH_SOCK`）加系统默认 PATH，再叠加 `~/.remote-agent/agent.env` 和 remote-agent 自己的变量（`RA_SESSION`、`RA_EXE`、`REMOTE_AGENT_HOME`、`CLAUDE_CODE_DISABLE_CRON`、`CLAUDE_CODE_DISABLE_1M_CONTEXT`）。daemon 的 PATH 是它启动时的快照，传下去的话 nvm 之类的工具会沿用旧路径，所以不传；`--clean-env` 让 PTY 代理只把这份环境交给 shell，不继承 tmux（即 daemon）的环境。
    - **CLI 怎么找**：命令和参数作为位置参数传给脚本，脚本本身是固定代码，不拼 shell 字符串。脚本解析到 CLI 后把路径写进会话目录的 `shell-bin` 再 `exec`；找不到就写 `shell-error` 并退出。daemon 读到路径（或从终端开的会话在 PATH 里找到的路径）就把它记成这个 CLI 的位置，之后的版本检查、机器元数据里的已装列表和 `doctor` 都用它——它们跟着会话实际跑的 CLI 走，而不是 daemon 启动时 PATH 里的那个；每次启动前清掉上一份报告。
    - **失败要看得见**：shell 一直没启动 CLI（例如配置里有等待输入的命令）时，超过 `ShellStartTimeout`（默认 1 分钟）daemon 结束这个会话并在状态详情里写明；shell 找不到 CLI（配置的 PATH 里没有）或没跑到脚本就退出（配置报错）时，会话直接以对应原因结束。两种都不会一直停在「启动中」。
  - **环境变量**：`~/.remote-agent/agent.env`（放代理等变量，所有 CLI 共用一份；daemon 由 launchd 启动时读不到 shell 里的配置。没有这个文件时读以前的 `codex.env`）叠加在两种来源之上，并设置 `RA_SESSION=<会话 ID>`、`RA_EXE=<remote-agent 的路径>`。
  - **不上命令行**：这些变量不经过 tmux 的命令行（命令行对本机所有用户可见，而环境变量里常有 API key），而是存进会话目录下只有自己可读的 `env.json`：从终端开的会话在恢复时沿用它，客户端开的会话只有起点环境（shell 现算的结果不落盘），每次启动另写一份副本交给 PTY 代理，读取后删除。
  - **hook**：用 `-c` 注入 `PermissionRequest`、`SessionStart` 两个 hook，只对这个会话生效。hook 的定义（命令和 `timeout`）必须固定：Codex 每个 hook 位置只记一份信任，定义一变就要重新信任，而且会顶掉之前的信任。所以命令写成 `"$RA_EXE" hook codex`，不含二进制的路径，换了路径或同时跑测试用的另一份二进制也不用重新信任（notes §3、§5）
- **退出清理**：会话结束后清理该次 PTY 启动创建的进程组。停止信号先交给 CLI，给它时间保存历史；无论主进程何时退出，都向同组剩余进程发 TERM，并在有界宽限后对仍存在的组发 KILL，避免主进程及时退出却留下忽略挂断的 helper。PTY 代理在终端消失后继续排空输出，避免 CLI 因输出阻塞无法退出。
- **locale**：daemon 没有 UTF-8 的 locale 时（launchd、systemd 启动就是这样）自己补上 `LC_CTYPE`，tmux 和 Codex 都继承它。否则 tmux 会把输出里的 tab 和非 ASCII 字符换成 `_`：会话列表读不出来，所有会话都会被当成已经消失，屏幕里的 `›` 也认不出来。标成已结束、但 tmux 会话其实还在的会话，daemon 启动时会重新接上
- **退出结算**：两个 CLI 确认退出后，先补读并持久化最后的 transcript，再把仍未结束的轮次记为中断。新启动的 CLI 不继承旧进程的运行状态；daemon 排队消息和 Claude 持有的消息一起结算：未写入的取消，transcript 已证明模型收到的记为提交，其余写入过的记为无法确认；先记结果，再移出队列，恢复时不自动重发。退出标记只记录进程已结束，不表示 transcript 已导入；重启时已退出会话也按事件 checkpoint 补读。最终读取或事件落盘失败时不结算输入，恢复前重试，避免漏回复或重复投递。
- **恢复会话**：`codex resume <Codex 会话 ID>`，沿用原来的参数，去掉位置参数（如第一句话），再用最近一轮的模型、effort 和审批模式覆盖；审批模式只在最近一轮的沙箱、审批策略和审批方与某个标准模式完全一致时才覆盖，免得把只读沙箱之类的更严设置放宽。Codex 不接受重复的 `-m`，命令行的审批选项又比 `-c` 优先，所以被覆盖的选项先从原参数里去掉。启动方式和最初的会话一致：从终端开的沿用 `env.json` 里的环境变量，并按其中的 PATH 重新找 CLI，客户端开的再经过登录 shell 现算一次（会话记着自己是哪种）。分叉同理（第 13 节）
- **启动弹窗**：用 `-c` 关掉检查更新、限额换模型提示等能关的弹窗；关不掉的 `Trust this folder?`、`Hooks need review` 每个目录或每套 hook 只问一次，客户端提示去终端处理。能不弹就不弹；信任目录是安全决定，留给用户在终端里做（notes §5）
- **启动时不注入**：Codex 在新目录启动时会先闪一下输入框再弹出信任对话框（notes §10），所以会话处于「启动中」时不注入，等状态检测连续两次看到同样的画面、进入空闲再说
- **防弹窗挡输入**：每次注入前先抓屏，确认没有弹窗挡着。判断画面时只看屏幕底部；以列表里选中的行判断有没有弹窗，标题只用来给弹窗命名，对话里出现同样的字不算（notes §5、§6、§10）
- **等画面**：轮询屏幕，等到预期画面出现再操作，并设超时；不用固定的 sleep（notes §6）
- **输入**：远程消息按到达顺序排队，一次注入一条；队列在受理前写入 `queue.json`，重启后接着发。每个会话的待处理输入（daemon 队列和 CLI 暂存合计）最多 256 条、文本合计最多 32 MiB，整个 daemon 的待处理文本最多 128 MiB。所有消息来源和新会话首条消息均在接管图片和插入队列前检查配额；超出返回 ResourceExhausted，不保留输入或图片所有权，等待处理或取消消息后释放容量。待处理请求 ID 始终参与去重，另记最近 1000 个已受理 ID；缓存滚动不会使仍排队或暂存的请求重复发送。写入前记下 `history.jsonl` 的位置和当前事件序号。事件记录和 `queue.json` 是先后两次写入：消息离开队列时先把结果记成事件，再从 `queue.json` 里去掉，结果记不下来就留在队列里稍后再试。daemon 重启时拿事件记录核对队列：结果已经记下的消息直接去掉，不再结算一次；最后一轮被中断而等待的消息还没存成暂停的，先补上暂停再恢复发送。已经写入、但 CLI 还没记下用户消息的那些（Codex 运行中发的消息要到下一次工具调用后才记；Claude Code 暂存着的）也从事件记录和暂存列表里重新认出来，之后出现的用户消息照样带上请求 ID 和来源；带图的消息除外，事件里没有它的文件和占位编号。`queue.json` 在但读不出来时，里面可能有已受理的消息和防重发的请求 ID，这个会话不再受理新消息、也不改写这个文件（其余照常：能看、能审批），等文件修好或删掉、重启 daemon 后恢复。
  - **写入**：注入时 daemon 先让 PTY 代理暂存本地按键，等 80ms 让已经敲下的键显示出来，再抓屏：输入框就绪且没有未发送的草稿，才一次写入 bracketed paste 包起来的正文和回车，然后放开暂存。暂存期间本地敲的键不丢，放开后按顺序进入新的输入框；PTY 是按顺序的字节流，它们一定排在这条消息的回车之后。
  - **PTY 背压**：PTY 写入不占用租约状态锁，本地和远程字节由同一个写入通道串行送入。远程写入最多等 2 秒，超时明确报告可能已经写入一部分，未写入的部分不再补发；租约照常过期，本地暂存按键在 CLI 恢复读取后继续送入。当前持有者续租不等待写入；新的暂存或远程写入在状态锁外等待前一批输入完成，等待和远程写入共用 2 秒期限，超时才报告失败，避免抓屏检查或新输入越过在途按键。
  - **有草稿或弹窗时**：本地有草稿或有弹窗时，消息继续排队，绝不覆盖或拼接草稿。
  - **确认提交**：写入后以 `~/.codex/history.jsonl` 新增一行（已知 Codex 会话 ID 时只认这个会话的行）或 rollout 里出现这条用户消息，确认提交成功（notes §1、§10）。每条消息的状态以事件记录：排队、已提交、无法确认。
  - **确认不了不重发**：10 秒内确认不了的记为「无法确认」，**不重发**，因为按键已经送到，重发可能提交两次；写入时恰好 daemon 停了的，重启后同样只等确认、不重发。
  - **迟到的记录仍然算数**：Codex 在一轮开始后才记录用户消息，可能晚于这 10 秒（notes §10）。「无法确认」之后 rollout 里出现了这条消息，daemon 补记「已提交」，和这条用户消息一次写入事件记录、排在它前面，顺序与按时确认的一样（客户端靠这个顺序判断消息是谁发的）。客户端以每条消息最后一个状态为准，被推翻的「无法确认」不再提示；这种补记的「已提交」确认的一定是紧跟其后的那条用户消息，客户端不拿它去认领前面的消息。daemon 只在内存里记着哪些消息无法确认：重启后才到的记录不再改口。
  - **互斥**：注入、回答提问和中断共用一把锁，同一时刻只有一个操作使用 PTY 代理；代理也只允许持有暂存的连接写入和放开。正文里的控制字符会被去掉，避免提前结束粘贴
- **运行中的消息分两种**：
  - steer 是插入这一轮，daemon 照上一条的规则在输入框就绪时写入：Codex 运行中按回车就是插入当前这一轮；Claude Code 运行中回车会先进它自己的队列，等当前工具调用结束再并入这一轮（claude-code-notes §10）。
  - queue 是等这一轮结束再发，由 daemon 留在自己的队列里，看到这一轮结束（Codex 的 `task_complete`，Claude Code 的 `turn_duration`）后才按上一条的规则写入，不借用 Codex 的 Tab：两个 CLI 行为一致，daemon 重启后还在，也能照常取消。空闲时两者没有区别。
  - **还没送到 Agent 的消息都能撤回**，不分 steer 和 queue：还在 daemon 队列里的直接移除（`CancelInput`）；Codex 的 steer 一写进终端就插进这一轮，算已送达，不能撤回；Claude Code 的 steer 写进后先留在 Claude Code 自己的队列里，直到当前工具结束才并入，这期间 daemon 按 ↑ 把它拉回输入框、清空，以 transcript 出现不是 `absorbed_mid_turn` 的 `queue-operation remove` 为撤回成功；先被并入了就报「已送达，不能取消」。↑ 会把 Claude Code 队列里的消息全部拉回，所以同时排着的其他消息在清空输入框之前先存回 daemon 的队列并暂停，确认输入框清空后才放开，照常重新写入；daemon 中途停了或输入框清不掉时它们保持暂停，等用户发送或取消，不会丢，也不会写进还留着原文的输入框。
  - **默认**：客户端默认发 steer，和两个 CLI 自己按回车一致；发送请求里带一个字段区分两种，没填时按 steer。
  - **一轮被中断后**，还没写入的消息（queue 的，以及 steer 但还没写入的）都暂停，不自动发出，等用户逐条选择发送或取消：中断往往说明方向变了，排好的后续消息可能已经不适用。暂停状态和原因同步给所有客户端
- **判断输入框**：抓屏时保留颜色属性（`capture-pane -e`），按**样式属性**判断，不按转义序列的字面写法：逐个解析行首的 SGR 序列得到加粗、变淡、反色，再看第一个可见字符。Codex 升级常换写法（0.159.0 把 `\e[1m` 换成了 `\e[0;1m`），样式本身不变。输入框的提示符是加粗的 `›`，占位提示是淡色字（前面可能先有背景色设置，判断时跳过开头的样式和空格，看第一个可见字符是不是淡色），列表里选中的行是加粗反色的 `›`。只有看到占位提示才认定输入框是空的：多行草稿的第一行可能是空的，其余行和底部状态栏分不开（notes §10）
- **找到 rollout**：`SessionStart` hook（发出第一条消息时触发）把 `RA_SESSION` 和 `transcript_path` 一起报给 daemon（notes §3）。CLI 是先启动、会话后登记的，启动得快的 CLI（Claude Code 在已信任的目录里）可能在登记完成前就发来这个 hook；daemon 让它等到登记完成再处理，不回「没有这个会话」，否则之后再没有 hook 的会话（如 bypass）就一直绑不上 transcript
- **轮次和空闲**：一轮以 `task_started` 开始，以 `task_complete` 或 `turn_aborted`（被中断）结束；屏幕底部的输入提示符作为辅助（notes §1、§8）
- **模型提问**：问题从 rollout 的 `function_call` 读出，它在等待回答时就已经写入，不需要 hook。回答时暂存本地按键、抓屏确认选择框还在，再注入选项编号；以 rollout 的 `function_call_output` 为准，先在终端里答了的就收回卡片。异步提问（`request_user_input_async`）不单独处理，一轮结束后当普通消息回复（notes §9）
- **中断**：只在一轮运行时发 Esc，绝不发 Ctrl-C。空闲时发 Ctrl-C 会清空输入框，再按一次会退出 Codex（notes §8）
- **切换模型和 effort**：空闲时操作 `/model` 菜单：按显示名在屏幕上找模型的编号并按下，在档位列表里用方向键移到目标档位后按 `s`，只改当前会话（回车会改全局默认值）。Max、Ultra 在 `More reasoning…` 子菜单里。以底部状态栏出现新的模型和档位为成功，认不出菜单就按 Esc 退出并报错。rollout 要到下一轮才记录新模型（notes §2），所以 daemon 先记一条 `SettingsChanged`，会话信息立即按它更新，下一轮的 `turn_context` 再校对。可选的模型和档位读自 `~/.codex/models_cache.json`；打开模型选择页时重新读取，避免客户端一直使用旧列表。配置中的默认模型也列为一个可明确选择的选项：缓存有它时保留其完整档位，即使它标为隐藏；缓存暂时没有它时仍列出模型，但不猜测支持的档位
- **切换审批模式**：询问、自动、完全放行分别是 `/permissions` 菜单的 1、2、3，按数字直接选中；完全放行还要在 `Enable full access?` 里按 1 确认，以屏幕出现 `Permission selection requested` 为成功。权限档位运行中也能切，下一轮起生效。计划模式在空闲时用 `/plan` 进入、Shift+Tab 退出，以状态栏右侧的 `Plan mode` 判断当前状态；回合运行中拒绝进入或退出 Plan，不写终端（[实测见 notes §4](codex-notes.md#4-审批模式)）。成功后记 `SettingsChanged`；有未发送草稿时拒绝操作，检查在持有终端控制期间进行
- **压缩上下文**：空闲时输入 `/compact`。压缩在 rollout 里是一条 `ContextCompaction`，无论是客户端发起的还是终端里敲的，都解析成「上下文已压缩」事件
- **计划**：Plan 模式下模型给出计划后，rollout 里的 `Plan` 条目解析成 `PlanProposed` 事件，屏幕上的 `Implement this plan?` 让会话处于「计划待批准」，客户端显示计划卡片，回答时注入 1、2 或 3（notes §4）。计划是否待批准、回答绑定的事件序号和画面哈希都以电脑当次的实时快照为准；卡片正文用快照点名的那条 `PlanProposed` 事件里的 Markdown（已验证、按序号绑定的历史事件），本机还没有这条事件或它是骨架时才退回快照里的终端文字（Claude Code 也一样）
- **工具开始**：rollout 在调用工具时先写一条 `custom_tool_call`（或 `function_call`），结束时写同一个 `call_id` 的 `*_call_output`，中间可能有描述它做了什么的 `item_completed`（如 `CommandExecution`）。开始解析成带 `call_id` 的 `ToolStarted`；期间完成的第一个条目用这个 `call_id` 报成 `ToolCall`，同一次调用的后续条目用 `<call_id>#2` 这样的 ID；没有任何条目的调用（很多 `exec` 就是这样）在输出到来时补一条 `ToolCall`，保证每个开始都有结束。`wait` 是在等之前让出的 exec 单元（输出以 `Script running with cell ID N` 开头），不算新的调用，它的输出结束的是那个 exec。让出这条输出不产生事件，所以 daemon 重启后解析器除了重放事件日志，还要把 rollout 从头到已读位置再过一遍，只取回「哪个单元属于哪次调用、哪个 `wait` 在等它、现在跑的是哪次调用」；只有重放后还有没结束的 `exec` 时才读
- **菜单操作的共同做法**：和注入一样拿控制锁、暂存本地按键，并在操作期间续期暂存；每一步都先确认画面再按键，等不到预期画面就按 Esc 退出。拿到控制锁后和每次按键前都检查请求是否已取消或过期；菜单等待和 tmux 子进程沿用请求期限，单次 tmux 调用另有 5 秒上限。取消后不再按键，包括退出菜单的 Esc；已写出的键不能撤回，已确认成功的操作仍记录结果。操作期间暂停状态检测，免得把自己打开的菜单当成弹窗
- **命令参数**：Go 代码调用 tmux 和 codex 时一律传参数数组，不拼 shell 字符串

## 7. 审批

`remote-agent hook codex` 作为 Codex 的 `PermissionRequest` hook，通过 unix socket 把请求交给 daemon。daemon 先读完 rollout，按最近一次 `turn_context` 的 `approvals_reviewer` 判断会话的审批方式：

| 会话的审批方式 | hook 的行为 | 用户看到什么 |
|---|---|---|
| 开着 `auto_review`（Codex 的 `Approve for me`） | 不输出、正常退出，交给 `auto_review` | 手机上不弹审批卡；模型在操作前拿不准时会在对话里问你（已实测），直接回复即可；`auto_review` 直接拒绝后模型会不会来问，未验证 |
| 没开 `auto_review` | 把请求转到客户端，等待回复；超时拒绝 | 审批卡片：允许、不允许（见下文「客户端只允许单次审批」） |

依据：Codex 先调用 hook，hook 不表态时才交给 `auto_review`；hook 只能返回 allow 或 deny 加 message，做不到原生审批框里的「以后不再询问」（notes §3、§4）。

- **hook 的超时**：hook 定义里的 `timeout` 设为 3600 秒，审批超时必须比它短。hook 自己超时的话，Codex 会改为在终端里弹原生审批框（notes §3），就做不到「超时拒绝」了
- **daemon 连不上**：hook 什么都不输出，交给 Codex 在终端里弹原生审批框，仍然由人决定。审批等待中 daemon 重启时，hook 会重试 30 秒，连上新的 daemon 后重新发起审批；旧的那条记为「已取消」

**Claude Code** 的审批走同一个入口 `remote-agent hook claude`，但规则不同，不照搬上面的 `auto_review` 分支：

| | 做法 | 依据 |
|---|---|---|
| 转不转给客户端 | 所有模式下都转：`PermissionRequest` 只在 Claude Code 要弹权限框时才触发，bypass 和 auto 放行的请求根本不会来 | [claude-code-notes §6](claude-code-notes.md#6-审批permissionrequest) |
| 终端里 | 原生权限框和 hook 同时出现，电脑和手机谁先答算谁的 | 同上 |
| 本地先答 | 屏幕上见过的权限框消失、这个工具已经有了结果或这一轮结束时，把卡片记为「已在终端处理」（`APPROVAL_DECISION_TERMINAL`）并让 hook 退出。本地选了「允许」时 Claude Code 不会结束 hook，只能靠 daemon 自己发现 | 同上 |
| 超时 | 照样返回拒绝；原生框随之消失 | 同上 |
| AskUserQuestion、ExitPlanMode | 它们也会触发 `PermissionRequest`，hook 直接不表态，不出审批卡；它们由第 16 节的提问和计划处理 | notes §6、§7、§8 |

### 客户端的审批模式

客户端的模式切换只做 Codex 和 Claude Code 都有的 4 种，这样接入 Claude Code 时不用改界面：

| 客户端 | Codex | Claude Code |
|---|---|---|
| 询问 | `Ask for approval`（`/permissions`） | manual |
| 自动 | `Approve for me`（`auto_review`） | auto |
| 计划 | Plan mode（空闲时 `/plan` 进入、Shift+Tab 退出，和权限相互独立） | plan |
| 完全放行 | `Full Access` | bypass（启动时没允许的会话置灰） |
| 不提供 | — | accept edits |

各项的实测情况见 [codex-notes §4](codex-notes.md#4-审批模式) 和 [claude-code-notes.md](claude-code-notes.md)。

- **客户端只允许单次审批**：「允许」通过 hook 返回 allow；「不允许」可附说明，通过 hook 返回 deny，不中断整轮。「以后不再问」由用户在原生终端里选择，daemon 不自动按原生审批框的第二项。现有 hook 和屏幕信息不能把这个选项可靠绑定到特定工具请求，同前缀命令、同名文件和留在历史里的文本都可能误匹配。daemon 不声明远程永久审批能力；客户端发来永久审批请求时明确拒绝，保留原审批等待用户处理。
- **「询问」的语义不抹平**：Codex 在工作区内改文件、跑命令本来就不问，只有联网和越界才问；Claude Code manual 每一步都问。客户端按 CLI 实际发来的请求显示
- **Codex 的计划模式**：计划模式和权限是两个开关。选「计划」只打开计划模式、权限不变；选其他三种会先关掉计划模式再切权限
- **以 CLI 为准**：客户端只发「切换」指令，显示的是从 rollout、transcript 或屏幕读回来的结果；在电脑终端里切的，聊天里记一条。终端切到了这 4 种以外的模式（如 accept edits），照实显示
- **会话中途切到完全放行要二次确认，新建会话不确认**：新会话的审批模式来自项目设置（第 13 节），在项目设置里选完全放行本身就是明确的选择，按它新建时不再弹确认，项目页的设置摘要用红字标出，会话里写在导航栏的状态行。
  - **项目设置没指定时**：项目设置没指定时用 daemon 设置里的默认模式，再没有就沿用 CLI 自己的配置。
  - **读出 CLI 的默认模式**：沿用 CLI 配置时，客户端事先不知道它是什么，所以 daemon 把每个 CLI 实际生效的默认模式读出来放进机器元数据（`AgentInfo.default_mode`，只读配置、不改任何文件）：Claude Code 按它的优先级读托管设置、项目的 `.claude/settings.local.json` 和 `settings.json`、用户的 `~/.claude/settings.json` 里的 `permissions.defaultMode`，都没有就是 manual；Codex 读 `config.toml` 顶层和所选 profile 的 `approval_policy`、`sandbox_mode`、`approvals_reviewer`，没写的按 Codex 的默认值。`config.toml` 用 TOML 解析器（BurntSushi/toml）读，不按行猜：`'never'` 这样的字面量字符串、`profiles.x.sandbox_mode = …` 这样的点号键、内联表都是合法写法，Codex 照它们启动，漏读一种就会把完全放行的配置报成询问。读不出来（文件读不了、不是合法 TOML、这几个键的值不是字符串）就标为未知。
  - **客户端怎么显示**：客户端用它在摘要里如实显示：完全放行照样用红字，未知写「跟随 CLI 设置」，两种都不拦截新建。
  - **为什么不拦截**：这些默认值都是用户自己写的配置，和在项目设置里选完全放行一样算明确选择，所以 daemon 也不据此拒绝新建

## 8. 项目标识

项目按会话工作目录的**绝对路径**判定：路径相同就是同一个项目，不同电脑上路径相同的目录也算同一个项目；项目名是路径的最后一段。分组在客户端完成（`web/src/model.ts`），路径在加密的会话元数据里，server 看不到。同名但路径不同的是两个项目，列表里用路径区分。

会话标题由 daemon 从第一条用户消息生成，写进加密的会话元数据：去掉开头的图片占位（`[Image #N]`），取第一行的首句（到第一个中文标点，或后面跟空格的英文标点为止，前 4 个字符内的断句不算），最多 40 列宽（汉字算 2 列），超出加省略号。理由：整句当标题既不概括内容又必然被截断，而首句不需要调用模型，内容也不出本机。只有图片没有文字的消息不产生标题，由下一条消息命名；还没有标题时客户端显示「项目名 · 开始时间」。

用户可以给会话重命名。自己起的标题存在 daemon 的会话记录（`session.json`）里，优先于自动标题，之后的消息不再改它；留空保存就清掉它、恢复自动标题。标题一行，最多 60 个字，由 daemon 去掉首尾空白并把换行等空白折成空格后校验。理由：标题本来就由 daemon 写进加密的会话元数据，改名走同一条路，所有客户端和通知自然一致，server 仍然只看到密文；代价是电脑离线时改不了。已结束的会话也能改。只改 remote-agent 显示的标题，不动 CLI 自己的会话名（Claude Code 的 `/rename`、Codex 的自动标题），免得为一个显示用的名字去驱动终端菜单。

### 会话列表排序

网页、宽屏侧栏和 Android 使用相同规则：「需要处理」先按审批、问题、计划、终端弹窗排列，同类型按当前待处理请求的开始时间从早到晚；多项审批或问题取仍待处理项中最早的时间，解决后转到下一项。「进行中」包括启动、运行、空闲和离线会话，按会话创建时间从新到旧，离线不改变位置。「已结束」按实际退出时间从新到旧。时间相同使用会话 ID 的字典序；项目排序时间相同时使用项目路径的字典序。分区变化会移入对应列表，当前选中会话继续遵守侧栏保留规则。

等待和退出时间由 daemon 从本地事件日志重建；计划等待从稳定终端画面首次显示批准提示时记录，弹窗从进入对应阻塞状态时记录。时间跟随加密会话摘要传输，server 无需解密或参与排序。后台输出和重连的上传时间只用于最近活动显示，不决定会话或项目列表的位置，也不决定新会话从哪个会话继承配置：继承取列表顺序里最靠前的会话，即未结束的优先（创建时间最新的），否则最近结束的。理由：会话列表按这个顺序分页取回，按它继承，已取到的部分就足以确定继承自谁；按上传时间的话，一个被改名或重传过的旧会话可能排在没取到的页上。会话没有等待或退出时间时用创建时间；摘要未解密时用零和 ID，摘要首次到齐后再按创建时间归位。

### 主页的范围

主页和宽屏侧栏是一条会话时间线：需要处理、进行中，然后是已结束的会话，按今天、昨天、近 7 天和月份分组。它的范围是某个项目或全部项目，由标题切换。理由：按项目分组的主页在只有一个项目时几乎是空的，要找的会话都藏在项目页里；把项目变成范围后，一个项目的人看不到项目这一层，多个项目的人仍然可以按项目看。

- **默认与记忆**：未移除的项目只有一个时范围是它，否则是全部项目。用户选过的范围记在这台设备上（网页 `localStorage`，Android 和 iOS 本机设置），不进账户偏好，因为不同设备常常看不同的项目；记住的项目已移除或不存在时按默认。Android 和 iOS 的本机设置是磁盘上的明文，所以记的不是项目路径，而是用账户密钥对路径算出的标记（第 9 节的 `home-scope`），对照项目列表才认得出是哪个项目；网页记的是路径。宽屏上打开某个项目会把范围换成它
- **范围内有什么**：全部项目列出未移除项目的全部会话；已移除项目的会话只在需要处理和进行中里出现，和上文「从项目列表移除」一致。某个项目的范围里，进行中和已结束只列它自己的会话；需要处理不受范围限制，始终列出账户里全部待处理的会话，免得别的项目的审批被范围挡住，不在范围内的那几行写出项目名
- **行内写什么**：第二行是状态词和预览；项目只在全部项目里写（以及上面说的范围外的待处理项），CLI 只在范围内的会话用过不止一种时写，机器只在账户里不止一台电脑时写。理由：只有一个项目、一种 CLI、一台电脑时，这三项每行都一样，是噪音
- **筛选**：范围内会话超过 8 个时提供按标题筛选，不分大小写的子串匹配，在客户端对已解密的会话摘要做，标题不离开客户端；不搜对话内容（[scope.md](scope.md)）
- **已结束的分页**：先显示 30 个，滚到底再加 30 个；显示到已取到的末尾时再向 server 取下一页，见下文「会话列表分页」
- **宽屏没有项目页**：选中项目后侧栏列出它的会话，主区域是它的新建输入框。手机保留项目页作为新建页，范围是某个项目时新建按钮直接进它

### 会话列表分页

客户端不一次取回全部会话。`ListRemoteSessions` 的第一页是全部未结束的会话，加最近结束的 50 个；之后每页是游标之后的 50 个已结束会话，从最近结束的到最早的，结束时间相同按会话 ID。理由：会话只增不减，全量取回的下载和解密都随总数增长；而界面真正需要完整的只有未结束的会话（需要处理、进行中），已结束的只在往下翻时才用到。

- **server 知道什么**：会话状态在加密的元数据里，server 分不出哪些已结束，所以 daemon 在 `PutSession` 里另外用明文告诉 server 结束时间（`ended_ms`，未结束是 0），server 只用它分页和排序。这比原来多暴露了「这个会话已结束、何时结束」；结束的时刻 server 本来就能从这次上传的时间大致看出（[scope.md](scope.md) 第 4 节）。客户端显示和排序仍用加密元数据里的时间，`ended_ms` 只当游标用。取 daemon 上报的值而不是 server 的更新时间，是因为重传元数据不该改变会话在列表里的位置
- **结束时间取值**：元数据里的结束时间；没有记录的取创建时间，和客户端排序的规则一致（上文「会话列表排序」）；都没有时取 1，保证已结束的会话不为 0。会话被恢复后回到 0
- **归在任务下的会话**：daemon 另用明文的 `task_owned` 布尔值说明该会话是否归在任务下；只在已结束分页中用 SQL 排除它；未结束集合和按 ID 查询照常返回，使离线期间出现的审批在冷启动和刷新时也能进入「需要处理」。这多暴露了「这个会话暂未被用户接手」这一点，不暴露任务 ID、标题、触发配置或执行消息。客户端以加密 `Session.task_owned` 为显示依据，从进行中和已结束列表中排除任务会话；审批、提问、计划和弹窗仍进入「需要处理」，并显示项目名
- **推送元数据**：`NOTIFY_KIND_SCHEDULED` 是明文路由类别，定时轮也不再发 `TURN_ENDED`。server 可以据此推断某个会话在运行定时任务、Agent 发过主动通知，包括未归在任务下的用户对话；结合 `task_owned` 能知道归属变化。任务 ID、标题、消息和通知正文仍加密，缺少推送本身不证明没有运行。
- **分页代价**：已结束查询仍沿 `sessions_ended` 索引扫描，并逐行用集合表主键做 `NOT EXISTS`；隐藏行很多时，凑满一页需要越过更多索引行，当前没有单独的可见会话索引或配额豁免。
- **和 server 不一致时**：daemon 连上后在 `ListSessionHeads` 里看到 `ended_ms` 或 `task_owned` 与本地不同，就重传元数据。`task_owned` 使用独立的集合表 `task_owned_sessions`，启动时 `CREATE TABLE IF NOT EXISTS`；不 ALTER 已有会话表、不改 schemaVersion（仍为 6）、不扫描或改写旧行，因此已有库直接启动，不要求运营者手动升级，也没有数据迁移。没有集合记录就是普通会话，未上报此值的 daemon 不会隐藏会话。集合变更与接受新元数据在同一事务，过旧修订或没有元数据的上传不能改变它；删除账户或电脑档案时同时清理
- **项目从哪来**：项目原来由客户端从全部会话里归出来，分页后只有旧会话的项目会消失。所以每台机器在加密的 `MachineMeta` 里带一份项目摘要：路径、已结束会话数、最近创建和最近结束的时间。它只在会话开始、结束或接手时变化，不随会话运行重传；归在任务下的会话不计入项目摘要。客户端的项目列表是各机器的项目摘要加上已取到的会话；是否有未结束的会话仍看会话本身。用「新项目…」选好目录时，客户端把所选机器写进这个项目的项目设置（第 13 节）；一个项目只在项目设置里出现、还没有会话时也列出来，按添加时间排在所有会话已结束的那一组，这样它在刷新后和账户的其他客户端上都在。项目设置里的机器已不是账户里的机器时不列。选的目录已经是项目时不写，项目设置保持原样。范围里「共 N 个」的 N 来自摘要里的已结束会话数
- **往下翻**：显示到已取到的已结束会话末尾、server 还有下一页时，取下一页。范围是某个项目时，一页里可能没有它的会话，就接着取，直到够显示一屏或取完
- **筛选**：按标题筛选要对全部标题做，所以开始筛选时把剩下的页都取回来，取完之前末尾写「正在加载更早的会话…」。筛选是偶尔的操作，为它在 server 上建索引就得让 server 看到标题
- **响应字节预算**：一次列表响应按 Protobuf 编码上界限制为 32 MiB，逐行读取时先计费再解码信封；第一页的未结束和已结束会话共用预算，按 ID 查询同样计费，重复 ID 也不豁免。超过时返回 `ResourceExhausted`，不静默截断；这不提供未结束会话的分页。
- **按 ID 取**：打开的会话不在已取到的范围里时（通知、链接、分叉来源），用 `session_ids` 单独取它；取不到才显示「找不到这个会话」
- **重新连接后**：第一页重新取回。本地已有而这一页里没有的会话：所属机器的保留行已从 server 消失才删掉（已撤销成员仍可有档案，不能仅凭当前成员列表删除）；已结束、且按游标排在这一页之后的保留（它属于后面的页）；其余的删掉（已不存在，或在别处被取到时再出现）
- **本地缓存**：网页缓存第一页的密文和机器列表，下次打开先显示。事件缓存不再按会话列表清理，只按容量淘汰最久没打开的，因为客户端不再知道完整的会话集合

### 项目列表偏好

项目仍按绝对路径分组。常用、隐藏和项目设置（第 13 节）都属于账户，在客户端之间同步；用独立用途密钥加密后交给 server 存储和转发，server 只能看到不含路径的对象 ID、修订号与密文。客户端解密后按项目路径匹配，不向 server 上传明文项目名或路径。常用按设为常用的顺序稳定排列，其他项目先按是否有未结束会话分组：有未结束会话的项目在前，所有会话已结束的项目在后；各组按项目内最近创建会话的时间从新到旧排列，相同时间按项目路径字典序。运行、空闲、等待处理和离线都算未结束，状态之间切换、输出和重连不改变项目顺序。新建会话可以前移项目，最后一个未结束会话退出时项目移到已结束组。旧会话缺少创建时间时用零，摘要首次解密后按创建时间归位。

偏好写入带预期修订号：冲突时取回最新密文、解密，再重做当前项目这一项改动，保留其他项目的并发改动。界面先显示保存中，server 接受这次 CAS 后更新列表；断线时显示缓存，修改的入口按禁用显示。新设备读取账户偏好；退出或清除本机数据只删除本地缓存，不删除账户的常用项目。

「移除项目」只是隐藏入口，不结束会话、不删除历史、不屏蔽提醒；隐藏项目不出现在项目列表或新建选择器，进行中的会话与待处理项仍照常展示。移除前确认一次，确认后没有撤销，也没有已移除项目的列表：界面上移除就是移除，少一套「恢复」的概念和页面。要再用，把同一个目录加成新项目，客户端发现它在隐藏列表里就取消隐藏，原来的会话、历史和项目设置都还在；从通知或会话进到隐藏项目的页面时可以查看，页面上有「重新添加」，加回来之前不能新建。新增会话不会把隐藏项目自动放回列表。偏好对象的格式没有变，仍是常用、隐藏和项目设置三个列表。

项目在范围菜单、新建时的选项目和项目管理三处是同一个列表：同样的分组和排序、同样的两行（名字；路径加进行中的数量，没有进行中而它的电脑都不在线时写「电脑不在线」）、同样的「新项目…」，只有行尾不同。两端各由一个共用的组件画，免得三处各自演变。

主页和范围菜单见 [client-v52 · 主页](design/client-v53.html#home)，项目管理的布局与具体交互见 [client-v52 · 项目管理](design/client-v53.html#projects)。目标机器离线时由用户选这次用的机器，不改项目设置，也不在输入中途自动更换机器或 CLI。在新建输入框旁切换 CLI 保留草稿，改用项目设置里这个 CLI 的那一套。

## 9. 账户、设备和密钥

一个账户对应一个随机的 32 字节**根密钥**。第一台管理 Client 在本机生成根密钥和设备身份，并在 server 上建账户。Android、iOS 和网页均可担任唯一管理端，Machine 不能担任；网页与 iOS 的管理流程仍在实现，当前进度见 [plan.md](plan.md)。一台 server 可以承载多个账户，怎么建、怎么隔离见下文「一台中继上的多个账户」。

### 管理 Client 与成员状态

协议 10 的唯一管理端由已验证成员 head 的 AuthorityID 指定，必须是 Client；不看 Android、iOS、网页或自报 platform。它沿用设备 Ed25519 密钥签成员状态和独立租约，恢复声明由恢复码签。Machine 不能创建创世管理身份、接任或成为恢复后的管理端。管理签名只在活跃前台进行；原生端还要求设备解锁，平台保护分别见 [android-client.md](android-client.md) 和 [ios-client.md](ios-client.md)。网页不具备同等的系统解锁保证，见下文威胁模型。

成员状态从固定的创世状态逐条哈希连接，绑定账户、安全域、Parent、Epoch、ContentEpoch、管理端、恢复公钥、成员 Ed25519/X25519 公钥及累计删除墓碑。只有成员、交换密钥、管理端或恢复公钥改变才增长链。日常续期不会产生状态、重封 grants 或使待恢复声明失效。每次转换由上一管理端签署；紧急恢复另附上一恢复公钥签署的证明。已接受的链只能严格延伸；冲突立即停止安全操作，不选最长链，也不信任中继偏好的分支。用户须核对各设备保存的固定值与状态，再明确重建、重新配对冲突设备；不得自动清除固定值。

内容时期使用随机 32 字节密钥，HPKE 分别封给成员。普通内容轮换以新密钥加密上一密钥写入签名内的 PrevSecret，新成员可沿链读取可达历史，移除成员拿不到新密钥。紧急恢复不带 PrevSecret，形成历史边界。根密钥不派生这些内容密钥，只用于初次注册、旧协议历史和本地项目标记。

租约是独立签名证书，绑定安全域、当前成员 head 哈希、签发和过期时间，由该 head 的管理端签署，最长严格为 72 小时。设备持久化最新接受的租约及时间下界；Android 普通前台同步也持久化本地观察时间，包括 head 未变、没有返回新证书和拉取失败的情况，不依赖控制信封推进下界。设备拒绝换 head、倒退和超长证书；控制和新内容发布检查使用 max(墙钟, 已存下界)。管理端前台剩余不足 24 小时且距上次签发至少 12 小时才续期。server 分发状态和最新租约，端点自行验证；每 60 秒同步，未知状态立即同步。网页、Android 和 iOS 只在目录成功应用后记录对应 head，另保留未完成维护工作；其他读取已经装入 head、目录 RPC 失败、重发连续 CAS 冲突，均不能据此确认已完成，后续轮询即使 head 不变也继续重试。租约过期导致的重发暂停不阻断历史目录读取；续期后自动设备描述和恢复对象重发继续，用户控制命令不因此自动重发。诊断只显示绑定当前 head 的已安装证书的真实到期时间，缺少匹配证书时明确表示未安装。

日常信封由发送者本地签名，随机 nonce，不分配持久发送计数器，也不逐条向管理端取授权。header 绑定状态、时期、发送者、用途、路由、序号和截止时间。控制要求当前成员、当前内容时期及有效租约；所有客户端用内容密钥生成新密文前也必须验证当前 head 的有效租约，包括偏好、设备元数据和恢复后的重新发布，不能只检查 control 用途。Machine 身份只能发布自己机器的内容，Header.Scope 禁止它向其他机器发指令或终端输入。所有已存对象均按其自己的签名状态验签，包括偏好、设备与机器元数据、会话密钥与元数据及其 checkpoint、事件和图片，不因作者移除或正常交接而丢失读取与来源证明；仍校验对象用途、路由和修订号。历史读取不赋予当前控制权限。可变对象按签名修订号 CAS，DeviceMeta 只能由设备自己写。

签署状态、独立租约及恢复/交接声明的时间取系统时间、绑定状态时间和持久化时间下限的最大值；同 head 续期还不能早于已安装证书。恢复声明沿用所签状态的时间，不单独读取时钟。时钟回拨不会产生早于绑定状态的证书。持久安全记录的 CAS 在同一事务或存储锁内读取当前记录，再检查链、证书及阶段单调性；同 head 更新合并已提交的时间下限和密钥缓存，旧快照不能覆盖新租约。

### 安全操作的持久化

建账户、重建安全域、独立租约签发、配对批准、删除、X 密钥轮换、恢复码轮换/否决、管理端交接和紧急恢复共用一条持久 pending operation：父哈希、精确签名字节、完成所需本地密钥材料、交付上下文和阶段。任何发布前先原子持久化；响应丢失或重启后重发相同字节，按已经验证的链延伸核对结果，不能因缺少 ack 另签竞争后继。配对要等候选确认收件才清除；交付过期时，所有者可明确移除已批准的候选成员，再开始新的配对。其他操作完成本地安装后清除。恢复码仅显示并确认保存，不持久化其私钥；普通交接和恢复码轮换未确认保存不得进入发布阶段。紧急恢复已被否决时，客户端提供显式放弃并重新申请的入口：先清除持久操作，成功后再重置页面；待处理、结果未明或已发布但未完成本地采纳的操作不能据此丢弃。

持久流程分别处理三种结果：已确认完成后清除待处理槽（包括候选私钥副本）；网络错误、超时或结果未明时保留并重试；批准过期、权限拒绝或前置条件拒绝时保留证据，并在启动错误页或设置流程提供明确的退出/重新开始入口，经用户确认后清除本机密钥和待处理项。不能只留下重试按钮。创建/重建草稿返回其创建界面继续凭据、工作量证明和恢复码确认，不把 proof-required 当作账户存储损坏。注册重试的签名注册字节与批准保持不变；未签名的 setup token 可由用户更正、signup proof 每次重试重新获取，独立 lease 可在不改变签名状态的前提下更新。每次发送仍先持久化实际请求。

Go daemon 在 Ready 后立即读取 stream 和回应 ping，再同步或发布 checkpoint；普通重连检查已完成发布 marker，不无条件重发。成员事务一旦提交，立即撤销被移除设备的所有 stream 和 hub 连接，再执行独立 lease 等后续可失败步骤。daemon 注册被拒绝时日志明确提示 `remote-agent account discard-registration`，用户执行后释放重试槽，再在管理端移除未完成候选并用新码配对；签名所有权回执作为非待处理档案保留，以便获管理端批准后接回旧会话，不恢复已撤销身份。

### 配对

当前管理 Client 发起配对。双方先承诺再揭示临时 X25519 公钥，承诺和四图案 SAS 绑定安全域、双方临时公钥、候选身份及类型；候选先确认，管理端再允许。四端在发送候选公钥前，先把候选的长期 Ed/X 私钥存入本机安全存储；草稿按服务器和固定的配对请求 id 隔离，同一请求复用草稿、不能被并发配对覆盖；新的配对请求生成新候选，避免复用可能已被撤销的未完成候选。收到并验证批准后，先原子保存可恢复的私有注册意图（精确注册请求、管理端签名批准、身份密钥、固定值、完整链及解密材料），再安装安全状态和账户，最后注册并确认收件。网页、原生客户端和 daemon 启动时先恢复该意图；网络失败保留它，响应丢失后仍重发同一请求，不重新占用配对槽。SAS 上下文在内存中五分钟过期；一旦签出成员转换，其发布与载荷交付即由持久安全操作接管，进程退出不能遗留无从完成的半个成员。

普通加入轮换内容密钥并带 PrevSecret；载荷含公开账户密钥、固定值、完整链和最新租约，不含根密钥。配对仍限制 256 状态、800 KiB，超限明确提示重建。已有本地协议 10 固定值必须完全一致，且链只能延伸。重新配对保留未被移除的 Ed 身份、替换 X 密钥；移除身份不可复用。旧 daemon 管理端、逐信封授权 RPC 和旧配对命令不保留。

账户公钥是公开资料，不是根密钥，也不能从 accountId 反推。新建、配对和恢复收到后先验证其 ID，再按服务器、账户和创世固定值持久保存为独立条目，不修改已有账户或安全记录格式。已有网页／iOS 成员缺此资料时，接任前优先重新配对一次：保留未撤销 Ed 和 pin，替换 X。也可在接任后用刚保存的新恢复码仅查询 recovery context，核对账户公钥、创世前缀与本地链延伸后补齐资料；不提交恢复、不启动 48 小时等待、不保存输入 seed。

### 删除与执行隔离

当前管理 Client 签署移除状态并轮换内容密钥。诚实 server 收到后立即吊销成员登记、token、推送和连接，保留机器、会话、事件和图片密文，按正常保留规则处理。管理端只对已不在成员列表中的电脑提供有确认的「删除这台电脑的记录」，server 在删除事务中再次拒绝当前成员；此操作清除中继档案但不删除本地 transcript，不把此操作混入吊销。

被移除的电脑以新 Ed 身份重新加入。管理端从原电脑的保留档案进入「重新加入并接续会话」，核对 SAS 后，在配对批准中签署候选公钥及被替换的 revoked device id；原电脑核对该 id 与自己的旧身份一致。server 在注册事务中验证当前管理端批准，且旧 id 已撤销、属于同一账户、不是当前成员、仍有机器档案，才把其机器、会话和图片行转到新 id。准入消费、配额检查和记录转移一起提交或回滚；事件和密文字节、会话 id 与序号不变，不恢复旧登记、token 或成员资格。未选择原档案的普通配对不转移记录；要接续仍保留在中继的同 id 会话，必须从原档案进入重新加入。

电脑持久保存签名替换证明，并随当前会话元数据发布。客户端以已验证链中候选首次加入时的管理端、公钥和旧机器移除状态验证连续替换关系，再接受缓存会话的新路由；历史事件和图片仍按原发送身份验签，只对证明涵盖的旧机器放行历史路由，不改写密文或放宽实时控制路由。多次移除、重新加入保留证明链；候选首次加入时的证明时限校验容许协议已有的五分钟时钟偏差，历史读取不按当前墙钟重新判过期。已显式删除中继档案的电脑按新设备加入，不存在可转移的记录，也不携带旧身份的替换证明；同一 Ed 身份的 X 轮换保留原证明链。

恶意中继扣留新状态时，旧 head 最多还有 72 小时有效期。到期后 daemon 拒绝新控制，并停止发布新会话内容（事件、元数据、图片、通知和实时终端），本地缓冲，CLI 继续运行。网页、Android 和 iOS 同样停止生成任何新内容密文，界面说明更改暂时无法保存，要求打开当前管理端续期；已保存的历史读取不需要有效租约。续租或安装更新状态后以当前时期重试；不能承诺租约过期时继续实时查看。已经受理的操作和定时任务不会被租约撤销。

执行 gate 包住校验、持久受理和结果记录，业务回调与结果加密在 gate 外；已经持久受理的操作可以完成，安全状态安装和关闭不等待业务 I/O。稳定请求 ID、原意、截止时间及有界持久受理日志保证最多受理一次，崩溃结果不明时不重做；持久时间下界防时钟回拨。中继错误不证明未执行，未知请求不得通过延长截止时间重做。

### 当前操作与历史

每台拥有会话的电脑按会话持久保存当前状态 checkpoint：当前快照放进 Session.current_checkpoint，和会话密钥一起以当前内容时期的信封保存为 current-checkpoint.pb，再上传。它包含可独立建立会话状态的快照及历史位置。启动、内容时期改变和本地状态变化后将 checkpoint 标为待发布，失败保留，直至当前时期发布成功；恢复和普通加入走同一 bootstrap。检查点生成、大小或落盘失败只使当前 bootstrap 保持待发布，不阻断该会话普通元数据和事件的上传；后续安全同步重试，不能把截断快照标为完整。它不要求客户端解开历史前缀，也不自动传输旧密钥。只发布当前快照，旧事件和图片保留原密文。

客户端分别呈现“历史密钥不可用”“等待所属电脑更新当前状态”“密文无效”。恢复边界是正常缺口，不触发损坏修复或无止境重拉；当前输入、审批和运行状态由验签的新鲜快照建立，操作仍绑定事件位置和摘要，执行电脑在后端会话同步保护下核对。旧 root 信封仅供未验证阅读。

各端只接受 HTTPS，中继开发允许 loopback HTTP（Android Debug 还允许模拟器地址）。API 拒绝重定向；浏览器 WebSocket 受浏览器能力限制。账户根密钥串仅为离线旧内容材料，不授权加入或恢复。

### 管理与恢复

正常交接：目标先作为 Client 配对加入，不按平台筛选。目标生成新恢复码，用户确认离线保存后只发布其恢复公钥；旧管理端核对并签署管理端变化、轮换内容密钥并带 PrevSecret，同时移除自己。新管理端负责签发新 head 的租约，旧端不能代签；目标未前台完成续租时，控制可能短暂停顿。唯一管理端不变成多管理端；不用 48 小时等待，也不产生历史边界。操作通过上述持久流程完成。

丢失管理身份：恢复码是紧急管理权凭证，由随机 seed 派生 Ed25519 私钥，附创世哈希前 10 字节。它不直接解开已存密文，但恢复成功会取得保留电脑的控制权，攻击者可能让原生 CLI 读取旧文件，当前终端快照也可能含早先内容。必须离线妥善保管。诚实中继验证恢复声明并等待 48 小时；旧管理端可签署更换恢复公钥的新状态否决，独立续租不会否决。恶意中继持有码时可以绕过等待和推送；创世指纹不证明最新 head。冲突仍安全停止。

恢复使用一张可重启继续的页面：显示截止时间、新码是否已保存、等待哪些保留电脑发布 checkpoint。恢复声明、设备身份、交换密钥和完成阶段在发布前持久化；不靠推送推进。新 Client 成为管理端，旧管理端被移除，新内容时期不带 PrevSecret。保留电脑上线后发布当前 checkpoint，新管理端能看当前会话，但不能自动读取恢复前历史。

新账户在管理 Client 本机生成根、身份、恢复公钥和创世状态，先持久化安全操作及精确注册请求再注册和固定；启动时重试已存的注册请求，恢复码确认仍由建立账户流程完成。旧账户重建也先保存精确创世状态、X 私钥和内容密钥，再尝试网络固定或导出离线固定；重启从同一草稿继续，不生成竞争创世状态。恢复码不再显示时，用户沿用已有离线备份，未备份则在采纳后立即更换恢复码。中继固定创世状态并完整校验账户与唯一管理端；旧账户高级保留升级须停服离线固定，不能让旧 token 抢首次固定。这里的重建仅针对协议 9→10 的旧协议升级；现有协议 10 账户开放其他 Client 管理能力不改协议、状态版本和存储格式，不要求重建账户。网页和 iOS 不新增旧协议迁移界面，旧协议步骤见[升级指南](self-hosting.md#upgrading-to-the-phone-authority-protocol-10)。

安全提醒不保证送达，恢复不靠推送推进。iOS 首版允许担任管理端，但没有后台安全提醒，不以 APNs 为前置条件，建议每天打开一次；不能保证在 48 小时内看到恢复申请。网页 Web Push 同样不能保证送达。前台每次同步都读取待恢复提示，即使 head 不变也更新；提示只表示中继的可用性信息，不是授权，否决仍需签署新状态。自动续租条件仍为剩余不足 24 小时且距签发至少 12 小时，不能把“每 72 小时打开一次”当作离线可用保证。

### 威胁模型与边界

- 中继看到公开路由、成员、租约和密文长度，可拒绝、扣留、回放或删除；没有端点私钥时不能伪造状态或信封，也不能解密内容。
- 单台成员电脑被攻破会泄露账户范围内可达的内容和历史密钥；不会自动愈合。Machine 的签名权限不能用于向其他机器发控制。管理 Client 被控制则能更改成员；网页注入或恶意同源脚本可使用页面密钥。
- 租约限制新控制与新内容发布的撤销窗口，不收回下载、旧密钥、已经执行的操作或排程。诚实中继立即吊销，恶意中继最长可拖至旧租约到期。
- 恢复码是紧急管理权凭证；诚实中继的 48 小时延迟不是对恶意中继的保证。恢复不直接解开旧密文，却赋予对保留电脑的未来控制。
- 只持恢复码的新客户端不能证明状态链最新；已固定设备拒绝冲突，用户负责核对并重新加入。管理身份与恢复码都丢失只能重建。

浏览器私钥以不可导出 CryptoKey 保存于 IndexedDB；不可导出只限制导出，恶意同源 JS 仍能调用签名和解密，保留的旧 root 材料也可被页面脚本使用。因此网页托管、发布账号、依赖与扩展都属于端点信任边界，不能声称其密钥保护等同原生端。网页可以担任管理端，但创建或接任前须说明托管代码和存储清理风险、确认恢复码已离线保存，并请求 navigator.storage.persist()；持久存储不能阻止用户清除数据，建议日常由原生端管理。不增加口令派生、云备份或多管理端。

安全状态部分损坏且仍有 pin 时必须停止，不能自动清 pin；整个网页来源的数据被清空后无法证明本机曾是管理端，只能依靠离线恢复码找回。不同网页来源各自配对。显式退出唯一管理端仍被允许，但须说明先交接、无恢复备份会丢管理权，pending 结果未明时应先核实，不能无提示丢弃唯一完成材料。

### 一台中继上的多个账户

范围见 [scope.md](scope.md) 第 2 节：账户之间看不见、改不动对方的任何东西。实现在 `internal/server/accounts.go`、`signup.go` 和 `store.go`。

**账户 ID 由 server 推出**：账户 ID 是账户公钥 SHA-256 的前 16 字节（和设备 ID 一样的算法），登记时从签名验证过的登记原文里取，客户端不能自己报。设备 ID 由设备公钥推出、全局唯一，一台设备只属于一个账户；被删除的设备在所有账户里都不能再登记。

**隔离靠 tenant**：所有账户数据放在同一个 SQLite 里，每张账户表都带 `account_id`：会话、事件、图片和偏好的主键以它开头，设备、机器、token 和推送订阅的主键是全局唯一的设备 ID 或 token 哈希，按账户查的索引以 `account_id` 开头。登录后的每个请求从 token 找到设备、再找到它的账户，处理函数只拿得到这个账户的 `tstore`（每条 SQL 都带账户条件）和 `accountHub`（只广播给这个账户的流、只找这个账户的机器）。处理函数里没有能指定别的账户的参数，所以漏掉检查也不会跨账户。终端流按「账户/流 ID」配对；推送的去重键、配对、登录 challenge、流和推送并发都按账户另有上限，一个账户占不满全局的份额。额度按写入所增加的那一项检查，某项满了只挡增加这一项的写入。额度之外的写入也有界：偏好对象按额度计数，每台设备最多留 16 个登录 token（再登录挤掉最旧的），trial 账户删除过 64 台设备后不能再加设备（记录最多七十来条），存过的图片（含已过期、只留一行的）最多 2 万张；一次没建成账户的注册不消耗工作量证明和地址的配额。同一个会话 ID 在不同账户里互不相干。

**SQLite 并发**：WAL 模式下，写入和事务内读取共用一个串行 writer 连接，保留 `synchronous=FULL`、5 秒 busy timeout 和外键检查；另有最多 4 个只读连接（`mode=ro`、`query_only=ON`，同样的连接级设置）服务独立的历史、图片、列表、偏好和 bearer token 查询。每个 store 方法明确选择连接，不按 SQL 文本猜读写。配额检查、安全状态与恢复流程、写入前后的设备和账户检查仍走 writer；写事务需要返回刚写入的数据时，也在同一事务内读取。读池不持有跨请求的事务，撤销 token、移除设备或暂停账户提交后，新开始的 token 查询会看到已提交的状态；已经开始的 WAL 读快照不受后来的写入影响。

**建账户的两种方式**（`--signup`）：

| 方式 | 谁能建 | 额度 |
|---|---|---|
| `token`（默认） | 带 server 配置里的 setup token | owner：32 台设备、16 台机器 |
| `open` | 任何人，先完成工作量证明：`GetSignupChallenge` 给一个 5 分钟有效的随机 challenge，客户端找一个 nonce 让 SHA-256(challenge‖nonce) 有足够多的前导零位（默认 20 位，普通电脑一秒内） | trial：8 台设备、2 台机器、200 个会话、256 MiB 事件、64 MiB 图片 |

open 模式下带对 setup token 的照样建 owner 账户。工作量证明挡批量脚本，另有每个地址每分钟 10 个 challenge、每小时 3 个新账户，全局每小时 30 个新账户；地址只认 `--trusted-proxies` 里的反向代理写进 `X-Forwarded-For` 的最后一跳，IPv6 按 /64 计。全中继最多 `--max-accounts` 个账户（token 模式默认 1，open 默认 100），每分钟检查一次磁盘，剩余不足 `--min-free-bytes`（默认 2 GiB）期间，所有账户都不能再添加设备、会话、事件、图片和偏好对象。没有协议版本变化：server 用错误码告诉客户端缺什么（缺 token 回 PermissionDenied，要工作量证明回 FailedPrecondition），daemon 照着补上再试。

**运维**：`remote-agent-server admin` 直接打开数据库，列出账户（只有 server 本来就看得到的计数和大小），暂停、恢复、换额度或删除账户。暂停的账户不能登录和登记，数据保留；运行中的 server 每 30 秒扫一遍在线的流（主流和终端流），断开被暂停、删除的账户的设备。server 不会自动删除闲置账户。

**存储格式**：数据库带 `PRAGMA user_version`。单账户时代的数据库（没有版本号但有表）server 拒绝打开并提示迁移，不写迁移代码；迁移步骤在 [self-hosting.md](self-hosting.md#upgrading-to-v0410)。

### 多客户端的界面状态

每个会话属于固定机器和 CLI。已接受的消息、队列、模型、模式、上下文与处理结果是共享状态，以 daemon 发出的事件与元数据为准；项目列表偏好跨端同步；客户端草稿、当前视图、滚动位置和通知偏好各自独立。多端输入仍按到达顺序注入，不增加会话独占。某个客户端断线只说明它的数据可能过期，不意味着电脑或其他客户端离线。

### 断线时显示什么

从客户端到电脑要经过三段：本机网络、服务器、电脑。客户端只报离自己最近的那一段故障，并且只在连接提示条一处说；更远的一段此刻无从得知，不沿用断线前的说法。界面见 [client-v52 · 断线](design/client-v53.html#link)。

| 判断 | 结论 | 没结束的会话 |
|---|---|---|
| 连着服务器 | 无提示；电脑在不在线以服务器说的为准 | 照常 |
| 系统说本机没有网络；Android 上解析不出服务器地址也算 | 本机网络不通 | 未连接 |
| 有网，开始连接或断开不到 10 秒 | 正在连接，不下结论 | 保持原样；这次启动后还没从服务器取到过列表时算未连接 |
| 有网，10 秒后仍没连上 | 连不上服务器，原因在详情里 | 未连接 |

- **为什么不沿用旧状态**：缓存里的电脑一律当作不在线读出来，断线前的「运行中」也可能早就结束。照旧显示会把本机没网说成电脑离线。已结束是不会变的事实，照常显示；等待审批的卡片和计数也保留，它们不会因为断线消失
- **10 秒**：切换 Wi-Fi 和蜂窝、服务器重启通常在几秒内恢复，这段时间只转圈。网络回来时重新计时
- **本机有没有网**：Android 用系统的默认网络回调，没有默认网络就是没网，失去时立即断开当前连接，不等心跳超时。不用系统的「已验证」标记：它依赖系统自己的探测地址，探测不通不代表到不了自部署的服务器。信号满格但实际不通时系统仍报告有网，这时解析服务器地址会失败，所以把解析失败也算作本机网络不通。浏览器只有 `navigator.onLine`，分不出「有网但不通」和「服务器停了」，统一说连不上服务器，并在详情里写明两种可能
- **电脑为什么不在线**：服务器只知道 daemon 的连接断了，分不出睡眠、断网还是程序退出，状态卡把三种可能都写出来。要区分需要 daemon 退出时告知服务器，属于协议改动，没有做
- **连接检测**：连着但慢、或时断时续时，上面这些提示什么都不说，所以另有一个手动的检测（设置里，以及宽屏侧栏底部的连接状态），按段测一次往返：到服务器是三次对 `/healthz` 的请求，取居中的一次，免得第一次建连或一个慢包算进去；到电脑是一条只读设置的加密指令（`getSettings`），走和真实操作相同的路：客户端 → 服务器 → daemon → 服务器 → 客户端。两者都是 server 和 daemon 本来就应答的请求，不用改协议。网页另列实时推送的主连接状态；请求往返成功不代表主连接已恢复，断线时说明会话变化可能延迟，并显示最近一次连接失败原因。服务器没回应时不再测电脑。服务器 500 ms、电脑 1500 ms 以上标「较慢」，是初始取值。只在打开和点「再测一次」时测，不在后台常测：常测要耗电和流量，而延时只在觉得慢的时候才有人看
- **读取失败**：没连着服务器时读取历史失败不单独提示，连上后自动补齐；连着时才在原处给出红条和重试，原因写成中文，底层错误只出现在详情里

设备目录和来源展示：server 只提供设备 ID、设备类型、签名状态链与加密元数据；成员身份以签名状态为准；人类可读的客户端名称不以明文登记。客户端名称放在独立用途密钥加密的元数据中；消息与队列的发送设备 ID，以及处理来源写在加密事件内，由 daemon 按已认证的指令来源记录，不能信任客户端自报的来源。来源没记录或无法可靠匹配时不写具体设备：消息不写来源（客户端判断是在电脑终端里输入的写「<机器名> 终端」），审批、提问写「另一端」，不猜具体设备，也不凭卡片消失推断允许或拒绝；怎么写见 [design-system §8](design-system.md#8-文案) 的「来源」。server 另外记下每个客户端主连接最近一次连上或断开的时间，和电脑的最近在线时间一样是明文；设备目录用它写「上次使用」，让人认出早就不用的客户端并移除。上次使用不代表正在观看或有独占权。

其他端处理了审批或提问时同步收回卡片，普通消息草稿保留；正在输入但未提交的拒绝理由暂存在本客户端，可复制，不能自动当作下一条审批的理由。终端尺寸属于共享 tmux 窗口，任何端主动适配后，所有端按收到的新尺寸更新；不能仅根据自己之前点过适配来显示「已适配」。取消适配与断开时遵循第 11 节的 latest 规则，不承诺恢复旧设备记录的尺寸。

## 10. 报文、同步和指令

字段以 `proto/remoteagent/v1/{envelope,relay,remote}.proto` 为准，这里只写约束和理由。

**信封**：内层先编码成 Protobuf，再用 AES-256-GCM 加密。`Header` 写明用途、机器、会话、序号或请求 ID、截止时间和发送方，序列化以后**原样**作为附加数据参与认证，接收方解开后按原始字节解码，从不重新编码。接收方逐项核对 header 和信封所在的位置（哪台机器、哪个会话、第几号、哪个请求），所以 server 没法把一个信封挪到别处。信封使用独立随机 12 字节 nonce，消息密钥绑定完整安全范围；不分配持久发送计数器。server 也会读 header（它是明文），只用来尽早拒绝放错位置的请求，安全性不依赖这一步。

**压缩**：密文压不动，所以压缩在加密之前做：内层超过 256 字节、且压缩后更小时，用 DEFLATE（RFC 1951，不带 zlib 或 gzip 的头）压缩后再加密，`Header.compression` 写明，它和 header 其余部分一起参与认证。会话密钥、图片和配对载荷不压缩：前两者压不动，配对发生在两端核对协议版本之前。接收方解密后按 header 解压，不认识的压缩方式一律拒绝，解压结果超过 64 MiB 也拒绝，免得一个小信封撑爆内存。选 DEFLATE 是因为它到处都有：Go 用 `compress/flate`，Android 用 `java.util.zip`；网页打包了 fflate（MIT，纯 JS），不用浏览器的 `CompressionStream`，因为 `deflate-raw` 这个格式在各浏览器里出现得比网页其余依赖的能力晚，而解不开压缩的客户端就读不了 daemon 发来的任何东西。事件、元数据、指令和终端输出都走这条路，server 上存的事件密文也跟着变小。代价是密文长度会反映内容的可压缩程度；server 看不到明文，也没法往同一个信封里掺入自己选的内容反复试探，所以不构成 CRIME 那样的攻击。HTTP 层保留 Connect 默认的 gzip 协商和请求解压：历史响应的重复信封元数据和 JSON 的 base64 仍可压缩。只有 Connect protobuf `GetImage` 响应关闭压缩，因为二进制图片密文几乎不能再缩小；gRPC 和 gRPC-Web 的策略不变。

**daemon 事件提交**：所有运行期事件共用追加并投影的入口，持久化成功后统一 `observe`，包括排序和 attention 时间；失败不做投影。原始 transcript 已由 parser 处理，不重复 Replay；设置、hook 和推断的轮次结束只在提交成功并持有读取锁后补相应 parser 状态。fork 初始化时尚无 session，历史写入后由 `newSession` 统一重放。设置、计划回答和远程审批回复的调用方会收到提交错误。设置或计划操作已经在原生 CLI 生效时，错误明确说明「电脑上已生效但没能记录」，不自动重做。审批请求先落盘才加入待审批列表；允许审批先落盘才认领请求并交给 hook，提交失败仍可重新回答；拒绝审批即使提交失败也照常交给 hook，并向远程调用方说明拒绝已交出但结果没能记录。审批请求无法记录、超时拒绝或其他拒绝结果无法记录时，hook 仍成功返回拒绝 payload，不能把记录错误当成传输错误，否则 CLI 会丢弃拒绝并退回原生审批；记录失败另由本机诊断和限频日志报告。hook 报出的提问和计划也在提交后才记为已报告。输入队列继续以 `queue.json` 保存受理和崩溃恢复状态；所有保存共用一个入口：先确认队列持久化，再尝试同一锁内的状态通知，保存成功则无论通知是否失败都唤醒注入器。入队、解除暂停、held 释放/重排、恢复和取消等均遵守此规则；同一请求 ID 的重试也只唤醒已有消息，不重复入队；队列保存成功、通知失败统一标记为已持久受理的记录错误；各队列调用方用同一个判别入口识别，不能把它当成未入队、清除跟踪或释放图片。同步 RPC 仍返回明确的记录错误，发送错误带原请求 ID；首条消息已经受理的新会话继续登记并管理，错误带已创建的会话 ID，不能按未启动清理。恢复输入和取消 held 后释放其他消息同样说明已经恢复或重新排队；已保存的消息仍可能发送，不能换请求 ID 重发。普通 RPC 当前不能同时返回成功结果和警告，客户端仍按通用错误呈现；结构化表达已受理及记录警告的协议设计未定，见 [plan.md](plan.md#待确认)。终端写入前的阶段错误不表示受理失败，注入器继续保留原消息等待重试。终端写入前的首次 PASTING_IMAGES、其他变化阶段和 SUBMITTING 事件先落盘，再保存对应队列阶段或 inflight 标记；任一步失败都恢复内存的未写入状态，不推进投递 gate，因此事件追加失败时不需要额外向故障磁盘写一份队列回滚，也不会因该失败把消息误判为 UNCONFIRMED。只有两步都成功才允许实际写终端；这不改变已写入消息的保守崩溃恢复规则。暂停保存失败时，运行期和启动恢复均保留内存的安全暂停，不发布未保存的 paused 通知；已提交的中断记录让下次启动重新保存暂停。最终取消/提交结果已经持久化、随后队列清理失败时，仍唤醒其余输入，重启按既有最终结果对账。后台状态观察没有同步调用方，提交失败不推进事件投影，下次观察继续尝试。存储故障保留在 daemon 内存，并尽力把本机快照写入状态目录的 `diagnostics/`，由 `remote-agent ls -a` 的独立诊断列直接读取；该目录与会话日志目录分开，便于诊断日志目录不可写的情况。下一次真实事件写入成功或成功恢复会话时清除运行期快照；诊断快照更新失败时可能保留上次观察时间，不能当作实时状态保证。整个文件系统已满等故障也可能阻止诊断快照保存，此时只有限频日志。每会话故障日志最多每分钟一条，不记录内容。诊断不进入 `Session.StatusDetail`，不触发 relay 元数据更新；客户端能否另加协议字段显示存储故障未定，见 [plan.md](plan.md#待确认)。

transcript 读取只把当前读批中已取得的行合并提交，每组最多 8 行、序列化后最多 1 MiB；单行超过上限时独立提交，仍保留整行事件的原子性。不等待后续行填满分组。需要消费来源标注或执行用户消息、问题回答、轮次结束、工具完成后续动作的行会提前结束分组，下一行在这些动作完成后才解析。每组一次写入和 Sync，成功后才发布序号、缓存、检查点、事件投影和通知；写入或 Sync 失败时截断整个未提交组，保留此前组的内存与日志状态，并重建 parser 后重读。远程审批回复等交互写入仍独立提交。磁盘格式不变，每条原始行仍有自己的批次标记和检查点；进程崩溃后的组内完整行前缀可能保留，但当时尚未向运行期读取者发布，重启从最后幸存行的检查点续读，不重复或遗漏事件。撕裂行所属的整条原始行事件仍全部丢弃。

**CLI 解析诊断**：适配器明确区分已知的无事件记录、未知类型和解析错误。已知元数据或重复记录直接忽略；未知类型和坏行在会话目录的 `parse-health.json` 中持久保存累计次数、最近字节范围、记录类型和错误类别，既不保存正文，也不保存可能引用输入值的原始错误字符串。同一路径的 transcript 缩短，或运行中的 reader 发现文件身份变化时，先持久化诊断水位失效，再读取新内容；累计次数和最近错误保留，新内容的坏行重新计数。重置同时记下路径和当时最后一条持久 transcript checkpoint 对应的事件序号，在新 transcript 事件提交前忽略属于旧内容的事件 checkpoint，避免重启再次把同一次重置当成新文件而重复计数；新 transcript 事件提交后恢复使用其 checkpoint，其他 daemon 事件不解除这条重置标记。水位重置写入失败时不消费新内容，并在运行期保留待重试标记，即使文件随后长过旧位置也先重试重置。普通重放不清水位，已有坏行不重复计数，真正解析错误仍受每会话每分钟一条的日志限制。本地 `remote-agent ls -a` 直接读取诊断文件，daemon 重启不清零；诊断不是会话恢复依据，文件不可读、损坏或截断时只在本机日志记录不含内容的错误类别，内存从空诊断开始，正常的元数据、事件和队列照常恢复并接受操作。文件访问允许时，下次保存诊断直接覆盖坏文件，不自动删除目录或修改权限；共享的 `local.proto` 同时被远程命令和客户端使用，因此不在其中添加诊断字段。`Session.StatusDetail` 只保留 CLI 状态说明，包括精确的 `stopped` 退出原因。未知记录只计数，在显式查询时作为普通诊断显示，不记故障、不发告警；真正的解析失败按会话最多每分钟记录一条不含正文的警告。超长行无法压缩时也作为失败记录交给 daemon，不能在 tail 层静默丢弃。

完整行的确定性解析失败不循环重试：适配器先完成可能失败的字段校验，再修改持续状态；返回错误时必须保留此前有效记录的待处理状态。保存诊断后继续使用原解析器，不因未知类型或坏行重建事件投影，否则会丢掉尚未产生事件的 ImageView、用户图片暂存等信息。这样一条永久坏行不会卡死会话；保留字节位置供人工检查原始 CLI 文件。诊断无法保存时不越过该行，只恢复到该行起点后重试，仍保留原解析器的先前有效状态。诊断与事件 checkpoint 是两次写入，按同一 transcript 的位置去重，防止在两者之间崩溃导致重复计数。跳过不合成轮次结束，不靠无输出时间推断结束；缺失的语义可能使会话继续等待，用户可查看原生终端。当前诊断保留汇总和最近位置，不提供自动重放或补全坏行内容。

**定时事件**：任务注入的用户消息在 `Origin` 中持久保存任务及运行 ID；daemon 在追加轮次结束事件前补上相同 ID 和是否通知的标注，不能修改 CLI 自己的 transcript。relay 补传只看已提交的事件标注，不依赖活跃任务表。`ScheduledNotification` 是 daemon 生成的持久事件，和结束标注一起供客户端折叠连续静默的定时轮；实际折叠界面留到客户端阶段。

**事件上传**：daemon 连上后先查 server 已有到哪个序号（`ListSessionHeads`），再按序号从后面接着传；server 只接受紧接着的序号，已有的跳过，有空缺的拒绝。server 已有的会话先传事件、再传元数据：事件是客户端在等的东西，先传元数据会让每批事件多等一次往返。daemon 记住每个会话上次传过的元数据，重连后只传有变化的；已结束会话的记录还写进会话目录（`relay.sent`，用会话密钥算的摘要，不含内容），重启后 server 仍持有同一修订号就不再重传，其余已结束的会话一次只同步一个，给进行中的会话留出请求名额。重试时同一序号的事件会用新 nonce 重新加密：本地日志里每个序号对应的内容不会变，所以解出来的明文相同，server 保留第一份。每个会话一把密钥，随机 nonce 的数量远低于 GCM 的使用上限。

事件加密前按未压缩 Protobuf 大小限制为 768 KiB，本机日志保留全文。先去掉最大的图片预览，再缩短显示文字；截断保留 UTF-8 边界，每个被缩短的字段都带「…（remote-agent：内容过长，已截断）」尾注，工具输出同时设 `output_truncated`。这种普通截断保持 kind、ID、序号、状态和全部选项标签。审批的说明、命令或工具输入出现该尾注时，三端显示「内容被截断，请在终端查看」，禁止允许及以后不再问，仍可拒绝。

仍超限时，先缩短选项标签；如果还放不下，就保留同 kind、序号和标量状态的骨架，每个重复字段最多保留首项，其他长文字限长，二进制载荷和未知字段去掉。保留的正常 ID 不改；只有这份最小骨架仍超限，才将超过 4096 字节的 ID 改为原文的 UTF-8 前 64 字节、`…#` 和 SHA-256 前 16 个 hex。重复成员被删减、标签被改写或降为骨架后，不允许客户端再按不完整内容或改写 ID 回答。

骨架在现有文字字段或改写 ID 中带「…（remote-agent：内容过大，请在终端查看/回答）」尾注，不新增协议字段。三端为全部事件 kind 显示「内容过大，请在终端查看/回答」，审批（包括拒绝）、提问、计划和队列操作均不提供远程操作。daemon 在原始事件成功落盘及启动重放时计算相同的降级结果，随待处理审批、问题和计划保存安全性；回答时只查表，不读取历史或重新裁剪。普通截断审批只允许拒绝，骨架拒绝全部回答；原 ID 与改写 ID 都检查，改写 ID 即使碰到另一请求也不会执行。限制不依赖上传游标或客户端版本，重启时由原日志重放重建；本地 CLI 和原生终端不受影响。通知使用同一降级结果，三个审批文本字段中已有的截断标记也计入通知的 `truncated`，不携带骨架审批按钮；骨架通知以会话序号去重，不把改写 ID 的内容前缀放入明文去重键或头部。原文恰好以相同尾注结束时也保守地引导到终端。事件不再以 `event_size` 永久失败，不替换 kind、不跳过序号，后续历史继续同步。

上传成功的游标在后续步骤失败时仍保留；通知欠账在没有新事件可传时也重试。本地读取在坏记录处中止时，先提交已解码的合法前缀，前缀提交失败时返回该提交错误；坏记录恢复尚未实现，见 [计划](plan.md#待确认)。Android 系统通知布局截断的待确认事项也仍见该计划。

会话同步的故障独立处理：本地密钥、元数据、事件读取或加密失败，以及 server 对会话上传的业务拒绝，只让该会话按 1、2、4、8、16、32、60 秒退避，封顶一分钟；其他会话继续同步和接收指令，追平后清零退避。RPC 鉴权失效（`Unauthenticated`）、连接不可达（`Unavailable`）、取消或超时仍结束本次连接并重连；整机元数据和会话 heads 请求失败也仍属连接级。server 已有会话但本地密钥丢失时跳过该会话，不生成替代密钥。图片降级和通知欠账仍按各自规则处理。

同步受阻时，daemon 记录 `relay: session sync blocked`，包括会话 ID、错误类别和该次记录时的下次重试时间；同一会话连续故障首次记录，此后至多每分钟一次，追平后记录 `relay: session sync recovered`。不记录原始错误文本，避免会话内容或路径进入新增诊断日志。现有本地接口没有独立同步诊断字段，`doctor` / `ls` 不展示该状态；限频期间日志中的重试时间不会逐次刷新，连接重建后重新核对 heads 并重置本轮退避。

**客户端同步**：先连上 WebSocket，再拉会话列表的第一页（[第 8 节](#会话列表分页)）和缺的事件，这样两者之间不会漏掉。server 先写库再推送；客户端按序号去重，推送来的事件如果前面有空缺，就先放着，再用 `GetEvents` 补齐。会话和机器的元数据带递增的修订号（header 的 `seq`），客户端只接受更新的版本，server 也只保留最新的。

**指令**：客户端的指令统一走 `Forward`，header 里带 128 位随机的请求 ID 和 60 秒后的截止时间。daemon 的处理规则：

- 截止时间已过的拒绝；比现在晚 10 分钟以上的也拒绝，并提示检查时钟
- 执行前先把请求 ID 记为「开始」并落盘，执行后记下结果，也落盘（`commands.json`）；文件无法读取或格式损坏时禁用远程指令，保留原文件，修复并重启后恢复，不把损坏记录当作空记录
- 同一个请求 ID 再来，直接返回记下的结果；如果只记了「开始」没有结果，说明上次执行到一半 daemon 停了，返回「结果未知」，**绝不重新执行**
- 记录保留到截止时间过后，因为过了截止时间的指令本来就会被拒绝

执行门只串行完成当前授权、接受记录和结果记录，不跨业务回调或业务侧的文件系统、CLI、网络 I/O。变更请求在持久化「已接受」时确定先后：撤销阻止此后接受新请求，已经接受的工作可以完成；各后端用自己的同步保护业务状态。安全状态安装和 endpoint 关闭不等待业务 I/O；若关闭先于回调完成，保留持久化的在途记录并返回结果未知，同 ID 重试绝不重跑。所有后端调用收到签名请求的截止时间。目录和只读文件快照查询另有本地等待上限和有界 I/O worker；无法取消的系统调用退出前保留 worker 配额，但不持有 endpoint 或 daemon 锁。

server 把指令原样转给那台机器的 WebSocket，最多等 30 秒。机器不在线时立即返回「不可用」，**不排队**；已经转发出去但没等到结果时，返回「可能执行了、也可能没有」，客户端用同一个请求 ID 重试即可。

**WebSocket**：路径 `/v1/stream`，承载二进制 Protobuf 帧。浏览器的 WebSocket 不能自定义请求头，所以第一帧发 token，认证通过前 server 不发任何数据；浏览器连接还要检查 `Origin`；原生 App 不发 `Origin`，server 用的 coder/websocket 对没有 `Origin` 的请求直接放行，App 同样靠第一帧的 token 认证。server 每 20 秒 ping 一次；发送队列超过每连接 256 帧或 16 MiB、每账户 32 MiB、整个中继 96 MiB 中的任一预算，就断开当前接收方，由它重连后从历史补。广播共用不可变的序列化字节，但每个接收方各占一份字节预算，直到写完或断开才释放；只数帧不够，一帧事件可以接近 1 MiB。Android 的主连接和终端连接也每 20 秒 ping 一次，换网络后悄悄断掉的连接靠它发现；浏览器发不了 ping，网页改为给建连设 15 秒上限，并在浏览器报告网络恢复时跳过退避立即重连。两端都留着上次登录的 token，回到前台直接用它开连接；只有 server 以 1008 拒绝第一帧时才丢掉 token 重新登录，网络丢掉的握手不算。每台机器同时只保留一条连接，新连接顶掉旧的。主连接和终端连接在 token 到期或设备被移除时都取消，认证登记和移除共用锁，避免连接在移除期间重新进入。

**后台和内存**：原生 App 进入后台时关闭主连接和终端连接；网页隐藏后设 60 秒宽限期，避免短暂切换应用或标签页就重连，`pagehide` 或 `freeze` 则立即关闭。网页回到前台时检查主连接最后收帧时间，超过默认心跳间隔加余量就立即重连，健康连接继续使用；终端跟随主连接，隐藏时不调整远端窗口尺寸。连接已关闭时回前台重新同步；有缓存内容的网页延后 1.5 秒显示重连提示，冷启动和明确离线仍立即提示。界面计时在后台暂停。两端只为当前消费者保留完整解密历史：网页页面与待处理卡片显式持有，Android 按事件流订阅保护，图片确认只在确实仍等待处理时持有。无人使用的历史按最近使用回收，默认最多 8 个会话、估算内容量 16 MiB，并在闲置一分钟后释放；估算不等于进程堆内存上限，活动会话仍保留完整历史以推导状态。回收不删除历史、Android 磁盘密文缓存或待发图片。网页同样把读到的事件密文存在浏览器的 IndexedDB 里（`web/src/eventcache.ts`）：再次打开会话时先从本地读，按原样解密和核对位置，只向 server 取之后的事件。理由：历史是整段下载的，而到 VPS 的链路慢（实测约 270 KB/s，最长的会话要下 30 秒以上），瓶颈在传输而不在解密或渲染。缓存里只有密文，密钥本来就在同一个浏览器里，没有新增暴露；server 已经没有的会话在列表刷新时清掉，总量超过 256 MiB 时按最近打开时间回收，退出账户时整库删除。本地副本比 server 的历史长或解不开时丢弃重取。Android 和 iOS 的磁盘密文缓存里某个会话有一条解不开时，同样整段丢弃这个会话的事件、从 server 重取。同一个库里还存着上次列出的机器、会话和账户的项目偏好（同样是密文）、各台机器上次报告的模型列表和 daemon 设置（解密后的，只有模型名和默认值），以及登录 token：打开网页时在第一次绘制前读出来，直接显示上次的列表、范围和新会话设置，机器和 server 回话后再更新，偏好在读到 server 的副本前不能修改；并直接用 token 连接，省掉登录的两次往返；token 被 server 拒绝时流会被关掉，下一次重试再登录。token 泄露的后果小于同样存在浏览器里的根密钥（第 9 节）。网页长会话只挂载视口附近的行，展开状态由会话视图保存；回看位置需要重载时，等完整历史或明确失败后恢复，避免把旧位置套在分页前缀上。网页和 Android 主连接串行处理并限制在途帧与字节，字节预算直到处理完成才释放；Android 在复制前拒绝超大的推送帧，积压超限时丢弃排队帧并重连补齐。网页终端预算直到 xterm 消费完成才释放，超预算断开后重新同步，不跳过字节。

**大小限制**：单个信封不超过 1 MiB；写入会话密钥信封另限 4 KiB，会话元数据信封另限 68 KiB，对应 32 字节密钥和 64 KiB 明文元数据限制，加上两层头部、签名、nonce、认证标签和 Protobuf 编码的余量。一次上传不超过 500 个事件，推送帧超过 1 MiB 就拆开发。历史按条数和序列化字节数共同分页，客户端按返回游标连续读取。WebSocket 认证 hello 使用独立的小帧上限；等待认证和活跃连接同时受固定限额约束，过载明确拒绝。HTTP RPC 在解码请求正文之前限制并发和读取时长；声明正文不超过 64 KiB 且未压缩的请求使用 32 个小请求名额，其余使用 4 个大请求名额，因为压缩正文解压后可以接近正文上限。确定账户的预先 token 查询另有全局 64 个并发名额，每次查询（含等待 SQLite 读连接）最多 5 秒，并响应请求取消；名额已满或查询超时返回 503 和 `Retry-After`，不读取正文，也不进入账户或解码等待队列。无效 token 的查询同样受限。有效 bearer token 在读取正文前确定账户，每个账户最多占 24 个小请求名额和 2 个大请求名额。已认证账户的请求在等待账户和全局名额时共用一个最多 5 秒的期限，期间响应请求取消；先取得账户名额，再等全局名额。等待人数另受限额约束：每账户每池最多与该池账户份额相同的等待人数，整个 relay 最多 256 个等待请求；两个阶段和交接过程共用一份等待额度，Forward 同时计入解码池与 Forward 池的等待人数，但在 relay 总数里只计一次。超过等待额度立即返回同样带 `Retry-After` 的 `ResourceExhausted`，不再创建等待通道或定时器；无需等待的请求不占等待额度。Forward 的账户份额（每账户 32、全局 64）与账户解码名额一起预留，全局 Forward 和解码名额也一起取得；等待时不读取正文、不分配解码器，也不预占部分全局名额。共享期限内仍未取得名额返回 `ResourceExhausted`，附带 `Retry-After`；登录、配对等未登录请求保留原有全局限额和立即返回 503 的行为。Forward 解码并重新鉴权后使用已预留的全局等待名额；小正文释放小请求名额，避免等待电脑回复时阻塞小 RPC。大正文和压缩正文仍保留原有的大请求名额，因为 Connect 在等待和响应写入期间仍持有解码后的请求，不能扩大它们的内存预算。名额一直保留到 HTTP 响应写完；认证请求使用更小的正文上限。RPC 响应从首次写出开始有固定写入期限：普通响应 30 秒，事件历史、会话列表和图片 60 秒，写入有进展也不延长；在释放名额前刷新 HTTP 缓冲，防止小响应在 handler 返回后的写入无限等待。此期限通过 `http.ResponseController` 按请求设置，不设置全局 `WriteTimeout`，WebSocket 保留自己的期限。推送去重状态和异步发送同样有容量限制，过载返回可重试错误，不消耗被拒通知的去重键。

账户份额按多台电脑、多个客户端一起使用考虑：24 个小请求名额为其他账户留下 8 个全局名额；32 个 Forward 名额覆盖三个六图草稿加连接检测和实时状态轮询，并保留一半全局份额；大请求仍只给一个账户一半内存名额。历史逐页串行，但多个会话会并发补历史；图片分块上传也会竞争大请求名额。因此 5 秒等待用于吸收短时突发，并不保证任意设备数量或慢链路下的正常操作都不会被拒绝。 全局队列对已经取得账户份额的认证请求按入队顺序处理：争用同一池的后来请求不能越过仍有效的较早请求，取消和到期的请求跳过；需要多个池的请求会保留各池的顺序，可能让同池的后续请求一起等待，不争用这些池的请求仍可前进。账户份额等待也在同一账户内按争用池的入队顺序交接，释放名额只通知获得名额的请求，不广播唤醒其他等待者；取消和到期由各请求自己的通道处理。两个阶段都不按账户轮转；未登录请求不入队，保留立即尝试已有池的行为。

自部署的 Caddy 配置使用普通 `reverse_proxy`，没有额外的整段响应缓冲或传输超时设置；[Caddy 默认仍有部分缓冲](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#streaming)。server 的写入期限限制的是写给代理的时间；代理已接收完整响应时，server 可以释放名额，不保证最终客户端也已经读完。慢读者验收应让响应超过代理和传输缓冲，实测部署中的背压；仓库配置检查不能代替对线上代理的验证。

**网页**：事件内容一律当文本渲染，不插入 HTML；Markdown 里只有 http(s) 的链接可以点，其他目标（大多是本机文件路径，也可能是 `javascript:`）显示成等宽文字；构建产物带 CSP，只允许运行自己的脚本。service worker 除了显示推送，还保存应用外壳（页面、脚本、样式、字体和图标）：打开网页时先用保存的页面回答，同时在后台取新的留给下一次，所以启动不等 Cloudflare 的连接（实测冷连接的握手要 0.6 到 2.7 秒）。新页面只和它点名的脚本、样式一起保存，免得两次发布之间留下一个取不到脚本的页面；这些文件同时下载，到 Cloudflare 的线路时快时慢、偶尔卡住（实测同一个 400 KB 的文件有时 3 秒，有时 90 秒只下了 28 KB），所以每个文件限时 30 秒、最多试 3 次，有一个取不到就整次作废、继续用旧页面。保存好新页面后，service worker 通知打开着的页面，页面发现保存的页面跑的脚本和自己不同，就在首页和设置页提示「新版本已下载」，点一下重新加载换过去；设置页还能手动「检查更新」，回到前台时超过 10 分钟没查过也会在后台查一次，因为装到主屏的应用多半是被切回来而不是重新打开。不提供清站点数据的按钮：实在换不过去，由用户自己在浏览器里清（会删掉账户密钥，要重新配对）。按需加载的部分在页面稳定后提前取好，取不到（服务器已经换了更新的版本）就丢掉保存的页面，真正用到时再整页重载到当前版本。API 在另一个域名，不经过 service worker。脚本分成几块：第三方库单独一块，发布新版时文件名不变，浏览器继续用缓存；终端（xterm）、配对用的曲线和二维码、图片编解码在用到时才取。网页和 server 要放在同一个注册域名下（`app.<域名>` 和 `ra.<域名>`）：拦截扩展常按「第三方请求」过滤，实测 AdGuard 会拦掉跨站发往 `*.*.top` 的 WebSocket（[browser-notes §1](browser-notes.md#1-adguard-拦截发往-top-的跨站-websocket)）。本地开发遇到这种拦截时，可以用 `RA_PROXY` 让 vite 把请求转发到 server，同时用 `VITE_SAME_ORIGIN_API=1` 构建。

## 11. 终端视图

客户端打开终端时，发一条加密指令 `OpenTerminal`，带上随机的流 ID。客户端和 daemon 各自用这个流 ID 连 server 的 `/v1/term`，server 把两条连接配对后原样转发，**不存储、不解析**：配对要求一端是客户端设备，另一端正是客户端指定的机器；先到的一方最多等 20 秒。

- **画面来源**：daemon 为每条流起一个 tmux control mode 客户端（`tmux -C attach`），它不参与窗口尺寸的计算。先开始接收 `%output` 里这个 pane 的输出，再用 `capture-pane -e` 和光标位置拼出快照，快照之后把收到的输出全部转发。抓屏前后到达的输出可能已经在快照里，会再画一遍；Codex 用绝对坐标绘制，重画不改变结果，而丢掉它们会让画面缺块。窗口尺寸变化时（`%layout-change`，比如电脑上调了终端大小），重新发快照
- **回看历史**：新建 tmux pane 的保留上限为 100000 行，已有 pane 不追溯扩大。实时画面不留本地回滚：在终端上往上滑（触摸、滚轮、触控板）进入回看，同一块区域换成只读的历史阅读区，没有单独的「历史」入口。首次请求在本机用 `capture-pane -e` 生成固定快照，再按游标倒序取每页最多 200 行、256 KiB 的整行，行内带 SGR 颜色序列；客户端只解析颜色和字形属性，按实时画面的字号和列宽显示，其他控制序列丢弃，不当作终端指令回放。滑近顶端自动加载更早内容并保留阅读位置；回看时新输出不移动画面，只提示有新输出，点提示、滑到底或按任意按键回到实时，按键照常发出。回看不改变远端程序。快照不随输出或窗口尺寸变化而改变，避免分页重叠或漏行；关闭连接后游标失效，再次回看重新抓取。为什么不把旧内容拼进实时终端的回滚：实时流从快照开始，拿不到可靠的对齐点，拼接会重行或漏行
  - 每条流只保留一份历史快照，存在权限为 0600、创建后立即 unlink 的本机临时文件中，不落到中继，也不会在 daemon 崩溃后留文件。单次捕获限 64 MiB、5 秒，超出报错，不悄悄删掉较早记录。单行超出一页预算也明确报错。
  - 历史请求和响应经过现有终端信封加密。独立工作协程抓取快照，输出和输入继续处理；只排队一条请求，洪泛时关闭该客户端的流。三端把历史响应计入积压上限；请求超时可重试，迟到或上一次回看的响应不进入新页面。
  - Codex 用 `--no-alt-screen` 启动，把输出留在 tmux 历史里。已丢弃或 CLI 未写入终端历史的内容不能恢复；完整对话仍看聊天页。
- **加密**：每一帧用当前时期与用途派生的密钥、结合会话种子封成信封，并由发送设备签名；类型分输出和输入，`request_id` 是流 ID，`seq` 是各自的帧序号，接收方要求序号严格递增，乱序或重放就断开
- **输入**：客户端敲的键经现有 tmux control 连接的私有输入管道发送 `send-keys -H`，逐条等命令结果，不把按键放进进程参数。整帧输入持有会话控制锁，多个终端流不会交错；命令超时就关闭这条流，避免把迟到的结果认成下一条的结果。按键进入 pane 后走的是和本地键盘相同的路，所以注入消息时对本地按键的暂存同样挡住它们
- **尺寸**：客户端每次连上终端，收到第一份快照后自动适配一次：`resize-window` 到客户端能放下的大小。用户点「还原」或关闭终端时把 `window-size` 设回 `latest`；在这个终端点过「还原」后重连不再自动适配，要手动点「适配」。没适配时客户端按列数缩小字号，最小缩到 6（Android 为 dp、iOS 为 pt、网页为 CSS px，与「字号」可选的最小值相同）；到 6 还放不下整行就保持 6，实时画面和回看都可以左右滑动查看，回看打开时停在实时画面当前的横向位置。手势按起手方向区分：横向是平移，向下拖是进入回看。Android 和 iOS 的「字号」可选 6 到 22。别处改了尺寸不自动抢回，免得两个客户端来回改。网页上已适配的终端在面板宽度变化（调整浏览器窗口、在「终端」和「并排」之间切换）后重新适配，高度变化不触发，所以手机键盘弹出不改远端尺寸。Android 已适配时主动调整字号也重新适配
- **积压**：输出通道满了就结束这条流，客户端重连后拿到新的快照；server 写一侧超过 10 秒写不出去，两边一起断开

## 12. 推送通知

server 首次启动时生成 VAPID 密钥对，存在数据库里。客户端订阅时说明要哪几类通知：「等我处理时」（审批、提问、计划、终端弹窗）和「一轮结束时」。网页和 Android 登记订阅时还默认加入独立的定时结果类别；它不受普通轮次结束开关影响。

- **谁决定推送**：server 看不懂事件，由 daemon 在事件上传成功之后调用 `Notify`，只说明会话 ID 和类别。只对两分钟内发生的事件通知，重连后补传旧事件不会推送。server 因推送容量已满而拒绝的通知，以及连接中断、没等到 server 答复的通知，daemon 记着，在这两分钟内每轮同步再发一次，重连后也一样；server 明确拒绝的不再发
- **定时结果**：定时轮次的结束不产生普通轮次结束推送，即使 daemon 重启或补传也一样。Agent 调用 `notify_user`，或启用了任务级「完成后通知」且本次运行尚无通知时由 daemon 补发，已持久提交的通知事件都走原有上传后 `Notify` 链路，使用 `NOTIFY_KIND_SCHEDULED`。每个通知事件以公开序号去重，互不合并；Web Push 的 tag 加入同一个事件键并保持类别在末尾，Android 使用会话与 FCM event 键作为通知 tag，点击用的 PendingIntent 也用这对标识区分，避免只靠数字哈希 ID 时不同会话或事件互相覆盖目标，不同事件各自保留，同一事件重投只更新自己。FCM event 只携带原本已公开的事件去重键，不放任务或运行 ID；不能把任务 ID 暴露到去重键。成功表示已记录以供投递，不保证用户收到。Web Push 的文案固定为「定时任务有新结果」，daemon 按[运行来源的标题规则](#主动通知与客户端发现)在记录通知事件时补齐最终标题，不依赖任务当前目标定义。封装 NotifyContent 时原样使用事件内的最终标题，签名和端到端加密后交给 Android；冷启动无需先拿到会话元数据，重试也不会被后续改名改变标题。正文同样加密，并遵守本机通知隐私设置。两分钟补传窗口及容量重试与其他通知相同
- **内容**：Web Push 只有通用文案（「有会话在等你处理」），外加用于跳转的会话 ID，符合 scope 第 4 节「推送不含具体内容」。同一会话同一类别 15 秒内只推一次
- **客户端**：网页和 Android 的 `NOTIFY_KIND_SCHEDULED` 不受应用前台抑制，照常弹系统通知；唯一例外是用户此刻正看着目标会话：Android 当前可见页面就是该会话，网页存在可见、聚焦且路由恰为该会话的窗口。首页、其他会话或子页面不算正在看目标会话，后台保存着该会话路由也不算。任务会话不在默认列表；三端在对话中显示独立通知行，在任务列表和运行记录显示最近结果，仍保留上述系统提醒规则。其他通知类型保持前台抑制；点通知打开对应会话。iPhone 上要先把网页添加到主屏幕才能订阅推送。推送服务返回 404 或 410 时，server 删掉这个订阅
  - 网页每次连接成功后按本机保存的推送偏好重新登记订阅，包括设备被移除后重新配对的情况；只在浏览器已有通知许可时恢复，不再次请求许可。
- **推送后端**：`SetPushTarget` 按类型登记推送目标，Web Push 和 FCM 并存，旧的 `SetPushSubscription` 留给网页。server 用 FCM HTTP v1 发送，服务账号文件由 `-fcm-service-account`（`RA_FCM_SERVICE_ACCOUNT`）指定，`deploy/deploy.sh` 发现本机有 `~/.config/remote-agent/fcm-service-account.json` 时把它复制到 server 的数据目录并设好；没配置就不发 FCM，`SetPushTarget` 返回未启用；FCM 说 token 失效时删除。没有可用的 GMS 时静默降级为 App 内查看，不做 UnifiedPush
- **Web Push 出站限制**：订阅端点必须使用公网 HTTPS 的 443 端口；每次连接解析 DNS，拒绝非公网地址并直接连接核验过的 IP，防止 DNS rebinding。请求不用环境代理，也不跟随重定向；失败日志不写可能含订阅凭据的 URL。
- **账户安全通知**：恢复码提交后的 48 小时等待期内，server 直接给管理端发一条通用推送（`NOTIFY_KIND_SECURITY`），不含内容，点开进账户安全页；Android 与网页支持，iOS 暂无后台提醒。客户端离线或关了推送时，下次打开仍能在首页和设置看到待处理的恢复。它不属于上面两类会话通知，但和它们共用容量与去重上限
- **Android**：推送走 FCM，内容是 daemon 加密的密文，通知里可以直接审批，见 [android-client.md](android-client.md)
- **iOS**：原生 App 还没有推送，只能打开 App 查看；要用 APNs，做不做未定，见 [ios-client.md](ios-client.md#还不能做的)

## 13. daemon 设置与远程新建会话

daemon 的设置存在 `~/.remote-agent/settings.json`，客户端可以读取和修改：审批超时（30 秒到 hook 超时之前）、新项目默认的模型、effort 和审批模式（项目设置的初值，也是项目设置不适用时的回退）。未设置的项沿用启动参数或 Codex 自己的配置。

- **远程新建会话**：客户端指定机器、目录、第一句话，以及可选的模型、effort、审批模式；daemon 把它们换成 codex 的 `-m` 和 `-c` 参数，第一句话像普通消息一样排队，等 Codex 的输入框出现再发。会话的环境变量由机器上用户自己的登录 shell 现算，不用客户端的（第 6 节），所以新装的命令和升级过的工具在下一个会话就能用。目录由客户端通过 `ListDirectories` 逐级浏览选择，隐藏目录不列出。daemon 分批读取并检查取消，扫描最多 20,000 项（包含隐藏项和普通文件），超出返回 ResourceExhausted；目录结果按名称排序，最多返回 1,000 个
- **新会话的配置属于项目，用哪个 CLI 每次新建时选**：每个项目有一份项目设置，写明新会话用的机器，以及每个 CLI 各一套的模型、effort 和审批模式（Claude Code 还有上下文窗口），改动只影响之后新建的会话。理由：配置是项目的属性，放在输入框的「＋」里会和「这条消息带图片」混成一层；从最近一个会话隐式继承又让人看不出、也预测不到下一次会用什么。CLI 是例外：同一个目录里不同的任务常常适合不同的 CLI，放进项目设置的话每换一次都要进出设置，还顺带改掉了项目的默认值；所以新建输入框旁常驻一个 CLI 切换，项目只记住上次用的那个作为下次的默认。切换一直看得见，下一次会用什么仍然可以预测；每个 CLI 各存一套，来回切换不丢另一套的模型和审批。项目设置存在账户偏好里（第 8 节），用 `account-prefs` 加密，按项目路径匹配，所以换设备也一样，server 看不到内容
  - **目录不是设置**：项目就是按目录路径认的（第 8 节），换目录等于换项目，所以项目设置里只显示路径、不能改；要在别的目录开会话，从主页标题的范围菜单换项目或选「新项目…」
  - **初值**：新项目从所选机器的默认设置（daemon 设置，见下文）开始；还没保存过设置的已有项目，用列表顺序里最靠前的会话（未结束的优先，否则最近结束的，见[第 8 节](#会话列表排序)）的配置作初值，计划模式换成机器默认。第一次从项目里新建会话时把所用配置存为项目设置，之后只有用户改才会变；某个 CLI 在这个项目里还没用过时，它那一套从机器默认开始；记住的 CLI 随每次新建更新
  - **审批模式**：可选询问、自动和完全放行；计划只是一段临时状态，不作项目默认。选了完全放行，新建时不二次确认，见第 7 节
  - **不适用时**：所选机器离线，项目页提示并让用户选这次用的机器，不改项目设置；所选模型或 effort 在这台机器或这个 CLI 上没有，就用机器的默认值并提示；记住的 CLI 在这次的机器上没装，就用装了的那个并提示，不改记住的值
  - **界面**：项目页标题下一行写所选 CLI 和它那一套设置的摘要，点开或从 ⋯ 进入项目设置；新建输入框旁是 CLI 切换，这台机器只装了一个 CLI 时不出现；新建区和会话输入框共用单行起步的布局，两处的「＋」都只用来添加图片，本会话的模式、模型和上下文在会话导航栏的 ⋯ 菜单里。这样新建只需要写第一句话，要改设置有固定的地方
- **分叉会话**：从一个会话当前的对话另开一个会话，原会话不动（`ForkSession`，本地命令 `remote-agent fork <id>`）。用的是 CLI 自己的分叉（`codex fork <id>`、`claude --resume <id> --fork-session`），所以新会话的上下文由 CLI 负责，remote-agent 不拼接或重放对话
  - **新会话是什么**：同一台电脑、同一个目录、同一个 CLI，有自己的 remote-agent 会话 ID、tmux 会话和密钥；环境变量、参数和「最近一轮的模型、强度、审批模式」都按恢复会话的规则取自原会话（第 6、16 节）。标题沿用原会话自己起的标题或自动标题，之后各改各的。不需要第一句话，CLI 就绪后直接空闲
  - **什么时候能分叉**：原会话空闲或已结束，并且发过消息。运行中、启动中，或有审批、提问、计划、终端弹窗等着时拒绝：一轮中间的记录还没写完，分叉出来的历史会停在半截，两个 CLI 对半轮的处理也没有实测。运行中分叉要不要做未定，见 [plan.md](plan.md)
  - **历史靠复制事件**：daemon 把原会话的事件复制给新会话，再记一条 `SessionForked`（原会话 ID 和当时的标题），之后才是新会话自己的事件。不从 CLI 的记录重读，因为两个 CLI 的分叉记录都不能直接当历史用：Codex 的新 rollout 只引用父 rollout，不含之前的内容；Claude Code 要到分叉后发第一条消息才写新 transcript（[codex-notes §11](codex-notes.md#11-分叉)、[claude-code-notes §11](claude-code-notes.md#11-压缩恢复和分叉)）。复制让两个 CLI 走同一条路，分叉后立刻能看到历史，消息的来源设备也保留
  - **复制什么**：对话本身（消息、推理、工具调用、轮次、用量、设置变化、已处理的审批和提问）。原会话自己的进程和队列状态（`SessionState`、`InputState`）不复制，没人处理过的审批和提问也不复制，在新会话里它们已经没法回答；原会话退出时停在一轮中间的，复制到这里补一条「已中断」的轮次结束。复制和读取位置在同一把锁下取，原会话此后写进记录的内容归新会话去读
  - **Claude Code 的重复记录**：新 transcript 开头是原会话记录的副本，沿用原来的 `uuid`。分叉时 daemon 把原 transcript 已读部分的 `uuid` 存进新会话目录（`fork-copied`），读新 transcript 时跳过这些行，免得历史出现两遍；没有 `uuid` 的记录都是新会话自己的
  - **图片**：复制的事件保留内嵌预览，大图标为「只有预览」：显示版用原会话的密钥加密、存在原会话名下，传完后本地已经删掉，新会话拿不到；要看大图回原会话。不重新上传，也不让客户端跨会话取图
  - **结果不确定时**：分叉的回复没收到时，客户端留着这次请求，再点重发的是同一个请求（[第 10 节](#10-报文同步和指令)的「指令」），daemon 从日志里答出已经建好的会话，不会分叉出第二个；菜单关了再开也一样。请求过期后不再重发，菜单里那一项变成「放弃上次的分叉」，放弃之后再点才是新的一次
  - **推送**：复制的事件不触发推送（`Session.forked_seq` 以前的都跳过），否则刚结束的一轮会在分叉时再提醒一次
- **机器级指令**：新建会话、列模型、浏览目录、读写设置不属于某个会话，信封头里不带会话 ID；daemon 拒绝带了会话 ID 的机器级指令
- **移除设备**：只在手机 App 发起，见第 9 节。手机上传含删除的新状态后，server 立即清理登记、登录和推送并记下墓碑，电脑的机器、会话、事件和图片密文保留，只有另行确认“删除这台电脑的记录”才清除；保留设备在 60 秒内拉取新状态，最坏由旧 head 的租约兜底。没有完成证明，也没有“等待电脑确认”。设备列表以签名状态为准；仅收到中继登录拒绝时，三端只表示“服务器拒绝了这台设备的登录”，不自动删除本机密钥，也不把中继的响应当成端点已经安装新状态。

### 工具执行反馈

过程不是用户关心的重点，客户端只用一行表示一次工具调用：运行中写命令和计时，失败写退出码，连续完成的折成「运行了 N 条命令」。不做工具详情页，不显示工具输出，也不提供跳转终端的入口：失败原因由 Agent 在回复里说明，想看过程的用户自己切到终端标签。这样客户端不需要解析和传输输出，也不会把不可靠的中间状态当成进度展示。daemon 上传事件时因此去掉工具输出，输入和标题相同时（shell 命令通常如此）也只留标题（`internal/relay/slim.go`）；本机的事件日志保持完整。实测这两项占已存事件字节的约 45%。

客户端收到 ToolStarted 后立即显示这一行，未完成的不能收进完成分组；等待审批和工具运行中分开显示。计时从 daemon 的事件时间算，各端同一起点，未知起点不猜；客户端断线时停住并写「等待同步」。Claude Code 按调用 ID 配对开始与结果；Codex 也按 `call_id` 配对，但这不代表能单独停止某个工具。转到后台的调用写「后台运行」，之后不追踪它是否结束；daemon 仍在 `ToolCall.background` 里标明来源（模型要求的、超时移到后台的、终端里按 Ctrl+B 的、一轮结束时仍在运行的），客户端不用从结果文字猜。中断只中断本轮，不保证终止后台命令（[codex-notes.md §8](codex-notes.md#8-中断和运行中的输入)）。

### 客户端状态推导的共同规则

网页、Android、iOS 从同一份按序事件推导领域状态，不能按客户端各自的到达顺序解释。契约和人工指定的期望值在 [`testdata/projection/`](../testdata/projection/README.md)：输入使用当前 proto 的 JSON，序号和 64 位计数写十进制字符串；输出保留领域事实、未知值和历史注解，不比较译文或布局。三端 runner 共读一个文件，核对观察点的完整重放；Android/iOS 还核对每个切点的 reducer 追加和 `EventProjection` 更新。这里只检验内存投影，没有快照协议、持久恢复或分页能力。Go `internal/remoteclient` 没有会话 reducer，只检查向量的 protobuf 格式、连续序号和切点，不再复制一套界面状态机。

- **来源认领**：有明确 `origin` 时以它为准，不猜设备身份；只有带 `request_id` 的用户消息消耗已有的提交认领。没有来源的消息沿用客户端的本地输入注解：提交先于消息时认领下一条；Claude 消息先于确认时，只追认最近三条事件内且晚于该请求首次入队的消息。`UNCONFIRMED` 后的确认只认领后面的消息，不能改变前面的本地输入注解。没有入队记录时仍允许短距离追认，这是当前事件缺失值的规则，不据此生成 `origin` 或 `device_id`。原生 CLI 自动产生的精确文本 `Implement the plan.` 不标为本地输入；有明确本地来源时仍按本地来源处理。改动 CLI 文本适配时三端一起更新向量。
- **工具配对**：开始与结果只按非空 `call_id` 精确匹配；缺 ID、不同 ID 和 `<id>#2` 不兜底消耗别的起点。轮次结束后保留未完成起点的关联，迟到的真实结果即使跨到下一轮，也追补原起点并撤掉其未知、中断注解。没有结果时保持未知，不能记作成功。
- **轮次边界**：轮次结束清同步问题；中断且尚未返回的工具可留作本轮后台提示，正常结束而未返回的工具只记“无结果”。新一轮清当前后台提示，历史注解继续保留。退出和分叉清运行中、待审批、待答及当前后台提示；未完成工具保留为历史未知，退出本身不证明中断。退出后仍可补记迟到结果；分叉隔开源会话的提交认领和未完成工具关联，不能用分叉后的同 ID 结果结算源会话。
- **后台工具**：结果的 `ToolCall.background` 是是否继续在后台运行的事实；输入里请求 `run_in_background` 不证明命令尚未结束。没有 `ToolStarted` 的后台结果也保留，以结果事件作为已知起点，不冒认其他调用。后台状态不是成功，下一轮不继续显示为本轮活动。
- **审批关联**：在全部已观察历史内，`(tool_name, input_digest)` 必须恰好有一个请求、一个晚于请求的调用，且该请求已有决议，才把决议关联到调用。任意第二个请求（包括未决请求）或调用都会造成歧义，撤销该合并；无 digest 时独立保留审批。这样后到事件不会让未证实的对应关系成为事实。
- **输入结算**：每个请求以最后一个明确 `InputState.status` 为准；首次受理的正文、图片和来源保留，缺省的 stage/mode 不覆盖已知值，pause 取本次值。`QUEUED` 和 `HELD_BY_CLI` 都仍待处理；`UNCONFIRMED` 表示已写入但无法确认，不能据此重发。`CANCELED` 且 reason 为 `exited` 才注记退出未发送，和用户取消分开；仅看到退出事件不伪造取消或提交结果。缺少 daemon 最终结算时，输入事实仍不完整。
- **提问**：同步问题按 ID 等待、按回答或轮次结束退场；异步问题保留正文和选项作为聊天消息，不成为待答卡，也不阻塞轮次。多题回答按事件中的顺序保留。
- **配置与压缩**：客户端设置先建立模型/effort 的预期，下一次非计划模式的有模型上下文再核对模型和已知 effort；计划模式的临时配置不冒充用户切换。已提计划后离开计划模式视为处理计划，不额外注记终端切模式。每次压缩保留此前占用和此后第一次 usage 的占用；无窗口时为未知，连续压缩只给最后一次补上后值。百分比是截到整数且最多 100；原生界面直接使用 core 的压缩事实，不能另算一套。

这里的推导函数 `R` 按连续事件前缀执行；在任意切点追加后继，结果须与从头重放相同。继续推导所需的状态不仅是可见结果，还包括首次入队序号、提交计数及待认领消息、未完成工具的 ID 关联、上一配置及待核对设置、已提计划标记、等待后续 usage 的压缩点。未来如果序列化 continuation，必须保留这些状态及历史消歧索引，再另外验证序列化恢复等价；本次切点测试没有证明持久快照恢复。

共享测试的命令及规范化字段见上述目录的 README；端到端和真机覆盖见 [验收记录](acceptance-notes.md#客户端状态推导共享向量)。

## 14. 适配 Codex 升级

remote-agent 依赖 Codex 的屏幕和 rollout，Codex 升级可能改变它们。做法是让变化尽量不破坏功能，破坏了要能看出来、能查出哪一项：

- **容忍写法变化**：画面按样式属性和文字判断（第 6 节）；菜单按标题和选项文字定位；rollout 里认不出的条目保留为通用工具调用，不报错
- **看得出来**：排队的消息发不出去时，daemon 在会话信息里给出原因（终端有草稿、有弹窗、认不出输入框）；认不出输入框超过 20 秒会记一条带 Codex 版本的警告，网页上提示可能是 Codex 升级改了界面
- **查得出来**：`remote-agent doctor` 用独立的 daemon、状态目录和 tmux，在 `~/.remote-agent/doctor-work` 里以 GPT-6-Luna 低档位真的跑一个会话，逐项检查：认出输入框、区分本地草稿、注入并读回回复、切模型、切审批模式和计划模式、中断、终端快照。失败时附上画面分析的结果（不含内容）
- **记录版本**：daemon 读 `codex --version` 放进机器元数据，可执行文件变了（CLI 升级）就重新读，不用重启 daemon；代码测试过的版本（`codex.TestedVersions`）和本机 doctor 通过的版本算「已验证」，否则启动日志和网页的机器详情里提示运行 doctor

## 16. 接入 Claude Code

Claude Code 和 Codex 走同一条路：原生 TUI 跑在 tmux 的 PTY 代理下，输出读 transcript，审批和轮次边界靠 hook，屏幕只用来判断状态。客户端能做的操作两者一致（第 7 节的 4 种审批模式就是按两者共有的定的）。具体做法依据 [claude-code-notes.md](claude-code-notes.md) 的实测，随实测补全。

- **会话属于哪个 CLI**：会话信息、新建会话、列模型都带 `Agent`；以前的会话没有这个字段，按 Codex 处理。机器元数据列出本机装了哪些 CLI 和版本，客户端只提供装了的
- **daemon 的分层**：会话生命周期、事件序号、持久化队列、控制锁、审批的竞争处理、同步和终端流是共用的；每个 CLI 各自实现三组接口（`internal/agent`）：启动和恢复（参数、版本、模型列表）、事件来源（绑定 transcript、增量解析、确认消息已提交）、终端控制（认输入框、注入、中断、回答提问、计划、切换设置）。屏幕、菜单、参数和 JSON 格式的知识只留在各自的包里（`internal/codex`、`internal/claude`）
- **环境变量**：和 Codex 共用 `~/.remote-agent/agent.env`（第 6 节），代理这类配置属于电脑，不属于某个 CLI
- **新建会话的默认值**：daemon 设置里 Codex 和 Claude Code 各有一套默认模型、推理强度和审批模式，作为新项目的初值；项目设置（第 13 节）里每个 CLI 的那一套各从对应的默认值开始
- **工具开始**：Claude Code 会并行调用工具，`ToolStarted` 带上调用 ID 配对，不按先后顺序

下面是 Claude Code 这一侧的具体做法，括号里的「notes §n」指 [claude-code-notes.md](claude-code-notes.md) 的第 n 节。

- **启动**：`claude --settings <会话目录>/claude-settings.json --session-id <uuid> …`，由 PTY 代理启动，来源判定和起点环境见第 6 节（终端开的会话直接执行；客户端开的先经过用户的登录 shell）。settings 文件只放 remote-agent 的 hook（`SessionStart`、`PermissionRequest`，以及只匹配 AskUserQuestion 和 ExitPlanMode 的 `PreToolUse`），命令同样写成 `"$RA_EXE" hook claude`；它和用户自己的 hook 一起运行，不改 `~/.claude/settings.json`，也不需要信任（notes §1、§3）。会话 ID 由 daemon 生成，记作会话的 CLI 会话 ID
- **模型、推理强度、审批模式**：新建时换成 `--model`、`--effort`、`--permission-mode`；没指定就不传，沿用 Claude Code 自己的配置。模型是**具体 ID**（`claude-sonnet-5-5`），来自 Claude Code 自己的模型目录；推理强度是这一行模型自己的档位（目录的 `runtime.effort_levels`），没有档位的模型不传。Claude Code 自己兜底：模型没有档位时忽略 `--effort`，档位超出模型时按上限收窄，认不出的值打印一行警告后忽略。「完全放行」对应 `bypassPermissions`：只有启动时就允许了 bypass 的会话能切过去（notes §5），daemon 按启动参数和 `~/.claude/settings.json` 的 `defaultMode` 判断，不可用时会话信息里标出来，客户端置灰。remote-agent 不替用户加 `--allow-dangerously-skip-permissions`
- **恢复会话**：transcript 已经存在时用 `--resume <id>`，否则（从没发过消息）仍用 `--session-id <id>`；沿用原来的参数（取多个值的选项保留全部的值，少一个就可能放宽限制），再用最近一轮的模型、推理强度和审批模式覆盖，同名选项先从原参数里去掉。Plan 模式下 Claude Code 临时换用的模型不算会话的模型，免得恢复后一直用它。bypass 是否可用按启动时记下的结果，不重新读可能已经改过的全局设置。恢复时 transcript 里的 `permission-mode` 记录是上次的模式（notes §2），所以当前模式以屏幕上的模式行为准。`--bare`、`--safe-mode` 会关掉 settings 里的 hook，不接受
- **启动弹窗**：信任目录的光标默认在 `No, exit`，回车就退出（notes §1），和 Codex 一样留给用户在终端里处理，客户端提示去终端
- **找到 transcript**：`SessionStart` hook 在信任目录后、第一条消息前就触发，带 `transcript_path`
- **解析 transcript**：带 `origin.kind: human` 的用户记录是新一轮的开始和用户消息，`task-notification` 的只开始一轮（后台工作结束后 Claude Code 自己回应）；`turn_duration` 是正常结束，`[Request interrupted by user…]` 是被中断，两者可能先后都有，只记第一个；`isMeta`、斜杠命令、压缩摘要都不算用户消息；运行中并入这一轮的消息（`queued_command` 附件）记为用户消息但不开新的一轮。`tool_use` 记为 `ToolStarted`（带调用 ID），`tool_result` 按调用 ID 配成 `ToolCall`；`thinking` 记为推理（终端里默认折叠，按 ctrl+o 能看到同样的内容）。`compact_boundary` 记为「上下文已压缩」。**模型就是记录里的 ID**（`message.model`，如 `claude-sonnet-5-5`），不再换算；终端里切模型要等下一条回复才出现在 `assistant` 记录里，Plan 模式下的回复又不算数，所以 `/model` 的输出记录也要读：它写的是显示名，用模型目录换回 ID（`Sonnet 5.5` → `claude-sonnet-5-5`），换不出的（目录里没有的名字）照原样留着。上下文占用由 `usage` 算出，窗口大小按 ID 从目录取（notes §2、§13）
- **输入**：和 Codex 相同的排队、暂存本地按键、bracketed paste。输入框的判断按 Claude Code 的画法：两条横线之间只有一行，`❯` 后面没有普通样式的字（光标是反色的一格，占位提示是淡色）才算空（notes §4）。运行中也可以注入，Claude Code 会把它排进当前这一轮；以 transcript 里出现这条用户消息或 `queue-operation` 的 `enqueue` 记录为已提交
- **计划框和菜单的折行**：窄屏时标题和选项会折行，识别时把相邻两行连起来看，选项的续行并入选项。`/model` 菜单末行的提示和切换成功的那句话同样会折行（notes §9），都去掉折行再比，否则模型已经切了却报失败
- **本地先答审批**：除了看到的权限框消失、这一轮结束，这个请求的工具调用完成也算，覆盖状态检测还没看到框就已经在终端答了的情况。调用和请求按完整输入的摘要对应（审批事件和工具调用都带这个摘要，客户端直接比较，不自己算）；几个请求输入完全相同时，一次完成收回其中最早的一个。审批请求一律出卡片，daemon 不预判「调用已经执行过」：
  - **限制**：在终端里答得太快、调用在审批请求登记到 daemon 之前就执行完了，这张卡片不会因为这次完成而收回，要等这一轮结束才收回；在这期间点它不起作用，因为 Claude Code 已经不等这个 hook 的答复了。曾经尝试用「最近完成的调用」提前跳过这类请求，连续几轮都引出了会静默跳过真实审批的竞争，所以放弃：宁可多一张过时的卡片，也不能漏掉一次审批
- **中断**：只在运行中发 Esc。Claude Code 首条输出前被中断时可能不写结束记录（[实测 §10](claude-code-notes.md#10-中断和运行中的输入)）；daemon 只有连续观察至少一秒的非忙碌输入框恢复了本轮原文（比较时忽略两边全部空白，避免中文和长 token 的软折行引入差异）、且本轮尚无 assistant 或工具输出，才在再次补读 transcript 和复查屏幕后补记中断。普通空闲画面、不同草稿或 Esc 写入成功都不够；补记同样先落盘再更新 parser 和轮次，并暂停未发送输入。抓屏无法区分原有空白和软折行，因此只在空白分布上不同的草稿也会匹配；仍须同时满足无输出、稳定画面和 transcript 复查条件。原文和有无输出由事件重放恢复，所以 daemon 重启后仍可确认这次中断。
- **模型提问**：让原生选择框照常出现。问题由 `PreToolUse` hook 报给 daemon（hook 立即返回、不表态），因为 transcript 可能要等回答之后才写入这次调用（notes §2）；transcript 里随后出现的同一调用不再重复。回答时暂存本地按键、确认屏幕上是这个问题（窄屏折行的问题去掉折行再比，认不出或认出多个就报错，不猜），再按选项编号，出现提交页就按 1。屏幕上已经是提交页（在终端里答完、还没提交）时不按任何键，报「问题不在屏幕上」：提交页也列着问题原文，但那里的 1 是提交终端里选的答案，2 是取消整次提问。多选时数字键是切换勾选，所以先读当前的勾选状态，只按和答案不一致的，再按 →。以 transcript 的 `tool_result` 为准，本地先答了就收回卡片。**不用阻塞 `PreToolUse` hook 回答**：那样虽然能直接把答案交给模型，但 hook 等待期间电脑终端里看不到问题，违背「电脑和手机操作同一个会话」（notes §7 两条路的实测对比）
- **计划**：`ExitPlanMode` 同样由 `PreToolUse` hook 报来，记为 `PlanProposed`，屏幕上的计划框让会话处于「计划待批准」。批准（`IMPLEMENT`）按「Yes, manually approve edits」那一项，执行后回到 manual；继续规划（`KEEP_PLANNING`）按 Esc，留在 Plan 模式；Claude Code 没有「清空上下文再执行」，这一项返回不支持。hook 批准计划不起作用（notes §8）
- **当前审批模式**：以屏幕上的模式行为准。在电脑终端里用 Shift+Tab 切的，daemon 从屏幕看到后记一条 `TurnContext`（`permission_mode`），不用等下一条消息；会话信息的 `mode` 按第 7 节的对应关系给出，accept edits 这类没有对应的给 UNSPECIFIED，原名在 `permission_mode` 里
- **切换审批模式**：空闲时切到 Plan 用 `/plan`，直接到达。其余用 Shift+Tab 在模式行上一格一格地走到目标模式，每按一次都读模式行确认；转一圈都没遇到目标就报错并回到原来的模式。按放行的范围，模式从严到宽是 plan、manual、accept edits、auto、bypass。运行中也能切（notes §5），但途中（以及目标不可用时回来的路上）只要有一个模式比目标宽，就不切，免得那一瞬间放行了工具调用。是否运行中在拿到终端控制之后才判断（切模型、压缩同样如此）：之前拿着控制的注入可能刚开始了一轮，所以要重新读 transcript，并把「已写入还没确认的消息」和屏幕上的忙碌迹象（输入框上方的转圈行、变暗的提示符，notes §4）也算作运行中。
  - **空闲时途经更宽的模式**（主要是从 Plan 模式切出：Shift+Tab 只能单向走，也没有离开 Plan 模式的命令，notes §5）：
    - **做法**：屏幕上有后台工作（模式行的 `· 1 shell`、输入框上方的 `Waiting for N background agent`、模式行下的后台子代理列表，notes §10）时不切，告诉用户原因；否则先算出整条路径，把要按的 Shift+Tab 一次写完，中间不读屏幕，最后核对模式行。
    - **哪些模式可用**：算路径要知道 bypass 和 auto 可不可用：bypass 按会话启动时记下的能力（`full_access_unavailable`）；auto 按会话当前模型在 Claude Code 模型目录里的那一行（`auto_permission_mode` 为 `unavailable` 的没有，notes §5、§13），或这个会话用这个模型时屏幕上出现过 auto；目录里没有这个模型（老的别名设置）时算未知，未知的按可能可用处理，运行中不走会经过它的路；状态栏的 `auto mode unavailable for this model` 不作依据，它在换到有 auto 的模型之后还会留一阵（notes §5）。已知不可用的目标直接报错，不按键。
    - **唯一的例外**是 auto 可不可用算不出来（还不知道会话的模型、屏幕也没提示）：这时按「不可用」计数，只会少按、不会多按；如果因此停在 auto 上（比目标宽），立即把差的键补上，这是第二次写入。目标实际不可用时回到原来的模式
  - **为什么这样取舍**：一律拒绝的话，bypass 或 auto 可用的会话（本机默认就是）就没法从远程离开 Plan 模式。空闲时这一轮没有工具调用；可能在这一瞬间调用工具的只有后台工作，看得到就拒绝
  - **残余风险**：连按期间 Claude Code 依次经过的宽松模式仍会存在几十毫秒（按键和界面刷新的时间，未精确测量）；屏幕上看不出来的后台工作（比如列表被挤出屏幕、Claude Code 改了提示的写法）挡不住；后台工作在检查之后、连按之前的一瞬间启动也挡不住
- **切换模型和推理强度**：空闲时 `/model`，用方向键移到模型那一行、推理强度按目标相对当前档位的方向按 ← 或 →（不假定循环：2.1.300 两端停住，2.1.284 到 2.1.287 会首尾相接，按方向在两种行为下都能到目标），按 `s` 只改当前会话。**那一行按模型目录的显示名找**（`Sonnet 5.5`）；菜单用短标签（`Sonnet`）时，同时核对目录的 `short_name` 和右侧说明开头的完整显示名，不能只按家族名认模型。不在可见窗口里（窗口矮时会滚动，首尾两行带 `↑`/`↓` 标记，行号始终是全表里的绝对编号）就按它在该表里的位置算步数，移完按名字核对，对不上就报错不按 `s`——菜单和目录对不上时宁可报错，也不能落到另一个模型上。弹出 `Switch model?` 时按它的「Yes, switch to」那一项，只在菜单已经消失、确认框和这一项都在时才按，免得把数字按进菜单改掉默认模型。以对话里出现 `Set model to … for this session only` 为成功。数字键、回车，以及 `/model <ID>` 都会改全局默认值，不用（notes §9）。目录里要求更新版本（`min_claude_code_version`）的行，装着的 CLI 不列，daemon 按 `claude --version` 先滤掉，模型列表和算步数用的是同一份；会话开始时还没有目录（刚装好、没跑过 Claude Code），或中途目录换了新模型，解析 transcript 时遇到认不出的名字或 ID 就重读目录，最多每分钟一次。在 2.1.300 上核对过完整显示名和短标签两种列法，更早版本不算已验证版本。
  - **可选的模型**：可选的模型是 Claude Code 自己缓存的模型目录（notes §13），daemon **只读**它，不写。会话信息里的模型就是这个目录里的 ID。目录缺失（新装的 CLI 还没取到、或用户关掉了它）时列表是空的，daemon 报「读不到模型列表」，客户端只能用 CLI 自己的默认模型，会话里也不能切换——ID 是 CLI 自己定的，宁可说没有，也不拿别处的名字去猜。
  - **上下文窗口**是项目设置里独立的一项（`ProjectSettings.standard_context`，新建时随 `CreateSessionRequest.standard_context` 交给 daemon），只对 Claude Code 有意义，默认 1M：这是 Claude Code 自己的默认值，所以没设置过的项目行为不变，用默认模型时也能选。
  - **选标准时**：选标准时 daemon 在会话环境里加 `CLAUDE_CODE_DISABLE_1M_CONTEXT=1`，固定为 200k（notes §2）；环境随会话保存，恢复时不变，会话信息里的窗口也按 200k 报告。
  - **选 1M 时**：什么都不用做：具体 ID 下窗口本来就是模型自己的（目录的 `runtime.max_input_tokens`），`[1m]` 后缀只是让 `/context` 把模型名写成 `…[1m]`，不影响窗口，所以不再加。没指定模型时不改参数。
  - **为什么不编码进模型名**：不把窗口编码进模型名：那样默认模型下没法选，也会让已有项目的含义悄悄改变。窗口在启动时就定了，会话里切换模型不涉及它。
  - **模型列表**：模型列表带每个模型最大的上下文窗口（`ModelInfo.context_window`，取自目录）和它有没有 auto（`ModelInfo.auto_unavailable`，即目录里 `auto_permission_mode` 为 `unavailable` 的行，如 Haiku 4.5；客户端据此置灰自动模式，不再按模型名判断）。Codex 不填窗口，因为 `models_cache.json` 里的窗口和会话实际报告的不一致（codex-notes §1），它的实际窗口在会话的上下文占用里看；auto 对 Codex 一律为否（不适用）。
- **压缩**：空闲时 `/compact`，以屏幕出现 `Compacting conversation` 或 transcript 出现 `compact_boundary` 为开始
- **额度**：从状态栏命令的输入采集，见下节

### 账户额度

设备页提供额度详情，按这台机器上安装的 CLI 分组，显示 CLI 登录账户的用量；它与会话上下文占用、累计 token、remote-agent 的图片存储配额分别展示。不同 CLI 不相加，不按模型或会话切分账户额度；不同机器也不凭套餐名推断为同一个账户。界面见 [client-v52 · 账户额度](design/client-v53.html#quota)。

Codex 继续用 rollout 的额度字段（[codex-notes §1](codex-notes.md#1-数据从哪读)）。Claude Code 的 transcript 没有账户额度，额度只在状态栏命令的输入里（[claude-code-notes §2](claude-code-notes.md#2-transcript)）。

- **采集**：daemon 在会话的 `--settings` 里把状态栏设成 `"$RA_EXE" statusline claude`（不改用户的设置文件）：它把输入转给 daemon（500 毫秒超时，失败也不影响状态栏），再用同样的输入运行用户原来的状态栏命令（启动会话时按 Claude Code 的优先级读出、存在会话目录里），输出和退出码原样交回，`padding`、`refreshInterval` 也照搬，所以终端里看到的状态栏不变。
- **读不到时**：托管设置里定了状态栏时它会盖过 daemon 的，额度就读不到，报「不支持」。
- **区分账户**：账户用 `~/.claude.json` 里 `oauthAccount` 的账户和组织 ID 算一个短指纹来区分（ID 本身不离开电脑），套餐取 `organizationType`，有 `oauthAccount` 才标为订阅登录；读不出账户时不合并，按来源会话分开。
- **保存**：额度按账户存在 `~/.remote-agent/quota.json`，重启后只沿用当前登录账户的记录，看到新账户的数字就清掉旧账户的。数字不变时一分钟内不刷新记录时间，免得机器元数据频繁变化。
- **上报**：结果放在 `MachineMeta.quotas`，每个 CLI 一项或几项，状态分等待（还没收到额度）、正常、失败和不支持。
- **边界**：采集只读取 CLI 已有数据，不主动给模型发消息，不把登录凭据交给 server，不调用未公开的账户接口。额度元数据端到端加密同步，server 只收密文，日志不记录额度或账户内容。

客户端按来源提供的窗口显示已用百分比、重置时间和最近收到时间。重置时间写两部分：还有多久（一天以上写到小时，一天以内写到分，按客户端时钟算）和重置的时刻（当天写「今天 14:10」，其他日子写出日期和星期，如「10月8日 周四 14:10」）。只写星期分不清是哪一天，只写时刻又要自己算还剩多久。时刻统一转换为北京时间（`Asia/Shanghai`，UTC+8），日期和星期也按北京时间判断，最近收到时间也一样，页面底部说明一次「时间按北京时间显示」。Claude Code 的 5 小时、7 天分别可缺失；只有真实收到其他限额窗口时才显示该窗口，不承诺按模型额度或额外用量。套餐名未知就省略，读到的内部代号换成名称显示（`prolite` 写 Pro Lite，`claude_max` 写 Max）；API 计费须由可靠的登录方式信息确认，不能从 `rate_limits` 缺失推断。API 用量和账单到服务商控制台查看，不把会话估算费用当成账户余额。

- 有效数据：80% 起橙色提示，100% 标「已用尽」；不自动切换 CLI 或模型，不拦截发送。缺重置时间只省略时间，缺用量则标「未获取」，不补成 0%。
- 尚未收到任何额度：显示「暂未获取额度」。明确不支持读取时显示「暂不支持读取额度」。单个窗口缺失不清空其他有效窗口；账户没有的窗口（CLI 根本没上报）不显示，不占一行「未获取」。「最近收到」的时间每个 CLI 只写一次。
- 机器离线、重置时间已过或来源确认数据陈旧：旧数值标「上次记录」，显示时间与原因，条形变灰。重置时间过了只标「等待更新」，不自行归零；客户端时间用于展示，不作为 CLI 已恢复可用的证明。
- 读取失败：说明失败并保留带时间的上次记录；「重新读取」只重读本机已采集数据，不能保证向服务商刷新，机器离线时置灰。额度页不提供跳转终端的入口，不支持读取时只提示可在本机 CLI 里查看 `/usage`。
- 确认换登录账户后清掉旧账户快照；无法可靠识别账户变更时不复用持久化缓存，显示未获取。多会话的账户额度不累加，只有能确认同一账户的数据才能合并，取最新的：Codex 按 rollout 里的上报时间；Claude Code 的状态栏输入不带时间，空闲会话会一直重复它上一次回复时的数字，所以逐个窗口比较，重置时间晚的算新，重置时间相同时取已用比例高的（一个窗口内用量只增不减），落后的上报不覆盖记录、也不刷新「最近收到」；状态栏输入也不带账户，所以换登录账户后，某个会话原样重复它在旧账户下报过的数字时不算新账户的（那是它上一次回复时旧账户的额度），等它的数字变了才计入；未知账户归属时保留来源会话区分。

## 18. 定时任务

定时任务属于 Remote Agent，由所属电脑的 daemon 保存和执行，不依赖 Codex 或 Claude Code 的内部调度。任务内容、目标目录和执行消息不以明文交给 server；远程管理复用加密的机器指令。任务模型由 `internal/schedule` 维护，本地 CLI、MCP 和协议接口共用。网页、Android 和 iOS 均提供独立定时入口、任务编辑和运行历史；当前实现与验收状态见 [plan.md](plan.md)。

### 托管会话的工具入口

每次新建和恢复托管会话时，增加名为 `remote_agent` 的本地 stdio MCP，命令为本机二进制的 `mcp` 子命令，并绑定 Remote Agent 会话 ID。Codex 使用单次 `-c` 配置覆盖，Claude Code 使用会话目录中的私有 MCP 配置；Claude 的显式 `--mcp-config` 来源合并到该文件，用户其他 MCP 保留。不修改全局配置、项目配置、AGENTS.md 或 CLAUDE.md，不注入会话指令、system prompt 或 skill；能力由 MCP 工具描述和参数 schema 提供。

Claude Code 托管进程设置 `CLAUDE_CODE_DISABLE_CRON=1`，关闭其会话内 cron 和 `/loop`；新建和恢复都应用，不改变普通启动的 CLI、桌面端或云端任务。Codex 未配置未经验证的内置调度禁用开关。外部 CLI 的版本支持和实测边界分别见 [codex-notes.md](codex-notes.md) 与 [claude-code-notes.md](claude-code-notes.md)。MCP 与 CLI 都连接私有本地 daemon socket；会话 ID 是上下文标识，不是独立授权凭据，同一操作系统用户属于本机信任域。

模型通过 MCP 获得的是受限委托：只管理本会话创建的任务，只恢复本会话；新会话限同项目、同 CLI 和相同的完整标准审批配置。Plan、未知或自定义权限不能通过该入口创建执行任务，不能把只读沙箱按界面的「询问」标签扩大为可写沙箱。创建、修改、手动执行和延迟派发都校验限制；来源权限改变后旧任务暂停，由用户 CLI 或远程客户端确认后接管：新会话的任务按目标里写的权限比对；恢复本会话的任务按创建时记在任务上的权限（`scoped_mode`）比对，没有这项记录的同样暂停。定时上下文保留到明确的人类输入或恢复；CLI 自己开的无用户消息后续轮继承原任务/运行 ID、MCP 限制与结束推送抑制；模型已收到定时输入后，运行历史按运行 ID 继续跟踪通知与摘要，不要求首轮以 completed 结束；尚未确认收到输入的运行仍由投递确认路径独占事件游标；中断、失败后的后续轮同样计入，直到人工输入或明确恢复、会话退出或另一次定时运行接管上下文。较新的跳过记录不会盖住旧运行。模型确认收到用户在定时轮中的插话后，才清除定时上下文；仅排队的人工消息不会解除当前轮限制。已被模型收到的人工插话使该轮结束按普通轮处理。绑定会话当前轮处于定时上下文时，MCP 不能创建、修改、恢复或立即运行任何任务；list、get、pause、cancel 仍仅作用于本会话委托的任务。尚未收到派发消息的预防限制仅用于任务新开的会话；排在原会话当前人工轮后面的定时消息不限制该人工轮。MCP 创建、修改、恢复或立即运行周期任务都要求 interval 至少 300 秒、after_turn 的 repeat 延迟至少 60 秒；派发时低于下限的旧任务暂停，原因为 `agent_schedule_interval_below_minimum`；权限变化仍用 `agent_schedule_permissions_changed`。显式的用户 CLI 和加密客户端没有这两条最小间隔限制。用户 CLI 和加密远程客户端仍拥有机器级任务管理能力。这约束模型的 MCP 工具，不提供同一操作系统用户之间的进程隔离。

用户从客户端或本机命令立即运行、恢复或修改执行定义后，任务转归用户管理。接管时保留原委托会话和接管入口，后续机器级编辑不覆盖这项来源。原会话的 MCP `schedule_list` 仍列出它，标明只读及客户端/本机命令接管；`get/update/pause/resume/run/cancel` 一律拒绝并提示让用户在客户端或 `remote-agent schedule …` 管理。其他会话不能借接管记录发现任务。只改名仍遵守下文的保留归属规则。

MCP 每次操作先确认 daemon 支持受限委托；不支持时拒绝工具调用。新 daemon 也拒绝旧 MCP 的无委托标记会话请求，明确的用户 CLI 调用使用独立入口标记。升级需要更新二进制并重启 daemon、重新连接会话内的 MCP 进程；升级前模型创建的未完成任务暂停，由用户 CLI 或远程客户端确认后接管。

### 定时上下文的请求准入

只有依据当前定时上下文作准入判断的 `create/update/resume/run` 和 `notify_user` 必须先读完并提交 transcript；读取或提交失败返回带重试提示的 `Unavailable`。安全控制不因这项读取失败而失效：中断、审批和 hooks 尽力刷新，失败记日志、使用缓存继续；只读和停止调度操作不等待 transcript。

| 请求入口 | 处理 |
|---|---|
| MCP `schedule_create/update/resume/run` | 严格准入；在读取串行化下取得调度锁并检查当前定时身份与创建来源兜底，定时上下文内拒绝 |
| 用户 CLI / Forward 的 `create/update/resume/run`，带绑定会话 | 同样先成功追赶记录；保留机器级管理权限，不套用模型限制 |
| `notify_user` | 严格准入；当前运行身份、次数和单条通知提交保持一致，不依赖轮询或 PermissionRequest hook |
| MCP / 本地 `list/get/pause/cancel` | 直接在调度锁下执行，不读取或等待 transcript；MCP 的任务归属限制保留 |
| 无绑定会话的机器级命令 | 不臆造实时会话；只按指定任务定义与持久历史操作，notify_user 仍必须有 MCP 绑定 |
| Hook：SessionStart、PermissionRequest、产生事件的 PreToolUse | 尽力刷新，读取失败按缓存继续原有行为；不因读取失败返回 Unavailable，从而不触发 hook 客户端的重启重试等待。事件自身写入失败仍按原规则处理；审批等待不持读取锁 |
| Interrupt | 控制锁前后都尽力刷新，失败仍按缓存 running 决定是否发 Esc；缓存空闲时不向草稿发中断键 |
| Stop / Resume 的退出结算 | 撤去严格 MCP 准入包装，保留原有退出结算安全边界：记录未读完时不伪造结束或重放未决输入，返回原有未结算错误 |

任务写操作的锁顺序是 `readMu → scheduleMu → mu`。读完并判断时已经取得调度锁；随后释放 `readMu`，继续持有 `scheduleMu` 完成准备和 schedules.json 保存，因此任务控制不能在检查与执行之间插入，慢任务准备或落盘也不阻塞 transcript 读取。创建来源兜底只覆盖新开会话收到派发消息之前，不能替代对普通恢复会话的读取。

其他读取已核对：原生事件提交/重放是有序归约，不是 MCP 准入；历史查询、快照和 relay 结束推送筛选只读已提交标注或创建元数据。`SessionPublicationFailed` 按不可变创建来源关联；人工输入接手按持久队列受理，不根据未导入的当前轮猜测。普通发送/撤回输入、审批/提问回答、设置与菜单操作保留各自既有控制规则；后台轮询、composer 推断和自动关闭保留读完记录、失败不结算或退避机制。

### 修改与改名

选择在现有 update 内识别仅标题变化，不增加 rename 操作：客户端继续提交它读取到的完整定义，daemon 统一判断，避免各端各自区分改名与重排。去掉标题后比较完整的公开 Spec JSON，而不是逐个列举可忽略字段，新增定义字段自然参与比较。只有标题确实变化且其余定义相同才是改名；完全相同的 update 保留原有整份替换语义。

仅改名时，只保存新标题并递增任务修订号，状态、原因、下次时间、相位、手动请求、活动执行与历史、运行的派发标题快照、迟到记录关联、来源及委托归属、更新时间均保留。运行中也可改名；改名请求在迟到执行确认和调度准备之前完成，不触发重排或重新启用任务，后台正常处理执行结果的规则不变。标题沿用非空且最多 512 字节的校验，修订冲突、持久化失败/不确定的规则不变；MCP 仍经过 update 的同一严格准入和归属/权限检查，校验不重新冻结或改变原委托。

其他定义字段有变化时，继续使用原 update 流程，包括活动执行完成前拒绝替换、重算调度、清除待开始的手动请求，以及机器级修改接管委托任务。失败的一次性任务通过实际修改消息或时间等执行定义重试；只改名保持失败。改名不要求原触发时间或截止仍在未来，也不重新验证未改变的目标路径。

### 触发与执行

支持一次性带时区的绝对时间、固定经过时长的周期、当地日历时间，以及当前轮结束后的延迟。固定间隔不承诺每日当地时间或夏令时语义。interval 的相位单独保存在内部 IntervalPhase，不写回 Spec.Trigger.At；用户的触发定义原样保存和返回。只改标题等非时间配置时保持相位，时间配置变化时重新确定相位。interval 更新定义和恢复都跳过已消费的自动时刻；恢复保留尚在未来且未消费的 NextRunAt，否则沿相位取不早于现在的下一点。周期触发（interval、calendar、重复 after_turn）派发前再与上一条非手动、非跳过运行核对，相同 ScheduledAt 不重复派发；一次性任务修改定义后可重新派发同一时刻；手动记录不参与相位计算。`calendar` 按 IANA 时区的当地时间和星期选择日期，空星期列表表示每天；daemon 内嵌时区数据库，创建时拒绝未知时区。每个 occurrence 的当地日期最多自动派发一次；补跑占用原 occurrence 的日期，跳过不占日期。「立即运行一次」对所有触发类型都是独立的额外请求（`ManualRequest` 保存请求时间和请求 ID），不借用自动游标或任务状态，不占自动次数和日历日期；仍受 `until` 硬截止约束。请求与自动运行共用唯一 Active 槽，互相等待；自动投递仍在 lateRuns 或任务状态 uncertain 时，已排队的手动请求也继续等待，不占执行槽；自动任务变为 failed 或终态时，将原先排队的普通请求记录为带原因的 skipped 后丢弃；手动占槽时到点的自动运行等它结束，再按补跑窗口运行或跳过。暂停、取消及涉及执行字段的定义替换清除尚未开始的手动请求，不撤回已开始的执行。uncertain、completed、cancelled 和 failed 周期任务拒绝手动请求，须先恢复或改定义；失败的一次性任务（at、非重复 after_turn）拒绝 resume，并明确提示立即额外执行或修改定义。用户在失败后显式立即执行的请求以 RetryFailed 标明重试意图，意图同时保存在运行记录中并跨重启保留。这是手动执行不改自动计划的唯一例外：显式重试成功时，仍处于 failed 的一次性任务变成 completed，原因为 explicit_retry_succeeded；重试失败仍保持 failed。用户在重试期间明确暂停或取消的状态保留。这不允许失败前排队的请求转成重试。手动执行失败、中断、无法确认只记录本次结果，不改变自动计划。重启时 dispatching 的手动执行记为无法确认，不重试，也不停止自动调度。春季跳过的时间取跳跃后的第一个有效时刻，秋季重复的时间取较早一次，不在较晚一次再运行。休眠补跑仍只取最近一次并按 `late_seconds` 判断。周期任务可用 `max_runs` 或带时区的 `until` 截止，创建/替换执行定义时已经过去的截止拒绝保存；截止之后拒绝立即运行，自动调度完成，已在运行的轮次照常结束。当天已自动运行再修改钟点，会立即计算真正的下一次。`after_turn` 在登记时绑定具体轮次；已经空闲或退出时从登记时计时，审批和提问不会结束这一轮。绑定轮次被中断或未经正常结束就退出时暂停，用户明确恢复后才重新安排。重复的延迟任务从每次执行结束后再计时，同一任务不重叠、不累计排队遗漏周期；可限制执行次数。

执行目标可恢复原会话，或在指定项目新开对话。恢复保持原 Remote Agent ID、CLI 对话 ID、环境及原有恢复规则。没有来源会话的任务，新开的会话复用[客户端新建会话的登录 shell 路径](#6-接入-codex)：从新终端的起点环境启动登录 shell，由 shell 现算环境并解析 CLI，不保存缺 PATH 的空调用方环境，也不直接依赖 daemon 缓存的 CLI 路径。启动方式随会话元数据持久保存，自动关闭后恢复、daemon 重启后恢复都复用现有的登录 shell 恢复逻辑，再次现算环境；不是在恢复时按任务当前定义猜测来源。有来源会话时保持原继承规则：新开对话从来源取项目、CLI 和可继承的配置，启动方式也沿用来源（来源从终端开的，就带上它保存的环境，按其中的 PATH 找 CLI；来源经登录 shell 启动的，就再次现算环境），换 CLI 时不继承另一 CLI 的模型与 effort。新会话不能直接以 Plan 模式启动；来源模式未知或非标准时，用户需明确指定启动模式。创建时已有明确配置的字段固定在任务中，留空且无法继承的字段使用执行时 daemon/CLI 默认值。

新开对话在首次持久保存元数据时就标记创建任务和归属，默认列表与项目摘要不含这些会话；按 ID 仍可查看全部历史。只有明确的 CLIENT/LOCAL 用户输入或用户明确恢复会话，才永久解除任务归属并重新发布元数据；未知或歧义来源不算接手，保留创建任务 ID。接手以持久队列中已受理的 CLIENT/LOCAL 输入（包括 Held）或带人类来源的恢复事件为准；公共队列保存入口在受理后接手，QUEUED 事件追加失败也不丢失，启动时再从持久队列修复元数据。选择队列作为事实来源，避免普通关闭与满额关闭各自补一套容易漏的队列判断；接手归属不提前解除当前模型轮的定时上下文。重放事件也可修复 session.json 写入失败。该次新开对话的执行正常结束、失败或中断后，未接手的 CLI 沿用结束会话流程退出，保留会话和历史；等待审批或提问不算结束。关闭前必须成功读完 transcript，再核对归属、当前轮和待发队列。输入与关闭共用生命周期顺序：输入先受理就接手并放弃关闭，关闭先开始就等它结束后恢复并发送。定时 resume_session 也在拿到生命周期锁后重新检查退出状态，恢复和准入保持同一顺序，不依赖锁前的存活快照。读取失败或条件不满足时按事件唤醒并退避，不每半秒反复读取；关闭不持有调度锁。执行结果 uncertain 时宁可保留 CLI，不自动关闭。自动关闭是否完成持久记录在会话元数据里，每次运行只执行一次；用户主动恢复不会被旧运行再次关闭。以后回复先走既有恢复流程再发送。发消息触发的隐式恢复使用系统来源，并与队列受理共用生命周期锁；恢复本身不算人工接手。消息持久受理后沿用队列的接手机制，含事件写入失败、目录同步返回不确定但队列已替换的边界；容量、图片或队列保存等受理失败时，保留任务归属并将新恢复的 CLI 重新交给自动关闭流程。明确点击恢复会话仍立即算人工接手。若隐式恢复受理失败后 CLI 尚未自动关闭，显式人工恢复遇到已在运行的任务会话，也在生命周期锁内认领归属并返回当前会话；沿用归属保存机制，不重启 CLI、不清除正在执行轮次的定时上下文。自动关闭即使此前已选中该会话，取得同一生命周期锁后也须重新检查归属。

执行消息进入现有 queue 模式，等待当前轮结束，不覆盖本地草稿、绕过弹窗或改变审批权限。任务暂停和取消只停止未来调度，不中断或撤回已经交给会话队列的消息；使用现有取消输入、中断和恢复输入操作处理当前执行。轮次正常结束只表示该次执行结束，不代表消息中的业务目标成功。

### 主动通知与客户端发现

任务级「完成后通知」默认开启；自动和手动运行均在派发时快照这项设置，后续编辑不改变旧运行。运行完成、失败、中断或取消后，daemon 在对应会话的事件日志中核对本次运行；已有 `notify_user` 事件就不补发，否则追加同一种定时通知事件。正常完成使用最终回复摘要（前 200 字），没有摘要时说明完成；失败、中断和取消明确说明结果。仅需异常或指定结果通知的任务关闭此开关，再由 agent 调用 `notify_user`。等待审批、排队和结果 uncertain 不算完成，跳过的 occurrence 不补发。通知追加失败不记为已通知，后续 tick 重试；事件提交与任务保存之间重启，以日志中持久事件去重，沿用原投递补传和通知隐私设置。运行记录区分 agent 与 daemon 来源；daemon 来源使用 SYSTEM origin，不新增推送类别或明文元数据。

通知仍附属于会话：启动失败且尚无执行会话时，使用派发时记录的来源会话（恢复任务使用目标会话）。任务没有任何可用会话时仅保留失败记录，不能通过现有会话通知链路请求推送；不为此伪造 CLI 会话。历史上已结束的运行不会因升级追补完成通知。

`notify_user` 使用上文统一的[定时上下文准入](#定时上下文的请求准入)，不依赖下一次轮询或 PermissionRequest hook；读取失败不消耗通知次数。它只在绑定会话的定时轮次内有效，普通轮次明确拒绝；它不是机器级任务管理指令。正文最多 200 字，标题最多 60 字，每次运行最多三次。自动与手动派发都在接受输入之前，将本次目标类型与任务名快照写入运行记录，移入历史和重启时保持不变；缺省标题按该运行的目标类型选择：new_session 取派发时任务名的前 60 字，resume_session 取目标会话当前显示标题的前 60 字（用户重命名优先于自动标题）。显式 title 始终覆盖缺省选择。最终标题随通知事件持久保存，后续封装签名 NotifyContent 不再查任务定义或客户端缓存，具体投递见 [§12](#12-推送通知)。缺少对应运行来源时明确拒绝缺省标题通知，不从任务当前定义猜测；显式标题不需要这项推断。计数从会话内已提交的通知事件重放，不依赖 MCP 进程或内存计数器；通知追加失败不消耗次数。运行记录保存是否发出过通知、次数、最后一条通知正文和本轮最后一条 final 回复前 200 字的摘要（去掉 Markdown 标题符号并合并空白）。“通知了你”表示已持久请求通知，不能证明送达；多次通知的完整正文保留在事件里。

`MachineCapabilities.scheduled_tasks` 表示可管理任务。`MachineMeta.schedule_revision` 只携带单调修订号，不携带任务列表；任务、运行记录、通知或下次时间等客户端可见状态变化时递增；事件游标和恢复记账不递增。修订号跨重启保留，以两秒窗口合并元数据更新。三端均按能力筛选机器，在修订号变化、电脑上线或中继重连后用既有加密 Schedule 机器指令重新取列表，不另加任务轮询。各端只缓存经过验证的签名密文响应，离线时重新验证并显示上次任务状态，禁止修改；任务内容在内存中解密。

三端通过独立「定时」入口聚合各电脑任务，提供新建/编辑、改名、暂停/恢复、立即额外运行和删除确认，以及按天查看运行历史。删除沿用 cancel 语义，停止未来调度，保留已开的对话。会话菜单可创建当前对话任务，对话定时条提供管理入口；运行记录按 ID 打开任务会话，并定位对应轮次。连续静默轮只有在同天、明确完成且没有通知、待处理或后续回复时才折叠；定位的轮次展开。任务会话接手沿用既有恢复/回复流程，不因打开运行记录就解除归属。界面与共同文案见 [client-v52 · 定时任务](design/client-v53.html#schedules)；iOS 的原生控件与无 APNs 边界见 [ios-client.md](ios-client.md)。

### 协议版本与升级

此前由错误的无来源直启逻辑创建、已保存为非登录 shell 且缺 PATH 的开发会话需重新派发创建，不迁移或推断修改其启动来源。

本阶段尚未发布；本轮运行记录增加派发来源快照，不迁移旧开发运行。更新前已派发且缺少该快照的运行应结束后重新派发，不能按修改后的任务定义补写来源；现有任务定义可继续派发新的运行。

协议为 12，Go、网页、Android、iOS 四处同值。任务定义新增通知策略，更新仍是完整替换；旧 iOS 的 Codable 模型会丢弃未知字段，再编辑时把 agent_only 悄悄重置为默认完成通知，因此协议 11 客户端不能控制协议 12 daemon。升级须一起更新 server、daemon、本地命令/MCP 与全部客户端；产品版本在实际发布时再提升，本任务不修改。已有任务未填写通知策略时未来运行默认通知；已有账户、数据库和 daemon 状态无需重建，不编写迁移。

定时任务主体自协议 11 起提供。新增字段虽然能被 protobuf 忽略，但旧客户端会把定时消息当普通消息、把实时广播或按 ID 取回的任务会话列进默认列表，旧 server 也不接受定时通知并会让任务会话挤满分页，所以不能把这些搭配视为可互通。三个客户端均已接入协议 11 的任务管理、定时消息和通知事件投影，并按任务归属筛选默认会话列表。独立定时入口、运行历史与离线读取也已实现；验收范围见[整合记录](acceptance-notes.md#定时任务三端整合2026-10-24)。

| daemon | server | 网页 / Android / iOS（分别适用） | 行为 |
|---|---|---|---|
| 12 | 12 | 12 | 三端可保留并编辑通知策略 |
| 11 | 12 | 任意 | daemon 新登录被 server 拒绝；升级前已连着的机器不会被中继代为重写，新客户端按机器协议拒绝控制 |
| 12 | 11 | 任意 | daemon 每次连接先登录，server 按登录协议拒绝，不能上传新任务会话 |
| 12 | 12 | 11 | 客户端新登录/配对被拒绝；已缓存 token 可能暂时读取历史，但按机器版本拒绝控制 |

协议读取点已核对：Go 的 daemon 会话追加、输入来源和调度、relay 同步/推送、server 列表/heads/通知、deviceauth 内容校验及 remoteclient；网页的 remote、model、device-security-client、push/service worker 和会话/项目列表；Android core 的 Remote/Model/Timeline/Skeleton/DeviceSecurityClient 与 App 的 Push/Notifications/ApprovalAttempt、Chat/Project；iOS core 的 RemoteLists/ChatState/ChatRows/Model/Skeleton/Timeline/Projects/ProjectRows/ProjectPage/DeviceSecurityClient。四端生成的 proto 解析与版本常量同步，事件投影仍保留原来的轮次边界行为。

历史仍按信封版本读取。旧登录 token 或未重连的连接不构成全局断开保证；不可信中继也不能替用户阻止旧程序，已有安全域的升级边界继续适用。更早协议升级仍按第 9 节的手动指南处理。

### 持久化与恢复

隐藏会话仍计入中继账户会话数，试用账户上限仍为 200。满额路径仅处理 `new_session` 的首次发布拒绝；`resume_session` 已有中继记录，不进入该路径。relay 回传 `relay_session_limit` 后，只按会话元数据中创建时持久化且恢复时不改写的 ScheduledTaskID/ScheduledRunID 关联这次运行，首次发布早于派发回写也一样；不读取任务当前的 Spec.Target。结束、拒绝和 uncertain 清理状态都按这对创建 ID 加会话 ID 精确匹配，因此用户改为 resume_session 不会取消旧 new_session 的清理或丢掉迟到的满额报告，同一会话后来的其他运行也不会覆盖创建运行的状态；运行记为 failed，自动执行按既有失败规则停住，手动执行只记录结果。这个尚未成功发布的会话交给已有自动关闭流程，即使仍在运行或有定时输入排队也关闭 CLI；关闭前仍须读完记录、确认尚未被本机人工接手，并沿用输入准入排序、异步关闭和失败退避。没有满额专用的撤回输入、中断或逐 tick 重试。客户端可据此显示「中继上的会话数已满」；本阶段不改变配额。

每台 daemon 最多保留 100 个未完成且未取消的任务，超出时创建或重新激活返回 ResourceExhausted；已完成和已取消任务的保留与删除不在此配额内。任务及最近 100 次执行记录保存在本机私有 `schedules.json`，原子替换并落盘。重命名前保存失败时回滚内存；文件已替换但目录同步失败时保留新状态并报告持久化不确定，不以旧内存覆盖新文件。创建支持稳定请求键，修改支持修订检查；受损或未知版本的文件会使 daemon 启动失败，不静默丢弃任务。

dispatching 状态在新建/恢复会话和注入消息之前持锁保存；会话启动和排队在调度锁外使用调度循环的 context 执行，再按 execution ID 持锁接回结果。启动阻塞不阻止任务管理或其他任务派发；期间的暂停和取消状态不会被启动结果覆盖。daemon 关闭时取消调度循环并等待派发 goroutine 退出，再释放 daemon 锁。关闭取消使尚未完成回写的执行保留持久化的 dispatching 记录，不记为执行失败；重启时与在该边界崩溃一样将这次执行记为“无法确认”，不自动重试；自动执行同时停住任务，手动执行不改变自动计划；已持久化的 queued/running 执行则通过原会话的队列、请求 ID 和事件游标继续跟踪，不重复发送。队列已持久受理、排队事件失败时也保留 active 执行及原请求 ID、会话 ID 和事件游标，执行状态为 queued，并通过该执行的 reason 说明「已排队但记录失败」；不记 could_not_queue_message，不禁止执行完成后的下一次调度，活跃期间新受理的手动请求等待它结束，不再生成第二个 Active；已有待发手动请求时拒绝重复请求。自动执行的消息提交无法确认、执行失败或中断时停止自动续跑；interval、calendar 明确恢复时重新计算下一次，只有截止或次数用尽才完成。手动运行仅记录本次结果，不改变自动调度。其中「无法确认」的那次执行，事后被 CLI 的记录确认了（第 6 节「迟到的记录仍然算数」），就按运行 ID 接回并跟到这一轮结束、照常续跑，不依赖最后一条历史记录，也不重发；等不到记录就一直停在不确定。这期间暂停任务不影响接回，任务保持暂停；恢复、替换执行定义或取消则表示放下那次执行，之后不再接回（操作前会先看一眼记录是否已到）。手动请求不触发自动执行的迟到接回，处于 uncertain 时直接拒绝，也不删除迟到游标。daemon 只在内存里记着哪次执行在等，重启后不再接回。

电脑和 daemon 需要运行，客户端无需在线；relay 断线不阻止本地调度，原有审批和消息同步机制仍有效。休眠或停机后默认只补最近一次、期限为 24 小时，可调整期限；超过期限记录跳过，周期任务转到下一次。绝对时间支持十年内的时间，间隔以秒计。当前加密接口提供查询和管理，发现与修订号已提供；客户端离线任务缓存、变更订阅与界面后续实现。
