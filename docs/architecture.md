# 架构与技术决策

项目边界见 [scope.md](scope.md)。本文记录各端怎么划分、彼此怎么通信、怎么接入 Codex，以及所有技术决策和理由。Codex 的实测行为见 [codex-notes.md](codex-notes.md)，还没定的问题见 [plan.md](plan.md) 的「待确认」。

## 1. 各端与部署

```
 手机 / 平板 / 浏览器              VPS（海外）                         每台电脑
 ────────────────────             ───────────                         ────────
 PWA / Android App                 Caddy（HTTPS）                      remote-agent（Go）
   │  网页来自 Cloudflare Pages      └─ remote-agent-server（Go）        ├─ daemon
   │  App 侧载安装                      SQLite                          ├─ 本地 CLI 命令
   │                                                                    └─ hook 入口
   └──────── HTTPS / WSS ────────▶ api.<域名> ◀──────── HTTPS / WSS ─────┘
                                                                     tmux ─ codex
```

| 端 | 形态 | 部署 |
|---|---|---|
| `remote-agent` | Go 单二进制：daemon、本地 CLI（`remote-agent codex` 等）和 hook 入口都在里面 | 每台电脑一个 |
| `remote-agent-server` | Go 单二进制，SQLite 存储，不直接对外暴露端口 | VPS 上，前面由 Caddy 负责 HTTPS 和反向代理，域名为 `api.<域名>`（当前部署在 `ra.remote-agent.top`，见下文） |
| `web` | PWA，React + Vite + TypeScript | Cloudflare Pages，挂在子域名 `app.<域名>` 上，用 CNAME 指过去，域名不用迁到 Cloudflare |
| `android` | 原生 App，Kotlin + Jetpack Compose，见第 15 节 | 自己签名的 APK，侧载安装 |

当前的 VPS 上已经有 Happy 用 docker compose 跑的 Caddy（占用 80/443），server 因此也用容器部署：接入 Caddy 所在的 docker 网络，不映射主机端口，Caddyfile 里只加一个站点块反代过去。镜像基于 `scratch`，以 nobody 运行，内存上限 128 MiB。`scratch` 里没有 CA 根证书，而 Web Push 和 FCM 都要访问 HTTPS，所以 server 二进制带上了 Go 的 `x509roots/fallback`（Mozilla 的根证书），系统里没有根证书时使用它。部署文件和脚本在 `deploy/`。

网页部署在 Cloudflare Pages 的项目 `remote-agent` 上（`remote-agent.pages.dev`），自定义域名 `remote-agent.top` 由阿里云 DNS 用 CNAME 指过去。用的是经典的 Pages 而不是 Workers 静态资源：Workers 绑定自定义域名要求域名托管在 Cloudflare，Pages 则支持外部 DNS 用 CNAME 接入。新版 wrangler 默认把 `pages project create` 转成 Workers，所以创建项目时要加 `--force`，之后的部署不用。构建时会生成 `_headers`，让 Pages 在响应头里带上和页面里一致的 CSP，外加 `frame-ancestors 'none'` 等只能靠响应头生效的限制。server 的 `ALLOWED_ORIGINS` 要包含网页的地址。

网页代码**不由 VPS 提供**：如果 VPS 被攻破后能替换网页的 JS，端到端加密就会被绕过。放在另一个平台上，攻击者必须同时攻破两处才行。Cloudflare 账号因此也成了关键资产，必须开启两步验证。

代码放在同一个仓库：一个 Go module，外加 `web/` 和 `android/` 两个目录。

### 产品版本与发布

各端使用根目录 `version.properties` 中的同一个产品版本，Android 的 `androidVersionCode` 每次发布递增。正式 tag 为 `vMAJOR.MINOR.PATCH`，与文件严格一致；daemon/server 的 `--version`、网页和 App 设置页显示产品版本和源提交。协议版本独立，不随产品版本自动增长；产品版本不同不是拒绝连接的理由，协议版本不同才是（见第 4 节的「版本」）。

Go 构建要求至少 1.26.8，发布流水线用 `govulncheck` 检查代码可达的已知漏洞。

发布按开发任务完成触发，不按时间触发：agent 完成一项功能或相关修复并验收后，按 [AGENTS.md](../AGENTS.md) 自动更新版本、推送 tag，无需逐次确认。新功能升 minor，修复升 patch，1.0 以前的不兼容改动升 minor，1.0 起升 major。纯文档、界面稿和测试改动不发版。GitHub 的 `Release` 流水线从 tag 运行 Go、网页、Android 检查，全部通过才发布正式签名 APK 和 `SHA256SUMS`。源提交写在发布说明中，各端仍统一版本；daemon/server 当前从源码安装部署、网页使用 Cloudflare Pages，所以不附 Go 二进制、网页压缩包或独立元数据文件，也不做 Go 多架构分发构建。已发布 tag 和附件不覆盖；暂时失败允许重跑，代码修复使用新版本。

正式 APK 缺少固定签名或 Firebase 客户端配置就停止发布，不退回 debug 签名。GitHub Secrets 的 `ANDROID_SIGNING` 保存签名 keystore 与签名参数，`ANDROID_GOOGLE_SERVICES` 保存客户端配置；FCM 服务账户和账户加密密钥不进入构建流水线。签名密钥必须另有本地备份。手动 `Build development APK` 生成独立 `.dev` 应用，与正式版数据分开，使用固定签名以便后续覆盖升级，推送关闭，产物保留 3 天。

Release 不自动部署 VPS/Cloudflare、不升级本机 daemon 或安装 APK，各端分别部署。当前部署脚本仍从本地工作目录构建，并嵌入版本和源提交；它不是从 Release 晋级产物的入口。各端不保证跨版本互通：协议版本变了就要一起升级，数据格式变了要手动迁移或重建，这些升级要求写在发布说明中。

## 2. 报文分层

所有跨网络的消息都分两层，类似信封和信纸：

- **外层（信封）**：发给谁、哪个会话、序号、鉴权。server 靠它来转发和存储，**server 能读**。
- **内层（内容）**：消息、工具调用、审批、终端数据、指令。先用 Protobuf 编码，再加密，**只有客户端和 daemon 能读**。

以手机发一条消息、Codex 回复为例：

```
 手机（PWA）                    server（VPS）                 电脑（daemon）                  Codex（tmux 里）
 ───────────                    ─────────────                 ──────────────                  ────────────────

 ① 用户输入
   "帮我修一下这个 bug"
        │
   [生成内层] 写成内层消息
   [加密]     内层 → 密文
   [生成外层] 装进信封：
     发给 机器A / 会话123
        │
        └──── 外层 ─────────▶ [读外层] 看收件人
                               存密文，转发给机器A
                               （内层打不开）
                                     │
                                     └──── 外层 ─────────▶ [读外层] 找到会话123
                                                           [解密]  密文 → 内层
                                                           [读内层] 拿到文字
                                                                 │
                                                                 └─ tmux 粘贴 + 回车 ─▶ ② Codex 开始干活
                                                                                             │
                                                                                        写 rollout 文件
                                                                                             │
                                                           [读 rollout] ◀────────────────────┘
                                                           [生成内层] "已修改 main.go …"
                                                           [加密]     内层 → 密文
                                                           [生成外层] 装进信封：
                                                             来自 机器A / 会话123，序号 42
                                                                 │
                               [读外层] 存下序号42 ◀──── 外层 ────┘
                               推给所有在线客户端
                                     │
 [读外层] 会话123 有新消息 ◀─ 外层 ──┘
 [解密]  密文 → 内层
 [读内层] ③ 显示 Codex 的回复
```

| 角色 | 外层（信封） | 内层（内容） |
|---|---|---|
| 手机 / 其他客户端 | 生成、读取 | 生成、读取 |
| server | 读取，按它转发、存储 | **碰不到**，只存和转发密文 |
| daemon | 生成、读取 | 生成、读取 |
| Codex | 不涉及 | 不涉及：只知道 tmux 输入进来的文字，以及自己写出的 rollout |

本地 CLI、hook 和 daemon 之间的通信不经过 server，只有一层，不需要加密。

发给 server 自己处理的请求（登录、拉列表和历史）只用到外层字段，返回的会话内容仍是密文。密钥怎么来、报文的具体格式见第 9、10 节；扫码配对的报文格式还没设计，见 plan.md。

## 3. 通信方式

**所有通信都通过 IDL 定义，不手写请求。** IDL 用 Protobuf，工具链用 `buf`；Go 端用 protoc-gen-go 和 connect-go，TS 端用 protobuf-es 和 connect-es。

```
 客户端                              server                             daemon
 ──────                              ──────                             ──────
 ① 普通请求（登录、查列表、拉历史）
    ──── HTTPS（ConnectRPC）────▶  处理并返回

 ② 发给 daemon 的指令（发消息、审批、新建会话…）
    ──── HTTPS，Forward ────────▶  不拆开，原样转发 ── 主 WebSocket ──▶  解密并执行
    ◀────────────── 结果原路返回 ─────────────────────────────────────

 ③ 实时推送（新事件、审批提醒、机器上下线）
    ◀──── 主 WebSocket（一直连着）──  主动推送  ◀──── 主 WebSocket ──── 上报

 ④ 终端画面（只在打开终端视图时）
    ◀──── 终端 WebSocket ────────▶  只转发，不存储 ◀── 终端 WebSocket ─▶  tmux
```

| 链路 | 承载方式 | 理由 |
|---|---|---|
| 一问一答（调 server） | ConnectRPC over HTTPS | 超时、错误码、重试都是现成的；接口由 proto 生成；可以用 curl 调试 |
| 客户端发给 daemon 的指令 | 统一走一个 `Forward` 接口：外层只写目标机器、请求 ID 和密文；具体指令在加密的内层里用 `oneof` 区分 | server 只按机器转发，连"是发消息还是审批"都分辨不出来 |
| 实时推送 | 主 WebSocket，打开 App 就连上，一直保持 | server 需要主动往下推；浏览器里的 ConnectRPC 不支持双向流 |
| 终端 | 单独一条 WebSocket，打开终端视图时建立，离开就断开 | 终端输出量大，和审批提醒挤在一条连接里会把提醒堵住；网络慢时可以单独断开重连，然后重新抓屏幕快照 |
| 本地 CLI、hook ↔ daemon | ConnectRPC over unix socket | 和上面用同一套工具；只有本机进程能连上 |

daemon 和 server 之间同样分主 WebSocket 和终端 WebSocket 两条连接。

## 4. 协议设计要点

以下原则已经定下，具体做法见第 10 节：

- **指令并发**：daemon 对转发指令设固定并发上限，重连共用同一个限额；重复请求等待可随连接取消，避免不可信 server 用大量密文或重放占满本机内存。
- **幂等**：`Forward` 里的指令都带稳定的请求 ID，daemon 记住已经处理过的请求，重试时直接返回原来的结果，不重复注入
- **防重放**：加密时把版本、发送方、目标机器、会话 ID、请求 ID 或序号、截止时间一起纳入认证数据；过期或重复的审批一律拒绝
- **历史和实时衔接**：server 先写库再推送；客户端按序号去重、补缺口
- **终端积压**：终端帧设大小上限，缓冲队列有长度上限；客户端太慢时断开终端流，重新抓快照
- **离线**：daemon 离线时，server 立即返回"不可用"，不替它排队
- **版本**：不做跨版本兼容，版本不一致就拒绝并提示更新，不逐项降级（规则见 [AGENTS.md](../AGENTS.md)）。全项目只有一个协议版本号（`internal/protocol`，网页和 Android 各有一份同值常量），旧版本会误解的改动才提升它。daemon 把它写进机器元数据，客户端发现不一致就不向这台机器发指令，并说明该更新哪一端；客户端把它写进每条指令，daemon 发现不一致就拒绝执行。本机命令和 daemon 之间通过本地 socket 的请求头和响应头互相核对，覆盖更新后没重启的 daemon 和旧会话里还在运行的 MCP 进程。server 只转发密文，不参与核对；它不认识的接口按普通错误返回。信封格式另有自己的版本号（`Header.version`），已存的历史靠它继续可读，所以协议版本提升不影响读取旧会话

## 5. 技术决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 语言 | daemon 和 server 都用 Go，全部重写，不复用 Happy 和 botmux 的代码 | 单二进制、内存占用低、方便分发；需要的功能远少于 Happy |
| 参考实现 | Happy（协议、加密、客户端交互）和 botmux（tmux、Codex 的各种坑）**只作参考** | 两者都是 MIT 协议，但它们是 TS 写的，而且范围远大于本项目 |
| 客户端 | 自己写 PWA（React + Vite + TypeScript），部署在 Cloudflare Pages；Android 另做原生 App（第 15 节） | PWA 一套代码覆盖所有设备，不上架应用商店，网页不和 server 放在一起；Android 是主力手机，终端和通知要做到原生体验 |
| 通信 | Protobuf 定义所有接口；一问一答走 ConnectRPC，实时推送和终端各用一条 WebSocket | 见第 3 节 |
| HTTPS | server 只监听本机端口，由 Caddy 负责证书和反向代理 | |
| server 存储 | SQLite | 单用户，部署简单 |
| tmux 接入 | 使用独立的 socket（`tmux -L remote-agent`）；P0 直接执行 tmux 命令（建会话、抓屏、存活检查），终端视图（P2）再接 control mode（`tmux -C`） | 不影响平时用的 tmux；P0 不需要 pane 的字节流，会话存活由 tmux 和 PTY 代理判断 |
| 输入 | tmux pane 里跑一层 PTY 代理（`remote-agent pty-host`），Codex 以原生 TUI 跑在它下面；本地按键和远程注入都经过它，见第 6 节 | 注入时要先确认输入框为空再写入；只靠 tmux 命令，检查和写入之间本地敲的键会混进远程消息 |
| tmux 依赖 | 必需；安装脚本和 `remote-agent` 启动时检查是否存在、版本是否满足 | |
| 输出来源 | Codex rollout jsonl，不从屏幕解析消息 | 屏幕内容不可靠 |
| 审批超时 | 拒绝；默认 10 分钟，`remote-agent daemon --approval-timeout` 可调 | 安全优先；手机上从收到提醒到处理需要时间 |
| 本地状态 | 每个会话一个目录：`session.json`、append-only 的 `events.jsonl` 和待发消息 `queue.json`；事件记录里带着读到的 rollout 位置，同时充当读取进度 | 重启后从记录的位置接着读，事件序号连续、不重复；已受理的消息不丢；单用户、单机，不需要数据库 |
| `/` 开头的输入 | 客户端不直接注入：常用命令做成按钮和面板，其余先提醒再发送 | 带参数的斜杠命令会被当成普通消息发给模型；打开菜单的命令在手机上看不到（[codex-notes §6](codex-notes.md#6-踩过的坑)） |
| 上下文提示 | 占用超过 80% 时提示，并提供「压缩」按钮（注入 `/compact`） | 数据来自 rollout 的 `token_count` |

## 6. 接入 Codex

下面每条做法都基于 [codex-notes.md](codex-notes.md) 里的实测，括号里的「notes §n」指它的第 n 节。升级 Codex 后要跟着复核。

- **启动**：tmux pane 里运行 `remote-agent pty-host -- codex …`。环境变量取自发起的 `remote-agent codex` 进程，再叠加 `~/.remote-agent/agent.env`（放代理等变量，所有 CLI 共用一份；daemon 由 launchd 启动时读不到 shell 里的配置。没有这个文件时读以前的 `codex.env`），并设置 `RA_SESSION=<会话 ID>`、`RA_EXE=<remote-agent 的路径>`。这些变量不经过 tmux 的命令行（命令行对本机所有用户可见，而环境变量里常有 API key），而是存进会话目录下只有自己可读的 `env.json`，供恢复会话时沿用；每次启动另写一份副本交给 PTY 代理，读取后删除。用 `-c` 注入 `PermissionRequest`、`SessionStart` 两个 hook，只对这个会话生效。hook 的定义（命令和 `timeout`）必须固定：Codex 每个 hook 位置只记一份信任，定义一变就要重新信任，而且会顶掉之前的信任。所以命令写成 `"$RA_EXE" hook codex`，不含二进制的路径，换了路径或同时跑测试用的另一份二进制也不用重新信任（notes §3、§5）
- **locale**：daemon 没有 UTF-8 的 locale 时（launchd、systemd 启动就是这样）自己补上 `LC_CTYPE`，tmux 和 Codex 都继承它。否则 tmux 会把输出里的 tab 和非 ASCII 字符换成 `_`：会话列表读不出来，所有会话都会被当成已经消失，屏幕里的 `›` 也认不出来。标成已结束、但 tmux 会话其实还在的会话，daemon 启动时会重新接上
- **恢复会话**：`codex resume <Codex 会话 ID>`，沿用原来的环境变量和参数，去掉位置参数（如第一句话），再用最近一轮的模型、effort 和审批模式覆盖；审批模式只在最近一轮的沙箱、审批策略和审批方与某个标准模式完全一致时才覆盖，免得把只读沙箱之类的更严设置放宽。Codex 不接受重复的 `-m`，命令行的审批选项又比 `-c` 优先，所以被覆盖的选项先从原参数里去掉
- **启动弹窗**：用 `-c` 关掉检查更新、限额换模型提示等能关的弹窗；关不掉的 `Trust this folder?`、`Hooks need review` 每个目录或每套 hook 只问一次，客户端提示去终端处理。能不弹就不弹；信任目录是安全决定，留给用户在终端里做（notes §5）
- **启动时不注入**：Codex 在新目录启动时会先闪一下输入框再弹出信任对话框（notes §10），所以会话处于「启动中」时不注入，等状态检测连续两次看到同样的画面、进入空闲再说
- **防弹窗挡输入**：每次注入前先抓屏，确认没有弹窗挡着。判断画面时只看屏幕底部；以列表里选中的行判断有没有弹窗，标题只用来给弹窗命名，对话里出现同样的字不算（notes §5、§6、§10）
- **等画面**：轮询屏幕，等到预期画面出现再操作，并设超时；不用固定的 sleep（notes §6）
- **输入**：远程消息按到达顺序排队，一次注入一条；队列在受理前写入 `queue.json`，重启后接着发。请求 ID 会记住最近 1000 个，重试不会重复发送。写入前记下 `history.jsonl` 的位置和当前事件序号。注入时 daemon 先让 PTY 代理暂存本地按键，等 80ms 让已经敲下的键显示出来，再抓屏：输入框就绪且没有未发送的草稿，才一次写入 bracketed paste 包起来的正文和回车，然后放开暂存。暂存期间本地敲的键不丢，放开后按顺序进入新的输入框；PTY 是按顺序的字节流，它们一定排在这条消息的回车之后。本地有草稿或有弹窗时，消息继续排队，绝不覆盖或拼接草稿。写入后以 `~/.codex/history.jsonl` 新增一行（已知 Codex 会话 ID 时只认这个会话的行）或 rollout 里出现这条用户消息，确认提交成功（notes §1、§10）。每条消息的状态以事件记录：排队、已提交、无法确认。10 秒内确认不了的记为「无法确认」，**不重发**，因为按键已经送到，重发可能提交两次；写入时恰好 daemon 停了的，重启后同样只等确认、不重发。注入、回答提问和中断共用一把锁，同一时刻只有一个操作使用 PTY 代理；代理也只允许持有暂存的连接写入和放开。正文里的控制字符会被去掉，避免提前结束粘贴
- **运行中的消息分两种**：steer 是插入这一轮，daemon 照上一条的规则在输入框就绪时写入：Codex 运行中按回车就是插入当前这一轮；Claude Code 运行中回车会先进它自己的队列，等当前工具调用结束再并入这一轮（claude-code-notes §10）。queue 是等这一轮结束再发，由 daemon 留在自己的队列里，看到这一轮结束（Codex 的 `task_complete`，Claude Code 的 `turn_duration`）后才按上一条的规则写入，不借用 Codex 的 Tab：两个 CLI 行为一致，daemon 重启后还在，也能照常取消。空闲时两者没有区别。**还没送到 Agent 的消息都能撤回**，不分 steer 和 queue：还在 daemon 队列里的直接移除（`CancelInput`）；Codex 的 steer 一写进终端就插进这一轮，算已送达，不能撤回；Claude Code 的 steer 写进后先留在 Claude Code 自己的队列里，直到当前工具结束才并入，这期间 daemon 按 ↑ 把它拉回输入框、清空，以 transcript 出现不是 `absorbed_mid_turn` 的 `queue-operation remove` 为撤回成功；先被并入了就报「已送达，不能取消」。客户端默认发 steer，和两个 CLI 自己按回车一致；发送请求里带一个字段区分两种，旧客户端不带时按 steer。**一轮被中断后**，还没写入的消息（queue 的，以及 steer 但还没写入的）都暂停，不自动发出，等用户逐条选择发送或取消：中断往往说明方向变了，排好的后续消息可能已经不适用。暂停状态和原因同步给所有客户端。字段和暂停状态尚未实现，见 plan.md
- **判断输入框**：抓屏时保留颜色属性（`capture-pane -e`），按**样式属性**判断，不按转义序列的字面写法：逐个解析行首的 SGR 序列得到加粗、变淡、反色，再看第一个可见字符。Codex 升级常换写法（0.159.0 把 `\e[1m` 换成了 `\e[0;1m`），样式本身不变。输入框的提示符是加粗的 `›`，占位提示是淡色字（前面可能先有背景色设置，判断时跳过开头的样式和空格，看第一个可见字符是不是淡色），列表里选中的行是加粗反色的 `›`。只有看到占位提示才认定输入框是空的：多行草稿的第一行可能是空的，其余行和底部状态栏分不开（notes §10）
- **找到 rollout**：`SessionStart` hook（发出第一条消息时触发）把 `RA_SESSION` 和 `transcript_path` 一起报给 daemon（notes §3）
- **轮次和空闲**：一轮以 `task_started` 开始，以 `task_complete` 或 `turn_aborted`（被中断）结束；屏幕底部的输入提示符作为辅助（notes §1、§8）
- **模型提问**：问题从 rollout 的 `function_call` 读出，它在等待回答时就已经写入，不需要 hook。回答时暂存本地按键、抓屏确认选择框还在，再注入选项编号；以 rollout 的 `function_call_output` 为准，先在终端里答了的就收回卡片。异步提问（`request_user_input_async`）不单独处理，一轮结束后当普通消息回复（notes §9）
- **中断**：只在一轮运行时发 Esc，绝不发 Ctrl-C。空闲时发 Ctrl-C 会清空输入框，再按一次会退出 Codex（notes §8）
- **切换模型和 effort**：空闲时操作 `/model` 菜单：按显示名在屏幕上找模型的编号并按下，在档位列表里用方向键移到目标档位后按 `s`，只改当前会话（回车会改全局默认值）。Max、Ultra 在 `More reasoning…` 子菜单里。以底部状态栏出现新的模型和档位为成功，认不出菜单就按 Esc 退出并报错。rollout 要到下一轮才记录新模型（notes §2），所以 daemon 先记一条 `SettingsChanged`，会话信息立即按它更新，下一轮的 `turn_context` 再校对。可选的模型和档位读自 `~/.codex/models_cache.json`；打开模型选择页时重新读取，避免客户端一直使用旧列表。配置中的默认模型也列为一个可明确选择的选项：缓存有它时保留其完整档位，即使它标为隐藏；缓存暂时没有它时仍列出模型，但不猜测支持的档位
- **切换审批模式**：询问、自动、完全放行分别是 `/permissions` 菜单的 1、2、3，按数字直接选中；完全放行还要在 `Enable full access?` 里按 1 确认，以屏幕出现 `Permission selection requested` 为成功。计划模式用 Shift+Tab 切换，以状态栏右侧的 `Plan mode` 判断当前状态。运行中也能切，下一轮起生效（notes §4）。同样先记 `SettingsChanged`
- **压缩上下文**：空闲时输入 `/compact`。压缩在 rollout 里是一条 `ContextCompaction`，无论是客户端发起的还是终端里敲的，都解析成「上下文已压缩」事件
- **计划**：Plan 模式下模型给出计划后，rollout 里的 `Plan` 条目解析成 `PlanProposed` 事件，屏幕上的 `Implement this plan?` 让会话处于「计划待批准」，客户端显示计划卡片，回答时注入 1、2 或 3（notes §4）
- **工具开始**：rollout 在调用工具时先写一条 `custom_tool_call`（或 `function_call`），结束时写同一个 `call_id` 的 `*_call_output`，中间可能有描述它做了什么的 `item_completed`（如 `CommandExecution`）。开始解析成带 `call_id` 的 `ToolStarted`；期间完成的第一个条目用这个 `call_id` 报成 `ToolCall`，同一次调用的后续条目用 `<call_id>#2` 这样的 ID；没有任何条目的调用（很多 `exec` 就是这样）在输出到来时补一条 `ToolCall`，保证每个开始都有结束。`wait` 是在等之前让出的 exec 单元（输出以 `Script running with cell ID N` 开头），不算新的调用，它的输出结束的是那个 exec
- **菜单操作的共同做法**：和注入一样拿控制锁、暂存本地按键，并在操作期间续期暂存；每一步都先确认画面再按键，等不到预期画面就按 Esc 退出。操作期间暂停状态检测，免得把自己打开的菜单当成弹窗
- **命令参数**：Go 代码调用 tmux 和 codex 时一律传参数数组，不拼 shell 字符串

## 7. 审批

`remote-agent hook codex` 作为 Codex 的 `PermissionRequest` hook，通过 unix socket 把请求交给 daemon。daemon 先读完 rollout，按最近一次 `turn_context` 的 `approvals_reviewer` 判断会话的审批方式：

| 会话的审批方式 | hook 的行为 | 用户看到什么 |
|---|---|---|
| 开着 `auto_review`（Codex 的 `Approve for me`） | 不输出、正常退出，交给 `auto_review` | 手机上不弹审批卡；模型在操作前拿不准时会在对话里问你（已实测），直接回复即可；`auto_review` 直接拒绝后模型会不会来问，未验证 |
| 没开 `auto_review` | 把请求转到客户端，等待回复；超时拒绝 | 审批卡片：和原生审批框一样的三项（见下文「客户端的审批选项」） |

依据：Codex 先调用 hook，hook 不表态时才交给 `auto_review`；hook 只能返回 allow 或 deny 加 message，做不到原生审批框里的「以后不再询问」（notes §3、§4）。

- **hook 的超时**：hook 定义里的 `timeout` 设为 3600 秒，审批超时必须比它短。hook 自己超时的话，Codex 会改为在终端里弹原生审批框（notes §3），就做不到「超时拒绝」了
- **daemon 连不上**：hook 什么都不输出，交给 Codex 在终端里弹原生审批框，仍然由人决定。审批等待中 daemon 重启时，hook 会重试 30 秒，连上新的 daemon 后重新发起审批；旧的那条记为「已取消」

**Claude Code** 的审批走同一个入口 `remote-agent hook claude`，但规则不同，不照搬上面的 `auto_review` 分支：

| | 做法 | 依据 |
|---|---|---|
| 转不转给客户端 | 所有模式下都转：`PermissionRequest` 只在 Claude Code 要弹权限框时才触发，bypass 和 auto 放行的请求根本不会来 | [claude-code-notes §6](claude-code-notes.md#6-审批permissionrequest) |
| 终端里 | 原生权限框和 hook 同时出现，电脑和手机谁先答算谁的 | 同上 |
| 本地先答 | 屏幕上见过的权限框消失、这个工具已经有了结果或这一轮结束时，把卡片记为「已在终端处理」（`APPROVAL_DECISION_TERMINAL`）并让 hook 退出。本地选了「允许」时 Claude Code 不会结束 hook，只能靠 daemon 自己发现 | 同上 |
| 超时 | 照样返回拒绝；原生框随之消失 | 同上 |
| AskUserQuestion、ExitPlanMode | 它们也会触发 `PermissionRequest`，hook 直接不表态，不出审批卡；它们由第 16 节的提问和计划处理 | notes §6、§7、§8 |

### 客户端的审批模式

客户端的模式切换只做 Codex 和 Claude Code 都有的 4 种，这样接入 Claude Code 时不用改界面：

| 客户端 | Codex | Claude Code |
|---|---|---|
| 询问 | `Ask for approval`（`/permissions`） | manual |
| 自动 | `Approve for me`（`auto_review`） | auto |
| 计划 | Plan mode（Shift+Tab，和权限相互独立） | plan |
| 完全放行 | `Full Access` | bypass（启动时没允许的会话置灰） |
| 不提供 | — | accept edits |

各项的实测情况见 [codex-notes §4](codex-notes.md#4-审批模式) 和 [claude-code-notes.md](claude-code-notes.md)。

- **客户端只允许单次审批**：「允许」通过 hook 返回 allow；「不允许」可附说明，通过 hook 返回 deny，不中断整轮。「以后不再问」由用户在原生终端里选择，daemon 不自动按原生审批框的第二项。现有 hook 和屏幕信息不能把这个选项可靠绑定到特定工具请求，同前缀命令、同名文件和留在历史里的文本都可能误匹配。daemon 不声明远程永久审批能力；客户端发来永久审批请求时明确拒绝，保留原审批等待用户处理。
- **「询问」的语义不抹平**：Codex 在工作区内改文件、跑命令本来就不问，只有联网和越界才问；Claude Code manual 每一步都问。客户端按 CLI 实际发来的请求显示
- **Codex 的计划模式**：计划模式和权限是两个开关。选「计划」只打开计划模式、权限不变；选其他三种会先关掉计划模式再切权限
- **以 CLI 为准**：客户端只发「切换」指令，显示的是从 rollout、transcript 或屏幕读回来的结果；在电脑终端里切的，聊天里记一条。终端切到了这 4 种以外的模式（如 accept edits），照实显示
- **会话中途切到完全放行要二次确认，新建会话不确认**：新会话的审批模式来自项目设置（第 13 节），在项目设置里选完全放行本身就是明确的选择，按它新建时不再弹确认，项目页的设置摘要用红字标出，会话里写在导航栏的状态行。项目设置没指定时用 daemon 设置里的默认模式，再没有就沿用 CLI 自己的配置。沿用 CLI 配置时，客户端事先不知道它是什么，所以 daemon 把每个 CLI 实际生效的默认模式读出来放进机器元数据（`AgentInfo.default_mode`，只读配置、不改任何文件）：Claude Code 按它的优先级读托管设置、项目的 `.claude/settings.local.json` 和 `settings.json`、用户的 `~/.claude/settings.json` 里的 `permissions.defaultMode`，都没有就是 manual；Codex 读 `config.toml` 顶层和所选 profile 的 `approval_policy`、`sandbox_mode`、`approvals_reviewer`，没写的按 Codex 的默认值。读不出来就标为未知。客户端用它在摘要里如实显示：完全放行照样用红字，未知写「CLI 配置（未读到）」，两种都不拦截新建。这些默认值都是用户自己写的配置，和在项目设置里选完全放行一样算明确选择，所以 daemon 也不据此拒绝新建（现有的 `confirm_full_access` 检查待去掉，见 plan.md）

## 8. 项目标识

项目按会话工作目录的**绝对路径**判定：路径相同就是同一个项目，不同电脑上路径相同的目录也算同一个项目；项目名是路径的最后一段。分组在客户端完成（`web/src/model.ts`），路径在加密的会话元数据里，server 看不到。同名但路径不同的是两个项目，列表里用路径区分。

会话标题由 daemon 从第一条用户消息生成，写进加密的会话元数据：去掉开头的图片占位（`[Image #N]`），取第一行的首句（到第一个中文标点，或后面跟空格的英文标点为止，前 4 个字符内的断句不算），最多 40 列宽（汉字算 2 列），超出加省略号。理由：整句当标题既不概括内容又必然被截断，而首句不需要调用模型，内容也不出本机。只有图片没有文字的消息不产生标题，由下一条消息命名；还没有标题时客户端显示「项目名 · 开始时间」。

### 会话列表排序

网页、宽屏侧栏和 Android 使用相同规则：「需要处理」先按审批、问题、计划、终端弹窗排列，同类型按当前待处理请求的开始时间从早到晚；多项审批或问题取仍待处理项中最早的时间，解决后转到下一项。「进行中」包括启动、运行、空闲和离线会话，按会话创建时间从新到旧，离线不改变位置。「已结束」按实际退出时间从新到旧。时间相同使用会话 ID 的字典序；项目排序时间相同时使用项目路径的字典序。分区变化会移入对应列表，当前选中会话继续遵守侧栏保留规则。

等待和退出时间由 daemon 从本地事件日志重建；计划等待从稳定终端画面首次显示批准提示时记录，弹窗从进入对应阻塞状态时记录。时间跟随加密会话摘要传输，server 无需解密或参与排序。后台输出和重连的上传时间只用于最近活动显示和新会话配置继承，不决定会话或项目列表的位置。会话没有等待或退出时间时用创建时间；摘要未解密时用零和 ID，摘要首次到齐后再按创建时间归位。

### 项目列表偏好

项目仍按绝对路径分组。常用、隐藏和项目设置（第 13 节）都属于账户，在客户端之间同步；用独立用途密钥加密后交给 server 存储和转发，server 只能看到不含路径的对象 ID、修订号与密文。客户端解密后按项目路径匹配，不向 server 上传明文项目名或路径。常用按设为常用的顺序稳定排列，其他项目先按是否有未结束会话分组：有未结束会话的项目在前，所有会话已结束的项目在后；各组按项目内最近创建会话的时间从新到旧排列，相同时间按项目路径字典序。运行、空闲、等待处理和离线都算未结束，状态之间切换、输出和重连不改变项目顺序。新建会话可以前移项目，最后一个未结束会话退出时项目移到已结束组。旧会话缺少创建时间时用零，摘要首次解密后按创建时间归位。

偏好写入带预期修订号：冲突时取回最新密文、解密，再重做当前项目这一项改动，保留其他项目的并发改动。界面先显示保存中，server 确认后更新列表；断线时显示缓存并暂停修改。新设备读取账户偏好；退出或清除本机数据只删除本地缓存，不删除账户的常用项目。

「从项目列表移除」只是隐藏入口，不结束会话、不删除历史、不屏蔽提醒；隐藏项目不出现在项目列表或新建选择器，进行中的会话与待处理项仍照常展示。从通知或会话进入时可以查看，并提供恢复入口；新建前先恢复。新增会话不会把隐藏项目自动恢复。移除后支持撤销，也可从「项目管理 → 已移除」恢复。

项目页布局与具体交互见 [client-v8](design/client-v8.html)。目标机器离线时由用户选这次用的机器，不改项目设置，也不在输入中途自动更换机器或 CLI。在项目设置里切换 CLI 保留草稿，清除不适用的模型和强度，并验证模式。

## 9. 账户、设备和密钥

一个账户对应一个随机的 32 字节**根密钥**。第一台电脑用 `remote-agent account init` 生成它；server 上只有一个账户，第一次登记设备时必须带上 server 配置里的一次性 setup token，账户建好后 token 就不再起作用。

所有密钥都从根密钥派生，一个用途一把（HKDF-SHA256，info 为 `remote-agent/v1/<用途>`）：

| 用途 | 派生出的密钥 | 用来 |
|---|---|---|
| `account-sign` | Ed25519 账户密钥 | 签设备登记；server 只存它的公钥 |
| `wrap` | AES-256 | 加密会话密钥 |
| `machine-meta` | AES-256 | 加密机器元数据（机器名、系统） |
| `command` | AES-256 | 加密客户端发给 daemon 的指令和返回结果 |
| `notify` | AES-256 | 加密推送里的通知内容，只给 Android App 在后台解密用（第 15 节） |
| `account-prefs` | AES-256 | 加密账户级的偏好对象（项目的常用、隐藏和项目设置，第 8、13 节） |
| `device-meta` | AES-256 | 加密客户端设备的元数据（名称、平台），见下文「设备目录」 |

每个会话另有一把随机的**会话密钥**，加密这个会话的事件和元数据。它存在 daemon 的会话目录里（`relay.key`），用 `wrap` 加密后上传到 server，客户端从 server 取回再解开。

**设备**：每台电脑、每个浏览器和每个 App 都有自己的 Ed25519 设备密钥，设备 ID 是公钥 SHA-256 的前 16 字节。登记时用账户密钥签名，server 用账户公钥验证；登录时设备签 server 给的一次性 challenge，换取 30 天有效的 token。设备登记由账户密钥签名，而不是由一台已登记的设备签名：单用户场景下根密钥本身就是信任根，这样新设备加入时不需要旧设备在线。

**指令签名**：`command` 密钥是账户里所有设备共用的，只能证明「账户里有设备发了这条指令」，而 server 不可信，它说的发送方也不能当真。所以客户端用自己的设备密钥给每条指令的信封签名（`Envelope.signature`），签的是上下文 `remote-agent/v1/envelope-signature\0` 加上 header、nonce、密文的原始字节，每段前面带 4 字节大端的长度。server 转发时核对 header 的发送方就是登录的设备，并附上这台设备登记时的原文和账户签名；daemon 先用账户公钥验证登记，再用登记里的设备公钥验证信封签名，两者都对才把来源记为这台设备（`ORIGIN_KIND_CLIENT`）。没有签名或签名验证失败的指令拒绝执行。字节格式的测试向量在 `internal/e2e/testdata/v2-vectors.json`。

**把根密钥交给新设备：配对**。已有设备（网页的「设置 › 添加设备」或 `remote-agent account pair`）显示二维码和 8 位配对码，新设备扫码、输码（网页），或用 `remote-agent account join --code` 加入。实现在 `internal/e2e/pair.go`、`internal/relay/pair.go` 和 `web/src/pairing.ts`，要点：

- **8 位码只用来找到配对**，不参与加密，也不算授权：server 能看到它，熵也只有 26 位多
- **先承诺、后揭示**：已有设备建配对时只交出自己一次性 X25519 公钥的 SHA-256；新设备发出公钥之后，已有设备才揭示公钥，新设备核对它和承诺一致。已有设备的公钥在看到新设备的公钥之前就定了，替换密钥的 server 没法挑选让两边图案碰巧一致的密钥
- **四个 emoji**：双方用 X25519 共享值和整个会话记录（配对 ID、两把公钥、新设备类型）经 HKDF 派生 32 位，映射到 256 个 emoji 里的 4 个。用户核对一致后在已有设备上允许，已有设备才用同一共享值派生的密钥封好根密钥和 server 地址交出去。被替换过密钥的两端算出的图案不同
- **二维码**带上承诺，扫码的新设备直接比对，不只依赖人工核对
- **限制**：配对 5 分钟过期，同一时间只有一个候选设备，每个码最多 3 次加入；错误的码在全局按每分钟限流。限流预算耗尽后不再查询任何配对码；已有设备取消时清掉待领取密文。配对状态只放在 server 内存里。密文只给持候选令牌的新设备，响应丢了可以重取；新设备加入完成后确认收到，server 随即清掉密文，把配对标为「已交付」再保留一分钟。发起方看到「已交付」才报成功，超时或配对中途消失则提示结果不确定
- 新设备拿到根密钥后，照常用账户密钥签名登记自己

新设备等待核对时可取消或因图案不一致返回填码页：停止本次轮询和后续自动加入，丢弃本次临时配对密钥，保留服务器地址、清空旧码；不把本地退出说成 server 已撤销。旧候选仍可能占着配对码，提示已有设备拒绝旧请求并生成新码。取消与允许同时发生时，注册前需重新检查取消状态；如果登记已经开始或完成，不能报「已取消」，应确认登记结果，再提示已经加入或结果尚未确认。界面见 [client-v2 · 设置与配对](design/client-v2.html#settings)。

各端的服务器地址只接受 HTTPS，本机 loopback 地址允许 HTTP 用于开发，Android 调试还支持模拟器的 `10.0.2.2`；正式 Android 的网络配置禁止 HTTP。服务器地址不能带用户凭据，Go 也拒绝片段和查询。Go、网页和 Android 的 API 请求拒绝重定向，避免登录签名、setup token 或 bearer 被转交给另一个地址。Go 和 Android 的 WebSocket 握手也拒绝重定向；浏览器 WebSocket 没有关闭重定向的 API，仍依赖所配置 HTTPS 服务及浏览器的混合内容策略。

账户密钥串 `ra1.<根密钥>.<server 地址>`（`remote-agent account secret`）仍可作为备用方式粘贴，它不放进 URL，以免留在浏览历史里。

**浏览器怎么存**：设备私钥存成不可导出的 `CryptoKey`（IndexedDB）；根密钥除了不可导出的 HKDF 密钥，还存一份原始字节，因为配对时要把它交给新设备（WebCrypto 的不可导出密钥取不回原始字节）。代价是页面一旦被注入脚本，根密钥能被带走；不过那种情况下脚本本来就能通过页面解密全部内容，差别在于带走后长期有效。配对上线前加入的浏览器没有原始字节，不能发起配对，要重新加入一次。不同的网页来源（如 localhost 和 `app.<域名>`）各有各的存储，换了地址要重新加入。App 怎么存见第 15 节。

### 多客户端的界面状态

每个会话属于固定机器和 CLI。已接受的消息、队列、模型、模式、上下文与处理结果是共享状态，以 daemon 发出的事件与元数据为准；项目列表偏好跨端同步；客户端草稿、当前视图、滚动位置和通知偏好各自独立。多端输入仍按到达顺序注入，不增加会话独占。某个客户端断线只说明它的数据可能过期，不意味着电脑或其他客户端离线。

v2 的设备目录和来源展示需要补充协议能力（进度见 plan.md）：server 只提供设备 ID、设备类型与加密元数据；人类可读的客户端名称不以明文登记。客户端名称放在独立用途密钥加密的元数据中；消息与队列的发送设备 ID，以及处理来源写在加密事件内，由 daemon 按已认证的指令来源记录，不能信任客户端自报的来源。来源没记录或无法可靠匹配时写「另一客户端」或「本地终端」，不猜具体设备，也不凭卡片消失推断允许或拒绝。设备目录的「已配对」不代表在线、正在观看或有独占权。

其他端处理了审批或提问时同步收回卡片，普通消息草稿保留；正在输入但未提交的拒绝理由暂存在本客户端，可复制，不能自动当作下一条审批的理由。终端尺寸属于共享 tmux 窗口，任何端主动适配后，所有端按收到的新尺寸更新；不能仅根据自己之前点过适配来显示「已适配」。取消适配与断开时遵循第 11 节的 latest 规则，不承诺恢复旧设备记录的尺寸。

## 10. 报文、同步和指令

字段以 `proto/remoteagent/v1/{envelope,relay,remote}.proto` 为准，这里只写约束和理由。

**信封**：内层先编码成 Protobuf，再用 AES-256-GCM 加密。`Header` 写明用途、机器、会话、序号或请求 ID、截止时间和发送方，序列化以后**原样**作为附加数据参与认证，接收方解开后按原始字节解码，从不重新编码。接收方逐项核对 header 和信封所在的位置（哪台机器、哪个会话、第几号、哪个请求），所以 server 没法把一个信封挪到别处。nonce 是 12 字节随机数。server 也会读 header（它是明文），只用来尽早拒绝放错位置的请求，安全性不依赖这一步。

**事件上传**：daemon 连上后先查 server 已有到哪个序号（`ListSessionHeads`），再按序号从后面接着传；server 只接受紧接着的序号，已有的跳过，有空缺的拒绝。重试时同一序号的事件会用新 nonce 重新加密：本地日志里每个序号对应的内容不会变，所以解出来的明文相同，server 保留第一份。每个会话一把密钥，随机 nonce 的数量远低于 GCM 的使用上限。

**客户端同步**：先连上 WebSocket，再拉会话列表和缺的事件，这样两者之间不会漏掉。server 先写库再推送；客户端按序号去重，推送来的事件如果前面有空缺，就先放着，再用 `GetEvents` 补齐。会话和机器的元数据带递增的修订号（header 的 `seq`），客户端只接受更新的版本，server 也只保留最新的。

**指令**：客户端的指令统一走 `Forward`，header 里带 128 位随机的请求 ID 和 60 秒后的截止时间。daemon 的处理规则：

- 截止时间已过的拒绝；比现在晚 10 分钟以上的也拒绝，并提示检查时钟
- 执行前先把请求 ID 记为「开始」并落盘，执行后记下结果，也落盘（`commands.json`）；文件无法读取或格式损坏时禁用远程指令，保留原文件，修复并重启后恢复，不把损坏记录当作空记录
- 同一个请求 ID 再来，直接返回记下的结果；如果只记了「开始」没有结果，说明上次执行到一半 daemon 停了，返回「结果未知」，**绝不重新执行**
- 记录保留到截止时间过后，因为过了截止时间的指令本来就会被拒绝

server 把指令原样转给那台机器的 WebSocket，最多等 30 秒。机器不在线时立即返回「不可用」，**不排队**；已经转发出去但没等到结果时，返回「可能执行了、也可能没有」，客户端用同一个请求 ID 重试即可。

**WebSocket**：路径 `/v1/stream`，承载二进制 Protobuf 帧。浏览器的 WebSocket 不能自定义请求头，所以第一帧发 token，认证通过前 server 不发任何数据；浏览器连接还要检查 `Origin`；原生 App 不发 `Origin`，server 用的 coder/websocket 对没有 `Origin` 的请求直接放行，App 同样靠第一帧的 token 认证。server 每 20 秒 ping 一次；某个客户端积压超过 256 帧就断开它，它重连后从历史补。每台机器同时只保留一条连接，新连接顶掉旧的。主连接和终端连接在 token 到期或设备被移除时都取消，认证登记和移除共用锁，避免连接在移除期间重新进入。

**大小限制**：单个信封不超过 1 MiB，一次上传不超过 500 个事件，推送帧超过 1 MiB 就拆开发。历史按条数和序列化字节数共同分页，客户端按返回游标连续读取。WebSocket 认证 hello 使用独立的小帧上限；等待认证和活跃连接同时受固定限额约束，过载明确拒绝。HTTP RPC 在解码请求正文之前限制并发和读取时长；认证请求使用更小的正文上限。推送去重状态和异步发送同样有容量限制，过载返回可重试错误，不消耗被拒通知的去重键。

**网页**：事件内容一律当文本渲染，不插入 HTML；Markdown 里只有 http(s) 的链接可以点，其他目标（大多是本机文件路径，也可能是 `javascript:`）显示成等宽文字；构建产物带 CSP，只允许运行自己的脚本。网页和 server 要放在同一个注册域名下（`app.<域名>` 和 `ra.<域名>`）：拦截扩展常按「第三方请求」过滤，实测 AdGuard 会拦掉跨站发往 `*.*.top` 的 WebSocket（[browser-notes §1](browser-notes.md#1-adguard-拦截发往-top-的跨站-websocket)）。本地开发遇到这种拦截时，可以用 `RA_PROXY` 让 vite 把请求转发到 server，同时用 `VITE_SAME_ORIGIN_API=1` 构建。

## 11. 终端视图

客户端打开终端时，发一条加密指令 `OpenTerminal`，带上随机的流 ID。客户端和 daemon 各自用这个流 ID 连 server 的 `/v1/term`，server 把两条连接配对后原样转发，**不存储、不解析**：配对要求一端是客户端设备，另一端正是客户端指定的机器；先到的一方最多等 20 秒。

- **画面来源**：daemon 为每条流起一个 tmux control mode 客户端（`tmux -C attach`），它不参与窗口尺寸的计算。先开始接收 `%output` 里这个 pane 的输出，再用 `capture-pane -e` 和光标位置拼出快照，快照之后把收到的输出全部转发。抓屏前后到达的输出可能已经在快照里，会再画一遍；Codex 用绝对坐标绘制，重画不改变结果，而丢掉它们会让画面缺块。窗口尺寸变化时（`%layout-change`，比如电脑上调了终端大小），重新发快照
- **加密**：每一帧用会话密钥封成信封，类型分输出和输入，`request_id` 是流 ID，`seq` 是各自的帧序号，接收方要求序号严格递增，乱序或重放就断开
- **输入**：客户端敲的键经 `tmux send-keys -H` 进入 pane，走的是和本地键盘相同的路，所以注入消息时对本地按键的暂存同样挡住它们
- **尺寸**：默认不改 tmux 窗口，客户端按列数缩小字号；「适配屏幕」（Android 已适配时主动调整字号也重新适配）才 `resize-window` 到客户端能放下的大小，取消适配或关闭终端时把 `window-size` 设回 `latest`
- **积压**：输出通道满了就结束这条流，客户端重连后拿到新的快照；server 写一侧超过 10 秒写不出去，两边一起断开

## 12. 推送通知

server 首次启动时生成 VAPID 密钥对，存在数据库里。客户端订阅时说明要哪几类通知：「等我处理时」（审批、提问、计划、终端弹窗）和「一轮结束时」。

- **谁决定推送**：server 看不懂事件，由 daemon 在事件上传成功之后调用 `Notify`，只说明会话 ID 和类别。只对两分钟内发生的事件通知，重连后补传旧事件不会推送
- **内容**：只有通用文案（「有会话在等你处理」），外加用于跳转的会话 ID，符合 scope 第 4 节「推送不含具体内容」。同一会话同一类别 15 秒内只推一次
- **客户端**：service worker 收到推送时，如果应用正开着并在前台，就不再弹通知；点通知打开对应会话。iPhone 上要先把网页添加到主屏幕才能订阅推送。推送服务返回 404 或 410 时，server 删掉这个订阅
- **Android**：推送走 FCM，内容是 daemon 加密的密文，通知里可以直接审批，见第 15 节

## 13. daemon 设置与远程新建会话

daemon 的设置存在 `~/.remote-agent/settings.json`，客户端可以读取和修改：审批超时（30 秒到 hook 超时之前）、新项目默认的模型、effort 和审批模式（项目设置的初值，也是项目设置不适用时的回退）。未设置的项沿用启动参数或 Codex 自己的配置。

- **远程新建会话**：客户端指定机器、目录、第一句话，以及可选的模型、effort、审批模式；daemon 把它们换成 codex 的 `-m` 和 `-c` 参数，第一句话像普通消息一样排队，等 Codex 的输入框出现再发。会话的环境变量用 daemon 自己的，不用客户端的。目录由客户端通过 `ListDirectories` 逐级浏览选择，隐藏目录不列出
- **新会话的配置属于项目**：每个项目有一份项目设置，写明新会话用的 CLI、机器、模型、effort 和审批模式，改动只影响之后新建的会话。理由：配置是项目的属性，放在输入框的「＋」里会和「这条消息带图片」混成一层；从最近一个会话隐式继承又让人看不出、也预测不到下一次会用什么。项目设置存在账户偏好里（第 8 节），用 `account-prefs` 加密，按项目路径匹配，所以换设备也一样，server 看不到内容。进度见 plan.md
  - **目录不是设置**：项目就是按目录路径认的（第 8 节），换目录等于换项目，所以项目设置里只显示路径、不能改；要在别的目录开会话，从主页右上角的新建按钮选别的项目或新项目
  - **初值**：新项目从所选机器的默认设置（daemon 设置，见下文）开始；还没保存过设置的已有项目，用最近一个会话的配置作初值，计划模式换成机器默认。第一次从项目里新建会话时把所用配置存为项目设置，之后只有用户改才会变
  - **审批模式**：可选询问、自动和完全放行；计划只是一段临时状态，不作项目默认。选了完全放行，新建时不二次确认，见第 7 节
  - **不适用时**：所选机器离线，项目页提示并让用户选这次用的机器，不改项目设置；所选模型或 effort 在这台机器或这个 CLI 上没有，就用机器的默认值并提示
  - **界面**：项目页标题下一行写这些设置的摘要，点开或从 ⋯ 进入项目设置；新建区和会话输入框共用单行起步的布局，两处的「＋」都只用来添加图片，本会话的模式、模型和上下文在会话导航栏的 ⋯ 菜单里。这样新建只需要写第一句话，要改设置有固定的地方
- **机器级指令**：新建会话、列模型、浏览目录、读写设置不属于某个会话，信封头里不带会话 ID；daemon 拒绝带了会话 ID 的机器级指令
- **移除设备**：客户端可以在 server 上删除一台设备：删掉它的登记、登录凭证和推送订阅，并断开全部主连接和终端连接；如果是机器，连同它的会话和事件密文一起删除，并断开它的连接。server 持久记录被移除的设备公钥标识，拒绝重放旧的签名注册请求恢复该设备。旧数据库升级时还会固定新注册的签名时间下限，拒绝用签名时间早于该下限的注册原文恢复已经丢失的设备记录；已登记设备的正常登录和原样重试不受影响。升级时已开始但未完成的配对需要重新发起，新设备的时钟必须晚于升级时间。这不是根密钥吊销：手里还有根密钥的设备仍可生成新的设备密钥重新登记。机器详情页底部提供「移除这台机器…」，先确认删除记录和断开连接的影响再执行；客户端详情保留独立的客户端移除入口

### 工具执行反馈

过程不是用户关心的重点，客户端只用一行表示一次工具调用：运行中写命令和计时，失败写退出码，连续完成的折成「运行了 N 条命令」。不做工具详情页，不显示工具输出，也不提供跳转终端的入口：失败原因由 Agent 在回复里说明，想看过程的用户自己切到终端标签。这样客户端不需要解析和传输输出，也不会把不可靠的中间状态当成进度展示。

客户端收到 ToolStarted 后立即显示这一行，未完成的不能收进完成分组；等待审批和工具运行中分开显示。计时从 daemon 的事件时间算，各端同一起点，未知起点不猜；客户端断线时停住并写「等待同步」。Claude Code 按调用 ID 配对开始与结果；Codex 也按 `call_id` 配对，但这不代表能单独停止某个工具。转到后台的调用写「后台运行」，之后不追踪它是否结束；daemon 仍在 `ToolCall.background` 里标明来源（模型要求的、超时移到后台的、终端里按 Ctrl+B 的、一轮结束时仍在运行的），客户端不用从结果文字猜。中断只中断本轮，不保证终止后台命令（[codex-notes.md §8](codex-notes.md#8-中断和运行中的输入)）。

## 14. 适配 Codex 升级

remote-agent 依赖 Codex 的屏幕和 rollout，Codex 升级可能改变它们。做法是让变化尽量不破坏功能，破坏了要能看出来、能查出哪一项：

- **容忍写法变化**：画面按样式属性和文字判断（第 6 节）；菜单按标题和选项文字定位；rollout 里认不出的条目保留为通用工具调用，不报错
- **看得出来**：排队的消息发不出去时，daemon 在会话信息里给出原因（终端有草稿、有弹窗、认不出输入框）；认不出输入框超过 20 秒会记一条带 Codex 版本的警告，网页上提示可能是 Codex 升级改了界面
- **查得出来**：`remote-agent doctor` 用独立的 daemon、状态目录和 tmux，在 `~/.remote-agent/doctor-work` 里以 GPT-6-Luna 低档位真的跑一个会话，逐项检查：认出输入框、区分本地草稿、注入并读回回复、切模型、切审批模式和计划模式、中断、终端快照。失败时附上画面分析的结果（不含内容）
- **记录版本**：daemon 启动时读 `codex --version`，放进机器元数据；代码测试过的版本（`codex.TestedVersions`）和本机 doctor 通过的版本算「已验证」，否则启动日志和网页的机器详情里提示运行 doctor

## 15. Android 客户端

Android 原生 App 要把手机上的体验做到原生水平，范围见 [scope.md](scope.md) 第 5 节，进度和未定的问题见 [plan.md](plan.md)。协议、同步、指令和终端的规则都和网页一样（第 10、11 节），这里只写 App 自己的选型和约束。

### 选型

| 组件 | 选型 | 理由 |
|---|---|---|
| 工程结构 | 纯 Android 工程，分成 `:core` 和 `:app` 两个模块，代码放在 `android/` | 见下文「模块」 |
| UI | Jetpack Compose + Material 3；状态用 Coroutines + StateFlow，事件在一个串行队列里归约 | 返回手势、键盘 insets、动态取色这些原生交互都能直接控制；前台界面和后台通知走同一套逻辑 |
| RPC | connect-kotlin + OkHttp，Connect 协议，二进制 Protobuf | ConnectRPC 官方的 Android 用法 |
| Protobuf | 用 `buf` 从 `proto/` 生成 javalite 和 connect-kotlin 代码 | `proto/` 仍是唯一的协议定义 |
| WebSocket | OkHttp，`/v1/stream` 和 `/v1/term` 各一条 | 和网页相同的两条连接 |
| 加密 | AES-256-GCM 用平台 JCA；X25519、Ed25519、HKDF 用 Bouncy Castle 的 lightweight API | 先保证和 Go、TS 逐字节一致，见下文「加密和密钥」 |
| 本地存储 | Room 存密文信封和同步游标，DataStore 存偏好 | 本地不保存明文 |
| 推送 | FCM data message（自己的手机有 GMS） | 见下文「推送和通知里审批」 |
| 终端 | Termux 的 `terminal-emulator` 和 `terminal-view`，源码放在 `android/terminal`，用 `AndroidView` 嵌进 Compose | 原生渲染和输入法都比 WebView 里的 xterm.js 好；为什么放源码见下文「终端」 |
| 扫码 | CameraX + ZXing core | 本地解码，只扫配对二维码这一种 |
| 构建和分发 | Gradle version catalog 锁定依赖版本；minSdk 26，targetSdk 35，compileSdk 36（connect-kotlin 0.9 依赖的 OkHttp 5.4 要求）；release 构建开 R8，另有一个 `minified` 构建类型，和 release 相同但允许明文 HTTP，用来在本机 server 上测 R8 的包；自己签名，侧载安装；Firebase 的 `google-services.json` 和签名配置放在仓库外的 `~/.config/remote-agent/`，没有时照常构建、推送关闭 | 不上架应用商店；`setAuthenticationRequired` 等 API 31 起的能力按版本判断 |

### 为什么是纯 Kotlin

| 方案 | 结论 | 理由 |
|---|---|---|
| KMP 共享核心 | 暂不采用 | 价值在于和 iOS 共享，iOS 还没定；connect-kotlin 只发布 JVM 版（2026-09-29 核实），放不进 `commonMain`，只能自己实现 Connect 协议。`:core` 不依赖 `android.*`，以后做 iOS 再迁，业务规则和测试都能保留 |
| gomobile 复用 Go | 暂不采用 | 能直接复用的只有 `internal/e2e`：`relay.JoinByPairing` 按机器登记并写 `account.json`，`remoteclient` 是测试用的客户端，不保存设备私钥；同步引擎和事件归约只有 TS 版，用 Go 也要新写。还要承担：Go 的 TLS 不走 Android 的网络安全策略，系统代理不自动生效，网络切换要由 Kotlin 通知，协程取消要桥接到 `context`，Go 和 JVM 两个堆，以及 NDK、R8、16 KB 页面的构建问题。做 iOS 时和 KMP 一起重新评估 |
| 只把加密交给 Go | 不采用 | 绑定层的固定成本一样不少，复用最少 |
| Flutter、React Native | 不采用 | 终端和系统交互仍要写原生模块；Flutter 多出一套 Dart；RN 也搬不动现有网页，它依赖 WebCrypto、IndexedDB、xterm.js 和 DOM |
| 包装 PWA（TWA、Capacitor） | 不采用 | 界面仍是网页，终端输入、键盘和系统交互达不到原生 |

### 模块

- **`:core`**：纯 Kotlin/JVM，不依赖 `android.*`。包括 proto、RPC 和 WebSocket、加密、配对、同步、事件归约和项目分组，都能在 JVM 上单独测试
- **`:app`**：Compose UI、终端视图、生命周期、Keystore、Room 和 DataStore、FCM 和通知、扫码。通过少量接口使用 `:core`，不把 Android 类型传进去

### 同步和生命周期

同步、指令的规则照搬网页（第 10 节）：先连主 WebSocket，收到 `Ready` 后再拉列表和缺的事件；按序号去重、补缺口；元数据只接受更新的修订号；指令重试沿用同一个请求 ID 和截止时间，结果未知就如实显示。

App 在前台时保持主 WebSocket；进入后台关闭主连接和终端连接，暂停自动历史分页与界面计时，改靠推送；回到前台重新认证、追赶历史，终端等待主连接就绪后取得新快照。不靠常驻后台的连接收通知。网页在页面隐藏时也暂停这两条连接和计时，恢复可见后重新同步。

Android 的事件列表用不可变分块快照，追加时复用完整旧页，前缀校验按页比较；聊天状态按追加事件增量推导，每次发布独立快照；普通消息复用旧聊天行，审批、工具结果和压缩等影响旧行的事件，以及 CLI 类型或显示上下文变化，仍完整重建。终端保留字节顺序，将相邻输出合并通知视图，并限制批次与队列大小；积压超限重新获取快照，不能跳过中间字节。模拟器前后 Profile 见 [android-notes §8](android-notes.md#8-客户端性能-profile)。

两端只为当前消费者保留完整解密历史：网页页面与待处理卡片显式持有，Android 按事件流订阅保护，图片确认只在确实仍等待处理时持有。无人使用的历史按最近使用回收，默认最多 8 个会话、估算内容量 16 MiB，并在闲置一分钟后释放；估算不等于进程堆内存上限，活动会话仍保留完整历史以推导状态。回收不删除历史、Android 磁盘密文缓存或待发图片。网页长会话只挂载视口附近的行，展开状态由会话视图保存；回看位置需要重载时，等完整历史或明确失败后恢复，避免把旧位置套在分页前缀上。网页主流串行处理并限制在途帧与字节，终端预算直到 xterm 消费完成才释放；超预算断开后重新同步，不跳过字节。

### 加密和密钥

- **实现**：Android 13（API 33）起平台 JCA 也有 XDH 和 Ed25519，但导入导出原始 32 字节密钥、从 seed 推出公钥都没验证过，验证通过前继续用 Bouncy Castle。直接用 Bouncy Castle 的 lightweight API，不依赖系统里名为 `BC` 的旧 provider
- **互通**：`:core` 的测试读取 `internal/e2e/testdata/vectors.json`；另加 Kotlin 生成、Go 和 TS 校验的反向向量。要特别对齐的是：header 按原始字节参与认证、密文后接 16 字节 tag、签名上下文末尾的 `\0`、配对 transcript 的长度前缀和 emoji 表、拒绝全零的 X25519 共享值、`uint64` 序号不经过有符号数
- **保管**：在 Keystore 里生成不可导出的 AES 密钥，用它加密根密钥和设备 seed，存在应用私有目录，不进云备份和设备迁移。API 28 起账户包装密钥要求设备解锁；生成失败时报错，不降级成锁屏可用的密钥。API 26–27 没有这个平台限制。签名和配对都要原始字节，所以用的时候它们仍会进内存，Keystore 只保护存储。AndroidX `security-crypto` 已弃用，不用 `EncryptedSharedPreferences`
- **通知密钥**：`notify`（第 9 节）单独包装保存，后台收到推送时就能解密；根密钥和 `command` 密钥不因为收通知而在后台解开

### 终端

Android 不执行终端输出里的 OSC 52 剪贴板写入，避免恶意文件或模型输出修改手机剪贴板；用户主动选择复制仍可用。本地 CLI 的结构化事件、模型和会话列表把控制码显示为转义文本，避免消息或文件内容操纵终端及审批显示；原生 tmux 字节流保留交互行为。

`terminal-emulator` 和 `terminal-view` 是 Termux 仓库里以 Apache 2.0 发布的两个模块（仓库其余部分是 GPLv3，2026-09-29 核实），只用这两个。`TerminalView` 绑定的 `TerminalSession` 是 `final`，还在 `updateSize` 里通过 JNI 起本地进程，引用发布的包就换不掉它。所以两个模块的源码固定在 v0.118.3 放进 `android/terminal`，只重写 `TerminalSession`：输入交给回调，远程的输出和快照由外部喂入，JNI 和 C 代码去掉（实测见 [android-notes §2](android-notes.md#2-termux-终端组件)）。升级上游时对照这一个文件合并。

Android 终端的字体依次是 JetBrains Mono、Sarasa Fixed SC 的符号子集（JetBrains Mono 没有的 `⏵`、`⎿`、`✻` 和盲文点阵等，约 290 KB）、系统字体（中文由它提供）。自带的回退链用 Android 10 起的 `Typeface.CustomFallbackBuilder`；Android 8–9 只有 JetBrains Mono 加系统字体，系统缺的符号仍显示不出。JetBrains Mono 的格宽是 0.6em，中文字形比两格窄：渲染器把比格子窄的字形按原宽居中画，不再横向拉伸；框线、色块和 Powerline 分隔符仍拉满格子以保持相连。实测见 [android-notes §2](android-notes.md#2-termux-终端组件)。字号默认 14dp，可在 10–22dp 间调整，保存在本机。适配和绘制使用同一字体在实际像素字号下测出的格宽、取整行高及顶部基线偏移；Termux 的字符宽度规则不变，比格子宽的字形仍然压缩进格子，避免破坏框线和光标对齐。

尺寸和积压的规则同第 11 节：默认不改 tmux 窗口，键盘弹出、旋转屏幕都不改远端尺寸，只有「适配屏幕」及已适配时主动调整字号才改；输出跟不上就断开重拿快照，不能丢字节接着显示。

### 推送和通知里审批

- **Web Push 出站限制**：订阅端点必须使用公网 HTTPS 的 443 端口；每次连接解析 DNS，拒绝非公网地址并直接连接核验过的 IP，防止 DNS rebinding。请求不用环境代理，也不跟随重定向；失败日志不写可能含订阅凭据的 URL。
- **推送后端**：`SetPushTarget` 按类型登记推送目标，Web Push 和 FCM 并存，旧的 `SetPushSubscription` 留给网页。server 用 FCM HTTP v1 发送，服务账号文件由 `-fcm-service-account`（`RA_FCM_SERVICE_ACCOUNT`）指定，`deploy/deploy.sh` 发现本机有 `~/.config/remote-agent/fcm-service-account.json` 时把它复制到 server 的数据目录并设好；没配置就不发 FCM，`SetPushTarget` 返回未启用；FCM 说 token 失效时删除。没有可用的 GMS 时静默降级为 App 内查看，不做 UnifiedPush
- **Android 订阅恢复**：获取 token 前检查 Google Play 服务是否可用，区分 Google 注册失败和中继服务器登记失败；暂时失败在前台指数退避重试，网络恢复时立即重试。新 token 或通知偏好替换旧重试，进入后台或退出账户时取消，回到前台重新登记。后台的新 token 回调只在账户已加载时登记一次，不读取账户密钥，也不持续重试；关闭两类通知时直接清空订阅，不依赖 Google token。推送故障不阻塞聊天、同步和审批，不显示顶部警告或自动弹窗；只在通知设置分组下方以灰色说明给出原因和可选操作，不显示 Java 异常链。不自动请求通知权限，用户在通知设置里点「开启」时才进入系统设置。重试不能解决手机网络持续无法访问 Google 的问题。
- **内容**：daemon 用 `notify` 密钥加密审批摘要（机器、会话、审批 ID、命令、截止时间），随 `Notify` 交给 server 原样转发。server 和 FCM 只看到密文；FCM 的 payload 上限是 4 KB，放不下时只发通用提醒
- **合并**：审批按审批 ID 去重，不再按「同一会话同一类别 15 秒内只推一次」合并，免得漏掉接连出现的审批
- **显示**：默认只显示通用文案，点开直接进审批页。App 设置里打开「在通知里显示内容并直接审批」后，手机解锁时才显示会话标题、命令和按钮，这样的通知用 `VISIBILITY_SECRET`，锁屏上整条不出现；锁着时收到的仍只发通用文案。`VISIBILITY_PRIVATE` 不够：用户允许锁屏显示敏感内容时它照样全文显示（scope 第 4 节，实测见 [android-notes §4](android-notes.md#4-fcm)）。账户只在前台读取，推送拉起的后台进程只用通知密钥。密文总是随推送下发，开关只在手机上决定怎么显示。App 在前台时不弹通知
- **按钮**：「允许 / 拒绝」设 `setAuthenticationRequired(true)`，先解锁手机才能点；API 31 以下做不到这一点，就不给按钮，点通知进审批页；每条通知用独立、不可变的 `PendingIntent`，只绑定自己那条审批；命令显示不全时，「允许」改为打开完整的审批页
- **执行**：点按钮时在广播里封好指令（请求 ID 和截止时间就此固定），交给 WorkManager 发 `Forward`；先显示「允许中…」，daemon 返回才算完成；结果未知时重试同一个信封，过了截止时间还不知道就如实显示
- **daemon 的校验**：超时和回复都要先抢到审批的 `claimed` 标记，只有一方生效，过期的回复不会被放行。另在审批里存一个绝对截止时间，处理回复时一并检查，作为额外防护
- **投递失败**：推送没送到不影响 daemon 的超时拒绝，审批仍可以打开 App 处理

## 16. 接入 Claude Code

Claude Code 和 Codex 走同一条路：原生 TUI 跑在 tmux 的 PTY 代理下，输出读 transcript，审批和轮次边界靠 hook，屏幕只用来判断状态。客户端能做的操作两者一致（第 7 节的 4 种审批模式就是按两者共有的定的）。具体做法依据 [claude-code-notes.md](claude-code-notes.md) 的实测，随实测补全。

- **会话属于哪个 CLI**：会话信息、新建会话、列模型都带 `Agent`；以前的会话没有这个字段，按 Codex 处理。机器元数据列出本机装了哪些 CLI 和版本，客户端只提供装了的
- **daemon 的分层**：会话生命周期、事件序号、持久化队列、控制锁、审批的竞争处理、同步和终端流是共用的；每个 CLI 各自实现三组接口（`internal/agent`）：启动和恢复（参数、版本、模型列表）、事件来源（绑定 transcript、增量解析、确认消息已提交）、终端控制（认输入框、注入、中断、回答提问、计划、切换设置）。屏幕、菜单、参数和 JSON 格式的知识只留在各自的包里（`internal/codex`、`internal/claude`）
- **环境变量**：和 Codex 共用 `~/.remote-agent/agent.env`（第 6 节），代理这类配置属于电脑，不属于某个 CLI
- **新建会话的默认值**：daemon 设置里 Codex 和 Claude Code 各有一套默认模型、推理强度和审批模式，作为新项目的初值；项目设置（第 13 节）里选定 CLI 后用这个 CLI 的那一套
- **工具开始**：Claude Code 会并行调用工具，`ToolStarted` 带上调用 ID 配对，不按先后顺序

下面是 Claude Code 这一侧的具体做法，括号里的「notes §n」指 [claude-code-notes.md](claude-code-notes.md) 的第 n 节。

- **启动**：`remote-agent pty-host -- claude --settings <会话目录>/claude-settings.json --session-id <uuid> …`。settings 文件只放 remote-agent 的 hook（`SessionStart`、`PermissionRequest`，以及只匹配 AskUserQuestion 和 ExitPlanMode 的 `PreToolUse`），命令同样写成 `"$RA_EXE" hook claude`；它和用户自己的 hook 一起运行，不改 `~/.claude/settings.json`，也不需要信任（notes §1、§3）。会话 ID 由 daemon 生成，记作会话的 CLI 会话 ID
- **模型、推理强度、审批模式**：新建时换成 `--model`、`--effort`、`--permission-mode`；没指定就不传，沿用 Claude Code 自己的配置。「完全放行」对应 `bypassPermissions`：只有启动时就允许了 bypass 的会话能切过去（notes §5），daemon 按启动参数和 `~/.claude/settings.json` 的 `defaultMode` 判断，不可用时会话信息里标出来，客户端置灰。remote-agent 不替用户加 `--allow-dangerously-skip-permissions`
- **恢复会话**：transcript 已经存在时用 `--resume <id>`，否则（从没发过消息）仍用 `--session-id <id>`；沿用原来的参数（取多个值的选项保留全部的值，少一个就可能放宽限制），再用最近一轮的模型、推理强度和审批模式覆盖，同名选项先从原参数里去掉。Plan 模式下 Claude Code 临时换用的模型不算会话的模型，免得恢复后一直用它。bypass 是否可用按启动时记下的结果，不重新读可能已经改过的全局设置。恢复时 transcript 里的 `permission-mode` 记录是上次的模式（notes §2），所以当前模式以屏幕上的模式行为准。`--bare`、`--safe-mode` 会关掉 settings 里的 hook，不接受
- **启动弹窗**：信任目录的光标默认在 `No, exit`，回车就退出（notes §1），和 Codex 一样留给用户在终端里处理，客户端提示去终端
- **找到 transcript**：`SessionStart` hook 在信任目录后、第一条消息前就触发，带 `transcript_path`
- **解析 transcript**：带 `origin.kind: human` 的用户记录是新一轮的开始和用户消息，`task-notification` 的只开始一轮（后台工作结束后 Claude Code 自己回应）；`turn_duration` 是正常结束，`[Request interrupted by user…]` 是被中断，两者可能先后都有，只记第一个；`isMeta`、斜杠命令、压缩摘要都不算用户消息；运行中并入这一轮的消息（`queued_command` 附件）记为用户消息但不开新的一轮。`tool_use` 记为 `ToolStarted`（带调用 ID），`tool_result` 按调用 ID 配成 `ToolCall`；`thinking` 记为推理（终端里默认折叠，按 ctrl+o 能看到同样的内容）。`compact_boundary` 记为「上下文已压缩」。模型和推理强度取自 `assistant` 记录，上下文占用由 `usage` 算出，窗口大小按模型推断（notes §2）
- **输入**：和 Codex 相同的排队、暂存本地按键、bracketed paste。输入框的判断按 Claude Code 的画法：两条横线之间只有一行，`❯` 后面没有普通样式的字（光标是反色的一格，占位提示是淡色）才算空（notes §4）。运行中也可以注入，Claude Code 会把它排进当前这一轮；以 transcript 里出现这条用户消息或 `queue-operation` 的 `enqueue` 记录为已提交
- **计划框和菜单的折行**：窄屏时标题和选项会折行，识别时把相邻两行连起来看，选项的续行并入选项
- **本地先答审批**：除了看到的权限框消失、这一轮结束，这个请求的工具调用完成也算，覆盖状态检测还没看到框就已经在终端答了的情况。调用和请求按完整输入的摘要对应（审批事件和工具调用都带这个摘要，客户端直接比较，不自己算）；几个请求输入完全相同时，一次完成收回其中最早的一个。审批请求一律出卡片，daemon 不预判「调用已经执行过」：
  - **限制**：在终端里答得太快、调用在审批请求登记到 daemon 之前就执行完了，这张卡片不会因为这次完成而收回，要等这一轮结束才收回；在这期间点它不起作用，因为 Claude Code 已经不等这个 hook 的答复了。曾经尝试用「最近完成的调用」提前跳过这类请求，连续几轮都引出了会静默跳过真实审批的竞争，所以放弃：宁可多一张过时的卡片，也不能漏掉一次审批
- **中断**：只在运行中发 Esc
- **模型提问**：让原生选择框照常出现。问题由 `PreToolUse` hook 报给 daemon（hook 立即返回、不表态），因为 transcript 可能要等回答之后才写入这次调用（notes §2）；transcript 里随后出现的同一调用不再重复。回答时暂存本地按键、确认屏幕上是这个问题（窄屏折行的问题去掉折行再比，认不出或认出多个就报错，不猜），再按选项编号，出现提交页就按 1。多选时数字键是切换勾选，所以先读当前的勾选状态，只按和答案不一致的，再按 →。以 transcript 的 `tool_result` 为准，本地先答了就收回卡片。**不用阻塞 `PreToolUse` hook 回答**：那样虽然能直接把答案交给模型，但 hook 等待期间电脑终端里看不到问题，违背「电脑和手机操作同一个会话」（notes §7 两条路的实测对比）
- **计划**：`ExitPlanMode` 同样由 `PreToolUse` hook 报来，记为 `PlanProposed`，屏幕上的计划框让会话处于「计划待批准」。批准（`IMPLEMENT`）按「Yes, manually approve edits」那一项，执行后回到 manual；继续规划（`KEEP_PLANNING`）按 Esc，留在 Plan 模式；Claude Code 没有「清空上下文再执行」，这一项返回不支持。hook 批准计划不起作用（notes §8）
- **当前审批模式**：以屏幕上的模式行为准。在电脑终端里用 Shift+Tab 切的，daemon 从屏幕看到后记一条 `TurnContext`（`permission_mode`），不用等下一条消息；会话信息的 `mode` 按第 7 节的对应关系给出，accept edits 这类没有对应的给 UNSPECIFIED，原名在 `permission_mode` 里
- **切换审批模式**：空闲时切到 Plan 用 `/plan`，直接到达。其余用 Shift+Tab 在模式行上一格一格地走到目标模式，每按一次都读模式行确认；转一圈都没遇到目标就报错并回到原来的模式。按放行的范围，模式从严到宽是 plan、manual、accept edits、auto、bypass。运行中也能切（notes §5），但途中（以及目标不可用时回来的路上）只要有一个模式比目标宽，就不切，免得那一瞬间放行了工具调用。是否运行中在拿到终端控制之后才判断（切模型、压缩同样如此）：之前拿着控制的注入可能刚开始了一轮，所以要重新读 transcript，并把「已写入还没确认的消息」和屏幕上的忙碌迹象（输入框上方的转圈行、变暗的提示符，notes §4）也算作运行中。
  - **空闲时途经更宽的模式**（主要是从 Plan 模式切出：Shift+Tab 只能单向走，也没有离开 Plan 模式的命令，notes §5）：屏幕上有后台工作（模式行的 `· 1 shell`、输入框上方的 `Waiting for N background agent`、模式行下的后台子代理列表，notes §10）时不切，告诉用户原因；否则先算出整条路径，把要按的 Shift+Tab 一次写完，中间不读屏幕，最后核对模式行。算路径要知道 bypass 和 auto 可不可用：bypass 按会话启动时记下的能力（`full_access_unavailable`）；auto 按模型（haiku 没有，其余 Claude 模型有：sonnet 实测，opus、fable 推测），或这个会话用同一模型时屏幕上出现过 auto；状态栏的 `auto mode unavailable for this model` 不作依据，它在换到有 auto 的模型之后还会留一阵（notes §5）。已知不可用的目标直接报错，不按键。**唯一的例外**是 auto 可不可用算不出来（还不知道会话的模型、屏幕也没提示）：这时按「不可用」计数，只会少按、不会多按；如果因此停在 auto 上（比目标宽），立即把差的键补上，这是第二次写入。目标实际不可用时回到原来的模式
  - **为什么这样取舍**：一律拒绝的话，bypass 或 auto 可用的会话（本机默认就是）就没法从远程离开 Plan 模式。空闲时这一轮没有工具调用；可能在这一瞬间调用工具的只有后台工作，看得到就拒绝
  - **残余风险**：连按期间 Claude Code 依次经过的宽松模式仍会存在几十毫秒（按键和界面刷新的时间，未精确测量）；屏幕上看不出来的后台工作（比如列表被挤出屏幕、Claude Code 改了提示的写法）挡不住；后台工作在检查之后、连按之前的一瞬间启动也挡不住
- **切换模型和推理强度**：空闲时 `/model`，用方向键移到模型那一行、←/→ 调推理强度，按 `s` 只改当前会话；弹出 `Switch model?` 时按它的「Yes, switch to」那一项，只在菜单已经消失、确认框和这一项都在时才按，免得把数字按进菜单改掉默认模型。以对话里出现 `Set model to … for this session only` 为成功。数字键和回车会改全局默认值，不用（notes §9）。可选的模型是 Claude Code 的别名（opus、fable、sonnet、haiku），列表写在代码里；会话信息里的模型是完整的模型 ID。**上下文窗口**是项目设置里独立的一项（`ProjectSettings.standard_context`，新建时随 `CreateSessionRequest.standard_context` 交给 daemon），只对 Claude Code 有意义，默认 1M：这是 Claude Code 自己的默认值，所以没设置过的项目行为不变，用默认模型时也能选。选标准时 daemon 在会话环境里加 `CLAUDE_CODE_DISABLE_1M_CONTEXT=1`，固定为 200k（notes §2）；环境随会话保存，恢复时不变，会话信息里的窗口也按 200k 报告。选 1M 且模型是有 1M 窗口的别名时，daemon 把它写成 `opus[1m]` 交给 `--model`，窗口本来就是 1M，这样做只是让终端标题写出 `(1M context)`；没指定模型时不改参数。不把窗口编码进模型名：那样默认模型下没法选，也会让已有项目的含义悄悄改变。窗口在启动时就定了，会话里切换模型不涉及它。模型列表带每个模型最大的上下文窗口（`ModelInfo.context_window`），客户端据此判断模型有没有 1M 可选（Haiku 没有）；Codex 不填，因为 `models_cache.json` 里的窗口和会话实际报告的不一致（codex-notes §1），它的实际窗口在会话的上下文占用里看
- **压缩**：空闲时 `/compact`，以屏幕出现 `Compacting conversation` 或 transcript 出现 `compact_boundary` 为开始
- **额度**：当前机器元数据仍只有 Codex 额度；v2 增加 Claude Code，见下节。

### 账户额度

设备页提供额度详情，按这台机器上安装的 CLI 分组，显示 CLI 登录账户的用量；它与会话上下文占用、累计 token、remote-agent 的图片存储配额分别展示。不同 CLI 不相加，不按模型或会话切分账户额度；不同机器也不凭套餐名推断为同一个账户。界面见 [client-v9 · 账户额度](design/client-v9.html#quota)。

Codex 继续用 rollout 的额度字段（[codex-notes §1](codex-notes.md#1-数据从哪读)）。Claude Code 的 transcript 没有账户额度，额度只在状态栏命令的输入里（[claude-code-notes §2](claude-code-notes.md#2-transcript)）。daemon 在会话的 `--settings` 里把状态栏设成 `"$RA_EXE" statusline claude`（不改用户的设置文件）：它把输入转给 daemon（500 毫秒超时，失败也不影响状态栏），再用同样的输入运行用户原来的状态栏命令（启动会话时按 Claude Code 的优先级读出、存在会话目录里），输出和退出码原样交回，`padding`、`refreshInterval` 也照搬，所以终端里看到的状态栏不变。托管设置里定了状态栏时它会盖过 daemon 的，额度就读不到，报「不支持」。账户用 `~/.claude.json` 里 `oauthAccount` 的账户和组织 ID 算一个短指纹来区分（ID 本身不离开电脑），套餐取 `organizationType`，有 `oauthAccount` 才标为订阅登录；读不出账户时不合并，按来源会话分开。额度按账户存在 `~/.remote-agent/quota.json`，重启后只沿用当前登录账户的记录，看到新账户的数字就清掉旧账户的。数字不变时一分钟内不刷新记录时间，免得机器元数据频繁变化。结果放在 `MachineMeta.quotas`，每个 CLI 一项或几项，状态分等待（还没收到额度）、正常、失败和不支持。采集只读取 CLI 已有数据，不主动给模型发消息，不把登录凭据交给 server，不调用未公开的账户接口。额度元数据端到端加密同步，server 只收密文，日志不记录额度或账户内容。

客户端按来源提供的窗口显示已用百分比、重置时间和最近收到时间。重置时间统一转换为北京时间（`Asia/Shanghai`，UTC+8），日期和星期也按北京时间判断，并标注「北京时间」；最近收到时间仍按客户端时区显示。Claude Code 的 5 小时、7 天分别可缺失；只有真实收到其他限额窗口时才显示该窗口，不承诺按模型额度或额外用量。套餐名未知就省略，读到的内部代号换成名称显示（`prolite` 写 Pro Lite，`claude_max` 写 Max）；API 计费须由可靠的登录方式信息确认，不能从 `rate_limits` 缺失推断。API 用量和账单到服务商控制台查看，不把会话估算费用当成账户余额。

- 有效数据：80% 起橙色提示，100% 标「已用尽」；不自动切换 CLI 或模型，不拦截发送。缺重置时间只省略时间，缺用量则标「未获取」，不补成 0%。
- 尚未收到任何额度：显示「暂未获取额度」。明确不支持读取时显示「暂不支持读取额度」。单个窗口缺失不清空其他有效窗口；账户没有的窗口（CLI 根本没上报）不显示，不占一行「未获取」。「最近收到」的时间每个 CLI 只写一次。
- 机器离线、重置时间已过或来源确认数据陈旧：旧数值标「上次记录」，显示时间与原因，条形变灰。重置时间过了只标「等待更新」，不自行归零；客户端时间用于展示，不作为 CLI 已恢复可用的证明。
- 读取失败：说明失败并保留带时间的上次记录；「重新读取」只重读本机已采集数据，不能保证向服务商刷新，机器离线时置灰。额度页不提供跳转终端的入口，不支持读取时只提示可在本机 CLI 里查看 `/usage`。
- 确认换登录账户后清掉旧账户快照；无法可靠识别账户变更时不复用持久化缓存，显示未获取。多会话的账户额度不累加，只有能确认同一账户的数据才能合并，按来源时间取最新；未知账户归属时保留来源会话区分。

## 17. 会话里的图片

客户端显示会话里出现过的图片，也能发图片给 Agent。显示的图片包括：用户粘贴的（电脑上或客户端发的）、Agent 查看的（Claude Code 的 `Read`，Codex 的 `view_image`、浏览器截图等）、Codex 生成的。界面见 [design/client-v2.html](design/client-v2.html#images)，两个 CLI 怎么记录图片见 [codex-notes §1](codex-notes.md#1-数据从哪读)、[claude-code-notes §2](claude-code-notes.md#2-transcript)。

- **只取 CLI 已经记下的图**：两个 CLI 都把图片的 base64 内嵌在 rollout 或 transcript 里，daemon 解析时一起拿到，不需要再读磁盘。Agent 在回复里提到的本机文件（比如 `![](out/chart.png)`）daemon 不去读：路径由模型决定，照着读就等于让模型能把本机任意文件送到手机上。想在手机上看这类文件，让 Agent 自己看一眼（`Read`、`view_image`），它就会作为「查看的图」出现
- **事件只带引用**：`UserMessage`、`ToolCall` 和新的「生成了图片」事件里带图片列表，每张有图片 ID、格式、原始尺寸、原始路径（知道的话）和一张内嵌的预览图
- **两种尺寸**：预览图长边 320px，编码成 JPEG（有透明的用 PNG），大约 5 到 20 KB，直接内嵌在事件里，聊天列表不用额外请求就能画出来；查看大图用的显示版长边不超过 2048px，单独加密上传，加密后的整个信封（连同 header、nonce、GCM 标签和 Protobuf 编码）不超过 1 MiB 的上限，放不下就依次降 JPEG 质量（85 到 55）、再每次缩小到 80%，透明图只缩小，点开时才下载。编码只用 Go 标准库的 JPEG、PNG，WebP 只读不写（`golang.org/x/image/webp` 只有解码器），不为 WebP 编码引入 cgo 依赖。解码有上限：编码后 48 MB、6000 万像素，动图只取第一帧，同时最多处理两张。原图不上传，还在电脑上的会话记录里。Codex 的原图常见 2 到 3 MB，放不进 1 MiB 的信封，也没必要在手机上看原始分辨率
- **加密和绑定**：显示版用会话密钥加密，header 的用途写「图片」，并带上机器、会话和图片 ID，和事件一样由接收方核对位置。图片 ID 是随机数，不用内容哈希，避免 server 看出两张图是否相同；同一会话里重复出现的图（Codex 每看一次存一份）由 daemon 用会话密钥算 HMAC 去重，只传一次
- **上传顺序**：显示版和事件走同一条按序上传的队列，先传图、后传引用它的事件，客户端看到事件时图已经在 server 上。图压不进信封上限，或者解码失败时，事件照常上传，这张图标为「没有同步」，只留预览（预览也做不出来就只写文件名）。上传失败不能堵住后面的审批和消息：server 拒绝（配额满）立即放弃，网络错误最多试五次（跨重连累计），之后事件照样上传、这张图标为只有预览。哪张图对应哪个 ID、是否已上传记在会话目录的 `images/index.json`，重启不重传也不丢引用；显示版传完就从本地删掉
- **读大记录**：几张原图的消息在 rollout 里是一行几十 MB。读记录时一次只读一行，超过 8 MiB 的行不整行读进内存也不跳过：先复制出一份去掉长字符串的 JSON（base64 换成指向文件位置的标记，长文字只留开头），图片处理时再按标记从文件里读出那一段
- **事件太大时**：先去掉预览（从大的开始），保住正文、图片引用和工具状态，还放不下才截断文字
- **渲染安全**：daemon 统一重新编码成 PNG 或 JPEG，不转发 SVG 之类可能带脚本的格式；客户端解密后再按文件头核对格式，网页用 `blob:` URL 显示，CSP 只多放行 `img-src blob: data:`
- **server 能看到的**：图片的数量、密文大小和上传时间，和事件的元数据同一个级别
- **保存期限和配额**：显示版在 server 上保存 30 天，整个账户最多存 1 GiB（server 的 `-image-retention`、`-image-quota` 可调）。配额在插入的同一个事务里检查，满了就拒绝新图（daemon 把事件降级为「没有同步」），不提前删掉没过期的图。过期的图删掉密文、留下一行记录，客户端因此能区分「已过期」和「从没同步」；同一个图片 ID 过期后不再存入，daemon 需要时换新 ID 重传。配额只算显示版的密文，不含事件里内嵌的预览，也不等于数据库文件的实际大小：SQLite 删掉的空间不会自动还给文件系统，WAL 和备份另算，备份里的密文按备份自己的保留期存在
- **保存和分享**：客户端查看大图时可以保存到本机或调系统分享。图片从这一步起离开 App，由用户自己决定

### 从客户端发图片

实测见 [claude-code-notes §10](claude-code-notes.md#10-中断和运行中的输入)、[codex-notes §10](codex-notes.md#10-屏幕和输入)。

- **怎么交给 CLI**：daemon 把图片写成本机文件，把文件路径用 bracketed paste 单独粘进输入框，两个 CLI 都会把它变成 `[Image #N]`，和在电脑上粘贴图片一样，仍然是原生输入。不写系统剪贴板再按粘贴键，因为那会覆盖用户电脑上的剪贴板
- **一条消息最多 6 张**：新建会话的第一条消息和之后的消息都一样
- **默认压缩**：网页各草稿共用单图准备队列，切换原图或移除后跳过尚未开始的旧请求；Android 也只同时准备一张图，避免多张源图的解码内存叠加。选图后在本机解码，缩到长边不超过 2048px，编码成 JPEG（带透明的用 PNG），iPhone 的 HEIC 这类格式也在这一步转掉；图片数据留出加密信封的开销；压缩图和原图统一走下面的分块协议，每个信封不超过 1 MiB。两个 CLI 本来就会把大图缩到 2000px 上下（notes），所以默认压缩基本不损失模型能看到的内容，还能避免 Codex 把几 MB 的原图写进 rollout
- **原图**：每条消息可以选择发原图，保留原始的像素和画质，适合有小字的截图。PNG、JPEG、WebP、GIF 原样发送；两个 CLI 不认的格式（HEIC 等）按原始尺寸转成高质量 JPEG。单张不超过 20 MB，按不超过 1 MiB 的信封分块传给 daemon，daemon 按顺序拼好、核对总长度和哈希后才算传完。界面上说明两个 CLI 仍会自己缩小过大的图
- **去掉元数据**：两种方式都去掉 EXIF 等元数据再发出，照片里的拍摄位置不会经 CLI 送到模型服务商。去掉之前先按 EXIF 里的方向把图转正，否则手机照片会横着或倒着交给 CLI，和客户端预览不一致。默认压缩在解码时按方向转正，重新编码后元数据自然没有了；原图的 JPEG 带方向标记时先无损旋转（尺寸不是 MCU 整数倍、做不了无损旋转时，以最高质量重新编码），再删掉 APP1 等元数据段（整个文件都要删，包括扫描之间和 EOI 之前的注释、APP 段，EOI 之后的内容也丢掉），PNG 删掉文本和 `eXIf` 块，GIF 删掉注释扩展和除循环播放以外的应用扩展（XMP 在里面），帧不动，没有方向标记的不改动像素数据
- **先传图、再发消息**：图片传给机器，不传给会话：每张图用机器级指令（header 里不带会话 ID，见第 13 节）分块发给 daemon，原图也不会被 60 秒的指令期限卡住。传输 ID 由客户端生成，每块带偏移，daemon 逐块落盘（fsync）后才回复已持久化的长度，重发的块必须和已收到的字节一致；中断后客户端查询状态从断点接着传。完成时 daemon 核对总长度、SHA-256、文件头的格式并确认能解码，再去掉 EXIF、XMP 和文本块（客户端已经去过一遍，这里兜底，要转正的 JPEG 重新编码），写到 `~/.remote-agent/uploads/pending/<图片 ID>.<扩展名>`（权限 0600，路径由 daemon 决定，不含空格，否则两个 CLI 都不认；`REMOTE_AGENT_HOME` 的路径带空格时 daemon 不声明上传能力），返回图片 ID。传输和图片都绑定开始上传的设备，别的设备不能续传或拿来发送；这里的设备必须由指令签名证明，server 转述的发送方不算数，所以没有签名的指令（v2 以前的客户端）可以照常发文字，但不能上传或使用图片。发消息或新建会话的指令带上这些 ID，daemon 受理时把文件移到 `uploads/<会话 ID>/` 下；新建会话先核对图片都在，再启动 CLI。一小时没有新增字节的传输、24 小时内没有被消息用上的图，daemon 自动删除；重复块和查询状态不延长期限。每次操作也检查期限，不等定期清理才失效。电脑上传目录默认限额 1 GiB，可在设备设置中调整，计入已有文件和未完成传输尚未收到的预留字节。新上传前清理过期文件，再按最近使用顺序回收可淘汰的原图，仍不足才拒绝并指向设备的占用和清理入口。排队的图片按消息请求 ID 记录引用；取消消息后只在最后一个引用释放、文件还没交给 CLI 时删除。重启以持久化队列恢复引用，避免中途退出留下永久占用。完成时清理后的文件仍不得超过单张上限，原始分块副本等写入成功才删除，这一步可临时多占一张图的空间。新建时换了机器，客户端把图重新传给新机器，所以发出之前客户端一直留着压缩好的图。和文字消息一样要求机器在线，server 不替用户保存要发的图；消息排队时图片已经在电脑上，不会重传
- **注入**：沿用现有的输入锁和暂存本地按键，输入框为空才开始。每张图的路径单独粘贴一次，只看输入框（两条横线之间或提示符那几行）里是否正好多了一个 `[Image #N]`、没有别的字：Claude Code 运行中排队的消息也以 `[Image #N]` 开头显示在输入框上方，搜整个屏幕会认错。全部认出后再粘贴正文和回车。暂存按键改成租约：每秒续一次，整条消息有总时长上限（10 秒加每张图 8 秒），PTY 代理的单次暂存仍最多 10 秒，daemon 卡住时用户的终端最多被挡这么久。每次写终端（粘贴路径、Ctrl-U、正文和回车）之前都要确认暂存仍然有效：最近一次续期得到确认、离到期还有余量，且没过总时长；存标记（fsync）或抓屏卡住导致暂存可能已经放开时，一律不再写，按回车前还要再抓一次屏确认输入框里正好是这条消息的占位。每一步写入前先把阶段存进 `queue.json`（等待、正在粘贴图片、图片已识别、正在提交），并作为 `InputState` 发给客户端
- **没能发送时**：某张图没变成占位（路径以文字留在输入框里、一直等不到、输入框里出现了别的字、弹出了菜单）就不按回车。输入框里只有这条消息粘进去的占位和路径时，用 Ctrl-U 清空并确认输入框变空，消息记为「提交前失败，已清理」（`FAILED`）；输入框里还有别的内容（比如暂存失效后本地敲的键），或者清完确认不了，就什么都不删，记为「需要到终端处理」（`NEEDS_TERMINAL`）。等占位超时时即使输入框是空的也记为后者，因为 Claude Code 可能稍后才把图转换进去。两种都不自动重试。不用 Ctrl-C 或 Esc 清空：Codex 空输入框按 Ctrl-C 会退出，Claude Code 运行中按 Esc 会中断这一轮。daemon 在粘贴图片中途停了，重启后不再写这条消息，也不删任何东西：旧 daemon 一停暂存就放开了，这期间用户可能清掉了失败的粘贴、又贴了自己的图（Codex 的编号还会重用），输入框里的内容认不出归属；Claude Code 也可能还在转换停之前贴进去的图。所以只有输入框在整个转换窗口（10 秒）里一直是空的，才记为失败（原因 `restarted`），否则记为需要到终端处理；窗口结束之前后面的消息不写入。已经按了回车的照旧只等确认
- **确认提交**：要同时有文字和图片的证据：CLI 记下的正文里必须有这条消息每张图的 `[Image #N]`，去掉这些占位（只去掉本次的，用户正文里自己写的占位保留）后和发出的正文一致。Codex 以 `history.jsonl` 或 rollout 的用户消息为准（后者的 `local_image` 路径就是上传的文件）；Claude Code 以带 `imagePasteIds` 的用户记录、`queue-operation` 的 `enqueue` 或 `queued_command` 为准。事件里的 `UserMessage` 按路径或编号认出是哪条发出的消息后，带上请求 ID、来源和每张图的上传 ID，发送端据此换掉自己的本地缩略图
- **清理和恢复**：首次上传和首次接受消息分别创建暂存、会话目录。daemon 启动时先补完中断的文件移动，再恢复会话输入；启动及每十分钟清理过期传输、一天以上的孤儿图片和损坏记录、已退出会话的上传目录，并重试退出后的删除。已使用图片记录随原图保留，避免文件仍在却无法验证归属。写入失败会清理临时文件；未完成的记录提交留下的文件也由定期清理兜底。会话元数据无法读取时不据此删除会话文件。
- **原图的保留与 LRU**：Codex 提交时才读取文件，Claude Code 粘贴时就读入；必须先保留上传、排队和正在提交的图片。两个 CLI 的历史图片已经以 base64 内嵌，历史回放不需要原文件，但模型仍可能按来源路径再读（[Claude Code 实测](claude-code-notes.md#10-中断和运行中的输入)）。daemon 确认记录里已有可读图片后，至少保留一分钟，且这一轮执行中仍保护这台会话的原图；队列不再引用、执行结束后才进入 LRU。此后按原始路径再次读取不保证成功，历史内嵌图片仍保留。无法确认读入的文件和升级前缺少引用信息的记录不参与淘汰，等会话结束清理。
- **缓存与草稿**：电脑的预览和待同步显示版共用 150 MiB 的文件缓存，按最近使用顺序淘汰；限额只算预览与显示版文件，图片索引和历史记录按会话历史保留。已同步图片仍可从 server 下载，预览已内嵌在事件中。离线积压的显示版被淘汰时明确降级为只有预览，不能继续宣称大图可下载；同一图片之后再出现时可从 CLI 记录重新编码。Android 查看缓存也为 150 MiB，按最近访问淘汰；已解密的查看图片只属于当前账户连接，退出或切换连接时清空，旧的异步加载不能回填到新账户；待发与待确认图片另设 256 MiB 上限（容纳六张 20 MiB 原图的草稿和发送过渡副本），不按 LRU 丢弃用户草稿。闲置七天的草稿清理，尚未确认的消息保留到确认或用户移除；容量不足时保留已有内容并提示。各期限和固定容量都是初始默认值，后续按实际用量调整。
- **占用与清理**：电脑详情显示上传图片的总占用和预览缓存，不按会话列出；可清理和正在上传的大小不为零时才写出来。只开放上传限额一个配置项。清理按钮写明可释放多少，只删除可回收原图和缓存，并说明未同步大图会退回预览；没有可清理的内容时不可点。Android 设置显示本机草稿和查看缓存的占用，清理查看缓存不删草稿。占用统计通过加密指令回复返回，不给 server 新增明文目录或内容。
- **显示**：发出去的图由 CLI 写进会话记录，按上面的规则显示，和在电脑上粘贴的图同一条路径；发送中先显示客户端本地的缩略图


## 18. 定时任务

定时任务属于 Remote Agent，由所属电脑的 daemon 保存和执行，不依赖 Codex 或 Claude Code 的内部调度。任务内容、目标目录和执行消息不以明文交给 server；远程管理复用加密的机器指令。任务模型由 `internal/schedule` 维护，本地 CLI、MCP 和协议接口共用；客户端界面尚未实现，见 [plan.md](plan.md)。

### 托管会话的工具入口

每次新建和恢复托管会话时，增加名为 `remote_agent` 的本地 stdio MCP，命令为本机二进制的 `mcp` 子命令，并绑定 Remote Agent 会话 ID。Codex 使用单次 `-c` 配置覆盖，Claude Code 使用会话目录中的私有 MCP 配置；Claude 的显式 `--mcp-config` 来源合并到该文件，用户其他 MCP 保留。不修改全局配置、项目配置、AGENTS.md 或 CLAUDE.md，不注入会话指令、system prompt 或 skill；能力由 MCP 工具描述和参数 schema 提供。

Claude Code 托管进程设置 `CLAUDE_CODE_DISABLE_CRON=1`，关闭其会话内 cron 和 `/loop`；新建和恢复都应用，不改变普通启动的 CLI、桌面端或云端任务。Codex 未配置未经验证的内置调度禁用开关。外部 CLI 的版本支持和实测边界分别见 [codex-notes.md](codex-notes.md) 与 [claude-code-notes.md](claude-code-notes.md)。MCP 与 CLI 都连接私有本地 daemon socket；会话 ID 是上下文标识，不是独立授权凭据，同一操作系统用户属于本机信任域。

模型通过 MCP 获得的是受限委托：只管理本会话创建的任务，只恢复本会话；新会话限同项目、同 CLI 和相同的完整标准审批配置。Plan、未知或自定义权限不能通过该入口创建执行任务，不能把只读沙箱按界面的「询问」标签扩大为可写沙箱。创建、修改、手动执行和延迟派发都校验限制；来源权限改变后旧任务暂停。用户 CLI 和加密远程客户端仍拥有机器级任务管理能力。这约束模型的 MCP 工具，不提供同一操作系统用户之间的进程隔离。

MCP 每次操作先确认 daemon 支持受限委托；不支持时拒绝工具调用。新 daemon 也拒绝旧 MCP 的无委托标记会话请求，明确的用户 CLI 调用使用独立入口标记。升级需要更新二进制并重启 daemon、重新连接会话内的 MCP 进程；升级前模型创建的未完成任务暂停，由用户 CLI 或远程客户端确认后接管。

### 触发与执行

支持一次性带时区的绝对时间、固定经过时长的周期，以及当前轮结束后的延迟。固定间隔不承诺每日当地时间或夏令时语义。`after_turn` 在登记时绑定具体轮次；已经空闲或退出时从登记时计时，审批和提问不会结束这一轮。绑定轮次被中断或未经正常结束就退出时暂停，用户明确恢复后才重新安排。重复的延迟任务从每次执行结束后再计时，同一任务不重叠、不累计排队遗漏周期；可限制执行次数。

执行目标可恢复原会话，或在指定项目新开对话。恢复保持原 Remote Agent ID、CLI 对话 ID、环境及原有恢复规则；新开对话从来源会话取项目、CLI 和可继承的配置，换 CLI 时不继承另一 CLI 的模型与 effort。新会话不能直接以 Plan 模式启动；来源模式未知或非标准时，用户需明确指定启动模式。创建时已有明确配置的字段固定在任务中，留空且无法继承的字段使用执行时 daemon/CLI 默认值。

执行消息进入现有 queue 模式，等待当前轮结束，不覆盖本地草稿、绕过弹窗或改变审批权限。任务暂停和取消只停止未来调度，不中断或撤回已经交给会话队列的消息；使用现有取消输入、中断和恢复输入操作处理当前执行。轮次正常结束只表示该次执行结束，不代表消息中的业务目标成功。

### 持久化与恢复

任务及最近 100 次执行记录保存在本机私有 `schedules.json`，原子替换并落盘。创建支持稳定请求键，修改支持修订检查；受损或未知版本的文件会使 daemon 启动失败，不静默丢弃任务。

dispatching 状态在新建/恢复会话和注入消息之前保存。daemon 在该边界退出时恢复为“无法确认”，不自动重试；已持久化的 queued/running 执行则通过原会话的队列、请求 ID 和事件游标继续跟踪，不重复发送。消息提交无法确认、执行失败或中断时停止自动续跑。

电脑和 daemon 需要运行，客户端无需在线；relay 断线不阻止本地调度，原有审批和消息同步机制仍有效。休眠或停机后默认只补最近一次、期限为 24 小时，可调整期限；超过期限记录跳过，周期任务转到下一次。绝对时间支持十年内的时间，间隔以秒计。当前加密接口提供查询和管理，客户端离线任务缓存、变更订阅与界面后续实现。
